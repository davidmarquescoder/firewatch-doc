O Firewatch agenda duas tarefas, ambas em `routes/console.php`:

```php [routes/console.php]
// Safety net: incidents stuck in the queue or in a run that stopped answering
// end as failed (with reason) and the team is notified.
Schedule::command('firewatch:fail-stale-incidents')->everyFiveMinutes()->withoutOverlapping();

// PL-093: audit trail retention (activitylog.clean_after_days).
Schedule::command('activitylog:clean --force')->dailyAt('03:30')->withoutOverlapping();
```

| Tarefa | Frequência | Para quê |
|---|---|---|
| `firewatch:fail-stale-incidents` | A cada 5 minutos (`*/5 * * * *`) | Encerra como `failed` os incidentes que ninguém vai terminar e avisa o time |
| `activitylog:clean --force` | Todo dia às 03:30 **UTC** | Apaga da trilha de auditoria os registros com mais de 365 dias |

## Quem roda

O serviço `scheduler` do `docker-compose.yml` (container `firewatch-scheduler`) roda `php artisan schedule:work`. Esse comando acorda a cada minuto e chama `schedule:run`, que executa as tarefas vencidas naquele minuto, uma depois da outra, num processo separado.

Sem o `scheduler` no ar, nada disso acontece: incidentes travados ficam abertos e a auditoria cresce sem limite. Em produção, sem Docker, o equivalente é uma linha no cron do servidor:

```bash
* * * * * cd /var/www && php artisan schedule:run >> /dev/null 2>&1
```

### O fuso

`config/app.php` usa `'timezone' => 'UTC'`, e as tarefas não definem um fuso próprio. As **03:30** da limpeza são 03:30 UTC, ou seja, **00:30 em Brasília**. O intervalo de 5 minutos do watchdog não depende do fuso.

### withoutOverlapping()

As duas tarefas usam `withoutOverlapping()`: se a execução anterior ainda não terminou, a nova é pulada. A trava é um lock no cache (Redis), com validade padrão de **24 horas**.

::warning
Se o `scheduler` for morto no meio de uma tarefa (um `docker compose restart` durante a limpeza, por exemplo), o lock fica no Redis até expirar, e a tarefa é pulada até lá. Para o watchdog, isso significa até 24 h sem rede de segurança. Para liberar os locks na hora:

```bash
docker compose exec app php artisan schedule:clear-cache
```
::

### Conferir

```bash
docker compose exec app php artisan schedule:list
```

Mostra as duas tarefas, a expressão cron e a próxima execução. Para rodar uma delas fora de hora, escolhendo na lista:

```bash
docker compose exec app php artisan schedule:test
```

O log do container `firewatch-scheduler` (`docker compose logs -f scheduler`) mostra uma linha por tarefa executada. A saída dos comandos não é guardada: o que importa fica no log do Laravel (`storage/logs/laravel.log`) e no próprio incidente.

## O watchdog: fail-stale-incidents

Um incidente pode ficar aberto para sempre se o worker cair, se o job se perder no Redis ou se o processo morrer entre fechar o run e fechar o incidente. O comando `firewatch:fail-stale-incidents` (`FailStaleIncidents`) chama `FailStaleIncidentsAction`, que olha todos os incidentes em `queued`, `investigating`, `fixing` ou `testing`:

| Situação | Depois de | Tipo de falha | Motivo gravado |
|---|---|---|---|
| Na fila e sem run começado | `FIREWATCH_RUNNER_STALE_QUEUED_MINUTES` (**180 min**) desde o `queued_at` (ou desde a criação do run `pending`) | `stale` | "A investigação ficou na fila por mais de 180 min sem começar. Confira se o runner-worker está no ar." |
| Run `running` que não terminou | hard timeout + `FIREWATCH_RUNNER_STALE_GRACE_MINUTES` (3720 s + 10 min = **72 min**) desde o `started_at` | `stale` | "A execução dos agentes parou de responder (mais de 72 min sem terminar) e foi encerrada pelo Firewatch." |
| Run `failed` ou `dry_run`, incidente ainda aberto | **5 min** desde o `finished_at` | O tipo do relatório, ou `no_fix` / `dry_run` | O `failure_reason` do run |

Para cada um, dentro de uma transação com o incidente travado (`lockForUpdate`):

1. Fecha o run com um relatório de falha no estágio `watchdog`, quando ele ainda estava aberto (ou cria um, se não havia).
2. Marca o incidente como `failed` com o tipo e o motivo.
3. Registra `Stale incident marked as failed` no log, como `warning`.
4. Enfileira `DeliverIncidentOutcome` com `afterCommit()`: o time é avisado pelo Slack e pelo Jira como em qualquer outra falha.

Ficam de fora:

- incidentes em `testing` cujo run terminou `fixed`: eles estão esperando o Pull Request, não travados;
- runs criados antes do `queued_at` atual, que são de uma tentativa anterior a uma reexecução;
- incidentes terminais, que são ignorados mesmo se aparecerem na consulta (a transação relê cada um).

::note
O watchdog fecha o incidente, mas **não** mata um container que ainda esteja rodando. Se o worker morreu, o container segue até o limite do próprio runner e sai. Para achar sobras: `docker ps -a --filter label=br.com.firewatch.runner=1`.
::

As regras de tempo e a relação com o botão Reexecutar estão em [Timeouts e reexecução](/investigacao/timeouts-e-reexecucao).

## A limpeza da auditoria: activitylog:clean

O comando vem do pacote `spatie/laravel-activitylog`. Ele apaga da tabela `activity_log` os registros mais antigos que `activitylog.clean_after_days`, que o Firewatch deixa em **365 dias** (`config/activitylog.php`, fixo no arquivo, sem variável de ambiente).

O `--force` é necessário porque o comando pede confirmação quando o ambiente é `production`, e o scheduler não tem quem responda.

Para apagar com outro prazo, à mão:

```bash
docker compose exec app php artisan activitylog:clean --days=90 --force
```

A trilha de auditoria inteira (o que é gravado, o mascaramento e a API) está em [Auditoria](/seguranca/auditoria).

## Testes

`tests/Feature/Failure/FailStaleIncidentsTest.php` chama a ação e o comando e cobre:

- incidente preso na fila é encerrado e o time é avisado;
- run que parou de responder é fechado;
- run com falha que deixou o incidente aberto é reconciliado, mas só depois dos 5 minutos (antes disso, fica para o job);
- incidente em `testing` com run `fixed` não é tocado;
- a reexecução manual não é confundida com o run anterior;
- incidentes terminais são ignorados.

O agendamento em si (`routes/console.php`) não tem teste automatizado: confira com `schedule:list`.
