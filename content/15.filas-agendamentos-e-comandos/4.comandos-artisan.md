Os comandos próprios do Firewatch ficam em `app/Console/Commands/`. O Laravel descobre e registra sozinho tudo o que está nessa pasta, sem lista em `bootstrap/app.php`.

| Comando | Classe | Para quê | Quando usar |
|---|---|---|---|
| `add-first` | `AddFirstDevUser` | Cria o primeiro usuário, com papel `developer` | Uma vez, na instalação |
| `firewatch:fail-stale-incidents` | `FailStaleIncidents` | Encerra incidentes travados | Agendado a cada 5 min; à mão para não esperar |
| `firewatch:replay-run` | `ReplayAgentRun` | Reproduz uma execução gravada na timeline ao vivo, sem IA | Ensaiar a demo, testar o painel |
| `firewatch:reset-agent-profiles` | `ResetAgentProfiles` | Volta os agentes ao padrão | Depois de edições no painel que deram errado |
| `make:auth` | `MakeAuth` | Gera a autenticação a partir de `stubs/auth/` | **Nunca** neste projeto |

`routes/console.php` ainda tem o `inspire`, um comando de exemplo que veio com o Laravel e mostra uma citação.

Todos rodam dentro do container `app`:

```bash
docker compose exec app php artisan <comando>
```

## add-first

```bash
docker compose exec app php artisan add-first
```

Cria o primeiro usuário do sistema, de forma interativa. É a única forma de entrar no painel numa instalação nova, porque só um usuário logado cria outros ([Primeiro acesso](/ambiente-e-setup/primeiro-acesso)).

O comando pergunta, nesta ordem:

| Pergunta | Regra |
|---|---|
| Primeiro nome | Obrigatório, até 255 caracteres |
| Sobrenome | Obrigatório, até 255 caracteres |
| CPF (apenas números) | Pontos e traço são removidos. 11 dígitos, único entre os usuários |
| E-mail | E-mail válido, único entre os usuários |
| Senha | Oculta. Mínimo de 8 caracteres |
| Confirme a senha | Igual à senha |

Com tudo válido, cria o usuário com o e-mail já verificado, `active` e sem troca de senha obrigatória, atribui o papel `developer` e mostra uma tabela com os dados. Com algum erro de validação, lista as mensagens e sai com código `1`, sem criar nada.

::warning
O comando **recusa** rodar se já existir qualquer usuário com o papel `developer`: "Já existe um usuário com a role de desenvolvedor no sistema!". Ele serve para a primeira entrada, não para criar contas. Os próximos usuários são criados pelo painel ([Papéis e permissões](/seguranca/papeis-e-permissoes)).
::

## firewatch:fail-stale-incidents

```bash
docker compose exec app php artisan firewatch:fail-stale-incidents
```

Roda o watchdog uma vez, na hora. É o mesmo comando que o scheduler chama a cada 5 minutos ([Agendamentos](/filas-agendamentos-e-comandos/agendamentos)). Não tem argumentos nem opções.

Para cada incidente encerrado, mostra o id e o motivo. No fim, o total:

```text
9f1c…: A investigação ficou na fila por mais de 180 min sem começar. Confira se o runner-worker está no ar.
1 incidente(s) marcados como failed.
```

Sai sempre com código `0`, também quando não encontra nada. Ele só encerra o que já passou dos limites: rodar à mão **não** adianta o prazo de um incidente que ainda está dentro dele.

## firewatch:replay-run

```bash
docker compose exec app php artisan firewatch:replay-run
```

Reproduz uma saída gravada do runner (NDJSON) pelo mesmo caminho de uma investigação real (`RunnerStreamMonitor` → `AgentEvent` → Reverb), no ritmo escolhido. O painel mostra a timeline enchendo como se os agentes estivessem trabalhando. **Não** sobe container, **não** chama a IA e **não** aciona integrações: nenhum PR é aberto e o Slack e o Jira não são chamados.

| Argumento / opção | Padrão | O que faz |
|---|---|---|
| `stream` | `docker/runner/examples/incident-001/replay.ndjson` | Arquivo NDJSON com a saída do runner. Caminho absoluto ou relativo à raiz do back-end |
| `--incident=` | | Usa um incidente existente em vez de criar um. Ele precisa estar `received` ou `failed` |
| `--application=` | a primeira aplicação ativa, por nome | Aplicação do incidente criado (id ou identificador no monitoramento) |
| `--delay=` | `600` | Pausa entre os eventos, em milissegundos. `0` reproduz tudo de uma vez |
| `--pr-url=` | | No fim, marca o incidente como **PR aberto** com este link (nenhum PR é criado) |
| `--force` | | Permite rodar com `APP_ENV=production`. Sem ele, o comando se recusa |

O que acontece:

1. Se a primeira linha do arquivo for `{"type":"replay","incident":{…}}`, ela descreve o incidente a criar (título, ambiente, severidade, ocorrências, stack trace). O incidente criado tem `fingerprint` `replay:<uuid>` e `context.replay = true`.
2. O incidente vai para `queued` com o motivo "Ensaio da demo", e um `AgentRun` é criado e marcado como `running`, com a branch lida da gravação e o time de agentes atual.
3. Mostra o id do incidente e, se `firewatch.panel.url` estiver configurado, o link para abrir no painel.
4. Cada linha passa pelo `RunnerStreamMonitor`, com o horário trocado para **agora**. Assim a timeline, a duração do run e o tempo até o PR saem reais.
5. No fim, fecha o run com o relatório da gravação. Run `fixed`: o incidente vai para `testing` (ou para `pr_opened`, com `--pr-url`, e um evento "Pull Request aberto" na timeline). Sem relatório ou sem correção: o incidente vai para `failed` com tipo `runner_error`.

O replay não passa pela fila, não ocupa um slot de runner e não confere o budget. Mas o run é fechado por `finishWithReport()` como qualquer outro: vai para a trilha de auditoria e passa pelo `checkAlerts()` do budget, com o custo que estiver na gravação. O uso para testes sem gastar créditos está em [Testar sem gastar créditos](/ambiente-e-setup/testar-sem-creditos).

## firewatch:reset-agent-profiles

```bash
docker compose exec app php artisan firewatch:reset-agent-profiles
docker compose exec app php artisan firewatch:reset-agent-profiles detetive cirurgiao --force
```

Restaura os perfis dos agentes do plantão para o padrão do `AgentProfileSeeder`, desfazendo as edições feitas no painel.

| Argumento / opção | O que faz |
|---|---|
| `slugs*` | Os perfis a restaurar. Sem nenhum, restaura todos os perfis padrão: `chefe-de-plantao`, `sentinela`, `detetive`, `advogado-do-diabo`, `cirurgiao`, `escrivao` |
| `--force` | Não pede confirmação |

| Restaura | Mantém |
|---|---|
| `name`, `avatar`, `role`, `description` | `model` |
| `allowed_tools`, `command_access`, `write_access` | `active` |
| `system_prompt` | a ordem |

Para cada slug, o comando:

- **cria** o perfil, ativo, se ele não existe;
- **restaura** o perfil se ele foi removido (soft delete);
- sobrescreve os campos acima e mostra `restaurado`, ou `já estava no padrão` se nada mudou.

Um slug que não é um dos perfis padrão faz o comando sair com erro, listando os disponíveis, antes de mudar qualquer coisa. Sem `--force`, ele pergunta antes de sobrescrever; responder "não" também sai com código `1`.

Perfis criados no painel, que não têm padrão, nunca são tocados. Os prompts padrão estão em [Prompts padrão](/perfis-de-agente/prompts-padrao).

## make:auth

::warning
**Não rode `make:auth` neste projeto.** Ele sobrescreve, sem perguntar, arquivos que o Firewatch já ajustou.
::

O `make:auth` (`MakeAuth`) vem do template base do back-end. Ele copia os stubs de `stubs/auth/`:

| Origem | Destino |
|---|---|
| `stubs/auth/controllers/*.stub` | `app/Http/Controllers/Auth/*.php` (`ShowController`, `StoreController`, `DestroyController`) |
| `stubs/auth/requests/*.stub` | `app/Http/Requests/Auth/*.php` (`LoginRequest`) |
| `stubs/auth/routes/auth.stub` | `routes/auth.php` |

O Firewatch já tem essa estrutura, com mudanças próprias (login com Google, troca de senha obrigatória, bloqueio de usuário inativo). Rodar o comando de novo apagaria essas mudanças. Ele só faz sentido para começar outro projeto a partir do mesmo template ([Primeiro acesso](/ambiente-e-setup/primeiro-acesso)).

## Comandos de pacotes que o Firewatch usa

Não são do Firewatch, mas aparecem no `docker-compose.yml`, no agendamento ou na operação do dia a dia:

| Comando | Onde | Para quê |
|---|---|---|
| `queue:listen` | Serviços `queue` e `runner-worker` | Os workers das filas ([Filas e Horizon](/filas-agendamentos-e-comandos)) |
| `schedule:work` | Serviço `scheduler` | Roda as tarefas agendadas |
| `reverb:start` | Serviço `reverb` | O servidor WebSocket ([Tempo real](/tempo-real)) |
| `activitylog:clean` | Agendado às 03:30 | Limpeza da auditoria |
| `queue:failed`, `queue:forget`, `queue:flush` | À mão | Ver e limpar a `failed_jobs` |
| `schedule:list`, `schedule:test`, `schedule:clear-cache` | À mão | Conferir o agendamento e liberar locks presos |
| `horizon` | Nenhum serviço | Instalado, mas não usado nos workers |

## Testes

| Arquivo | Cobre |
|---|---|
| `tests/Feature/Failure/FailStaleIncidentsTest.php` | `firewatch:fail-stale-incidents` e a ação por trás |
| `tests/Feature/Console/ReplayAgentRunTest.php` | O replay da gravação da demo pela timeline ao vivo, `--pr-url`, a recusa de um incidente fora de `received`/`failed` e o arquivo inexistente |
| `tests/Feature/AgentProfile/ResetAgentProfilesCommandTest.php` | Restaura o padrão mantendo o que só o painel define, restaura só os slugs pedidos e cria os que faltam, recusa slugs desconhecidos e pede confirmação |

`add-first` e `make:auth` não têm teste automatizado.
