O Firewatch tem três jobs, todos em `app/Jobs/`:

| Job | Conexão / fila | `tries` | `timeout` | Quem enfileira |
|---|---|---|---|---|
| `InvestigateIncident` | `investigations` / `investigations` | `0` (limitado por `retryUntil`) e `maxExceptions = 1` | hard timeout do runner + 60 s (**3780 s**) | Trigger e Reexecutar |
| `DeliverIncidentOutcome` | `redis` / `default` | `1` | 300 s | `InvestigateIncident` e o watchdog |
| `SendBudgetAlert` | `redis` / `default` | `3` | o do worker | `CostBudget::checkAlerts()` |

Nenhum dos três é refeito quando dá errado no meio do trabalho. Uma investigação refeita gastaria créditos de IA de novo; uma entrega refeita abriria um segundo PR ou avisaria o time duas vezes. O `SendBudgetAlert` é a exceção: ele só manda uma mensagem e tem três tentativas.

## InvestigateIncident

Roda o time de agentes num incidente que está na fila: abre o card no Jira, monta o prompt, sobe o container do runner, acompanha o stream e fecha o `AgentRun` com o relatório. O caminho completo está na parte [Investigação](/investigacao); aqui ficam as propriedades de fila.

```php
class InvestigateIncident implements ShouldQueue, ShouldBeUnique
{
    public int $tries = 0;            // espera por vaga sem limite de tentativas…
    public int $maxExceptions = 1;    // …mas a primeira exceção falha o job
    public bool $failOnTimeout = true;
    public int $timeout;              // hardTimeout() + 60
    public int $uniqueFor;            // timeout + stale_queued_minutes × 60

    public function retryUntil(): \DateTimeInterface
    {
        return now()->addMinutes(self::maxWaitMinutes()); // 180 min
    }
}
```

| Propriedade | Valor padrão | Por quê |
|---|---|---|
| Conexão e fila | `firewatch.runner.connection` / `firewatch.runner.queue` (`investigations`) | Definidas no construtor. O `retry_after` dessa conexão cobre uma execução inteira ([Filas e Horizon](/filas-agendamentos-e-comandos)) |
| `tries = 0` | sem limite | Esperar por um runner livre usa `release()`, e cada `release()` conta como tentativa. Com `0`, o limite passa a ser só o prazo do `retryUntil()` |
| `retryUntil()` | agora + 180 min | O mesmo prazo que o watchdog dá a um incidente na fila (`FIREWATCH_RUNNER_STALE_QUEUED_MINUTES`) |
| `maxExceptions = 1` | | Qualquer exceção falha o job na hora. Uma investigação nunca é refeita sozinha |
| `timeout` | 3600 + 120 + 60 = **3780 s** | Maior que o limite do `DockerRunner` (`hardTimeout()`), para o runner matar o container e registrar a falha antes de o worker desistir |
| `failOnTimeout = true` | | Estourar o `timeout` falha o job em vez de devolvê-lo à fila |
| `ShouldBeUnique`, `uniqueId()` | o id do incidente | No máximo um job por incidente na fila ou em execução |
| `uniqueFor` | 3780 + 180 × 60 = **14 580 s** | O lock continua com o job enquanto ele é devolvido à fila esperando vaga; precisa cobrir a espera e a execução |

### Quem enfileira

| Origem | Classe | Quando |
|---|---|---|
| Webhook, comando `/firewatch` do Slack ou simulação | `EvaluateIncidentTriggerAction` | O motor de regras decide acionar os agentes ([Motor de regras](/registro-e-trigger/motor-de-regras)) |
| Botão Reexecutar (`POST` na API do incidente) | `RetryIncidentInvestigationAction` | Um usuário pede uma nova tentativa ([Timeouts e reexecução](/investigacao/timeouts-e-reexecucao)) |

Os dois fazem o mesmo, dentro de `DB::transaction` e com o incidente travado por `lockForUpdate()`: passam o incidente para `queued` e chamam `InvestigateIncident::dispatch($locked)->afterCommit()`. O job só chega ao Redis depois do commit, com o status já gravado.

### handle()

1. Relê o incidente. Se ele não está mais `queued` (foi removido, ignorado ou já terminou), registra `InvestigateIncident skipped` no log e termina sem erro.
2. Tenta um slot em `RunnerSlots`. **Sem vaga**: grava em `status_reason` quantas execuções estão em andamento e chama `release(slot_wait_seconds)` (30 s). O job volta para a fila e o incidente continua `queued`.
3. **Com vaga**: cria o `AgentRun`, confere o budget, abre o card, roda o container e fecha o run e o incidente. O slot é devolvido num `finally`, mesmo se algo quebrar.
4. Ao final, enfileira `DeliverIncidentOutcome` com o run.

### failed()

O Laravel chama `failed()` quando o job falha: exceção, `timeout` ou fim do prazo `retryUntil()` sem conseguir vaga. Ele fecha o que ficou aberto e avisa o time:

| Situação | O que faz |
|---|---|
| Fim do prazo sem vaga (`MaxAttemptsExceededException`) | Cria um run, fecha como falho no estágio `queue` e marca o incidente `failed` com tipo `stale` |
| Exceção ou timeout com o run em andamento | Fecha o run no estágio `job` e marca o incidente `failed` com tipo `internal` (ou o tipo que o `FailureClassifier` achar no relatório) |
| O run já tinha terminado como `fixed` | A falha veio depois do trabalho: mantém a correção, deixa o incidente em `testing` e enfileira a entrega mesmo assim |
| Incidente já terminal ou removido | Nada |

Em todos os casos que fecham alguma coisa, `failed()` enfileira `DeliverIncidentOutcome`, para o time saber da falha pelo Slack e pelo Jira. Detalhes em [Resultado e falhas](/investigacao/resultado-e-falhas).

## DeliverIncidentOutcome

Entrega o resultado de um run terminado: abre o Pull Request (se houver correção), notifica pelo Slack e atualiza o card do Jira. Cada passo é independente e grava o próprio evento na timeline. O passo a passo está em [DeliverIncidentOutcome](/saida/deliver-incident-outcome).

| Propriedade | Valor | Por quê |
|---|---|---|
| Conexão e fila | a padrão (`redis` / `default`) | Não precisa de Docker e não deve esperar atrás das investigações |
| `tries = 1` | | Refazer poderia abrir um segundo PR ou avisar o time duas vezes |
| `timeout = 300` | | Criar branch, enviar o commit e abrir o PR são chamadas HTTP a um provedor externo. O `--timeout=360` do worker `queue` fica acima dele de propósito ([Filas e Horizon](/filas-agendamentos-e-comandos)) |
| Dados | `public AgentRun $run` (`SerializesModels`) | Só o id vai para a fila; o run é relido com `fresh()` |

| Quem enfileira | Quando |
|---|---|
| `InvestigateIncident::investigate()` | Depois de fechar o run (também quando o budget do mês bloqueou a execução) |
| `InvestigateIncident::failed()` | Depois de fechar um run que falhou, ou para garantir a entrega de um run `fixed` |
| `FailStaleIncidentsAction` | Depois de encerrar um incidente travado, com `->afterCommit()` |

O `handle()` começa conferindo o run: se ele não existe mais ou ainda não terminou, registra `DeliverIncidentOutcome skipped` e termina. Num run `dry_run`, só grava na timeline que as integrações não foram acionadas.

Os erros de cada integração são capturados e viram eventos `error` na timeline; o job em si quase nunca falha. Se falhar, vai para `failed_jobs` e não é refeito.

## SendBudgetAlert

Avisa o time de que o gasto do mês chegou ao percentual de alerta ou ao teto (100%). As regras dos limites estão em [Budget](/conectores-aplicacoes-budget-e-metricas/budget).

```php
new SendBudgetAlert(
    threshold: 80,        // ou 100
    spentUsd: 41.2,
    monthlyUsd: 50.0,
    month: '2026-11',
);
```

| Propriedade | Valor | Por quê |
|---|---|---|
| Conexão e fila | a padrão (`redis` / `default`) | |
| `tries = 3` | | Só manda uma mensagem. Os erros de cada conector já são capturados, então uma nova tentativa só acontece se o job inteiro quebrar |
| `timeout` | não declarado | Vale o padrão do `queue:work` que roda o job: 60 s |
| Trait | `Illuminate\Foundation\Queue\Queueable` | O formato atual do Laravel, que já inclui `Dispatchable`, `InteractsWithQueue` e `SerializesModels` |

### Quem enfileira

`CostBudget::checkAlerts()` é o único lugar. Ele é chamado em dois momentos:

- no fim de **todo run**, dentro de `AgentRun::finishWithReport()` (num `try/catch`: um erro no alerta nunca impede o run de fechar);
- quando alguém **salva os limites** em Custos e limites (`BudgetController::update`), porque um teto menor pode já ter sido ultrapassado.

`checkAlerts()` trava `firewatch:budget-alerts` no cache por até 10 s, confere quais limites o mês já passou e enfileira um `SendBudgetAlert` para cada um que ainda não foi avisado. Os limites avisados ficam em `app_settings` por mês, então cada um sai **uma vez por mês**.

### handle()

1. Monta título e texto (`message()`): um para o percentual de alerta, outro para o teto atingido.
2. Chama `alert()` em cada conector notificador ativo (hoje, o Slack), em ordem de nome. Um conector com erro é reportado e os outros continuam.
3. Grava `budget_alert` na trilha de auditoria, com os valores e a lista de conectores que receberam ([Auditoria](/seguranca/auditoria)).
