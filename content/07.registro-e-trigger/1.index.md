Depois que o adapter produz um [`IncomingEvent`](/entrada/adapters#o-contrato-incomingevent), o registro decide **em qual incidente** ele cai. O objetivo é um só: **um bug, uma investigação**. Um pico de 300 erros iguais precisa virar um incidente com 300 ocorrências, e não 300 execuções dos agentes.

## O pipeline

`IngestIncomingEventAction` é o ponto de entrada comum ao webhook, ao comando do Slack e ao botão Simular incidente:

```php [app/Actions/Incident/IngestIncomingEventAction.php]
public function handle(IncomingAdapter $adapter, array $payload): IncidentRegistration
{
    $event = $adapter->normalize($payload);

    $application = Application::findByMonitoringIdentifier($event->application)
        ?? throw IgnoredIncomingPayloadException::because("no active application with monitoring identifier [{$event->application}]");

    $registration = $this->register->handle($application, $event);

    return $registration->withDecision($this->evaluate->handle($registration->incident));
}
```

| Passo | Classe | Resultado |
|---|---|---|
| 1. Normalizar | adapter da fonte | `IncomingEvent` ou [exception](/entrada/payloads-ignorados-e-invalidos) |
| 2. Achar a aplicação | `Application::findByMonitoringIdentifier()` | Só aplicações **ativas**; senão o evento é ignorado |
| 3. Registrar | `RegisterIncomingEventAction` | Incidente novo ou existente |
| 4. Decidir | `EvaluateIncidentTriggerAction` | `TriggerDecision` ou `null` (veja [Motor de regras](/registro-e-trigger/motor-de-regras)) |

O resultado é um `IncidentRegistration` (`final readonly`):

| Propriedade / método | Significado |
|---|---|
| `incident` | O incidente onde o evento caiu |
| `created` | `true` se foi criado agora; `false` se o evento foi somado a um existente |
| `deduplicated()` | O contrário de `created` |
| `decision` | A decisão das regras, ou `null` quando o incidente já tinha passado da fase de decisão |
| `withDecision()` | Cópia com a decisão preenchida (o objeto é imutável) |

## Encontrar ou criar

`RegisterIncomingEventAction::handle()` procura o incidente que deve absorver o evento com `Incident::findForDeduplication()`:

```php [app/Models/Incident/Incident.php]
public static function findForDeduplication(Application $application, string $fingerprint, CarbonInterface $silentSince): ?self
{
    return static::findOpenFor($application, $fingerprint)
        ?? static::query()
            ->where('application_id', $application->getKey())
            ->where('fingerprint', $fingerprint)
            ->where('last_seen_at', '>=', $silentSince)
            ->latest('last_seen_at')
            ->first();
}
```

A chave é sempre **aplicação + fingerprint**. A busca tem duas etapas:

1. **Um incidente aberto** (`received`, `queued`, `investigating`, `fixing`, `testing`), o mais recente. Incidentes abertos absorvem repetições **sem limite de tempo**.
2. Se não houver aberto, **um incidente terminado** (`ignored`, `pr_opened`, `failed`) cujo erro foi visto pela última vez **dentro da janela** (`last_seen_at` nas últimas `reopen_after_hours` horas).

Se nenhum dos dois existir, o evento **cria** um incidente novo, com status `received`. Incidentes apagados (soft delete) nunca são reaproveitados.

::mermaid
---
code: |
  flowchart TD
    E[IncomingEvent<br/>aplicação + fingerprint] --> O{Incidente aberto<br/>com o mesmo fingerprint?}
    O -- sim --> AB[Absorve: soma ocorrências]
    O -- não --> W{Incidente terminado com<br/>last_seen_at nas últimas 72 h?}
    W -- sim --> AB
    W -- não --> N[Cria incidente novo<br/>status received]
    AB --> T[EvaluateIncidentTriggerAction]
    N --> T
caption: Um incidente aberto sempre ganha de um terminado, mesmo que o terminado tenha sido visto há menos tempo.

## Absorver uma repetição

Quando o evento cai num incidente existente, `absorb()` atualiza só os contadores:

| Campo | Regra |
|---|---|
| `occurrences` | **Soma** as ocorrências do evento |
| `affected_users` | Fica com o **maior** valor entre o atual e o do evento (não soma) |
| `last_seen_at` | Fica com a data **mais recente** entre a atual e a do evento. Uma entrega atrasada não puxa a data para trás |
| `severity` | Só **sobe**: um evento mais grave eleva o incidente; um mais leve não rebaixa |
| `status`, título, payloads | **Não mudam** |

O status não muda nem num incidente terminado. Um incidente `pr_opened` que recebe o mesmo erro de novo continua `pr_opened`, só com mais ocorrências. Faz sentido: o PR com a correção ainda está esperando revisão ou deploy, e investigar de novo só gastaria créditos.

::note
`affected_users` usa o maior valor, e não a soma, porque as fontes mandam números diferentes. Uma issue do Sentry traz o total de usuários **até agora** (somar contaria em dobro), e um `event_alert` traz só `1` (o usuário daquele evento). Consequência: com eventos do Sentry do tipo `event_alert`, `affected_users` **nunca passa de 1**. Uma regra `min_affected_users` maior que 1 só é atingida por fontes que mandam o total (issues do Sentry, webhook genérico).

Já `occurrences` sempre **soma**. Para issues do Sentry, que trazem o total acumulado em `count`, duas entregas da mesma issue (`created` com 3 e `unresolved` com 10) resultam em 13 ocorrências.
::

## Criar um incidente

`create()` grava o incidente com:

| Coluna | Valor |
|---|---|
| `application_id`, `fingerprint`, `title`, `environment`, `severity`, `occurrences`, `affected_users` | Do evento |
| `raw_payload` | Payload original, **criptografado** (`encrypted:array`) e oculto na API |
| `sanitized_payload` | `IncomingEvent::toArray()` passado pelo [`SensitiveDataMasker`](/seguranca/mascaramento). É o único payload que vai para o painel e para o modelo |
| `first_seen_at`, `last_seen_at` | A data do evento (ou agora) |
| `status` | `received` (padrão da coluna) |

### A data do evento

`seenAt()` protege os incidentes de relógios errados:

- Sem `occurred_at`, ou com uma data **no futuro**, usa **agora**.
- Com uma data válida, converte para o fuso da aplicação antes de gravar.

## Concorrência

Duas entregas do mesmo erro chegando juntas (um pico, ou um reenvio do Sentry) poderiam criar dois incidentes. Duas travas evitam isso:

| Trava | Onde | Protege |
|---|---|---|
| **Lock de cache** `incidents:dedup:{aplicação}:{fingerprint}` | `RegisterIncomingEventAction` | O "procura ou cria" é atômico por fingerprint. A segunda requisição espera até **10 s** (`LOCK_WAIT_SECONDS`); o lock expira sozinho em 20 s |
| **Lock de linha** (`lockForUpdate`) no incidente | `EvaluateIncidentTriggerAction` | Só uma das requisições aplica a decisão, então os agentes não rodam duas vezes |

O lock de cache usa o driver de cache da aplicação (Redis no `docker-compose`). Se a espera passar de 10 s, a requisição falha com `500` e a fonte reenvia depois.

## A janela `reopen_after_hours`

```php [config/firewatch.php]
'incidents' => [
    'reopen_after_hours' => (int) env('FIREWATCH_INCIDENT_REOPEN_AFTER_HOURS', 72),
],
```

Apesar do nome, **nada é reaberto**: nenhum incidente terminado volta para `received`. A janela só decide se uma repetição **cai no incidente antigo** ou **abre um novo**:

| O erro voltou… | Resultado |
|---|---|
| Com o incidente ainda aberto | Soma no incidente aberto, sem limite de tempo |
| Até 72 h depois da **última** ocorrência de um incidente terminado | Soma no incidente terminado, que **mantém o status** |
| Mais de 72 h depois da última ocorrência | **Incidente novo**, tratado como regressão, que passa pelas regras e pode acionar os agentes |

A janela conta a partir de `last_seen_at`, e não de quando o incidente terminou. Um erro que continua acontecendo todo dia **nunca** abre incidente novo: cada ocorrência empurra o `last_seen_at` e mantém o incidente antigo dentro da janela. O incidente novo só aparece depois de 72 h de **silêncio**.

| Cenário (janela de 72 h) | O que acontece |
|---|---|
| PR aberto na segunda; o erro continua até o deploy na quarta; volta no sábado | Quarta → sábado = 3 dias e meio de silêncio: **incidente novo** (regressão) |
| Incidente `ignored` (ambiente de staging); o erro acontece todo dia | Soma sempre no mesmo incidente `ignored` |
| Incidente `failed`; alguém corrige à mão; o erro volta 2 dias depois | Soma no `failed`. Use **Reexecutar investigação** no painel para tentar de novo |

Para mudar a janela, defina `FIREWATCH_INCIDENT_REOPEN_AFTER_HOURS` no `.env` do back. Janelas curtas abrem mais incidentes (e mais investigações); janelas longas juntam regressões com o bug antigo.

## Testes

`tests/Feature/Incident/RegisterIncomingEventActionTest.php` cobre: o primeiro evento cria um incidente `received`; o mesmo fingerprint soma no aberto e num incidente em investigação; a severidade só sobe; fingerprints ou aplicações diferentes criam outro incidente; fingerprints derivados deduplicam; incidentes terminados absorvem dentro da janela (71 h) e não depois dela (73 h); o aberto ganha do terminado; apagados não são reaproveitados; datas futuras e atrasadas não corrompem o `last_seen_at`; e o lock em registros concorrentes.
