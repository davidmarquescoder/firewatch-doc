Antes de subir o container, o job chama `InvestigationPromptBuilder::build($incident)`. O resultado é um `RunnerInput` com tudo o que o Claude Code vai receber dentro do runner. Tudo vem do banco: o incidente e os **perfis de agentes** editados no painel.

## RunnerInput

`App\Services\Runner\RunnerInput` é um `final readonly`. `writeTo()` grava cada parte num arquivo, que o `DockerRunner` copia para `/runner/input` no container:

| Propriedade | Arquivo | Como o runner usa |
|---|---|---|
| `prompt` | `prompt.md` | O pedido: `claude -p "<prompt>"` |
| `systemPrompt` | `system-prompt.md` | `--append-system-prompt-file`: as instruções do orquestrador |
| `agents` | `agents.json` | `--agents`: os subagentes, no formato do Claude Code |
| `policy` | `policy.json` | A guarda de ferramentas (`tool-guard.sh`) decide o que cada agente pode chamar |
| `team` | Nenhum | Retrato dos perfis usados, gravado em `agent_runs.team` para auditoria |

`agentsJson()` sempre gera um **objeto**, mesmo sem subagentes (`{}`), porque o Claude Code não aceita uma lista. `policyJson()` completa a política com `version: 1`, `main: null` e `agents: {}` quando faltam.

## O prompt do incidente

`prompt()` descreve o incidente em Markdown:

````md [prompt.md]
# Incidente: Attempt to read property "role" on null

- **Aplicação**: FlowStock (`flowstock-back`)
- **Ambiente**: production
- **Severidade**: Erro (`error`)
- **Ocorrências**: 3
- **Usuários afetados**: 1
- **Primeira ocorrência**: 2026-11-16T22:10:04+00:00
- **Última ocorrência**: 2026-11-16T22:12:40+00:00
- **Incidente Firewatch**: `019a8f3c-…`

## Erro

```
Attempt to read property "role" on null
```

## Stack trace

```
#0 app/Http/Controllers/OrderController.php(42): …
```

## Contexto (dados sensíveis mascarados)

```json
{ "request": { "url": "https://…/orders", "user": { "email": "[email]" } } }
```

Investigue, corrija e deixe os testes passando seguindo o fluxo obrigatório.
````

Cuidados na montagem:

| Cuidado | Como |
|---|---|
| **Mascarar de novo** | Título, ambiente, stack trace e contexto passam pelo [`SensitiveDataMasker`](/seguranca/mascaramento) outra vez, mesmo já vindo do `sanitized_payload`. É defesa em profundidade: um incidente gravado antes de uma regra nova de máscara também sai mascarado |
| **Stack trace grande** | Acima de 30 000 bytes (`MAX_STACK_TRACE_BYTES`), fica o começo e o fim, com "… (stack trace truncado) …" no meio |
| **Contexto grande** | O JSON é cortado em 20 000 bytes (`MAX_CONTEXT_BYTES`), com "… (contexto truncado)" |
| **Crases no conteúdo** | Cada bloco de código usa uma cerca **maior** que qualquer sequência de crases dentro dele, para um stack trace com ```` ``` ```` não quebrar o Markdown |
| **Dados que faltam** | Sem stack trace, o prompt pede para localizar a falha pelo erro e pelo código. Sem contexto, a seção não aparece. Datas e ambiente ausentes viram "não informado" |
| **Datas** | Em UTC, ISO 8601 |

## O prompt do orquestrador

`systemPrompt()` junta duas partes:

1. o `system_prompt` do perfil **orquestrador** ativo (o Chefe de Plantão). Sem perfil ativo, usa o prompt padrão do seeder (`chefe-de-plantao`);
2. a seção **"Time escalado nesta execução"**, gerada a partir dos subagentes ativos.

A seção gerada garante que a tabela de delegação bate com os agentes que foram de fato injetados, mesmo depois de alguém renomear, desativar ou criar perfis no painel:

```md
## Time escalado nesta execução

Gerado pelo Firewatch a partir dos perfis ativos no painel. Para delegar, use a ferramenta `Agent` com
`subagent_type` exatamente igual à coluna **subagent_type**. …

| Etapa | Função | subagent_type | Agente | Ferramentas | Comandos | Arquivos |
|---|---|---|---|---|---|---|
| 1 | Triagem | `sentinela` | Sentinela | Read, Grep, Glob | nenhum | nenhum |
| 2 | Causa raiz | `detetive` | Detetive | Read, Grep, Glob, Bash | só leitura | nenhum |
| 3 e 5–6 | Testes | `advogado-do-diabo` | Advogado do Diabo | … | leitura e testes | só testes |
…
```

- As linhas seguem a ordem das funções em `AgentRoleEnum` (triagem, causa raiz, testes, correção, Pull Request). A coluna **Etapa** vem de `step()`: o testador cobre as etapas 3 e 5–6.
- Com mais de um agente na mesma função, a seção manda usar o primeiro e recorrer aos outros só se ele falhar.
- Uma função **sem agente ativo** aparece em "Sem agente ativo para: …", com a instrução de o orquestrador fazer essa etapa ele mesmo, seguindo as mesmas regras.
- `|` e quebras de linha nos nomes são escapados para não quebrar a tabela.

## Os subagentes

`agents` tem uma entrada por perfil ativo que não é orquestrador, indexada pelo `slug`. `AgentProfile::toAgentDefinition()` gera:

```json [agents.json]
{
  "detetive": {
    "description": "Encontra a causa raiz…",
    "prompt": "Você é o Detetive…\n",
    "tools": ["Read", "Grep", "Glob", "Bash"]
  }
}
```

`tools` e `model` só aparecem quando o perfil os define. Sem `tools`, o agente herda todas as ferramentas, mas a política abaixo ainda vale.

## A política de ferramentas

`toolPolicy()` diz o que cada agente pode fazer. A guarda de ferramentas do runner aplica essa política e recusa qualquer chamada fora dela:

```json [policy.json]
{
  "version": 1,
  "main": { "name": "Chefe de Plantão", "tools": null, "commands": "full", "write": "any" },
  "agents": {
    "detetive": { "name": "Detetive", "tools": ["Read", "Grep", "Glob", "Bash"], "commands": "read_only", "write": "none" }
  }
}
```

| Campo | Significado |
|---|---|
| `main` | A sessão principal (orquestrador). Sem perfil de orquestrador, recebe o acesso padrão: todas as ferramentas, comandos `full`, escrita em qualquer arquivo |
| `agents` | Um item por subagente, pelo `slug` |
| `tools` | Ferramentas permitidas (`null` = todas) |
| `commands` | Acesso a comandos de shell (`command_access` do perfil) |
| `write` | Quais arquivos o agente pode alterar (`write_access` do perfil) |

Um agente **fora** da política (agentes nativos do Claude Code ou definidos pelo repositório) não pode fazer nada. Os níveis estão em [Níveis de acesso](/perfis-de-agente/niveis-de-acesso) e a guarda em [Guarda de ferramentas](/runner/tool-guard).

## O retrato do time

`team` guarda, para cada perfil usado, `id`, `slug`, `name`, `role`, `avatar`, `model`, `tools`, `commands`, `write` e `prompt_sha256` (o hash do prompt). Ele fica no `AgentRun`: dá para saber exatamente com qual versão de cada agente uma investigação rodou, mesmo depois de o perfil ser editado. Quem lê esse campo e como ele se comporta está em [Papéis e times](/perfis-de-agente#o-time-gravado-em-agent_runs).

## Testes

`tests/Feature/Runner/InvestigationPromptBuilderTest.php` cobre: a descrição do incidente; tudo o que vai ao modelo mascarado de novo, inclusive incidentes antigos; stack trace e contexto ausentes; cercas de código dentro do stack trace; agentes vindos dos perfis ativos; a seção do time na ordem do fluxo; o orquestrador padrão sem perfil; a política vinda dos perfis e o acesso padrão da sessão principal; o time do seeder completo; os arquivos gravados para o container; e `agents.json` como objeto mesmo vazio.
