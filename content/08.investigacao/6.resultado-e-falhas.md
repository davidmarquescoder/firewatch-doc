Toda execução termina com um **relatório** no formato do runner (`docker/runner/EVENTS.md`, `schema_version: 1`), gravado em `agent_runs.report`. Ele vem de uma de duas fontes:

| Fonte | Quando | Marca |
|---|---|---|
| O runner | Evento `report`, o caminho normal, com sucesso ou falha | |
| O FireWatch | O runner não chegou a reportar: erro de configuração, container morto, timeout, teto de custo, queda do job, watchdog | `generated_by: "firewatch"` |

## O relatório

Os campos que o Laravel lê:

| Campo | Uso |
|---|---|
| `status` | `fixed`, `failed` ou `dry_run`: vira o status do `AgentRun` |
| `exit_code` | Código de saída do runner |
| `failure` | `{stage, reason, exit_code}` quando `status = failed`. O `FailureClassifier` acrescenta `kind` e `explanation` |
| `git.work_branch` | A branch de trabalho |
| `claude` | Modelo, `session_id`, tokens, `cost_usd`, `num_turns`, erro e `api_error_status` |
| `timing` | `started_at`, `finished_at`, `duration_seconds` |
| `tests`, `flow`, `changes`, `agent_report` | Detalhes da verificação, do fluxo obrigatório, dos arquivos alterados e do relatório dos agentes |

O relatório montado pelo FireWatch (`InvestigateIncident::failureReport()`) tem o mínimo: `status: failed`, `exit_code`, `failure` (com `stage`, `reason` e às vezes `kind`), `git.work_branch`, `claude: null`, `timing` e `generated_by: "firewatch"`.

`AgentRun::finishWithReport()` limpa o relatório (`scrubReport`) e preenche as colunas do run: status, código de saída, `failure_stage`, `failure_reason` (a explicação do classificador, ou o motivo cru), branch, modelo, sessão, datas, duração, tokens, custo e turnos. Um run só pode ser fechado **uma vez**: fechar de novo lança `LogicException`.

## Códigos de saída do runner

| Código | Significado |
|---|---|
| `0` | Corrigido: os agentes relataram `fixed`, o fluxo obrigatório foi comprovado e a suíte passou (ou dry run) |
| `1` | Erro inesperado no script do runner |
| `2` | Configuração inválida (variável faltando, branch sem `firewatch/`…) |
| `3` | Falha ao clonar o repositório |
| `4` | Falha ao instalar as dependências |
| `5` | O Claude Code terminou com erro (chave inválida, limite de gasto…) |
| `6` | A suíte de testes falhou na verificação feita depois dos agentes |
| `7` | Os agentes não entregaram correção (sem relatório, relatório `failed` ou nenhum arquivo alterado) |
| `8` | Fluxo obrigatório não cumprido (nenhum teste alterado, só testes alterados, teste removido, ou teste que **passa sem a correção**) |
| `124` | Timeout de uma etapa (`failure.stage` diz qual) |
| `137` | Morto pelo kernel, em geral por falta de memória |
| `143` | Interrompido (SIGTERM/SIGINT) |

## FailureClassifier

`App\Services\Runner\FailureClassifier::annotate()` recebe o relatório antes de ele ser gravado. Para relatórios `fixed` ou `dry_run`, não faz nada. Para um `failed`:

1. **Tipo**: usa o `failure.kind` que já veio no relatório. Sem ele, mapeia o `exit_code` (de `failure` ou da raiz) pela tabela acima. Um código desconhecido vira `runner_error`.
2. **Explicação**: num relatório do FireWatch, o `reason` já foi escrito para o time e é mantido. Num relatório do runner, `explain()` escreve uma explicação em português para o tipo.
3. Grava `failure.kind` e `failure.explanation`, que é **mascarada** e cortada em 1000 caracteres.

O `failure.reason` original do runner continua no relatório para auditoria. O painel e as notificações mostram a explicação.

### Explicações específicas

| Tipo | O classificador explica |
|---|---|
| `timeout` | "Tempo esgotado na etapa de instalação de dependências: …", com a etapa traduzida (`setup`, `clone`, `install`, `agents`, `claude`, `flow`, `verify`, `result`, `total`) |
| `tests_failed` | A correção foi aplicada, mas a suíte falhou, com a linha de resumo dos testes. Se os agentes **afirmaram** que a suíte passava, avisa para revisar o ambiente de testes |
| `flow_violation` | Lista o que faltou no fluxo (`flow.violations`). Se os agentes afirmaram que o teste falhava antes da correção, mas o runner comprovou que ele **passava** sem ela, diz isso |
| `no_fix` | O motivo que os próprios agentes deram (`agent_report.failure_reason`), ou que eles terminaram **sem** escrever o relatório final |
| `ai_error` | Pelo `api_error_status`: 401/403 credencial recusada, 429 limite de requisições, 5xx API indisponível. Um erro com "budget" é o teto de custo da execução |
| `clone`, `install`, `configuration`, `out_of_memory`, `cancelled` | Texto fixo com o que conferir (token e repositório, comando de instalação, `FIREWATCH_RUNNER_MEMORY`…) |

## Os failure kinds

`IncidentFailureKindEnum` diz **por que** um incidente terminou `failed`. Fica em `incidents.failure_kind`, com o motivo detalhado em `status_reason`, e alimenta o painel, as notificações e as métricas. `nextStep()` dá a orientação que vai nas notificações.

| Kind | Rótulo | De onde vem | Próximo passo (`nextStep()`) |
|---|---|---|---|
| `configuration` | Configuração inválida | Código 2, ou `RunnerLaunchException` antes do Docker (sem repositório, conector errado, sem credencial do Claude, falha no `docker create`/`cp`) | Revisar a configuração da aplicação e dos conectores e reexecutar |
| `clone` | Falha ao clonar o repositório | Código 3 | Conferir o token e o slug do repositório e reexecutar |
| `install` | Falha ao instalar dependências | Código 4 | Conferir o comando de instalação e reexecutar |
| `ai_error` | Erro no Claude | Código 5 | Conferir a credencial e o saldo da API e reexecutar |
| `tests_failed` | Testes não passaram | Código 6 | Nada foi enviado: investigar manualmente |
| `no_fix` | Causa ou correção não encontrada | Código 7, ou run `failed` sem tipo | Investigar manualmente a partir da causa provável |
| `flow_violation` | Fluxo obrigatório não cumprido | Código 8 | Nada foi enviado: investigar manualmente |
| `timeout` | Tempo esgotado | Código 124, ou o FireWatch matou o container no `hardTimeout()` | Reexecutar ou investigar manualmente |
| `out_of_memory` | Memória esgotada | Código 137 | Aumentar `FIREWATCH_RUNNER_MEMORY` ou investigar manualmente |
| `cancelled` | Execução interrompida | Código 143 | Reexecutar |
| `runner_error` | Erro no runner | Código 1 ou desconhecido, incluindo o container que saiu sem relatório | Ver os logs do runner-worker e reexecutar |
| `internal` | Erro interno do Firewatch | `InvestigateIncident::failed()` por exception ou timeout do worker | Ver os logs do runner-worker e reexecutar |
| `stale` | Execução sem resposta | Nenhum slot até o `retryUntil()`, ou o [watchdog](/investigacao/timeouts-e-reexecucao#o-watchdog-failstaleincidents) | Conferir se o runner-worker está no ar e reexecutar |
| `delivery_blocked` | Correção não enviada | `DeliverIncidentOutcome` recusou enviar uma correção pronta | Revisar a correção pelo painel |
| `dry_run` | Execução de teste | Run `dry_run` (`FIREWATCH_RUNNER_DRY_RUN=1`) | Desativar o dry run para os agentes trabalharem |
| `budget` | Teto de custo atingido | O teto **mensal** já estava estourado: o container nem subiu | Aumentar o teto em Custos e limites ou aguardar o próximo mês |

`isAgentFailure()` é verdadeiro só para `tests_failed`, `no_fix` e `flow_violation`: os agentes **rodaram** e não entregaram uma correção aceitável. Os outros tipos são falhas **em volta** dos agentes (configuração, infraestrutura, orçamento).

::note
O teto de custo **por execução** é diferente do mensal. Quando o Claude Code para por `--max-budget-usd`, o runner sai com código 5 e o tipo é `ai_error`, com a explicação "O teto de custo desta execução foi atingido…". O tipo `budget` é só para o mês estourado **antes** de começar.
::

## Do run para o incidente

`closeIncident()` e `failed()` usam o run fechado para decidir o incidente:

| Run | Incidente | `failure_kind` | `status_reason` |
|---|---|---|---|
| `fixed` | Fica em `testing` até o PR | | |
| `dry_run` | `failed` | `dry_run` | "Execução de teste (DRY_RUN): repositório e dependências preparados, mas os agentes não foram chamados." |
| `failed` | `failed` | `report.failure.kind`, ou `no_fix` | `failure_reason` do run, ou "Os agentes terminaram sem entregar uma correção." |

Em todos os casos, `DeliverIncidentOutcome` é despachado: a falha também chega ao Slack e ao Jira, com o rótulo e o próximo passo.
