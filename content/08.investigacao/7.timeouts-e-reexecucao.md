Uma investigação pode travar em vários lugares: na instalação, no Claude, nos testes, no worker ou na fila. Cada camada tem um limite, e eles são **encaixados**: o limite de dentro sempre acaba antes do de fora. Assim, quem está mais perto do problema registra a falha com o motivo certo.

## Os limites, de dentro para fora

| Camada | Limite (padrão) | Variável | Quando estoura |
|---|---|---|---|
| Instalação de dependências | 900 s | `FIREWATCH_RUNNER_INSTALL_TIMEOUT` | O runner sai com 124, `failure.stage = install` |
| Claude Code | 1800 s | `FIREWATCH_RUNNER_CLAUDE_TIMEOUT` | 124, `stage = claude` |
| Suíte de testes (verificação) | 600 s | `FIREWATCH_RUNNER_TEST_TIMEOUT` | 124, `stage = verify` |
| Execução total do runner | 3600 s | `FIREWATCH_RUNNER_MAX_DURATION` | 124, `stage = total`. O runner ainda escreve o relatório |
| `hardTimeout()` do Laravel | total + 120 s = **3720 s** | `FIREWATCH_RUNNER_KILL_GRACE` | O `DockerRunner` faz `docker kill`: tipo `timeout` "O runner excedeu o tempo máximo (3720 s)…" |
| `$timeout` do job | hard + 60 = **3780 s** | | O worker mata o job: `failed()` com o tipo `internal` |
| Lock de vaga | hard + 300 = **4020 s** | | A vaga se libera sozinha se o worker morreu |
| `retry_after` da fila | **4200 s** | `FIREWATCH_RUNNER_QUEUE_RETRY_AFTER` | A fila entregaria o job a outro worker; por isso fica acima de tudo |
| Watchdog: run em execução | hard + 10 min = **4320 s** (72 min) | `FIREWATCH_RUNNER_STALE_GRACE_MINUTES` | O run é fechado como `stale` |
| Espera por vaga / na fila | **180 min** | `FIREWATCH_RUNNER_STALE_QUEUED_MINUTES` | `stale` |

::warning
Ao aumentar `FIREWATCH_RUNNER_MAX_DURATION`, aumente também `FIREWATCH_RUNNER_QUEUE_RETRY_AFTER` para continuar **acima** do `$timeout` do job. Se ele ficar abaixo, a fila entrega o mesmo job a um segundo worker no meio da execução. O segundo worker encontra o incidente fora de `queued` e desiste, mas a vaga e o worker ficam ocupados à toa, e a situação é difícil de diagnosticar.
::

## Nada é refeito sozinho

Cada tentativa gasta créditos do Claude, então o FireWatch **nunca** reexecuta uma investigação por conta própria:

- `$maxExceptions = 1`: a primeira exception falha o job.
- Esperar por uma vaga **não** é tentativa (`$tries = 0`, `release()` sem exception).
- Uma falha do runner não é uma exception: o job termina normalmente com o run `failed`.

Para tentar de novo, alguém precisa pedir: é o **Reexecutar**.

## Reexecutar uma investigação

```http
POST /api/v1/incident/{incident}/retry
```

| | |
|---|---|
| Controller | `IncidentController::retry()` |
| Middlewares | A pilha do painel + `throttle:10,1,incident-retry` |
| Action | `RetryIncidentInvestigationAction` |
| Resposta | `202` com "Investigação reenfileirada: os agentes vão rodar novamente." e o incidente |
| Auditoria | Evento `incident_retried` |

### As travas

`blocker()` devolve o motivo pelo qual o incidente **não** pode ser reexecutado, ou `null`:

| Ordem | Condição | Mensagem |
|---|---|---|
| 1 | O incidente não está `failed` | "Só incidentes com falha podem ser reexecutados (status atual: …)." |
| 2 | A aplicação foi apagada | "A aplicação do incidente foi removida." |
| 3 | A aplicação está inativa | "A aplicação está inativa: ative-a para reexecutar a investigação." |
| 4 | Já usou `max_retries` reexecuções | "Limite de 3 reexecuções atingido para este incidente." |

Um motivo vira `422` com erro no campo `incident`.

**Reexecuções usadas** = número de `AgentRun` do incidente − 1, já que o primeiro run é a investigação original. O limite vem de `FIREWATCH_INCIDENT_MAX_RETRIES` (padrão `3`, mínimo `0`). Com `0`, ninguém reexecuta.

::note
A conta é por **runs**, não por cliques. Um run aberto só para registrar uma falha (teto mensal estourado, nenhum slot livre, queda do job) também conta como uma tentativa.
::

### O que acontece

Dentro de uma transação:

1. trava a linha do incidente (`lockForUpdate`), para dois cliques ao mesmo tempo não enfileirarem duas execuções;
2. confere as travas de novo, já com a linha travada;
3. `transitionTo(queued, 'Reexecução solicitada por <e-mail>.')`, que grava um novo `queued_at`;
4. despacha `InvestigateIncident` **depois do commit**.

A nova tentativa cria um `AgentRun` novo no mesmo incidente, reaproveita o card do Jira e o nome da branch. Runs anteriores ao novo `queued_at` são tratados como de outra tentativa pelo `failed()` do job e pelo watchdog.

### No painel

`IncidentResource` traz `retry: {allowed, reason, used, max}` quando o incidente vem com a aplicação e a contagem de runs. O componente `components/incident/RetryInvestigationButton.vue` usa esse campo:

- **Bloqueado**: o botão fica desabilitado, com o `reason` num tooltip.
- **Liberado**: abre um modal de confirmação com a última falha (`status_reason`) e "Reexecuções usadas: 1 de 3. Depois desta, restam 1.".
- **Depois**: um toast de sucesso ou de erro com a mensagem da API.

## O watchdog: FailStaleIncidents

Se o worker cair, o Redis perder o job ou o processo morrer entre fechar o run e fechar o incidente, um incidente ficaria aberto para sempre. O comando `firewatch:fail-stale-incidents` é a rede de segurança:

```php [routes/console.php]
Schedule::command('firewatch:fail-stale-incidents')->everyFiveMinutes()->withoutOverlapping();
```

`FailStaleIncidentsAction` olha os incidentes em `queued`, `investigating`, `fixing` e `testing`, trava cada um (`lockForUpdate`) e diagnostica pelo run mais recente:

| Situação | Condição | Kind | Fecha o run? |
|---|---|---|---|
| **Nunca começou** | Incidente `queued`, sem run (ou run `pending`) há mais de 180 min, contados do run ou do `queued_at` | `stale`: "A investigação ficou na fila por mais de 180 min sem começar. Confira se o runner-worker está no ar." | Sim (cria um se preciso) |
| **Parou de responder** | Run `running` com `started_at` há mais de 72 min | `stale`: "A execução dos agentes parou de responder (mais de 72 min sem terminar)…" | Sim |
| **Run fechado, incidente aberto** | Run `failed` ou `dry_run` terminado há mais de 5 min | O `failure.kind` do run (ou `dry_run`/`no_fix`) com o motivo do run | Não: já estava fechado |

Fora desses casos, o incidente é deixado em paz:

- Um incidente em `testing` com o run `fixed` **não** está parado: está esperando o PR.
- Um run que falhou há menos de 5 min fica para o job fechar, que normalmente faz isso milissegundos depois.
- Um run anterior ao último `queued_at` é de outra tentativa e não conta.

Cada incidente fechado vira `failed`, gera o log `Stale incident marked as failed` e despacha `DeliverIncidentOutcome` depois do commit. O time é avisado exatamente como numa falha vista pelo próprio job.

Para rodar na mão:

```bash
docker compose exec app php artisan firewatch:fail-stale-incidents
```

A saída lista cada incidente fechado com o motivo e termina com "N incidente(s) marcados como failed.".

::note
O watchdog fecha o incidente, mas **não** mata um container que ainda esteja rodando. Se o worker morreu, o container continua até o próprio limite do runner (`RUNNER_MAX_DURATION`) e depois sai. Para achar sobras, use `docker ps -a --filter label=br.com.firewatch.runner=1`.
::
