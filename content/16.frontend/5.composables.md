Os composables ficam em `app/composables/` e são auto-importados. Há três tipos:

| Tipo | Composables | O que fazem |
|---|---|---|
| **Clientes da API** | `useIncidents`, `useAgentRuns`, `useApplications`, `useConnectors`, `useAgentProfiles`, `useBudget`, `useAuditLog`, `useMetrics` | Funções `async` que chamam um endpoint e devolvem os dados tipados. **Não guardam estado**: quem chama decide onde guardar |
| **Estado compartilhado** | `useCurrentUser`, `useAgentDirectory`, `useNow`, `useRealtimeConnection` | Estado único para todos os componentes (`useState` ou um mapa no módulo) |
| **Tempo real e telas** | `useRealtimeChannel`, `useGlobalChannel`, `useIncidentChannel`, `useLiveIncident` | Assinam canais do Reverb enquanto o componente está montado; o `useLiveIncident` é o estado inteiro da tela ao vivo |

Todos os clientes da API usam o **`useSanctumClient()`** do `nuxt-auth-sanctum`: um `$fetch` com a base `NUXT_PUBLIC_SANCTUM_BASE_URL`, o cookie de sessão e o cabeçalho `X-XSRF-TOKEN`. Filtros vazios (`undefined` ou `''`) são tirados da query antes do envio, para o back-end aplicar os padrões. Os formatos de resposta estão na [Referência da API](/referencia-da-api).

## Clientes da API

### useIncidents

| Função | Endpoint | Devolve |
|---|---|---|
| `list(query)` | `GET /api/v1/incident` | `IncidentList`: `data`, `meta` (paginação) e `stats` (`total`, `by_status`, `avg_time_to_pr_seconds`) |
| `show(id)` | `GET /api/v1/incident/{id}` | `Incident`, com o `stack_trace` já mascarado |
| `retry(id)` | `POST /api/v1/incident/{id}/retry` | `{ message, data: Incident }` |
| `simulate(applicationId, input)` | `POST /api/v1/application/{id}/simulate-incident` | `{ message, data: { created, incident } }` |

A query de `list` aceita `page`, `per_page`, `status`, `severity`, `search`, `application_id`, `period` (`24h`, `7d`, `30d`) e **`statuses`**: vários status de uma vez, enviados como `statuses[]=queued&statuses[]=investigating…`. É assim que a aba "Em andamento" filtra.

O arquivo também exporta os tipos usados em todo o painel (`Incident`, `IncidentStatus`, `IncidentSeverity`, `IncidentRetryInfo`…) e o **`apiErrorMessage(error, fallback)`**: tira a primeira mensagem legível de uma resposta de erro do Laravel (o primeiro erro de validação, senão `message`, senão o texto padrão).

### useAgentRuns

| Função | Endpoint | Devolve |
|---|---|---|
| `listForIncident(incidentId)` | `GET /api/v1/incident/{id}/runs` | As execuções do incidente, a mais recente primeiro |
| `get(runId)` | `GET /api/v1/agent-run/{id}` | `AgentRunDetail`: a execução com o `report` resumido |
| `events(runId, after, limit = 500)` | `GET /api/v1/agent-run/{id}/events` | Uma página: `data`, `has_more`, `last_sequence` |
| `allEvents(runId, after)` | o mesmo, em laço | Todos os eventos depois de `after`, página por página, com um limite de **40 páginas** (20 mil eventos) |

O tipo `RunReport` descreve o resumo do relatório que a tela ao vivo mostra: `summary`, `root_cause`, `fix`, `risk`, `failure`, `pull_request`, `changes` (arquivos, linhas, `diff`, `diff_truncated`), `tests`, `flow` (violações, avisos, reprodução do bug), `git` e `policy_denials`.

### useApplications

| Função | Endpoint | Devolve |
|---|---|---|
| `list(filters)` | `GET /api/v1/application` | `data`, `meta`, `stats` (`total`, `active`, `inactive`) |
| `listActive()` | `GET /api/v1/application?active=1&per_page=100` | Só `id`, `name`, `monitoring_identifier`, `active`: para selects |
| `create(payload)` | `POST /api/v1/application` | A aplicação criada |
| `update(id, payload)` | `PUT /api/v1/application/{id}` | A aplicação atualizada |
| `remove(id)` | `DELETE /api/v1/application/{id}` | nada |

Exporta também os padrões que espelham o model do Laravel (`DEFAULT_BASE_BRANCH = 'main'`, `DEFAULT_RUNNER_IMAGE = 'firewatch-runner:latest'`, `DEFAULT_TRIGGER_RULES`), a lista `RUNNER_IMAGES` (PHP + Node e Python) e o **`describeTriggerRules(rules)`**, que resume as regras numa frase: "Erro ou acima · production · 3+ ocorrências".

### useConnectors

| Função | Endpoint | Devolve |
|---|---|---|
| `list(filters)` | `GET /api/v1/connector` | `data`, `meta`, `stats` (`total`, `active`, `error`, `inactive`) |
| `create(payload)` | `POST /api/v1/connector` | O conector criado |
| `update(id, payload)` | `PUT /api/v1/connector/{id}` | O conector atualizado |
| `remove(id)` | `DELETE /api/v1/connector/{id}` | nada |
| `test(id)` | `POST /api/v1/connector/{id}/test` | `{ result: { ok, message, remote, details }, connector }` |

O campo `credentials` de um `Connector` é só um mapa de booleanos (`{ token: true }`): diz quais credenciais estão salvas, nunca o valor ([Credenciais dos conectores](/seguranca/credenciais-dos-conectores)).

Duas funções auxiliares:

- **`connectorWebhookUrl(connector)`**: monta a URL que a ferramenta externa deve chamar (`<SANCTUM_BASE_URL><webhookPath>/<id>`), para os tipos que recebem webhook ou comando do Slack. `null` para os outros.
- **`parseApiError(error)`**: devolve `{ status, message, fields }`, com o primeiro erro de cada campo de um `422`. Sem `status` (servidor fora do ar), a mensagem é "Não foi possível conectar ao servidor.". Os formulários usam para marcar os campos com erro.

### useAgentProfiles

| Função | Endpoint | Devolve |
|---|---|---|
| `list()` | `GET /api/v1/agent-profile` | `data` e `stats` (`total`, `active`) |
| `get(id)` | `GET /api/v1/agent-profile/{id}` | O perfil com `subagent_file` (o `.md` que vai para o container) |
| `update(id, payload)` | `PUT /api/v1/agent-profile/{id}` | O perfil atualizado |

Não há `create` nem `remove`: o time é fixo, o painel só edita ([Perfis de agente](/perfis-de-agente)).

### useBudget

| Função | Endpoint | Devolve |
|---|---|---|
| `show()` | `GET /api/v1/budget` | `BudgetStatus` |
| `update(settings)` | `PUT /api/v1/budget` | `BudgetStatus` depois de salvar |

`BudgetStatus` traz os limites (`per_run_usd`, `monthly_usd`, `alert_percent`) e a situação do mês: `month`, `spent_usd`, `remaining_usd`, `percent`, `runs_count`, `blocked` e `next_run_usd`, o teto que a próxima execução vai receber ([Budget](/conectores-aplicacoes-budget-e-metricas/budget)).

### useAuditLog

| Função | Endpoint | Devolve |
|---|---|---|
| `list(query)` | `GET /api/v1/audit-log` | `data` e `meta` |

Filtros: `log` (`configuration`, `incident`, `action`, `agent`), `subject_type`, `subject_id`, `causer=system` (só o que o sistema fez), `search`, `from`, `page`, `per_page`. Somente leitura ([Auditoria](/seguranca/auditoria)).

### useMetrics

| Função | Endpoint | Devolve |
|---|---|---|
| `overview(days)` | `GET /api/v1/metrics/overview?days=7\|30\|90&timezone=…` | `MetricsOverview` |

Manda o fuso do navegador (`Intl.DateTimeFormat().resolvedOptions().timeZone`), para os dias do gráfico baterem com o relógio de quem olha. A resposta tem `live` (ativos e na fila agora), `current` e `previous` (o período e o anterior, para comparar), `daily`, `applications` e `failure_kinds` ([Métricas](/conectores-aplicacoes-budget-e-metricas/metricas)).

## Estado compartilhado

### useCurrentUser

Lê o usuário da sessão do `useSanctumAuth()`. A resposta de `GET /api/v1/auth` é `{ user: {...} }`, e o composable desembrulha.

| Expõe | Tipo | O que é |
|---|---|---|
| `user` | `ComputedRef<CurrentUser \| null>` | `id`, `name`, `email`, `active`, `must_change_password`, `social_login`, `avatar` |
| `firstName` | `ComputedRef<string>` | A primeira palavra do nome |
| `initials` | `ComputedRef<string>` | Primeira letra do primeiro e do último nome ("DM") |
| `avatarUrl` | `ComputedRef<string \| undefined>` | `avatar.url` |
| `isAuthenticated` | `Ref<boolean>` | Do Sanctum |
| `logout` | função | Do Sanctum; o menu do usuário chama com `{ method: 'DELETE' }` |

### useAgentDirectory

Dá nome, papel e avatar a quem aparece nos eventos da timeline, a partir do slug.

| Expõe | O que é |
|---|---|
| `profiles` | `useState('agent-directory')`: a lista de perfis, carregada **uma vez** por `useAgentProfiles().list()`, no cliente, e compartilhada por todos os componentes |
| `identify(slug)` | `{ slug, name, role, roleLabel, avatar_url, icon }` |
| `roleOf(slug)` | Só o papel (`triage`, `investigator`, `tester`…), usado para calcular as etapas do fluxo |

`identify` resolve, nesta ordem: os dois "agentes" de sistema (`runner` → "Runner", ícone de container; `firewatch` → "Firewatch", integrações), um perfil com aquele slug, e por fim um nome derivado do próprio slug (`cirurgiao-v2` → "Cirurgiao V2"). Um agente removido do time continua aparecendo com um nome legível nas execuções antigas.

### useNow

```ts
const now = useNow(1000); // Ref<number>, Date.now() atualizado a cada segundo
```

Um relógio reativo **compartilhado por intervalo**: todos os componentes que pedem `useNow(1000)` usam o mesmo `setInterval`, que só existe enquanto houver alguém montado. É o que move os cronômetros ("em andamento há 2 min 05 s") sem um timer por linha.

### useRealtimeConnection

| Expõe | O que é |
|---|---|
| `state` | `useState('realtime-connection-state')`: `initialized`, `connecting`, `connected`, `unavailable`, `failed` ou `disconnected`, vindo do `pusher-js` |
| `connected` | `state === 'connected'` |

Liga um único `bind('state_change')` na conexão do Echo, na primeira vez que alguém usa. Sem Echo (chave vazia, servidor), o estado fica `unavailable`. O `<RealtimeConnectionStatus>` mostra esse estado como "Ao vivo", "Conectando…" ou "Tempo real indisponível".

## Tempo real

`useRealtime.ts` espelha o back-end ([Eventos e payloads](/tempo-real/eventos-e-payloads)):

```ts
export const REALTIME_CHANNELS = {
    global: 'firewatch',
    incident: (incidentId: string) => `incidents.${incidentId}`,
} as const;

export const REALTIME_EVENTS = {
    incidentStatusChanged: '.incident.status-changed',
    agentRunStatusChanged: '.agent-run.status-changed',
    agentEventRecorded: '.agent-event.recorded',
} as const;
```

Também exporta os tipos `AgentEvent`, `AgentRun` e os três payloads.

### useRealtimeChannel

```ts
useRealtimeChannel(channel, { '.incident.status-changed': (payload) => … });
```

A base dos outros dois. Assina o canal **privado** com `echo.private(name)` quando o componente é montado e sai quando ele é desmontado. O nome pode ser reativo: se mudar (outro incidente na mesma página), sai do antigo e entra no novo. `null` não assina nada.

Vários componentes podem ouvir o mesmo canal ao mesmo tempo. Um contador no módulo (`subscribers`) só chama `echo.leave()` quando o último sai, para um componente não derrubar o canal do outro.

Devolve `{ error }`, preenchido se a autorização do canal falhar (o erro também vai para o console como `[realtime] falha ao assinar private-…`). No servidor (SSR) não faz nada.

### useGlobalChannel e useIncidentChannel

Atalhos tipados:

| Composable | Canal | Handlers aceitos |
|---|---|---|
| `useGlobalChannel(handlers)` | `private-firewatch` | `onIncidentStatusChanged`, `onAgentRunStatusChanged` |
| `useIncidentChannel(incidentId, handlers)` | `private-incidents.{id}` | os dois acima e `onAgentEventRecorded` |

Só os handlers passados viram `listen()`. As listas e o dashboard usam o canal global; a tela de um incidente usa o canal do incidente.

### useLiveIncident

É o estado completo da tela ao vivo de um incidente: carrega pela API, segue pelo canal do incidente e se recupera de eventos perdidos. Está descrito em detalhe em [A tela ao vivo](/frontend/tela-ao-vivo).

| Expõe | O que é |
|---|---|
| `incident`, `runs`, `run`, `events` | O incidente, as execuções, a execução selecionada (com o relatório) e a timeline dela |
| `fresh` | `Set` das sequências recém-chegadas, para destacar por 2,5 s |
| `selectedRunId`, `isLatestRun`, `isLive` | Qual execução está na tela e se os agentes ainda trabalham nela |
| `loading`, `error` | Carregamento e mensagem de erro |
| `load()`, `selectRun(id)`, `refreshRunDetail()`, `awaitNextRun()` | Ações |
