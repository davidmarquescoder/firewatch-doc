`App\Jobs\DeliverIncidentOutcome` é a última etapa de toda investigação. Ele recebe o `AgentRun` terminado e entrega o resultado às integrações de saída, na ordem do fluxo principal:

::mermaid
---
code: |
  flowchart TD
      S[AgentRun terminado] --> D{dry_run?}
      D -->|sim| X[registra: integrações não acionadas]
      D -->|não| P[1. Pull Request<br/>só para run fixed]
      P --> N[2. Notifiers<br/>Slack, sempre]
      N --> I[3. Issue tracker<br/>Jira da aplicação, se houver]
---
::

| Configuração | Valor | Por quê |
|---|---|---|
| `$tries` | 1 | **Sem nova tentativa**: repetir poderia notificar duas vezes ou abrir um segundo PR |
| `$timeout` | 300 s | Cobre as chamadas de API de três integrações, com timeout próprio cada uma |

## Quem dispara

| Origem | Situação |
|---|---|
| `InvestigateIncident::handle()` | Fim normal, com o run fechado (inclusive bloqueado pelo teto de custo) |
| `InvestigateIncident::failed()` | Exceção no job ou nenhum runner livre a tempo, e também um run `fixed` cujo job caiu depois (a correção ainda é entregue) |
| `FailStaleIncidentsAction` | O watchdog fechou um run ou incidente travado. Dispara com `afterCommit()`, depois da transação |

Detalhes do fechamento em [Investigação](/investigacao) e [Timeouts e reexecução](/investigacao/timeouts-e-reexecucao).

## Antes dos passos

1. Recarrega o run com `incident.application.repositoryConnector`.
2. Run inexistente ou não terminado: registra um aviso no log e **não entrega nada** (`unfinished_run_is_not_delivered`).
3. Monta o `InvestigationReport` ([Contratos](/saida#investigationreport)).
4. Run `dry_run`: registra "Execução de teste (DRY_RUN): integrações de saída não acionadas." e para. Nada sai do Firewatch num teste sem créditos.

## 1. Pull Request

Só roda quando o run é `fixed` e o incidente ainda não tem `pr_url`. O `pr_url` preenchido é o que impede um segundo PR numa entrega repetida.

::mermaid
---
code: |
  flowchart TD
      A{fixed e sem pr_url?} -->|não| Z[pula]
      A -->|sim| B{incidente em testing?}
      B -->|não| L[log de aviso, pula]
      B -->|sim| C{pullRequestBlocker?}
      C -->|motivo| F[incidente failed<br/>delivery_blocked]
      C -->|nenhum| E{provider para o tipo?}
      E -->|não| U[status_reason: ainda não disponível]
      E -->|sim| G[createBranch → pushChanges → openPullRequest]
      G -->|erro| R[status_reason: abertura falhou<br/>incidente fica em testing]
      G -->|ok| O[pr_url + pr_opened]
---
::

| Resultado | Incidente | Evento na timeline (`outcome`) |
|---|---|---|
| Não está em `testing` | Inalterado (só log) | Nenhum |
| Bloqueado pelo relatório | `failed`, kind `delivery_blocked`, "Correção não enviada: <motivo>" | Erro "Pull Request não aberto: …" (`blocked`) |
| Tipo de conector sem provider | `status_reason` "Correção pronta, mas a abertura de Pull Request ainda não está disponível para <tipo>." | Mensagem (`unavailable`) |
| Erro em qualquer chamada | `status_reason` "Correção pronta, mas a abertura do Pull Request falhou: <motivo>" | Erro "Falha ao abrir o Pull Request: …" (`failed`) |
| PR aberto | `pr_url` e transição para `pr_opened` | Mensagem "Pull Request aberto: <url>" (`delivered`), com id do PR, commit e branch nos metadados |

As três chamadas usam:

| Chamada | Argumentos |
|---|---|
| `createBranch` | `workBranch()`, `baseCommit()` |
| `pushChanges` | A branch, `diff()` e `commitMessage()` |
| `openPullRequest` | `PullRequestData(workBranch, baseBranch, pullRequestTitle, pullRequestDescription)` |

Quando a entrega falha (provider ausente ou erro de API), o incidente **continua em `testing`**: a correção existe, foi verificada, e o diff continua no relatório do run (`changes.diff`) para o time abrir o PR à mão. Só o bloqueio por relatório inseguro vira `failed`, porque ali a correção não é confiável. As mensagens das exceções já chegam legíveis e sem credenciais; o job as corta em 300 caracteres. Qualquer `Throwable` é capturado e reportado (`report($e)`), não só as exceções do contrato.

## 2. Notifiers

Para **cada** conector ativo de um tipo registrado em `firewatch.outgoing.notifiers` (hoje, `slack`), em ordem de nome:

1. pega o notifier do tipo em `OutgoingIntegrations`;
2. chama `notify($connector, $report)`;
3. registra "Time notificado via Slack (Slack Acme)." (`delivered`).

Roda para qualquer desfecho, inclusive `failed`. Como vem **depois** do passo do PR, a mensagem já sabe se o PR saiu ([Slack](/saida/slack#os-três-desfechos)).

## 3. Issue trackers

Num único Jira, escolhido por `issueTrackerConnectorFor()` (o mesmo do `open()`): o **vinculado à aplicação**; sem vínculo, o primeiro ativo por nome. Chama `sync($connector, $report)`. Sem nenhum Jira conectado (ou com o vinculado inativo), o passo é pulado sem evento e sem chamar o Jira. Outros conectores Jira não recebem nada. O `sync()` comenta, liga o PR e troca a etiqueta ([Jira](/saida/jira#sync-no-fim)). Se o incidente ainda não tem `jira_key`, a chave devolvida é gravada; uma chave existente nunca é trocada. Registra "Card OPS-123 atualizado no Jira." (`delivered`).

## Tratamento de erros

O princípio é: **um passo nunca impede o próximo**, e nenhum erro some.

| Onde | Captura | Efeito |
|---|---|---|
| Passo do PR | `try`/`catch (Throwable)` em volta das três chamadas | Incidente com `status_reason`, evento de erro, segue para os notifiers |
| Cada conector de notifier ou tracker | `try`/`catch (Throwable)` por conector (`eachConnector()`) | Evento "Falha na integração Slack (Slack Acme): …" (`failed`), segue para o **próximo conector** |
| Gravar o evento | `try`/`catch` em `record()` | Log de erro. A entrega não para por não conseguir registrar |

Toda exceção capturada passa por `report($e)` e vai para o tratamento de exceções do Laravel (log). A mensagem que vai para a timeline é cortada em 300 caracteres.

Um Slack fora do ar não impede o card no Jira; um GitHub recusando o token não impede o Slack de avisar que a correção está pronta sem PR. Os testes `pull_request_failure_does_not_stop_the_notifications` e `notifier_failure_is_recorded_and_the_issue_still_synced` garantem isso.

## Os eventos na timeline

Todo desfecho vira um `AgentEvent` do agente `firewatch` no run, para o painel mostrar o que aconteceu depois dos agentes:

| Campo | Valor |
|---|---|
| `agent` | `firewatch` (`AgentEvent::AGENT_FIREWATCH`) |
| `type` | `message` (sucesso, indisponível, pulado) ou `error` (falha, bloqueio) |
| `content` | A frase em português |
| `metadata.integration` | `repository`, `notifiers`, `issue_trackers` ou `all` (dry run) |
| `metadata.provider` | Tipo do conector: `bitbucket`, `github`, `slack`, `jira` |
| `metadata.connector_id` | Nos notifiers e trackers |
| `metadata.outcome` | `delivered`, `failed`, `blocked`, `unavailable` ou `skipped` |
| Extras do PR | `url`, `pull_request_id`, `commit`, `branch` |

A abertura do card antes dos agentes (`OpenIncidentIssueAction`) registra eventos do mesmo formato, com `metadata.stage: open` ([Jira](/saida/jira#open-antes-dos-agentes)). Os eventos são transmitidos ao painel como qualquer outro ([Streaming](/investigacao/streaming)).

## Tipos percorridos

O passo 2 percorre os tipos de `OutgoingIntegrations::typesFor('notifiers')`, que lê o `config/firewatch.php`, como o `SendBudgetAlert`. O passo 3 (e o `OpenIncidentIssueAction`) usa um único conector: o vinculado à aplicação ou, sem vínculo, o primeiro ativo de um tipo com classe em `issue_trackers`. Registrar uma integração nova no config basta para ela receber os resultados (`a_notifier_registered_only_in_the_config_is_delivered`). Um conector ativo de um tipo sem classe no config não é percorrido.

O provider de repositório vem do conector da aplicação e também basta registrá-lo em `firewatch.outgoing.repository`.

## Pontos de atenção

- **`comment()` não é usado.** O contrato de repositório tem o método (exigido pelo design do projeto) e os dois providers o implementam, mas a entrega ainda não comenta no PR.
- **Sem nova tentativa automática.** Uma entrega que falhou por instabilidade momentânea não é repetida. O incidente fica em `testing` com o motivo em `status_reason`, e o diff continua no relatório do run.
- **A ordem importa.** O Slack e o Jira dependem do `pr_url` gravado no passo 1 para dizer se o PR saiu. Mudar a ordem faria o time ser avisado de "correção sem PR" antes de o PR existir.

## Testes

`tests/Feature/Outgoing/DeliverIncidentOutcomeTest.php` usa os fakes de `tests/Fakes/` e cobre: run `fixed` abrindo o PR e depois notificando e sincronizando o card; run falho notificando sem PR; dry run sem entrega; falha no PR sem parar as notificações; falha no notifier registrada e o card ainda sincronizado; relatórios inseguros nunca chegando ao repositório; avisos do fluxo em destaque para o revisor; provider de repositório ainda não implementado registrado como indisponível e notifiers e trackers fora do config ignorados; notifier registrado só no config recebendo o resultado; conectores inativos ignorados e chaves de card existentes mantidas; PR nunca aberto duas vezes; texto dos agentes mascarado antes de sair; descrição gerada quando os agentes não escreveram nenhuma; e run não terminado não entregue.
