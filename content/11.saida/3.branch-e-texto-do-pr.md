Antes de qualquer escrita no repositório, três camadas decidem **se** e **onde** a correção pode ir: o nome da branch, as checagens do relatório e o `BranchPolicy`. Depois, o `InvestigationReport` monta o texto que acompanha a correção: título e descrição do PR e a mensagem de commit.

## O nome da branch

A branch é escolhida **antes** dos agentes, por `DockerRunner::workBranch($incident)`, e o runner a cria localmente depois do clone:

```text
firewatch/<prefixo>-<slug do título>
```

| Parte | Origem |
|---|---|
| `firewatch/` | `DockerRunner::BRANCH_PREFIX`, o mesmo de `BranchPolicy::PREFIX` |
| Prefixo | A chave do card no Jira (`OPS-123`) quando ela existe e tem o formato `ABC-123`; senão, a referência do incidente (`inc-1a2b3c4d`, os 8 últimos caracteres do id) |
| Slug | Título do incidente **mascarado**, em ASCII minúsculo, com tudo que não é letra ou número virando `-`, cortado em 40 caracteres |

Exemplos:

```text
firewatch/OPS-123-attempt-to-read-property-role-on-null
firewatch/inc-1a2b3c4d-sqlstate-23000-integrity-constraint
```

O título é mascarado antes porque o nome da branch é **público** no repositório e no Jira. A chave do card no nome é o que faz o Bitbucket (e o Jira, pela integração de desenvolvimento) ligar branch, commits e PR ao card sozinho. Por isso o card é aberto antes dos agentes ([Jira](/saida/jira#open-antes-dos-agentes)).

Uma reexecução do mesmo incidente gera o **mesmo nome**, já que o card e o título são os mesmos. É por isso que os providers sabem lidar com uma branch que já existe ([GitHub e Bitbucket](/saida/repositorios#createbranch)).

## BranchPolicy

`App\Services\Outgoing\BranchPolicy::assertWritable($branch, $baseBranch)` é chamado por **todo** método que escreve, nos dois providers (`createBranch`, `pushChanges` e `openPullRequest`, este com a branch de destino como base). Ele lança `RepositoryProviderException` quando:

| Regra | Mensagem |
|---|---|
| Não começa com `firewatch/` | "Branch "main" recusada: o Firewatch só escreve em branches firewatch/." |
| Tem caractere fora de `A-Z a-z 0-9 . _ / -` | Idem |
| Tem `..` ou `//`, termina com `/` ou com `.lock` | Idem |
| É igual à branch base da aplicação | "Branch "…" recusada: é a branch base da aplicação." |

A última regra cobre o caso estranho de uma aplicação cuja branch base também começa com `firewatch/` (`refuses_a_branch_equal_to_a_firewatch_base_branch`).

O `BranchPolicy` é a última linha de defesa. As mesmas regras aparecem antes em outros lugares:

| Onde | O que confere |
|---|---|
| Entrypoint do runner | `WORK_BRANCH` com prefixo `firewatch/`, válida para o git e diferente da base. Sai com código 2 se não ([Entrypoint](/runner/entrypoint)) |
| Hook `pre-push` no clone | Recusa push para fora de `refs/heads/firewatch/*` |
| Guarda de ferramentas | Recusa `git push`, `merge` e `pull` para todos os agentes |
| `pullRequestBlocker()` | Branch e base de novo, mais as provas do fluxo (abaixo) |
| `BranchPolicy` | Em cada chamada à API |

Nenhum provider tem código de merge, e o contrato proíbe que tenha.

## pullRequestBlocker()

Mesmo com o run `fixed`, a entrega relê o relatório antes de tocar no repositório. `InvestigationReport::pullRequestBlocker()` devolve o **primeiro** motivo para não abrir o PR, ou `null`:

| Ordem | Condição | Motivo |
|---|---|---|
| 1 | O run não é `fixed` | Os agentes não entregaram uma correção. |
| 2 | Branch de trabalho sem `firewatch/` | Branch de trabalho inválida ("…"): só branches firewatch/ podem receber alterações. |
| 3 | Branch de trabalho igual à base | A branch de trabalho não pode ser a branch base. |
| 4 | Sem `git.base_commit` | O relatório não informa o commit base da correção. |
| 5 | Sem arquivos alterados ou diff vazio | O relatório não tem alterações para enviar. |
| 6 | `changes.diff_truncated` | O diff da correção passou do limite do runner e foi truncado: não é seguro aplicá-lo. |
| 7 | `tests.status` diferente de `passed` | A suíte de testes não passou na verificação do runner (…). |
| 8 | `flow.status` diferente de `passed` | O runner não confirmou o fluxo obrigatório (…): não há prova de que o teste reproduz o erro. |
| 9 | `flow.reproduction.status` diferente de `failed_without_fix` | O runner não comprovou que o teste falha sem a correção (…). |

Todos os campos vêm das partes do relatório **medidas pelo runner**, não do que o agente afirmou. Com um motivo, a entrega marca o incidente como `failed` com o kind `delivery_blocked` e "Correção não enviada: <motivo>" ([DeliverIncidentOutcome](/saida/deliver-incident-outcome)).

## O título do PR

`pullRequestTitle()`:

1. Pega a **primeira linha** do título escrito pelo Escrivão (`pull_request.title`, mascarado).
2. Normaliza: tira `[Firewatch]` repetido, prefixos de commit convencional (`fix:`, `feat(api):`, `hotfix!:`, `chore:`, `refactor:`, `bugfix:`), espaços duplicados e ponto final.
3. Sem título do agente, usa `Corrige: <título do incidente>` (também normalizado e mascarado).
4. Põe o prefixo `[Firewatch] ` e corta em 100 caracteres com `…`.

```text
fix: Bloqueia usuário sem papel no middleware.
→ [Firewatch] Bloqueia usuário sem papel no middleware
```

O prompt do Escrivão pede no máximo 60 caracteres justamente porque o prefixo entra depois ([Prompts padrão](/perfis-de-agente/prompts-padrao)).

## A descrição do PR

`pullRequestDescription()` monta o Markdown em cinco blocos:

```md [descrição do PR]
> **Incidente [inc-1a2b3c4d](https://painel/incidents/…)** · Loja · severidade alta · 42 ocorrências · 7 usuários afetados

## O que quebrou
…
## Causa raiz
…
## Correção
…
## Teste adicionado
…
## Risco
…

---
### Verificado pelo Firewatch

- **Reprodução**: o teste falhou sem a correção (`vendor/bin/pest tests/Feature/CompanyTest.php`)
- **Suíte de testes**: passed — `Tests: 214 passed`
- **Risco**: Baixo
- **Incidente**: [inc-1a2b3c4d — abrir no painel do Firewatch](https://painel/incidents/…)

**Arquivos alterados**

- `app/Http/Middleware/EnsureActiveCompany.php` (modified, +3 −1)
- `tests/Feature/ActiveCompanyTest.php` (modified, +18 −0)

**Atenção na revisão**

- Arquivo sensível alterado (dependências, CI ou configuração): composer.json

_Correção gerada pelos agentes do Firewatch. Revise antes de aprovar: nada é mesclado sem aprovação humana._
```

| Bloco | De onde |
|---|---|
| Cabeçalho | Link para o incidente no painel, aplicação, severidade, ocorrências e usuários afetados (só se houver) |
| Preâmbulo | Texto que o Escrivão escreveu antes do primeiro `##`, se houver |
| As cinco seções | Do Escrivão, **sempre nessa ordem** e com esses títulos |
| Seções extras | Seções `##` do Escrivão com títulos desconhecidos, depois das cinco |
| Verificado pelo Firewatch | Escrito pelo Firewatch a partir do que o runner mediu |

### Como as seções do Escrivão são lidas

A descrição do agente é partida nos títulos `##` (não `###`). Cada título é comparado em ASCII minúsculo, sem `:` no fim, com uma lista de nomes aceitos:

| Seção | Títulos aceitos |
|---|---|
| O que quebrou | o que quebrou, o que aconteceu, problema |
| Causa raiz | causa raiz, causa |
| Correção | correção, solução |
| Teste adicionado | teste adicionado, testes, teste |
| Risco | risco, nível de risco |

- Seção repetida: vale a primeira com conteúdo.
- Seção que o agente **deixou de fora** (ou vazia) é preenchida com o relatório: título e resumo do incidente; `root_cause`; `fix`; `test_added` em código; rótulo e motivo do risco. Sem nada disso, "Não informada pelos agentes."
- As seções **Entrega do Escrivão** e **Verificado pelo Firewatch** do agente são **descartadas**. A segunda é do Firewatch: um agente não pode escrever a própria verificação.

O link do incidente usa `FIREWATCH_PANEL_URL` (ou `FRONTEND_URL`) com `FIREWATCH_PANEL_INCIDENT_PATH` (padrão `/incidents/{id}`). Sem URL de painel, a referência aparece em código, sem link, e a seção de verificação mostra também o id completo.

## A mensagem de commit

`commitMessage()` gera o commit único que os providers criam:

```text
fix: Bloqueia usuário sem papel no middleware

Usuários sem papel causavam erro 500 ao acessar a empresa ativa.

Firewatch-Incident: 9f3c2a1e-…
Firewatch-Run: 9f3c2b77-…
Jira: OPS-123
```

| Linha | Origem |
|---|---|
| Assunto | `fix: ` + título normalizado (do Escrivão, ou do incidente), cortado em 71 caracteres mais `…` |
| Corpo | `summary` do relatório, mascarado (omitido se vazio) |
| `Firewatch-Incident`, `Firewatch-Run` | Ids, para achar a investigação a partir do `git log` |
| `Jira` | A chave do card, quando existe. Liga o commit ao card |
