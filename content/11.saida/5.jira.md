O `JiraIssueTracker` mantém **um card por incidente** no Jira Cloud (REST API v3). Ele age em dois momentos:

| Momento | Método | Quem chama | O que faz |
|---|---|---|---|
| Antes dos agentes | `open()` | `OpenIncidentIssueAction` (dentro do `InvestigateIncident`) | Cria o card. A chave vai para `incidents.jira_key` e para o nome da branch |
| Fim da investigação | `sync()` | `DeliverIncidentOutcome` | Comenta o resultado, liga o PR e troca a etiqueta. Cria o card se ainda não existir |

O status do card no workflow **não é mexido**: cada projeto tem as próprias transições, e mover o card é decisão do time.

## Conector

| Campo | Onde | Exemplo |
|---|---|---|
| `email` | Credencial | Conta que criou o token |
| `api_token` | Credencial | Token de API da Atlassian |
| `base_url` | Settings, obrigatório, `https://` | `https://acme.atlassian.net` |
| `project_key` | Settings, obrigatório | `OPS` (é guardado e comparado em maiúsculas) |
| `issue_type` | Settings, opcional | `Bug`, `Tarefa`… |

A autenticação é **Basic** com e-mail e token. Antes de cada operação, `client()` confere e-mail, token, `base_url` em `https://` e `project_key`; sem eles, falha com "O conector "…" precisa de base_url (https) e project_key." O timeout por chamada é `JIRA_TIMEOUT` (15 s), com 5 s de conexão.

## open() antes dos agentes

`OpenIncidentIssueAction::execute($incident, $run)` roda logo depois da checagem de teto de custo e **antes** de escolher a branch:

1. Se o incidente já tem `jira_key`, devolve a chave e não chama o Jira. Uma reexecução reaproveita o card e, com ele, o nome da branch.
2. Escolhe o Jira com `OutgoingIntegrations::issueTrackerConnectorFor()`: o **vinculado à aplicação** (`applications.issue_tracker_connector_id`), e só ele (inativo = sem card); sem vínculo, o **primeiro Jira ativo por nome**; sem nenhum Jira conectado, segue sem card, sem evento na timeline e sem chamar o Jira.
3. Chama `open()`. Com sucesso, grava `jira_key` e registra na timeline "Card OPS-123 criado no Jira (Jira Acme)."
4. Se falhar, registra "Card no Jira não criado: <motivo>. A investigação segue sem vínculo com o card." e a investigação continua, com a branch `firewatch/inc-<id>-…`.

É **melhor esforço**: um Jira fora do ar nunca impede a investigação.

### O card criado

`open()` primeiro confere se o incidente já tem uma chave **deste projeto** (`OPS-…` para `project_key: OPS`). Uma chave de outro projeto não é reaproveitada: o conector cria um card novo no seu projeto.

```json [POST /rest/api/3/issue]
{
  "fields": {
    "project": { "key": "OPS" },
    "issuetype": { "name": "Bug" },
    "summary": "[Firewatch] Attempt to read property \"role\" on null",
    "labels": ["firewatch"],
    "description": { "type": "doc", "version": 1, "content": [ … ] }
  }
}
```

| Campo | Valor |
|---|---|
| `summary` | `[Firewatch] ` + título do incidente **mascarado**, numa linha, até 250 caracteres |
| `labels` | `firewatch` |
| `description` | Em ADF: aviso de que os agentes estão investigando, **Erro** (título em bloco de código), **Contexto** (aplicação, severidade, ocorrências, usuários afetados, primeira ocorrência, link do incidente no painel) |

A chave devolvida precisa ter o formato `ABC-123`.

### Tipo do card

| `settings.issue_type` | Comportamento |
|---|---|
| Preenchido | Usa esse tipo. Se o projeto recusar, o erro aparece; **sem** tentativa alternativa |
| Vazio | Lê os tipos do projeto e escolhe pela lista `JIRA_ISSUE_TYPES` |

Sem tipo no conector, o tracker consulta `GET issue/createmeta/<projeto>/issuetypes` e escolhe:

1. o **primeiro nome da lista** `services.jira.issue_types` (`JIRA_ISSUE_TYPES`, padrão `Bug,Problema,Erro,Defeito,Task,Tarefa`) que o projeto tem, sem diferenciar maiúsculas. A lista tem as traduções porque o Jira mostra os nomes no idioma do projeto;
2. se nenhum bate, o **primeiro tipo do projeto que não é subtarefa**;
3. se a consulta falha (rede, permissão), o primeiro nome da lista, e um tipo recusado aparece no erro da criação.

O card é criado com o nome do jeito que o projeto escreve (`Tarefa`, não `tarefa`).

## sync() no fim

`sync($connector, $report)`:

1. Chama `open()`: reaproveita a chave do incidente ou cria o card (caso o `open()` inicial tenha falhado).
2. **Comenta** o resultado (`POST issue/<key>/comment`).
3. Com PR aberto, cria um **link remoto** (`POST issue/<key>/remotelink`) com `globalId: firewatch-pr-<id do incidente>`. O mesmo `globalId` atualiza o link em vez de duplicar.
4. Troca a **etiqueta de resultado**: remove as três e adiciona a atual (`PUT issue/<key>` com `update.labels`).

| `outcome()` | Etiqueta |
|---|---|
| `pr_opened` | `firewatch-pr-aberto` |
| `fix_without_pr` | `firewatch-sem-pr` |
| `failed` | `firewatch-falhou` |

A etiqueta `firewatch` da criação continua. Com as duas, dá para filtrar no Jira, por exemplo, `labels = firewatch-falhou`.

A entrega grava a chave em `jira_key` se o incidente ainda não tinha uma.

### O comentário

Começa com **Firewatch: <manchete>** e muda conforme o desfecho:

| Desfecho | Conteúdo |
|---|---|
| PR aberto | Link para o PR (título do PR), **Resumo**, **Causa raiz**, **Correção** e uma lista com risco, teste adicionado e status da suíte |
| Correção sem PR | **Resumo** e **Por que não há Pull Request** (`status_reason`) |
| Falhou | **Motivo — <kind>**, etapa, **Resumo**, **Causa provável** e **Próximo passo** |

Termina com o link "Ver a investigação no painel do Firewatch", quando há URL de painel. Seções sem texto são omitidas, e cada texto é cortado em 5 000 caracteres. Todo texto vem mascarado do `InvestigationReport`.

## ADF

A API v3 do Jira não aceita Markdown nem texto simples em descrições e comentários: ela exige o **Atlassian Document Format**, uma árvore JSON. `App\Services\Outgoing\Jira\Adf` é um construtor mínimo com só o que o Firewatch usa:

| Método | Nó ADF |
|---|---|
| `doc(array $content)` | `{type: doc, version: 1, content}`. Nós `null` são descartados |
| `heading($text, $level = 3)` | `heading` com `attrs.level` |
| `paragraph(...$inline)` | `paragraph`. Aceita strings (viram texto) ou nós inline |
| `bulletList($items)` | `bulletList` → `listItem` → `paragraph`, um por item |
| `codeBlock($text)` | `codeBlock` |
| `text($text)` | `text`. Texto vazio vira `" "`, porque o ADF recusa nós de texto vazios |
| `strong($text)`, `code($text)` | `text` com a marca `strong` ou `code` |
| `link($text, $url)` | `text` com a marca `link` e `attrs.href` |

```php
Adf::doc([
    Adf::heading('Contexto'),
    Adf::bulletList([
        [Adf::strong('Aplicação: '), 'Loja'],
        [Adf::strong('Incidente: '), Adf::link('inc-1a2b3c4d — abrir no painel do Firewatch', $url)],
    ]),
]);
```

```json
{
  "type": "doc", "version": 1,
  "content": [
    { "type": "heading", "attrs": { "level": 3 }, "content": [{ "type": "text", "text": "Contexto" }] },
    { "type": "bulletList", "content": [
      { "type": "listItem", "content": [{ "type": "paragraph", "content": [
        { "type": "text", "text": "Aplicação: ", "marks": [{ "type": "strong" }] },
        { "type": "text", "text": "Loja" }
      ]}]}
    ]}
  ]
}
```

Como o ADF é estruturado, **não há marcação para escapar**: um `*` ou `<` no texto do agente é só texto. Essa é a diferença para o Slack, onde o texto passa por escape ([Slack](/saida/slack#escape-e-limites)).

O texto do agente entra como **parágrafo simples**: o Markdown que o agente escreveu (listas, negrito) aparece literal no Jira, sem conversão.

## Erros

| HTTP | Dica |
|---|---|
| 400 | dados recusados pelo projeto |
| 401 | e-mail ou API token inválidos |
| 403 | sem permissão no projeto |
| 404 | projeto ou card não encontrado |
| 429 | limite de requisições atingido |

O detalhe junta `errorMessages[]` e os pares `campo: mensagem` de `errors`. Exemplo: "Jira: falha ao criar o card do incidente: dados recusados pelo projeto (HTTP 400) — issuetype: Especifique um tipo de item válido."

## Testes

`tests/Feature/Outgoing/JiraIssueTrackerTest.php` cobre: card criado no projeto; card do mesmo projeto reaproveitado e de outro projeto não; tipo padrão escolhido pela lista, pelo primeiro tipo que não é subtarefa e, sem acesso aos tipos, pelo primeiro nome da lista; nenhum fallback com tipo configurado; erros sem o token; `sync` com comentário, link do PR e etiqueta; `sync` de run falho com motivo e sem link; `sync` criando o card que falta; a chave na branch e na mensagem de commit; e o registro no config.
