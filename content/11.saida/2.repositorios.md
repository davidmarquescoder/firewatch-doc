O repositório é tocado em dois momentos, com **duas credenciais diferentes**:

| Momento | Quem | Credencial | Faz |
|---|---|---|---|
| Começo da investigação | Runner (container) | `runner_token` (somente leitura), ou `access_token` se ele faltar | `git clone` da branch base |
| Fim, com correção | Laravel (`DeliverIncidentOutcome`) | `access_token` (escrita) | Branch, commit e PR, pela API REST |

O runner **nunca** faz push: ele devolve o diff no relatório. O token de escrita nunca entra no container ([Arquitetura](/visao-geral/arquitetura)).

## Clone no runner

O `DockerRunner` monta as variáveis do clone a partir do conector da aplicação e do `config/firewatch.php`:

```php [config/firewatch.php]
'runner' => [
    'repository' => [
        'clone_urls' => [
            'bitbucket' => env('FIREWATCH_BITBUCKET_CLONE_URL', 'https://bitbucket.org/%s.git'),
            'github'    => env('FIREWATCH_GITHUB_CLONE_URL', 'https://github.com/%s.git'),
        ],
        'usernames' => [
            'bitbucket' => 'x-token-auth',
            'github'    => 'x-access-token',
        ],
    ],
],
```

| Variável do runner | Valor |
|---|---|
| `REPO_URL` | `clone_urls[<tipo>]` com o `repository_slug` no `%s`. Ex.: `https://bitbucket.org/acme/loja.git` |
| `REPO_USERNAME` | `usernames[<tipo>]`: **`x-token-auth`** no Bitbucket, **`x-access-token`** no GitHub |
| `REPO_TOKEN` | `runner_token` ou `access_token`, entregue pelo **stdin**, nunca no ambiente |

Um conector que não é de repositório, ou um tipo sem URL de clone, para a execução com `RunnerLaunchException` (falha do tipo `configuration`).

### Por que o usuário importa

Tokens de acesso não autenticam com o usuário de quem os criou. Cada serviço espera um **usuário fixo** junto do token no HTTPS:

| Serviço | Token | Usuário no git |
|---|---|---|
| Bitbucket | Repository, project ou workspace access token (`ATCTT…`) | `x-token-auth` |
| GitHub | Fine-grained ou classic | `x-access-token` |

O entrypoint usa `GIT_ASKPASS` para responder usuário e senha. O token nunca entra na URL nem no `.git/config` ([Isolamento](/runner/isolamento#o-token-do-repositório)). Se a `REPO_URL` vier com um `usuario@` embutido, o entrypoint o **remove**, porque ele teria prioridade sobre o `REPO_USERNAME` e o Bitbucket recusaria o token. Quando o runner é chamado sem `REPO_USERNAME`, o padrão do próprio entrypoint é `x-token-auth`.

O usuário vem **só** do config, por tipo de conector: não existe credencial `username` no conector.

Para GitHub Enterprise ou Bitbucket Data Center, troque a URL de clone por `FIREWATCH_GITHUB_CLONE_URL` / `FIREWATCH_BITBUCKET_CLONE_URL` e a URL da API por `GITHUB_API_URL` / `BITBUCKET_API_URL` (abaixo). Lembre de liberar o host no proxy de egress da fase de setup ([Egress](/runner/egress)).

## Configuração da API

```php [config/services.php]
'bitbucket' => [
    'api_url' => env('BITBUCKET_API_URL', 'https://api.bitbucket.org/2.0'),
    'timeout' => (int) env('BITBUCKET_TIMEOUT', 30),
],
'github' => [
    // https://api.github.com, ou https://<host>/api/v3 no GitHub Enterprise Server.
    'api_url' => env('GITHUB_API_URL', 'https://api.github.com'),
    'timeout' => (int) env('GITHUB_TIMEOUT', 30),
],
```

O `timeout` vale por requisição. A conexão tem 10 s. Os dois clientes mandam `User-Agent: Firewatch` e autenticam com **Bearer** (`Authorization: Bearer <access_token>`).

## Antes de qualquer chamada

`client()` de cada provider valida o cenário e falha com uma mensagem clara antes de chamar a API:

| Checagem | Mensagem |
|---|---|
| O conector da aplicação é do tipo certo | "A aplicação "Loja" não tem um conector Bitbucket." |
| O conector está ativo | "O conector "Bitbucket Acme" está inativo." |
| Existe `access_token` | "O conector … não tem access token." |
| `repository_slug` no formato `a/b` (letras, números, `.`, `_`, `-`) | "Slug de repositório inválido … (esperado workspace/repositorio)." |

Um `runner_token` sozinho não serve aqui: escrever exige o `access_token`.

## Bitbucket

`BitbucketRepositoryProvider` usa a REST API 2.0 do Bitbucket Cloud. O token precisa de **leitura e escrita no repositório e em pull requests**.

### createBranch

::mermaid
---
code: |
  flowchart TD
      A[BranchPolicy + commit válido] --> B{branch existe?}
      B -->|não| C[POST refs/branches<br/>name + target.hash]
      B -->|sim, no mesmo commit| D[nada a fazer]
      B -->|sim, em outro commit| E{PR aberto dessa branch?}
      E -->|sim| F[erro: branch em revisão]
      E -->|não| G[DELETE refs/branches/…] --> C
---
::

- O commit base precisa ter de 7 a 40 caracteres hexadecimais. A comparação aceita hash curto contra longo (prefixo comum de pelo menos 7).
- Uma branch com o mesmo nome e outro conteúdo é **sobra de uma tentativa anterior** do mesmo incidente (o nome vem do incidente). Ela é recriada, **a não ser** que tenha um PR aberto: aí alguém pode estar revisando, e o provider recusa: "A branch "…" já existe com outro conteúdo e tem um Pull Request aberto."

### pushChanges

O provider **não roda git**. Ele reconstrói o conteúdo final de cada arquivo e cria o commit pela API:

1. `ChangeSet::fromDiff($diff)` interpreta o diff ([Diff](/saida/diff)).
2. Recusa arquivos chamados `message`, `author`, `parents`, `files` ou `branch` na raiz: são nomes de campo do `POST /src`, e o arquivo seria lido como o campo.
3. Lê a cabeça da branch (`GET refs/branches/<branch>`).
4. Para cada arquivo modificado ou removido, lê o conteúdo **nessa cabeça** (`GET src/<commit>/<caminho>`) e aplica o patch em PHP. Um arquivo que não existe dá "O diff altera "…", mas o arquivo não existe na branch."
5. Envia **um** `POST src` multipart com `message`, `branch`, `parents=<cabeça>`, um campo por arquivo novo ou alterado (o nome do campo é o caminho) e um `files=<caminho>` por arquivo removido.
6. Pega o hash do commit no header `Location` (`…/commit/<hash>`). Sem o header, relê a cabeça da branch; se ela não mudou, falha: "O Bitbucket aceitou o envio, mas a branch "…" não recebeu o commit."

O `parents` é a garantia contra sobrescrita: se alguém empurrou para a branch entre a leitura e o envio, o Bitbucket responde **409** ("a branch mudou durante o envio") e nada é gravado. O autor do commit é a identidade do token.

### openPullRequest

1. Procura um PR **aberto** com aquela branch de origem (`GET pullrequests?q=source.branch.name="…" AND state="OPEN"`). Se existe, devolve esse, sem criar outro.
2. Senão, `POST pullrequests` com `title`, `description`, `source.branch.name`, `destination.branch.name` e `close_source_branch: true` (a branch é apagada quando o PR for mesclado).
3. Devolve `id` e `links.html.href`.

### comment

`POST pullrequests/<id>/comments` com `content.raw`. O id precisa ser só dígitos.

### Erros

| HTTP | Dica na mensagem |
|---|---|
| 401 | credenciais inválidas ou expiradas |
| 403 | o token não tem permissão para esta operação |
| 404 | repositório ou recurso não encontrado |
| 409 | a branch mudou durante o envio |
| 429 | limite de requisições atingido |
| Outro | resposta inesperada do serviço |

O detalhe vem de `error.message` da resposta. Exemplo: "Bitbucket: falha ao abrir o Pull Request: o token não tem permissão para esta operação (HTTP 403) — Your credentials lack one or more required privilege scopes."

## GitHub

`GitHubRepositoryProvider` usa a REST API com `Accept: application/vnd.github+json` e `X-GitHub-Api-Version: 2022-11-28`. O token pode ser **fine-grained** (Contents e Pull requests com leitura e escrita no repositório) ou **classic** (escopo `repo`).

### createBranch

1. Mesmas validações de branch e commit do Bitbucket.
2. Resolve o commit base para o **hash completo** (`GET commits/<hash>`), porque o GitHub não aceita hash curto em refs.
3. Se a branch não existe, `POST git/refs` com `refs/heads/<branch>`.
4. Se existe no mesmo commit, nada a fazer.
5. Se existe em outro commit sem PR aberto, **reposiciona** com `PATCH git/refs/heads/<branch>` e `force: true`. Com PR aberto, recusa como no Bitbucket.

### pushChanges

Usa a Git Data API para montar o commit:

::mermaid
---
code: |
  flowchart LR
      H[cabeça da branch] --> T[árvore base<br/>GET git/commits/head]
      T --> F[conteúdo de cada arquivo<br/>GET contents/… raw]
      F --> P[aplica o patch<br/>ChangeSet]
      P --> B[POST git/blobs<br/>um por arquivo]
      B --> NT[POST git/trees<br/>base_tree + mudanças]
      NT --> C[POST git/commits<br/>parents = cabeça]
      C --> R[PATCH git/refs<br/>force: false]
---
::

- **Modos de arquivo preservados.** Antes de montar a árvore, o provider lê a árvore base recursiva e mantém o modo atual de cada arquivo (`100755` continua executável). Arquivo novo é `100644`. Link simbólico (`120000`) ou submódulo (`160000`) é recusado.
- **Arquivo removido** entra na árvore com `sha: null`.
- **Fast-forward só.** O último passo move a branch com `force: false`. Se ela mudou desde a leitura, o GitHub responde **422** e nada é sobrescrito.
- O hash devolvido precisa ter 40 caracteres hexadecimais.

### openPullRequest e comment

- Procura um PR aberto da branch (`GET pulls?head=<dono>:<branch>&state=open`). Se existe, devolve esse.
- Senão, `POST pulls` com `title`, `body`, `head` e `base`. O `body` é cortado em 65 000 caracteres (limite do GitHub).
- `comment()` usa `POST issues/<id>/comments`: no GitHub, PR é uma issue para comentários gerais.

### Erros

| Situação | Dica |
|---|---|
| 429, ou 403 com `x-ratelimit-remaining: 0` | limite de requisições atingido |
| 401 | token inválido ou expirado |
| 403 | o token não tem permissão para esta operação |
| 404 | repositório não encontrado ou sem acesso para o token |
| 409 | conflito no repositório |
| 422 | dados recusados (por exemplo, a branch mudou durante o envio) |

O detalhe junta `message` e os itens de `errors[]` da resposta.

## Diferenças entre os dois

| | Bitbucket | GitHub |
|---|---|---|
| Usuário do clone | `x-token-auth` | `x-access-token` |
| Branch obsoleta sem PR | Apaga e recria | Reposiciona com `force: true` |
| Commit | Um `POST /src` multipart | Blobs → árvore → commit → ref |
| Proteção contra sobrescrita | `parents` → 409 | `force: false` → 422 |
| Modo de arquivo (executável) | Não preservado | Preservado |
| Hash curto do commit base | Aceito | Resolvido para o completo |
| Fecha a branch ao mesclar | Sim (`close_source_branch`) | Configuração do repositório |
| Limite da descrição | Sem corte | 65 000 caracteres |
