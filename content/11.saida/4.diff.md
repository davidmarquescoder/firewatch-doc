O runner devolve a correção como texto, em `report.changes.diff`: um `git diff --no-renames` contra o commit base, com os arquivos novos incluídos. As APIs do Bitbucket e do GitHub não aceitam um diff; elas querem o **conteúdo final** de cada arquivo. As classes de `app/Services/Outgoing/Diff/` fazem essa ponte, iguais para todos os providers:

::mermaid
---
code: |
  flowchart LR
      D[changes.diff<br/>texto] -->|UnifiedDiff::parse| FP[FilePatch por arquivo<br/>com seus Hunks]
      FP -->|ChangeSet::fromDiff| CS[ChangeSet]
      O[conteúdo do arquivo<br/>na cabeça da branch] --> AP
      CS -->|apply| AP[FilePatch::apply]
      AP --> FC[FileChange<br/>conteúdo novo ou remoção]
      FC --> C[commit pela API<br/>do provider]
---
::

Cada provider só precisa saber duas coisas: ler um arquivo num commit e gravar o commit final ([GitHub e Bitbucket](/saida/repositorios#pushchanges)).

## Por que não rodar git

O Laravel poderia clonar o repositório, aplicar o diff com `git apply` e dar push. Não faz isso por três motivos:

- **O token de escrita ficaria num clone em disco** do servidor do Laravel, com um processo `git` tocando o repositório.
- **Clonar repositórios grandes** em cada entrega custa tempo e disco.
- **A API dá a garantia de não sobrescrever** de graça (`parents` no Bitbucket, fast-forward no GitHub).

O preço é implementar a aplicação do patch em PHP. Ela é deliberadamente **estrita**.

## Aplicação estrita

Um `git apply` comum tolera diferenças: procura o trecho algumas linhas acima ou abaixo (offset) e ignora um pouco de contexto (fuzz). O Firewatch **não**. Cada linha de contexto e cada linha removida precisa bater **byte a byte**, final de linha incluído, **na posição exata** que o hunk diz.

A razão é a regra central do Firewatch: a correção foi testada contra um código específico, o do commit base. Se o arquivo mudou na branch desde então, aplicar o patch "por aproximação" geraria um código que **ninguém testou**. Nesse caso a entrega falha com "O conteúdo de "app/X.php" na linha 42 não confere com o diff: o arquivo mudou desde o commit analisado." e o time é avisado de que a correção está pronta, mas sem PR.

Na prática, como a branch é criada no commit base (`createBranch(…, $baseCommit)`), os arquivos lidos são exatamente os que o runner viu, e a aplicação sempre bate. A rigidez protege contra branches reaproveitadas e relatórios inconsistentes.

## UnifiedDiff

`UnifiedDiff::parse(string $diff): array<FilePatch>` lê o texto.

1. Diff vazio ou que não começa com `diff --git ` é recusado.
2. O texto é partido **só em `\n`**: um `\r` antes dele faz parte da linha, então arquivos CRLF continuam CRLF.
3. Cada bloco `diff --git a/<p> b/<p>` vira um `FilePatch`. Com `--no-renames`, os dois caminhos são iguais; se não forem, o cabeçalho é recusado.
4. O cabeçalho estendido (até o primeiro `@@`) define a ação: `new file mode` → `added`, `deleted file mode` → `deleted`, senão `modified`. Os marcadores `---`/`+++` precisam apontar para o mesmo caminho (ou `/dev/null`).
5. Cada `@@ -a,b +c,d @@` vira um `Hunk`. As linhas são contadas contra `b` e `d`; se o hunk acabar antes, ele está **truncado** e é recusado.
6. `\ No newline at end of file` tira o `\n` da linha anterior.
7. O mesmo arquivo duas vezes no diff é recusado.

### O que é recusado

Tudo o que a API não consegue reproduzir a partir de texto é recusado com `DiffException`, em vez de ser ignorado em silêncio:

| Caso | Motivo |
|---|---|
| Arquivo binário (`Binary files …`, `GIT binary patch`) | Não há conteúdo de texto para reconstruir |
| Link simbólico ou submódulo (modo `120000`/`160000`) | Não é um arquivo comum |
| Renomeação ou cópia (`rename from`, `similarity index`) | O runner gera com `--no-renames`; se aparecer, algo está errado |
| Caminho entre aspas (caracteres especiais) | O git escapa o nome; não é decodificado |
| Caminho absoluto, com `..`, `.`, segmento vazio ou dentro de `.git/` | Escaparia do repositório |
| Hunk incompleto ou linha que não começa com espaço, `-`, `+` ou `\` | Diff truncado ou corrompido |

Uma mudança **só de modo** (bit de executável, sem hunks) é aceita pelo parser e descartada pelo `ChangeSet`: o conteúdo é o que vai no commit.

::note
O runner já sinaliza diffs grandes demais com `changes.diff_truncated`, e o `pullRequestBlocker()` para a entrega antes de chegar aqui ([BranchPolicy e texto do PR](/saida/branch-e-texto-do-pr#pullrequestblocker)). O parser recusar hunks incompletos é a segunda barreira.
::

## Hunk

```php [app/Services/Outgoing/Diff/Hunk.php]
final readonly class Hunk
{
    public const CONTEXT = ' ';
    public const REMOVE = '-';
    public const ADD = '+';

    public function __construct(
        public int $oldStart, public int $oldCount,
        public int $newStart, public int $newCount,
        public array $lines, // [tipo, texto com o terminador de linha]
    ) {}
}
```

Os números vêm do cabeçalho `@@` (contagem ausente vale 1). Cada linha guarda o tipo e o texto **com o terminador** (`"\n"`, `"\r\n"` ou nenhum, na última linha sem quebra).

## FilePatch

```php [app/Services/Outgoing/Diff/FilePatch.php]
final readonly class FilePatch
{
    public const ADDED = 'added';
    public const MODIFIED = 'modified';
    public const DELETED = 'deleted';

    public function __construct(public string $path, public string $action, public array $hunks) {}

    public function apply(?string $original): string;
}
```

`apply($original)` reconstrói o arquivo:

1. Parte o original em linhas **mantendo o terminador** de cada uma.
2. Para cada hunk, em ordem: copia as linhas intactas até o início do hunk (`oldStart - 1`, ou `oldStart` quando o hunk só insere), confere cada linha de contexto e removida contra o original e escreve as de contexto e as adicionadas.
3. Copia o resto do arquivo.

Recusas de `apply()`:

| Situação | Mensagem |
|---|---|
| Hunk antes do anterior ou depois do fim do arquivo | Hunk fora de ordem ou além do fim de "…" (linha N). |
| Linha de contexto ou removida diferente | O conteúdo de "…" na linha N não confere com o diff: o arquivo mudou desde o commit analisado. |
| Arquivo `added` que já existe com conteúdo | "…" já existe no repositório, mas o diff o cria como novo. |
| Arquivo `deleted` que sobra com conteúdo | O diff remove "…", mas o arquivo tem conteúdo que o diff não cobre. |

## ChangeSet e FileChange

`ChangeSet` é a fachada que os providers usam:

| Método | Faz |
|---|---|
| `ChangeSet::fromDiff($diff)` | `UnifiedDiff::parse()`, descarta mudanças só de modo. Sem nenhum arquivo com conteúdo: "O diff não altera o conteúdo de nenhum arquivo." |
| `paths()` | Os caminhos tocados (o Bitbucket usa para recusar nomes reservados) |
| `apply(callable $readOriginal)` | Para cada patch, chama `$readOriginal($path)` (menos para arquivos novos), aplica e devolve `FileChange[]` |

```php [app/Services/Outgoing/Diff/FileChange.php]
final readonly class FileChange
{
    public function __construct(public string $path, public ?string $content, public bool $added = false) {}

    public function isDeleted(): bool { return $this->content === null; }
}
```

O `$readOriginal` é do provider e lê o arquivo **na cabeça da branch** de trabalho. Ele lança `RepositoryProviderException` se o arquivo não existir ali.

## Do FileChange ao commit

| | Bitbucket | GitHub |
|---|---|---|
| Arquivo novo ou alterado | Campo multipart `<caminho>` com o conteúdo | `POST git/blobs` (base64) e entrada na árvore com o `sha` do blob e o modo |
| Arquivo removido | Campo `files=<caminho>` | Entrada na árvore com `sha: null` |
| Commit | O próprio `POST /src` | `POST git/trees` + `POST git/commits` + `PATCH` da ref |

Como `DiffException` estende `RepositoryProviderException`, a entrega trata as duas do mesmo jeito: registra na timeline e deixa o incidente com a correção pronta, sem PR.

## Testes

`tests/Unit/Outgoing/UnifiedDiffTest.php` usa diffs gerados por um `git diff` real e cobre: o conteúdo novo reconstruído em vários casos (inserção no fim e no meio, arquivo novo, vazio e removido, sem quebra de linha no fim, CRLF, UTF-8, linhas em branco); arquivo que mudou desde o commit analisado; criar arquivo que já existe; binários; diff truncado; casos inseguros ou não suportados (renomeação, link simbólico, caminho com `..`, `.git/`, caminhos divergentes, texto que não é diff do git, diff vazio); e mudança só de modo sem hunks. Os testes dos providers cobrem o mesmo erro de ponta a ponta (`does_not_push_when_the_file_changed_on_the_branch`).
