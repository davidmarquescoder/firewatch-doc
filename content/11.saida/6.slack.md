O `SlackNotifier` posta no canal do conector o resultado de **toda** investigação terminada: com PR, com correção sem PR ou com falha. O time sempre sabe o que aconteceu, mesmo quando os agentes não conseguem corrigir nada.

| Classe | Papel |
|---|---|
| `Slack\SlackNotifier` | Implementa `Notifier`: valida o conector, chama `chat.postMessage` e traduz erros |
| `Slack\SlackIncidentMessage` | Monta a mensagem de um incidente: texto simples e blocos do Block Kit |

## Conector

| Campo | Onde | Para quê |
|---|---|---|
| `bot_token` | Credencial, obrigatória | Token do bot (`xoxb-…`), com o escopo `chat:write` |
| `channel` | Settings, obrigatório | Nome (`#incidentes`) ou id (`C0123…`) do canal |
| `signing_secret` | Credencial, opcional | Só para os comandos de barra (entrada), não para notificar |

O bot precisa estar **no canal** (`/invite @Firewatch`). Sem `bot_token` ou `channel`, nada é enviado e a entrega registra "O conector "…" não tem bot token ou canal configurado."

```php [config/services.php]
'slack' => [
    'api_url' => env('SLACK_API_URL', 'https://slack.com/api'),
    'timeout' => (int) env('SLACK_TIMEOUT', 15),
],
```

Token e canal **não** ficam no `.env`: vêm sempre do conector, então cada conector Slack pode usar outro workspace ou canal.

## O envio

`POST <api_url>/chat.postMessage` com `Authorization: Bearer <bot_token>`:

```json
{
  "channel": "#incidentes",
  "text": ":white_check_mark: Correção pronta para revisão — Attempt to read property \"role\" on null — Loja — 7 usuários afetados — PR: https://…",
  "blocks": [ … ],
  "unfurl_links": false,
  "unfurl_media": false
}
```

- `text` é a versão sem formatação: aparece na notificação do celular, em leitores de tela e em clientes sem blocos.
- `unfurl_*: false` evita que o Slack expanda o link do PR e do painel numa prévia.

O Slack responde **HTTP 200 até em erro**. O sucesso é `"ok": true`; com `ok: false`, o `error` vira a mensagem, com uma dica:

| `error` | Dica |
|---|---|
| `not_in_channel` | convide o bot para o canal com /invite |
| `channel_not_found` | confira o nome ou o ID do canal no conector |
| `invalid_auth`, `not_authed`, `token_revoked`, `account_inactive` | bot token inválido ou revogado |
| `missing_scope` | o app precisa do escopo chat:write |
| `is_archived` | o canal está arquivado |
| `ratelimited` | limite de mensagens atingido |

Exemplo: "O Slack recusou a mensagem para #incidentes: not_in_channel (convide o bot para o canal com /invite)." Status HTTP de erro vira "O Slack respondeu HTTP 502 ao enviar a mensagem." e falha de rede vira "Não foi possível conectar ao Slack (…)". O timeout é `SLACK_TIMEOUT` (15 s), com 5 s de conexão.

## A mensagem

`SlackIncidentMessage::blocks()` monta, de cima para baixo:

| Bloco | Conteúdo |
|---|---|
| `header` | A manchete do desfecho (até 149 caracteres) |
| `section` | Título do incidente em negrito |
| `section` com `fields` | Aplicação, usuários afetados, ocorrências, severidade e, se não falhou, **Risco da correção** e **Testes** |
| `section` | **Resumo** (se houver) |
| `section` | Detalhe do desfecho (abaixo) |
| `actions` | Botões **Revisar Pull Request** (primário) e **Ver incidente no painel** |
| `context` | Referência do incidente (com link), link do PR, duração, custo e "Firewatch" |

Campos vazios e blocos sem conteúdo são omitidos. Sem URL de painel, não há botão do painel e a referência aparece em código.

### Os três desfechos

O desfecho vem de `InvestigationReport::outcome()`, lido depois do passo do PR ([Contratos](/saida#outcome)):

| Desfecho | Manchete | Detalhe |
|---|---|---|
| `pr_opened` | :white_check_mark: Correção pronta para revisão | **Causa raiz** e **Correção** |
| `fix_without_pr` | :warning: Correção pronta, mas o Pull Request não foi aberto | **Por que não há Pull Request**: o `status_reason` do incidente |
| `failed` | :x: Os agentes não conseguiram corrigir o incidente, ou :x: A investigação falhou antes de terminar | **Motivo — <tipo>**, a etapa, **Causa provável** (se os agentes chegaram a uma) e **Próximo passo** |

O campo **Testes** resume o que o runner mediu: "Suíte passou · bug reproduzido", "Suíte passou", "Suíte falhou", "Suíte excedeu o tempo" ou "Não executados".

## Notificações de falha

A regra do projeto é que **o time é avisado mesmo quando dá errado**. Por isso toda saída do `InvestigateIncident` termina num `DeliverIncidentOutcome`, que chama o Slack independente do resultado:

| Situação | Quem fecha | Exemplo de motivo |
|---|---|---|
| Agentes não corrigiram (`tests_failed`, `no_fix`, `flow_violation`) | `InvestigateIncident` | O teste novo não falhou sem a correção |
| Falha antes ou em volta dos agentes (clone, instalação, timeout, memória, IA) | `InvestigateIncident` | Clone do repositório falhou |
| Teto mensal de custo atingido | `InvestigateIncident`, antes de subir o runner | Teto mensal de custo atingido: US$ 50,00 de US$ 50,00 em 2026-11 |
| Exceção no job ou nenhum runner livre a tempo | `InvestigateIncident::failed()` | Nenhum runner ficou livre em N min (limite de 2 execuções simultâneas) |
| Run travado ou incidente parado na fila | `firewatch:fail-stale-incidents` (`FailStaleIncidentsAction`), com `afterCommit()` | Monitoramento (execução sem resposta) |
| Correção pronta, PR bloqueado ou com erro | `DeliverIncidentOutcome` | Correção não enviada: a suíte de testes não passou… |

A mensagem de falha responde três perguntas:

1. **Por quê**: o `failure_reason` do run (ou o `status_reason` do incidente), com o rótulo do `failure_kind`.
2. **Onde**: a etapa em que parou, com rótulo legível (`failureStage()`): "Clone do repositório", "Trabalho dos agentes", "Suíte de testes", "Fila de execução", "Monitoramento (execução sem resposta)"…
3. **E agora**: o próximo passo do `failure_kind` e a situação da reexecução, por exemplo "… Dá para reexecutar pelo painel (2 reexecuções restantes)." ou, sem reexecuções, o motivo de não dar.

A manchete não culpa os agentes por falhas de infraestrutura: só `tests_failed`, `no_fix` e `flow_violation` levam "Os agentes não conseguiram corrigir o incidente" ([Contratos](/saida#failureheadline-e-nextstep)). Os motivos e os próximos passos de cada tipo estão em [Resultado e falhas](/investigacao/resultado-e-falhas#os-failure-kinds).

Um run `dry_run` (`FIREWATCH_RUNNER_DRY_RUN=1`) **não** notifica: a entrega para antes de qualquer integração.

## Alertas operacionais

`alert($connector, $title, $text)` envia um aviso sem incidente: um `header` com :warning: e o título e uma `section` com o texto. Hoje só o `SendBudgetAlert` usa, quando o gasto do mês cruza os limiares de alerta ou o teto ([Investigação](/investigacao)):

```text
:warning: Teto mensal de custo atingido
O Firewatch gastou US$ 50,00 de US$ 50,00 em 2026-11. Novas investigações ficam bloqueadas até o próximo mês ou até o teto ser aumentado em Custos e limites.
```

O job percorre **todos** os conectores ativos com notifier, ignora falhas individuais (reporta e segue) e grava na auditoria a ação `budget_alert` com a lista de conectores avisados. Diferente da entrega, ele tem 3 tentativas.

## Escape e limites

Todo texto livre chega **mascarado** do `InvestigationReport` ([Mascaramento](/seguranca/mascaramento)). Aqui ele só é **escapado** para o mrkdwn do Slack: `&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`. Sem isso, um `<!channel>` no texto do erro chamaria o canal inteiro, e um `<https://x|clique>` viraria um link disfarçado.

| Limite do Slack | Como é respeitado |
|---|---|
| `header`: 150 caracteres | Cortado em 149 com `…` |
| `section`: 3 000 caracteres | Cortado em 2 900 com `…` |

## Testes

`tests/Feature/Outgoing/SlackNotifierTest.php` cobre: a mensagem de PR aberto com resumo, usuários e os dois links; correção sem PR dizendo por quê; investigação falha notificada com o motivo; texto mascarado e escapado; referência sem botão quando não há URL de painel; erro do Slack legível e sem token; conector sem canal não envia; a entrega notificando depois de abrir o PR; e o registro no config.

`tests/Feature/Outgoing/FailureNotificationTest.php` cobre: falha dos agentes com motivo, etapa e próximo passo; falha de infraestrutura sem culpar os agentes; run travado fechado pelo watchdog e notificado; o time mandado para a investigação manual sem reexecuções; e todo `failure_kind` com um próximo passo.
