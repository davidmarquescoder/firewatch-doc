A **saída** é tudo o que o Firewatch faz fora dele depois (e um pouco antes) da investigação: criar a branch, enviar a correção e abrir o Pull Request, avisar o time e manter o card do incidente. Cada tipo de integração tem um **contrato** e uma ou mais implementações, escolhidas pelo tipo do conector:

| Contrato | Para quê | Implementações | Credenciais do conector |
|---|---|---|---|
| `RepositoryProvider` | Branch, commit da correção, Pull Request | `BitbucketRepositoryProvider`, `GitHubRepositoryProvider` | `access_token` (escrita) |
| `Notifier` | Mensagem para o time | `SlackNotifier` | `bot_token` + `settings.channel` |
| `IssueTracker` | Card do incidente | `JiraIssueTracker` | `email` + `api_token` + `settings.base_url`/`project_key` |

Tudo fica em `app/Services/Outgoing/`:

```text
app/Services/Outgoing/
├── Contracts/                 RepositoryProvider, Notifier, IssueTracker
├── OutgoingIntegrations.php   tipo do conector → classe
├── InvestigationReport.php    visão do relatório para as integrações
├── BranchPolicy.php           só branches firewatch/, nunca a base
├── PullRequest.php            id + url (resposta)
├── PullRequestData.php        source, destination, título, descrição (pedido)
├── *Exception.php             RepositoryProvider/Notification/IssueTracker
├── Diff/                      UnifiedDiff, FilePatch, Hunk, ChangeSet, FileChange
├── Bitbucket/  GitHub/        providers de repositório
├── Slack/                     SlackNotifier, SlackIncidentMessage
└── Jira/                      JiraIssueTracker, Adf
```

Quem chama:

| Quando | Quem | O que chama | Página |
|---|---|---|---|
| Antes dos agentes | `InvestigateIncident` → `OpenIncidentIssueAction` | `IssueTracker::open()` | [Jira](/saida/jira) |
| Fim da investigação | `DeliverIncidentOutcome` | `RepositoryProvider` → `Notifier::notify()` → `IssueTracker::sync()` | [DeliverIncidentOutcome](/saida/deliver-incident-outcome) |
| Teto de custo | `SendBudgetAlert` | `Notifier::alert()` | [Slack](/saida/slack#alertas-operacionais) |

## RepositoryProvider

```php [app/Services/Outgoing/Contracts/RepositoryProvider.php]
interface RepositoryProvider
{
    public function createBranch(Application $application, string $branch, string $fromCommit): void;
    public function pushChanges(Application $application, string $branch, string $diff, string $commitMessage): string;
    public function openPullRequest(Application $application, PullRequestData $pullRequest): PullRequest;
    public function comment(Application $application, string $pullRequestId, string $body): void;
}
```

| Método | Recebe | Devolve | Regra |
|---|---|---|---|
| `createBranch` | Branch e o commit base em que os agentes trabalharam | nada | Idempotente: se a branch já aponta para o commit, não faz nada |
| `pushChanges` | Branch, o diff do runner (`git diff`) e a mensagem de commit | Hash do commit novo | **Um** commit em cima da cabeça da branch. Nunca sobrescreve uma branch que mudou no meio do caminho |
| `openPullRequest` | `PullRequestData` (source, destination, título, descrição) | `PullRequest` (`id`, `url`) | Se já existe um PR aberto da branch, devolve esse |
| `comment` | Id do PR e o texto | nada | Faz parte do contrato, mas a entrega ainda não o usa |

O conector e o repositório vêm da **aplicação**: `repositoryConnector` e `repository_slug` (`workspace/repositorio` no Bitbucket, `dono/repositorio` no GitHub). O contrato documenta as regras que toda implementação precisa manter:

- só escrever em branches com prefixo `firewatch/`;
- nunca escrever na branch base;
- nunca fazer merge.

As duas implementações aplicam isso pelo [`BranchPolicy`](/saida/branch-e-texto-do-pr#branchpolicy) em **toda** escrita, e nenhuma delas tem código de merge.

## Notifier

```php [app/Services/Outgoing/Contracts/Notifier.php]
interface Notifier
{
    public function notify(Connector $connector, InvestigationReport $report): void;
    public function alert(Connector $connector, string $title, string $text): void;
}
```

`notify()` é chamado para **toda** investigação terminada, com correção ou não: o time é avisado mesmo quando os agentes falham. `alert()` é para avisos operacionais sem incidente, hoje só os de teto de custo.

## IssueTracker

```php [app/Services/Outgoing/Contracts/IssueTracker.php]
interface IssueTracker
{
    public function open(Connector $connector, Incident $incident): string;
    public function sync(Connector $connector, InvestigationReport $report): string;
}
```

Um card por incidente, guardado em `incidents.jira_key`. `open()` roda **antes** dos agentes, para a chave entrar no nome da branch (`firewatch/OPS-123-…`) e o repositório ligar branch, commits e PR ao card. `sync()` roda no fim e registra o resultado, criando o card se ele ainda não existir. Os dois devolvem a chave.

## OutgoingIntegrations

O registro é um mapa no `config/firewatch.php`, por tipo de integração:

```php [config/firewatch.php]
'outgoing' => [
    'repository'     => [
        'bitbucket' => App\Services\Outgoing\Bitbucket\BitbucketRepositoryProvider::class,
        'github'    => App\Services\Outgoing\GitHub\GitHubRepositoryProvider::class,
    ],
    'notifiers'      => [
        'slack' => App\Services\Outgoing\Slack\SlackNotifier::class,
    ],
    'issue_trackers' => [
        'jira' => App\Services\Outgoing\Jira\JiraIssueTracker::class,
    ],
],
```

`App\Services\Outgoing\OutgoingIntegrations` lê esse mapa:

| Método | Devolve |
|---|---|
| `repositoryProvider(ConnectorTypeEnum $type)` | A instância (pelo container do Laravel) ou `null` |
| `notifier($type)` | Idem |
| `issueTracker($type)` | Idem |
| `typesFor('notifiers' \| 'issue_trackers' \| 'repository')` | Os tipos de conector que têm classe nesse mapa |

Dois comportamentos importam:

- **Tipo sem classe não é erro.** `null` significa "ainda não entregue para esse tipo". Para o repositório, a entrega registra "ainda não disponível" na timeline; conectores de notifier e issue tracker sem classe no mapa nem são percorridos.
- **Classe errada é erro de programação.** Se a classe configurada não implementa o contrato, o registro lança `LogicException`.

Como as classes saem do container, os testes trocam qualquer uma por um fake só mudando o config: `tests/Fakes/FakeRepositoryProvider.php`, `FakeNotifier.php` e `FakeIssueTracker.php` gravam as chamadas em memória.

### Adicionar uma integração

1. Crie o tipo em `ConnectorTypeEnum`, com credenciais e settings ([Enums](/modelo-de-dados/enums)).
2. Implemente o contrato em `app/Services/Outgoing/<Servico>/`.
3. Registre a classe em `firewatch.outgoing.<kind>.<tipo>`.
4. Para repositórios, inclua também a URL de clone e o usuário em `firewatch.runner.repository` ([GitHub e Bitbucket](/saida/repositorios#clone-no-runner)).

Siga as mesmas regras das implementações atuais: mensagens de erro legíveis, em português e sem credenciais, e texto livre sempre vindo mascarado do `InvestigationReport`.

## InvestigationReport

Nenhuma integração lê o `report` do `AgentRun` direto. Todas recebem um `App\Services\Outgoing\InvestigationReport`, criado com `InvestigationReport::fromRun($run)`, que é uma visão **somente leitura** do relatório do runner preparada para sair do Firewatch.

Três princípios valem para tudo o que ele devolve:

1. **O que o runner mediu vale mais do que o que o agente disse.** Status dos testes, arquivos alterados, reprodução do bug e diff vêm das seções medidas pelo runner (`tests`, `changes`, `flow`), nunca do `agent_report`.
2. **Todo texto livre é mascarado de novo.** Resumo, causa raiz, correção, título e descrição do PR, motivo da falha e título do incidente passam pelo `SensitiveDataMasker` antes de sair ([Mascaramento](/seguranca/mascaramento)). O diff é código e vai como está.
3. **Texto vazio vira `null`.** Cada integração decide o que mostrar no lugar.

| Grupo | Métodos |
|---|---|
| Resultado | `status()`, `isFixed()`, `isDryRun()`, `outcome()` |
| Texto do incidente | `incidentTitle()`, `statusReason()` |
| Texto dos agentes (mascarado) | `summary()`, `rootCause()`, `fix()`, `riskReason()`, `testAdded()` |
| Falha | `failureReason()`, `failureKind()`, `failureStage()` (rótulo legível), `failureHeadline()`, `nextStep()` |
| Risco | `riskLevel()` (`low`/`medium`/`high` ou `null`), `riskLabel()` (Baixo, Médio, Alto, Não informado) |
| Git | `workBranch()`, `baseBranch()`, `baseCommit()`, `diff()`, `changedFiles()` |
| Verificação do runner | `testsStatus()`, `testsSummaryLine()`, `flowStatus()`, `reproductionStatus()`, `reproductionCommand()`, `flowWarnings()` |
| Pull Request | `pullRequestBlocker()`, `pullRequestTitle()`, `pullRequestDescription()`, `commitMessage()` ([BranchPolicy e texto do PR](/saida/branch-e-texto-do-pr)) |
| Custo | `costUsd()` |

### outcome()

Slack e Jira contam ao time um de três desfechos. `outcome()` é lido **depois** do passo do PR, porque depende do `pr_url`:

| Valor | Quando |
|---|---|
| `pr_opened` | O incidente tem `pr_url` |
| `fix_without_pr` | Os agentes corrigiram (`fixed`), mas o PR não saiu: bloqueado, provider indisponível ou falha na entrega |
| `failed` | Qualquer outro caso |

### failureHeadline() e nextStep()

A manchete separa culpa: se o `failure_kind` é `tests_failed`, `no_fix` ou `flow_violation` (`isAgentFailure()`), é "Os agentes não conseguiram corrigir o incidente"; senão (clone, instalação, timeout, erro interno…), "A investigação falhou antes de terminar".

`nextStep()` junta o próximo passo do `failure_kind` ([Os failure kinds](/investigacao/resultado-e-falhas#os-failure-kinds)) e, para incidentes `failed`, a situação da reexecução: "Dá para reexecutar pelo painel (2 reexecuções restantes)." ou o motivo de não dar.

## Exceções

| Exceção | Lançada por |
|---|---|
| `RepositoryProviderException` | Providers de repositório e `BranchPolicy` |
| `DiffException` (estende a anterior) | `UnifiedDiff`, `FilePatch`, `ChangeSet` |
| `NotificationException` | `SlackNotifier` |
| `IssueTrackerException` | `JiraIssueTracker` |

Todas são `RuntimeException` com uma regra comum: a mensagem vai para a **timeline do incidente**, então é escrita em português para o time e **nunca** contém token, nem mesmo em erros de rede. O padrão das mensagens é `"<Serviço>: falha ao <ação>: <dica> (HTTP <código>) — <detalhe do serviço>."`, com o detalhe cortado em 200 caracteres. Os testes `errors_are_readable_and_never_contain_the_token` (Bitbucket, GitHub), `errors_never_contain_the_token` (Jira) e `slack_error_is_readable_and_has_no_token` conferem isso.
