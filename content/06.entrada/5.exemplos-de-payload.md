Os exemplos abaixo são os arquivos do próprio repositório. A saída de cada um foi gerada rodando o adapter de verdade (`normalize()->toArray()`): é exatamente o que vai, mascarado, para `incidents.sanitized_payload`.

| Arquivo | Fonte | Usado em |
|---|---|---|
| `docs/incoming/generic-webhook.example.json` | Webhook genérico | `GenericWebhookAdapterTest`, `WebhookEndpointTest` e a documentação do conector |
| `tests/Fixtures/sentry/event_alert.json` | Sentry, recurso `event_alert` | `SentryAdapterTest`, `WebhookEndpointTest` |
| `tests/Fixtures/sentry/issue_created.json` | Sentry, recurso `issue` com `action: created` | `SentryAdapterTest` |

Todos descrevem o **mesmo bug** da aplicação de demonstração (`flowstock-back`): `Attempt to read property "role" on null` no `EnsureCompanyIsActive`.

    },
    "occurrences": 3,
    "affected_users": 2,
    "severity": "error",

    "occurred_at": "2026-11-09T12:00:00+00:00"

::

O que observar:

- Os frames viraram texto **na ordem enviada**, no formato `arquivo:linha Classe->funcao()`.
- Sem `fingerprint` no payload, ele foi **derivado** de aplicação + título + primeiro frame. Mandar o mesmo erro de novo soma ocorrências no mesmo incidente.
- `context` passou intacto. O mascaramento acontece depois, no registro.

O payload mínimo aceito é só `application` e `title`:

```json
{ "application": "flowstock-back", "title": "Erro 500 ao salvar pedido" }
```

Para enviar o exemplo assinado, veja o `curl` em [Verificação de assinatura](/entrada/verificacao).

## Sentry: `event_alert`

O webhook que o Sentry manda quando uma **regra de alerta** dispara para a integração. É o mais completo: tem a exceção com os frames, o usuário e a requisição.

O que observar:

- `application` veio do **slug na `url`** (`flowstock-back`), e não de `project: 1`.
- Os frames foram **invertidos**: o Sentry lista do mais antigo para o mais recente, e o FireWatch mostra o ponto do erro primeiro. O frame de framework ganhou `[vendor]`.
- Da requisição, sobraram **só `method` e `url`**. O `Authorization`, o cookie de sessão e a senha do corpo nem entram no evento.
- O e-mail do usuário ainda está aqui. Ele vira `[redacted]` no `sanitized_payload`, porque a chave `email` é sensível para o [mascaramento](/seguranca/mascaramento).
- `fingerprint` é `sentry:<issue_id>`: alertas e issues da mesma issue do Sentry caem no mesmo incidente.

::

O que observar:

- `count` chega como **string** (`"3"`) e vira inteiro.
- `level: fatal` vira `critical`.
- O "stack trace" é só uma linha montada a partir do `metadata`. Para os agentes, o `event_alert` é bem mais útil: prefira configurar uma regra de alerta para a integração.
- Issues não trazem ambiente: `environment` fica `null`. Com as regras padrão (`environments: ["production"]`), o incidente é **ignorado** (veja [Motor de regras](/registro-e-trigger/motor-de-regras)).
- O mesmo arquivo com `"action": "resolved"` é [ignorado](/entrada/payloads-ignorados-e-invalidos) com `202`.

## Comando do Slack

O Slack manda um formulário (`application/x-www-form-urlencoded`). Não há fixture em arquivo: os testes montam o formulário em `SlackCommandEndpointTest`. Um exemplo, com os campos já decodificados:

::code-group
```text [Entrada: formulário do Slack]
command=/firewatch
text=investigar flowstock-back Erro 500 ao salvar pedido
     OrderService.php:88
user_id=U123
user_name=ana
channel_id=C1
token=<token legado>
response_url=https://hooks.slack.com/commands/…
trigger_id=…
```

```json [Saída: IncomingEvent]
{
    "application": "flowstock-back",
    "title": "Erro 500 ao salvar pedido",
    "stack_trace": "OrderService.php:88",
    "context": {
        "requested_via": "slack_command",
        "manual_request": true,
        "slack": { "user_id": "U123", "user_name": "ana", "channel_id": "C1" }
    },
    "occurrences": 1,
    "affected_users": 0,
    "severity": "error",
    "environment": null,
    "fingerprint": "f87981204891b738f0b6a24d1f920944695f33cc7a9bf1e58bd1c6cec1903285",
    "occurred_at": "2026-11-16T22:15:28+00:00"
}
```
::

O que observar:

- A segunda linha do texto virou o `stack_trace`.
- `token`, `response_url` e `trigger_id` **não** entram no `raw_payload`.
- `occurred_at` é a hora do comando, e não a hora do erro.
- Severidade sempre `error` e sem ambiente: o comando não tem como informar esses dados. Como é um pedido manual (`manual_request: true`), a regra de ambiente **aceita** o incidente mesmo com as regras padrão, e os agentes são acionados (veja [Pedidos manuais](/registro-e-trigger/motor-de-regras#pedidos-manuais)).

## Testando localmente

Com um conector `generic_webhook` cadastrado e uma aplicação ativa com `monitoring_identifier = flowstock-back`:

```bash
cd firewatch-back
export FIREWATCH_URL=http://localhost:8000
export CONNECTOR_ID=<uuid do conector>
export FIREWATCH_SECRET=<segredo do conector>

BODY=$(cat docs/incoming/generic-webhook.example.json)
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$FIREWATCH_SECRET" -hex | sed 's/^.* //')

curl -s -X POST "$FIREWATCH_URL/api/webhooks/$CONNECTOR_ID" \
  -H 'Content-Type: application/json' \
  -H "X-Firewatch-Timestamp: $TS" \
  -H "X-Firewatch-Signature: sha256=$SIG" \
  --data "$BODY"
```

A resposta `202` traz o `incident_id` e a decisão das regras. Se as regras decidirem acionar os agentes, uma investigação **real** começa e consome créditos do Claude. O botão **Simular incidente** do painel faz o mesmo sem webhook nem assinatura, e também passa pelas regras de acionamento. Para ensaiar sem custo, veja [Testar sem gastar créditos](/ambiente-e-setup/testar-sem-creditos).
