Erros chegam ao FireWatch por **duas rotas públicas**, sem sessão e sem login. Quem prova a origem é o **segredo do conector**, que vai no próprio endereço (o UUID do conector) e na assinatura de cada requisição.

| Rota | Controller | Fontes | Corpo | Limite |
|---|---|---|---|---|
| `POST /api/webhooks/{connector}` | `WebhookController` | Sentry e webhook genérico | JSON | 120 por minuto |
| `POST /api/slack/commands/{connector}` | `SlackCommandController` | Comando `/firewatch` do Slack | `application/x-www-form-urlencoded` | 60 por minuto |

Elas ficam em `routes/api.php`, **fora** do prefixo `/v1` e da pilha `auth:sanctum` do painel:

```php [routes/api.php]
// Incoming events from monitoring tools / generic webhooks (signature or token, no session)
Route::post('/webhooks/{connector}', WebhookController::class)
    ->middleware(['verify-webhook', 'throttle:120,1,webhooks'])
    ->name('api.webhooks.receive');

// "/firewatch ..." Slack slash command (Slack request signing)
Route::post('/slack/commands/{connector}', SlackCommandController::class)
    ->middleware(['verify-webhook', 'throttle:60,1,slack-commands'])
    ->name('api.slack.commands');
```

O `{connector}` é o **UUID** do conector, que o painel mostra ao editar o conector. Ele não é segredo: sem a assinatura, conhecer o endereço não abre nada.

## Do pedido ao incidente

::mermaid
---
code: |
  flowchart TD
    R[POST /api/webhooks/id] --> T{throttle<br/>120/min por IP}
    T -- excedeu --> E429[429]
    T --> V{VerifyIncomingWebhook}
    V -- conector inexistente<br/>ou não recebe eventos --> E404[404]
    V -- assinatura inválida --> E401[401]
    V -- conector inativo --> E403[403]
    V --> C[WebhookController]
    C -- tipo não é de entrada --> E404b[404]
    C -- corpo não é objeto JSON --> E422a[422]
    C --> I[IngestIncomingEventAction]
    I --> A[adapter.normalize]
    A -- InvalidIncomingPayloadException --> E422b[422]
    A --> F{aplicação ativa com o<br/>monitoring_identifier?}
    F -- não --> IGN[202 ignored]
    A -- IgnoredIncomingPayloadException --> IGN
    F -- sim --> REG[RegisterIncomingEventAction<br/>dedup por fingerprint + mascaramento]
    REG --> TR[EvaluateIncidentTriggerAction<br/>regras de acionamento]
    TR --> OK[202 com incident_id e decisão]
caption: Caminho de um webhook. O mesmo IngestIncomingEventAction atende o comando do Slack e o botão Simular incidente.
---
::

O controller só traduz HTTP. O trabalho fica em `IngestIncomingEventAction`, compartilhado por três entradas:

| Entrada | Adapter |
|---|---|
| `POST /api/webhooks/{connector}` | `SentryAdapter` ou `GenericWebhookAdapter`, conforme o tipo do conector |
| `POST /api/slack/commands/{connector}` | `SlackCommandAdapter` |
| Botão **Simular incidente** (`POST /api/v1/application/{id}/simulate-incident`, autenticado) | `GenericWebhookAdapter`, com um payload montado pelo `SimulateIncidentAction` |

Os passos do pipeline:

1. **Normaliza** o payload com o adapter do tipo e obtém um [`IncomingEvent`](/entrada/adapters#o-contrato-incomingevent).
2. **Encontra a aplicação** com `Application::findByMonitoringIdentifier()`, que só considera aplicações **ativas**. Sem aplicação, o evento é [ignorado](/entrada/payloads-ignorados-e-invalidos).
3. **Registra** o incidente (`RegisterIncomingEventAction`): procura um incidente da mesma aplicação com o mesmo fingerprint, aberto ou visto nas últimas 72 horas (`FIREWATCH_INCIDENT_REOPEN_AFTER_HOURS`), e, se achar, soma a ocorrência (e eleva a severidade, se a nova for maior); senão cria um novo. Um lock por fingerprint evita dois incidentes para o mesmo erro quando as entregas chegam juntas. O payload original vai criptografado para `raw_payload` e a cópia mascarada para `sanitized_payload` (veja [Mascaramento](/seguranca/mascaramento)).
4. **Avalia as regras de acionamento** e devolve a decisão (`trigger`, `hold` ou `ignore`).

## Rate limits

Os limites usam o `throttle` padrão do Laravel (`ThrottleRequests`), com janela de 1 minuto.

| O que | Como funciona |
|---|---|
| **Ordem** | O Laravel coloca o `throttle` **antes** do `verify-webhook` (prioridade de middlewares). Requisições com assinatura errada também contam |
| **Chave** | Sem usuário logado, a chave é `domínio da rota + IP`, com um prefixo por rota (`throttle:120,1,webhooks` e `throttle:60,1,slack-commands`). O contador é **por IP** e **separado** em cada rota: um pico de webhooks não bloqueia o comando do Slack |
| **Excedeu** | `429 Too Many Attempts.`, com os cabeçalhos `Retry-After` e `X-RateLimit-*` |

::note
O IP é o que chega ao PHP. Atrás do nginx do `docker-compose` é o IP do cliente. Atrás de um balanceador ou proxy externo, sem configurar os proxies confiáveis (`trustProxies` no `bootstrap/app.php`), **todas** as fontes aparecem com o IP do proxy e dividem os mesmos 120 por minuto.
::

O Sentry reenvia webhooks que falham. Para um pico de erros, os 120 por minuto costumam bastar, porque a deduplicação transforma o pico em **um** incidente com várias ocorrências. Se o limite for atingido, as entregas recusadas com `429` simplesmente não somam ocorrências.

## Respostas de `/webhooks/{connector}`

A regra do `WebhookController`: **`202` para tudo que foi entendido**, inclusive o que o FireWatch decidiu ignorar, para a fonte não ficar reenviando; **`422` só para o que não dá para ler**.

| Status | Quando | Corpo |
|---|---|---|
| `202` | Incidente criado | `message: "Incidente criado."`, `data.created: true` |
| `202` | Ocorrência somada a um incidente existente | `message: "Ocorrência registrada em incidente existente."`, `data.created: false` |
| `202` | Evento válido, mas ignorado | `message: "Evento recebido e ignorado."`, `data.ignored: true` |
| `422` | Corpo não é um objeto JSON (vazio, lista, texto) | `message: "O corpo do webhook deve ser um objeto JSON."` |
| `422` | Falta campo obrigatório ou campo inválido | `message` com o nome do campo (em inglês) |
| `401` / `403` / `404` | Recusado pelo `verify-webhook` | Veja [Verificação de assinatura](/entrada/verificacao) |
| `404` | Conector do tipo Slack chamado nesta rota | `Webhook não encontrado.` |
| `429` | Limite por IP | Padrão do Laravel |

Resposta de sucesso:

```json
{
  "message": "Incidente criado.",
  "data": {
    "ignored": false,
    "incident_id": "9d6f1c2e-4b1a-4c3e-9a5b-2f7e8d9c0a1b",
    "created": true,
    "status": "queued",
    "trigger": {
      "outcome": "trigger",
      "outcome_label": "Acionar agentes",
      "reason": "…",
      "checks": [ … ]
    }
  }
}
```

`data.trigger` é `null` quando o incidente já tinha passado da decisão (na fila, investigando ou terminado).

## Respostas de `/slack/commands/{connector}`

O Slack mostra qualquer resposta diferente de `200` como uma falha genérica ("o comando falhou"). Por isso o `SlackCommandController` responde **sempre `200`** depois da verificação, com uma mensagem no formato do Slack:

| Situação | `response_type` | Texto |
|---|---|---|
| `investigar` registrou um incidente novo | `in_channel` (todos veem) | `:fire: @ana pediu uma investigação em *flowstock-back*: _Erro 500 ao salvar pedido_` + status |
| `investigar` caiu num incidente existente | `in_channel` | `:repeat: … relatou de novo um erro já registrado…` + ocorrências e status |
| `ajuda`, `?` ou texto vazio | `ephemeral` (só quem chamou) | Instruções de uso |
| Palavra desconhecida | `ephemeral` | `Não conheço o comando …` + instruções |
| Aplicação desconhecida ou inativa | `ephemeral` | `Não encontrei uma aplicação ativa com o identificador …` + lista das aplicações ativas |
| Faltou aplicação ou descrição | `ephemeral` | `Faltou informação no comando.` + instruções |

Cada pedido aceito também gera o evento `slack_investigation_requested` na [auditoria](/seguranca/auditoria), com o id e o nome do usuário do Slack. Os textos vindos do usuário são escapados (`&`, `<`, `>`) antes de voltar para o Slack.

Antes da verificação, as respostas de erro (`401`, `403`, `404`, `429`) seguem iguais às da outra rota, e o Slack as mostra como falha. Um conector Sentry ou webhook genérico chamado nesta rota recebe `404`.
