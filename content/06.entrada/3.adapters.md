Cada fonte de erro fala um formato diferente. Os **adapters** traduzem esses formatos para um único objeto, o `IncomingEvent`, e o resto do FireWatch (deduplicação, regras de acionamento, investigação) só conhece esse objeto.

Adapters **só traduzem**. Eles não validam assinatura (isso é do [`verify-webhook`](/entrada/verificacao)), não gravam incidentes e não mascaram dados (isso é do `RegisterIncomingEventAction`).

## O contrato `IncomingAdapter`

```php [app/Services/Incoming/IncomingAdapter.php]
interface IncomingAdapter
{
    /** O tipo de conector cujos payloads este adapter entende. */
    public function source(): ConnectorTypeEnum;

    /**
     * @throws InvalidIncomingPayloadException Quando falta dado para montar o evento.
     */
    public function normalize(array $payload): IncomingEvent;
}
```

O `IncomingAdapterFactory` escolhe o adapter pelo tipo do conector:

| `ConnectorTypeEnum` | Adapter |
|---|---|
| `sentry` | `Adapters\SentryAdapter` |
| `generic_webhook` | `Adapters\GenericWebhookAdapter` |
| `slack` | `Adapters\SlackCommandAdapter` |
| outros | `LogicException` (não recebem eventos) |

O comando do Slack não usa a factory: o `SlackCommandController` recebe o `SlackCommandAdapter` direto, porque também precisa do `parse()` para responder à ajuda.

## O contrato `IncomingEvent`

`App\Services\Incoming\IncomingEvent` é um `final readonly class`. O construtor **valida e normaliza**, então um evento que existe já é um evento válido.

| Campo | Tipo | Padrão | Normalização e validação |
|---|---|---|---|
| `application` | `string` | | `trim`. Vazio → `InvalidIncomingPayloadException::missing('application')`. É comparado com `applications.monitoring_identifier` |
| `title` | `string` | | Espaços e quebras de linha viram um espaço; cortado em **512** caracteres com `…`. Vazio → `missing('title')` |
| `stackTrace` | `?string` | `null` | `rtrim`; vazio vira `null` |
| `context` | `array` | `[]` | Dados extras da fonte. **Ainda não mascarados** |
| `occurrences` | `int` | `1` | Menor que 1 → `invalid('occurrences')` |
| `affectedUsers` | `int` | `0` | Negativo → `invalid('affected_users')` |
| `severity` | `IncidentSeverityEnum` | `error` | |
| `environment` | `?string` | `null` | |
| `fingerprint` | `string` | derivado | Se a fonte não manda, é calculado (abaixo) |
| `occurredAt` | `?CarbonImmutable` | `null` | Datas no futuro são limitadas a "agora" no registro |
| `rawPayload` | `array` | `[]` | Payload original, gravado **criptografado** |

`toArray()` (e `jsonSerialize()`) devolve tudo **menos o `rawPayload`**, que pode ter segredos. É desse array, mascarado, que nasce o `incidents.sanitized_payload`.

### Fingerprint

O fingerprint decide quando dois erros são **o mesmo incidente**. Se a fonte manda um (o Sentry manda o id da issue; o webhook genérico aceita `fingerprint`), ele é usado. Senão, `IncomingEvent::deriveFingerprint()` calcula:

```text
sha256( application
        + título em minúsculas com todos os dígitos trocados por "#"
        + primeira linha não vazia do stack trace )
```

Trocar os dígitos evita que `Pedido 123 não encontrado` e `Pedido 456 não encontrado` virem dois incidentes. Usar só o primeiro frame evita que diferenças no fundo da pilha (middlewares, vendor) separem o mesmo bug.

## SentryAdapter

Entende os webhooks da **integração interna** do Sentry. O tipo do recurso é detectado pelo **formato do corpo** (não pelo cabeçalho `Sentry-Hook-Resource`):

| Recurso | Onde está | Quando o Sentry manda | Tem stack trace? |
|---|---|---|---|
| `event_alert` | `data.event` | Uma regra de alerta disparou para a integração | Sim |
| `error` | `data.error` | Todo evento de erro (plano Business) | Sim |
| `issue` | `data.issue` | Ciclo de vida da issue | Não |

Nenhum dos três → `invalid('data')`. Sem `data` → `missing('data')`.

### Eventos (`event_alert` e `error`)

| Campo do `IncomingEvent` | De onde vem |
|---|---|
| `application` | Slug do projeto extraído de `event.url` (`…/projects/{org}/{slug}/events/…`); senão `event.project` (o id numérico) |
| `title` | `event.title` → `event.message` → `"<tipo>: <valor>"` da exceção principal |
| `stackTrace` | Cadeia de exceções, a mais recente primeiro (`Caused by:` nas seguintes); frames do ponto do erro para fora, `arquivo:linha função()`, e `[vendor]` nos que não são `in_app` |
| `context` | `culprit`, `platform`, `release`, `user`, `contexts`, `request` (**só `method` e `url`**), `tags` (convertidas para mapa) e `sentry` (`resource`, `event_id`, `issue_id`, `web_url`, `triggered_rule`) |
| `occurrences` | `1` |
| `affectedUsers` | `1` se o evento tem `user`, senão `0` |
| `severity` | `event.level` ou a tag `level` (veja a tabela abaixo) |
| `environment` | `event.environment` ou a tag `environment` |
| `fingerprint` | `sentry:<issue_id>`: todas as ocorrências da mesma issue caem no mesmo incidente |
| `occurredAt` | `event.datetime` ou `event.timestamp` |

Cabeçalhos, cookies, corpo e variáveis de ambiente do `request` são **descartados** já no adapter: eles costumam ter tokens e senhas e não ajudam no diagnóstico.

::warning
**O slug do projeto no Sentry é o identificador.** Cadastre a aplicação com `monitoring_identifier` igual ao slug do projeto (por exemplo `flowstock-back`). Se o evento não tiver `url`, o adapter cai no id numérico do projeto, que não vai bater com o slug, e o evento é ignorado.
::

### Issues (`issue`)

Só as ações `created` e `unresolved` (`SentryAdapter::OPENING_ISSUE_ACTIONS`) abrem ou somam incidente. `resolved`, `assigned`, `archived`, `ignored` e as outras são [ignoradas](/entrada/payloads-ignorados-e-invalidos) com `202`.

| Campo | De onde vem |
|---|---|
| `application` | `issue.project.slug` → `issue.project.id` |
| `title` | `issue.title` (obrigatório) |
| `stackTrace` | Não há stack trace em issues: só uma linha `#0 <arquivo> <função>()` a partir de `metadata`, ou `#0 <culprit>` |
| `context` | `culprit`, `platform`, `metadata` e `sentry` (`action`, `issue_id`, `short_id`, `web_url`, `first_seen`) |
| `occurrences` | `issue.count` (mínimo 1) |
| `affectedUsers` | `issue.userCount` |
| `fingerprint` | `sentry:<issue.id>` |
| `occurredAt` | `lastSeen` → `firstSeen` |

### Severidade

| Nível do Sentry | FireWatch |
|---|---|
| `fatal` | `critical` |
| `error`, `warning`, `info`, `debug` | o mesmo |
| `sample` | `info` |
| ausente ou desconhecido | `error` |

## GenericWebhookAdapter

A entrada que não depende de ferramenta: qualquer sistema (ou um `curl`) abre um incidente mandando um JSON simples. Também é o adapter do botão **Simular incidente**.

| Campo | Obrigatório | Aceita | Erro |
|---|---|---|---|
| `application` | ✓ | string (ou inteiro) | `missing` / `invalid: must be a string` |
| `title` | ✓ (ou `message`) | string | `missing('title')` |
| `message` | | Alternativa a `title` | |
| `stack_trace` | | String pronta **ou** lista de frames | `invalid: must be a string or a list of frames` |
| `severity` | | `debug`, `info`, `warning`, `error`, `critical` e apelidos | `invalid: expected one of …` |
| `environment` | | string | |
| `fingerprint` | | string. Sem ele, é derivado | |
| `occurrences` | | inteiro ≥ 1 (também `"3"`) | `invalid: must be an integer` |
| `affected_users` | | inteiro ≥ 0 | `invalid: must be an integer` |
| `occurred_at` | | ISO 8601 ou unix timestamp (inteiro) | `invalid: expected an ISO 8601 date or unix timestamp` |
| `context` | | objeto JSON | `invalid: must be an object` |

Campos desconhecidos são aceitos e ficam só no `raw_payload`.

**Frames do stack trace.** Cada item da lista pode ser uma string (usada como está) ou um objeto `{file, line, class, function}`, que vira `#0 arquivo:linha Classe->funcao()`. A ordem é **mantida**: mande o ponto do erro primeiro.

**Apelidos de severidade** (`SEVERITY_ALIASES`):

| Recebido | Vira |
|---|---|
| `trace` | `debug` |
| `notice` | `info` |
| `warn` | `warning` |
| `err` | `error` |
| `fatal`, `emergency`, `alert` | `critical` |

Maiúsculas e espaços nas pontas não importam. Sem `severity`, o padrão é `error`.

## SlackCommandAdapter

Permite abrir um incidente pelo Slack:

```text
/firewatch investigar <aplicação> <descrição do erro>
<linhas seguintes, opcionais, viram o stack trace>
```

O adapter tem dois métodos:

**`parse(string $text): SlackCommand`** lê o texto do comando:

1. Desfaz o escape do Slack: `<https://x|rótulo>` vira `rótulo`, `<https://x>` vira o link e as entidades HTML (`&amp;`, `&lt;`, `&gt;`) voltam ao normal.
2. Separa a primeira linha em até três partes: palavra-chave, aplicação e o resto (a descrição). As linhas seguintes viram `details`.
3. Identifica a ação pela palavra-chave, sem diferenciar maiúsculas:

| Palavras | Ação (`SlackCommand`) |
|---|---|
| `investigar`, `investiga`, `investigate` | `INVESTIGATE` |
| `ajuda`, `help`, `?` ou texto vazio | `HELP` |
| qualquer outra | `UNKNOWN` |

`SlackCommand` é um `readonly` com `action`, `application`, `description`, `details` e `raw`.

**`normalize(array $payload): IncomingEvent`** monta o evento a partir do formulário que o Slack envia:

| Campo | De onde vem |
|---|---|
| `application` | Segunda palavra |
| `title` | O resto da primeira linha |
| `stackTrace` | As linhas seguintes |
| `context` | `requested_via: slack_command`, `manual_request: true` e `slack` (`user_id`, `user_name`, `channel_id`, `channel_name`, `team_domain`) |
| `occurredAt` | Agora |
| `fingerprint` | Derivado: repetir a mesma descrição soma ocorrências no mesmo incidente |
| `rawPayload` | O formulário **sem** `token`, `response_url` e `trigger_id` (`DROPPED_FIELDS`), que funcionam como credenciais de curta duração |

Uma ação que não é `investigar` lança `invalid('text')`, mas na prática o controller já respondeu com a ajuda antes de chamar o `normalize()`.

## Criando um adapter novo

1. Crie o tipo em `ConnectorTypeEnum`, declare as credenciais e inclua-o em `isIncoming()` (o `receivesWebhooks()` já considera os tipos de entrada).
2. Escreva o verificador (`WebhookVerifier`) e registre-o no `WebhookVerifierFactory`.
3. Escreva o adapter (`IncomingAdapter`) e registre-o no `IncomingAdapterFactory`.
4. No adapter, guarde em `context` só o que ajuda a investigar. Descarte cabeçalhos, cookies e corpos de requisição.
5. Use `IgnoredIncomingPayloadException` para eventos válidos que não são erro e `InvalidIncomingPayloadException` para o que não dá para ler.
6. Adicione uma fixture real em `tests/Fixtures/<fonte>/` e testes unitários como os de `tests/Unit/Incoming`.
