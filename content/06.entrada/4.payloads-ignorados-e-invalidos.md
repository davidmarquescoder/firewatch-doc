Nem todo payload que chega vira incidente. A entrada separa dois casos, cada um com sua exception em `app/Services/Incoming`:

| | `IgnoredIncomingPayloadException` | `InvalidIncomingPayloadException` |
|---|---|---|
| Significa | "Entendi, mas não é para o FireWatch" | "Não consegui ler" |
| Quem erra | Ninguém | Quem montou o payload |
| A fonte deve reenviar? | **Não** | Não adianta: precisa corrigir o payload |
| Webhook responde | `202` com `data.ignored: true` | `422` com o motivo |
| Grava incidente? | Não | Não |

## As classes

```php [app/Services/Incoming/InvalidIncomingPayloadException.php]
class InvalidIncomingPayloadException extends InvalidArgumentException
{
    public static function missing(string $field): self
    {
        return new self("Incoming payload is missing the required field [{$field}].");
    }

    public static function invalid(string $field, string $reason): self
    {
        return new self("Incoming payload field [{$field}] is invalid: {$reason}.");
    }
}
```

```php [app/Services/Incoming/IgnoredIncomingPayloadException.php]
class IgnoredIncomingPayloadException extends InvalidIncomingPayloadException
{
    public static function because(string $reason): self
    {
        return new self("Incoming payload ignored: {$reason}.");
    }
}
```

As mensagens trazem **o nome do campo, nunca o valor**: o payload pode ter segredos ou dados pessoais, e a mensagem volta para quem chamou e vai para o log.

::warning
`IgnoredIncomingPayloadException` **estende** `InvalidIncomingPayloadException`. Ao tratar as duas, capture a de ignorado **primeiro**, como fazem os controllers. Na ordem inversa, todo evento ignorado viraria `422` e o Sentry passaria a reenviar eventos que deveriam ser descartados.
::

## Quando um payload é ignorado

| Caso | Onde | Motivo (log) |
|---|---|---|
| Nenhuma aplicação **ativa** com aquele `monitoring_identifier` | `IngestIncomingEventAction` | `no active application with monitoring identifier [x]` |
| Issue do Sentry com ação que não abre incidente (`resolved`, `assigned`, `archived`, `ignored`…) | `SentryAdapter::fromIssue()` | `Sentry issue action [resolved] does not open incidents` |

Aplicação desconhecida é **ignorada**, e não inválida, de propósito: um projeto do Sentry ligado à integração, mas sem aplicação cadastrada no FireWatch (ou com a aplicação desativada), não é erro de quem enviou. O `202` faz o Sentry parar de tentar.

Depois de registrado, um incidente ainda pode terminar como `ignored` pelas **regras de acionamento** (ambiente, severidade mínima…). Isso é outro mecanismo: o incidente existe, fica com status `ignored` e a resposta traz `data.trigger.outcome: "ignore"`, com `data.ignored: false`.

## Quando um payload é inválido

| Origem | Exemplos de mensagem |
|---|---|
| **Controller**: corpo vazio, texto, lista JSON (`[…]`) | `O corpo do webhook deve ser um objeto JSON.` (é o único `422` em português) |
| **`IncomingEvent`**: campos do contrato | `…missing the required field [application].`, `…[title].`, `…field [occurrences] is invalid: must be at least 1.`, `…field [affected_users] is invalid: must not be negative.` |
| **`SentryAdapter`** | `…missing the required field [data].`, `…field [data] is invalid: expected a Sentry event_alert, error or issue resource.`, `…[data.event.project]`, `…[data.event.title]`, `…[data.issue.project.slug]`, `…[data.issue.title]` |
| **`GenericWebhookAdapter`** | `…field [stack_trace] is invalid: must be a string or a list of frames.`, `…[severity] is invalid: expected one of debug, info, warning, error, critical.`, `…[occurred_at] is invalid: expected an ISO 8601 date or unix timestamp.`, `…[context] is invalid: must be an object.`, `…[occurrences] is invalid: must be an integer.` |
| **`SlackCommandAdapter`** | `…field [text] is invalid: expected "investigar <application> <description>".`, `…[application]`, `…[title]` |

Um `{}` (objeto vazio) passa pelo controller e cai no adapter, que reclama do primeiro campo obrigatório.

## O que cada entrada responde

### `POST /api/webhooks/{connector}`

```json
// 202: ignorado
{
  "message": "Evento recebido e ignorado.",
  "data": { "ignored": true }
}
```

```json
// 422: inválido
{
  "message": "Incoming payload is missing the required field [application]."
}
```

O ignorado também gera um `Log::info('Incoming webhook ignored')` com o `connector_id` e o motivo, útil para descobrir por que eventos de um projeto não estão aparecendo. O inválido não gera log: o `422` já diz o motivo a quem enviou.

### `POST /api/slack/commands/{connector}`

Sempre `200` (o Slack não mostra outros status), com a mensagem só para quem chamou (`ephemeral`):

| Caso | Mensagem |
|---|---|
| Ignorado (aplicação desconhecida ou inativa) | `Não encontrei uma aplicação ativa com o identificador \`x\`.` + `Aplicações disponíveis: …` |
| Inválido (faltou aplicação ou descrição) | `Faltou informação no comando.` + instruções de uso |

### Botão Simular incidente

`POST /api/v1/application/{id}/simulate-incident` passa pelo mesmo pipeline, mas o payload é montado pelo próprio FireWatch a partir da aplicação escolhida. Se a aplicação estiver **inativa**, o `SimulateIncidentAction` recusa antes de chegar ao pipeline: `422` com erro de validação no campo `application` (coberto por `SimulateIncidentApiTest`).
