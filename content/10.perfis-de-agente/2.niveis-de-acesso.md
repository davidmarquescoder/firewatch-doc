Um perfil diz o que o agente pode fazer com **três chaves independentes**. Elas são gravadas no perfil, viajam para o runner no `policy.json` e são aplicadas lá dentro pelo hook `firewatch-tool-guard` em **toda** chamada de ferramenta.

| Chave | Campo do perfil | No painel | No `policy.json` | Controla |
|---|---|---|---|---|
| Ferramentas | `allowed_tools` | **Ferramentas permitidas** | `tools` | Quais ferramentas do Claude Code o agente chama |
| Comandos | `command_access` | **Comandos permitidos** | `commands` | O que o `Bash` pode rodar |
| Arquivos | `write_access` | **Arquivos que pode alterar** | `write` | Onde `Edit`, `Write`, `MultiEdit` e `NotebookEdit` podem gravar |

As chaves se somam: uma chamada só passa se as três concordarem. Liberar `Bash` em **Ferramentas** com **Comandos** em `none` não deixa o agente rodar nada; o `Bash` aparece, mas toda chamada é recusada.

## Ferramentas

`allowed_tools` é uma lista de nomes de `AgentProfile::AVAILABLE_TOOLS`:

| Ferramenta | No painel | Marcada como arriscada |
|---|---|---|
| `Read`, `Grep`, `Glob` | Ler, buscar e listar arquivos | |
| `Bash` | Executar comandos | Sim |
| `Edit` | Editar arquivos | Sim |
| `Write` | Criar arquivos | Sim |
| `NotebookEdit` | Editar notebooks | Sim |
| `Agent` | Delegar a subagentes | |
| `TodoWrite` | Lista de tarefas | |

A lista tem dois efeitos:

1. **Vai no `agents.json`** (`tools`), então o Claude Code nem oferece ao subagente as ferramentas fora dela.
2. **Vai no `policy.json`** (`tools`), e a guarda recusa qualquer ferramenta fora dela. Isso cobre o orquestrador, que não passa pelo `agents.json`, e ferramentas que o Claude Code ofereça por fora da lista.

`null` (ou nenhuma marcada no formulário) libera **todas**, inclusive ferramentas futuras do Claude Code. O `TodoWrite` é sempre permitido pela guarda, mesmo fora da lista.

## Acesso a comandos

`AgentCommandAccessEnum`, aplicado às chamadas de `Bash`:

| Valor | No painel | Pode rodar |
|---|---|---|
| `none` | Nenhum | Nenhum comando |
| `read_only` | Somente leitura | `git log/blame/show/diff/status…`, `ls`, `cat`, `grep`, `find` sem `-exec`, `sed -n`, `php -l`, `composer show`… |
| `tests` | Leitura e testes | Leitura + o executor de testes: o `$TEST_COMMAND` da aplicação, `pest`, `phpunit`, `php artisan test`, `npm test`, `vitest`, `jest`, `pytest`… |
| `full` | Qualquer comando | Qualquer comando dentro do container, menos `git push`, `git merge` e `git pull` |

A lista completa do que conta como leitura e como teste, e como o guarda parte o comando em trechos, está em [Guarda de ferramentas](/runner/tool-guard#o-que-é-leitura). A regra geral é **recusar na dúvida**: redirecionamento para arquivo, `$(…)`, crases e quebras de linha derrubam o comando inteiro nos níveis `read_only` e `tests`.

## Acesso a arquivos

`AgentWriteAccessEnum`, aplicado a `Edit`, `Write`, `MultiEdit` e `NotebookEdit`:

| Valor | No painel | Pode alterar |
|---|---|---|
| `none` | Nenhum | Nada |
| `tests` | Só testes | Só arquivos de teste, dentro do repositório |
| `code` | Só código | Só arquivos que **não** são teste, dentro do repositório |
| `any` | Qualquer arquivo | Qualquer caminho, dentro ou fora do repositório |

"Teste" usa **a mesma regra** da verificação que o runner faz no fim ([Entrypoint](/runner/entrypoint)): pastas `tests/`, `test/`, `__tests__/`, `spec/`, `specs/` ou nomes como `*Test.php`, `test_*.py`, `*.test.ts`. Assim o Advogado do Diabo (`tests`) e o Cirurgião (`code`) nunca caem num arquivo que a verificação classifica do outro lado. Em `tests` e `code`, o caminho é resolvido com `realpath -m` e precisa ficar dentro do repositório e fora de `.git/`.

## Do perfil ao policy.json

::mermaid
---
code: |
  flowchart LR
      A[Perfil no painel] -->|toToolPolicy| B[InvestigationPromptBuilder::toolPolicy]
      B --> C[RunnerInput::policyJson]
      C --> D["/runner/input/policy.json<br/>somente leitura, dono root"]
      D --> E[entrypoint valida<br/>e gera --settings]
      E --> F[firewatch-tool-guard<br/>PreToolUse em toda chamada]
---
::

1. `AgentProfile::toToolPolicy()` devolve `name`, `tools`, `commands` e `write` do perfil.
2. `InvestigationPromptBuilder::toolPolicy()` monta `{version: 1, main, agents}`: `main` vem do orquestrador ativo; `agents` tem uma entrada por subagente ativo, pelo `slug`. Sem orquestrador, `main` recebe `{"name": "Chefe de Plantão", "tools": null, "commands": "full", "write": "any"}`.
3. `RunnerInput::policyJson()` serializa, sempre com `agents` como objeto (`{}` mesmo vazio).
4. O `DockerRunner` copia o arquivo para `/runner/input/policy.json`. A pasta é do root: o usuário `runner`, e portanto os agentes, conseguem ler a política, mas não reescrevê-la ([Isolamento](/runner/isolamento#sem-privilégios)).
5. Na etapa `agents`, o entrypoint valida a política (níveis conhecidos, `version: 1`) e sai com código 2 se ela for inválida. Depois instala o hook com `--settings`, que o `.claude/settings.json` do repositório não consegue desligar.
6. Em cada chamada, o guarda escolhe a política pelo `agent_type` (o slug do subagente) ou `main`, decide e registra cada recusa em `report.policy.denials`.

```json [policy.json (time padrão)]
{
  "version": 1,
  "main": { "name": "Chefe de Plantão", "tools": null, "commands": "full", "write": "any" },
  "agents": {
    "sentinela": { "name": "Sentinela", "tools": ["Read", "Grep", "Glob"], "commands": "none", "write": "none" },
    "detetive": { "name": "Detetive", "tools": ["Read", "Grep", "Glob", "Bash"], "commands": "read_only", "write": "none" },
    "advogado-do-diabo": { "name": "Advogado do Diabo", "tools": ["Read", "Grep", "Glob", "Bash", "Edit", "Write"], "commands": "tests", "write": "tests" },
    "cirurgiao": { "name": "Cirurgião", "tools": ["Read", "Grep", "Glob", "Bash", "Edit", "Write"], "commands": "tests", "write": "code" },
    "escrivao": { "name": "Escrivão", "tools": ["Read", "Grep", "Glob"], "commands": "none", "write": "none" }
  }
}
```

O `name` está ali para a mensagem de recusa, que volta ao agente como erro da ferramenta: "Firewatch: Detetive (detetive) não pode criar nem alterar arquivos."

## O orquestrador também fica sabendo

As mesmas permissões aparecem para o orquestrador nas colunas **Ferramentas**, **Comandos** e **Arquivos** da tabela do time ([Papéis e times](/perfis-de-agente#do-perfil-ao-time-da-execução)), com os rótulos curtos de `shortLabel()` ("só leitura", "leitura e testes", "só testes", "só código"…). O prompt dele manda delegar cada etapa a quem tem a permissão certa e, se um subagente relatar uma recusa do Firewatch, **não tentar contornar**.

Isso evita desperdício: sem a tabela, o orquestrador poderia pedir ao Detetive para escrever o teste, ver a chamada recusada e gastar uma rodada à toa.

## Combinações e cuidados

| Combinação | Efeito |
|---|---|
| `Bash` sem nível de comando (`none`) | A ferramenta existe, mas toda chamada é recusada |
| Nível de comando sem `Bash` nas ferramentas | O nível não tem efeito |
| `Edit`/`Write` com `write: none` | Toda escrita recusada |
| `commands: full` com `write` restrito | **O `write` vira decorativo**: o agente escreve qualquer arquivo pelo shell (`echo > x`, `sed -i`). No time padrão, só o orquestrador tem `full` |
| `commands: tests` com `write: code` (Cirurgião) | O agente pode, em tese, rodar código que acabou de escrever por dentro da suíte. Continua contido pelo container e pela rede restrita |
| `allowed_tools: null` num subagente | Todas as ferramentas, mas `commands` e `write` continuam valendo |

::warning
Os padrões de um perfil novo são `none`/`none`. Um agente criado pelo painel para corrigir código só consegue trabalhar depois que alguém escolher **Comandos permitidos** e **Arquivos que pode alterar**.
::

### Perfis criados antes dos níveis

A migration `2026_11_10_140000_add_access_to_agent_profiles_table` criou `command_access` e `write_access` com padrão `none` e, para o time continuar funcionando, preencheu os perfis existentes **pelo papel**:

| Papel | Comandos | Arquivos |
|---|---|---|
| `orchestrator` | `full` | `any` |
| `investigator` | `read_only` | `none` |
| `tester` | `tests` | `tests` |
| `fixer` | `tests` | `code` |
| `triage`, `writer` | `none` (padrão) | `none` (padrão) |

Depois disso, o papel e os níveis são independentes: mudar o papel de um perfil **não** muda os níveis dele.

## O que a guarda não cobre

Os níveis restringem **chamadas de ferramenta**. Eles não limitam leitura (`Read`, `Grep` e `Glob` leem qualquer arquivo que o usuário `runner` consiga ler) e não são um sandbox: a análise de comandos é sintática. A contenção de fundo continua sendo o container sem privilégios e a rede restrita. Detalhes em [Guarda de ferramentas](/runner/tool-guard#limitações-conhecidas).
