O stdout do runner é **NDJSON**: um objeto JSON por linha, e nada mais. A referência completa, com exemplos tirados de execuções reais, é o `docker/runner/EVENTS.md`. Esta página resume o contrato. Como o Laravel consome cada linha está em [Streaming](/investigacao/streaming).

## Duas fontes num só stream

O campo `type` separa as fontes:

| `type` | Fonte |
|---|---|
| `runner` | O próprio `firewatch-run`: etapas, falhas e o relatório final |
| `system`, `assistant`, `user`, `result` | O Claude Code (`--output-format stream-json --verbose --forward-subagent-text`), repassado sem alteração |

## Eventos do runner

Todos têm o mesmo formato, mais campos específicos da etapa:

```json
{"type":"runner","stage":"clone","status":"completed","message":"Repositório clonado","timestamp":"2026-11-09T21:26:05.066Z","head":"734ac4a…"}
```

| Campo | Conteúdo |
|---|---|
| `stage` | `setup`, `clone`, `install`, `agents`, `claude`, `flow`, `verify`, `result`, `finished` ou `report` |
| `status` | `started`, `completed`, `skipped` ou `failed`. No `report`, o status final |
| `message` | Texto em português, pronto para a timeline |
| `timestamp` | UTC, ISO 8601 com milissegundos |

| stage | Status possíveis | Campos extras |
|---|---|---|
| `setup` | started, completed, failed | `base_branch`, `work_branch` e `limits` no `completed` |
| `clone` | started, completed, failed | `head` (SHA da base) no `completed` |
| `install` | started, completed, skipped, failed | `command` no `started` |
| `agents` | completed, failed | `count`, `agents` (slugs) e `policy_enforced` |
| `claude` | started, completed, skipped, failed | `model` e `timeout_seconds` no `started`. `skipped` no dry run |
| `flow` | started, completed, skipped, failed | Dois `started`: o início e a reprodução sem a correção (com `command`). `completed`: `test_files`, `code_files`, `warnings`, `reproduction` |
| `verify` | started, completed, skipped, failed | `command` no `started` |
| `result` | failed | Só aparece em falha (código 7) |
| `finished` | completed | `work_branch`, `changed_files` (quantidade) e `tests`. No dry run, só a mensagem |
| `report` | `fixed`, `failed` ou `dry_run` | `report`: o relatório inteiro |

Uma falha em qualquer etapa sai com `status: "failed"` e `exit_code`, e logo depois vem o `report`:

```json
{"type":"runner","stage":"setup","status":"failed","message":"Nenhuma credencial do Claude: defina ANTHROPIC_API_KEY ou CLAUDE_CODE_OAUTH_TOKEN","timestamp":"…","exit_code":2}
```

```
sucesso: … verify/completed → finished/completed → report (fixed)
falha:   … <etapa>/failed (exit_code)          → report (failed)
dry run: … claude/skipped   → finished/completed → report (dry_run)
```

::warning
O `report` só **não** sai quando o container é morto de fora: o `docker kill` do `hardTimeout()` do Laravel ou o OOM killer. Nesses casos o Laravel trata como "container sem relatório" e usa o código de saída (`timeout`, `out_of_memory` ou `runner_error`).
::

## Eventos do Claude Code

O runner não mexe neles. Os que importam para o FireWatch:

| Evento | O que traz |
|---|---|
| `system` / `init` | `session_id`, `model`, `claude_code_version`, `tools` e `agents` (confirma que os subagentes chegaram). Pode aparecer mais de uma vez |
| `system` / `thinking_tokens` | Só progresso: o texto do raciocínio não é exposto |
| `assistant` | **Um** bloco por evento: `text`, `thinking` (vazio, só com `signature`) ou `tool_use` (`id`, `name`, `input`). Erros de API chegam com `model: "<synthetic>"` e o campo `error` |
| `user` | `tool_result` com `tool_use_id`, `content` e `is_error`. Pode ser grande e ter dados sensíveis lidos do repositório |
| `system` / `task_started`, `task_progress`, `task_updated`, `task_notification`, `background_tasks_changed` | Ciclo de vida dos subagentes. A resposta do subagente vem no `task_notification` (`status`, `summary`) |
| `result` | Fim de **um turno**: `is_error`, `result`, `total_cost_usd`, `usage`, `num_turns`, `terminal_reason`, `api_error_status`, `subagent_stats` |

`assistant` e `user` têm `parent_tool_use_id`: `null` é a sessão principal (o Chefe de Plantão), e um `toolu_…` aponta para o `tool_use` `Agent` que iniciou o subagente. É assim que o Laravel descobre qual agente fez cada coisa.

Pegadinhas observadas na 2.1.321:

- Erro de autenticação vem com `subtype: "success"` e `is_error: true`. **`is_error` é a fonte da verdade**, nunca o `subtype`.
- Com subagentes em segundo plano há vários `init` e vários `result`. O último `result` é o final. `total_cost_usd` é acumulado da sessão (não some), e `usage` é só do turno (some).
- O turno que roda depois de um subagente pode não entrar no `total_cost_usd`: o custo pode vir um pouco abaixo do real.
- Um `result` não significa que acabou. O fim é o evento `report` **e** o processo terminar.

## O report.json

O relatório junta o que o **agente** escreveu com o que o **runner mediu**. Quando os dois divergem, vale a medição: se o agente diz `full_suite_passed: true` e a suíte falhou na `verify`, `tests.status` é `failed`.

| Campo | Fonte | Conteúdo |
|---|---|---|
| `schema_version` | runner | `1` |
| `status` | runner | `fixed`, `failed` ou `dry_run` |
| `exit_code` | runner | O mesmo código de saída do processo |
| `failure` | runner | `{stage, reason, exit_code}` quando `failed`, senão `null` |
| `summary`, `root_cause`, `fix` | agente | Texto |
| `risk` | agente | `{level, reason}` |
| `pull_request` | agente | `{title, description}` em Markdown |
| `changes` | runner | `files[]` (`path`, `status` `added`/`modified`/`deleted`/`type_changed`, `additions`, `deletions`, `binary`), `files_count`, `additions`, `deletions`, `diff`, `diff_bytes`, `diff_truncated` |
| `flow` | runner | `status` (`passed`, `failed`, `skipped`, `not_run`), `test_files`, `code_files`, `violations`, `warnings`, `reproduction` (`{status, command, exit_code, output_tail}`) |
| `policy` | runner | `enforced` e `denials[]` (`{agent, tool, input, reason, timestamp}`) |
| `tests` | runner + agente | `command`, `status` (`passed`, `failed`, `timeout`, `skipped`, `not_run`), `exit_code`, `counts`, `summary_line`, `output_tail` (80 linhas, sem cores), `test_added` e `agent_claims` (`failed_before_fix`, `full_suite_passed`) |
| `git` | runner | `repository`, `base_branch`, `base_commit`, `work_branch` |
| `claude` | runner, do stream | `session_id`, `model`, `claude_code_version`, `is_error`, `error`, `api_error_status`, `num_turns`, `duration_ms`, `cost_usd`, `tokens` (`input` com cache, `output`), `subagents`, `final_message`. `null` se o Claude Code não rodou |
| `limits` | runner, do cgroup | `memory_bytes`, `cpus`, `pids`, `timeouts_seconds`, `network` (os proxies). `null` = sem limite |
| `timing` | runner | `started_at`, `finished_at`, `duration_seconds` |
| `agent_report` | agente | O `agent-report.json` como veio |

Detalhes da coleta:

- **`changes`** usa um índice temporário do git, então entram os arquivos novos, mas não os ignorados pelo `.gitignore` nem os criados pela instalação (que foram para `.git/info/exclude`). O diff é contra o `BASE_COMMIT` e é cortado em `DIFF_MAX_BYTES` (1 MB).
- **`tests.counts`** vem da linha de resumo: `Tests: …` (PHPUnit, Pest, Jest, Vitest) ou `==== 1 failed, 2 passed in 0.12s ====` (pytest). Exemplo: `{"failed": 1, "passed": 6, "assertions": 7}`.
- **`claude.tokens.input`** soma `input_tokens`, `cache_creation_input_tokens` e `cache_read_input_tokens` de todos os `result`. `cost_usd` é o `total_cost_usd` do último.
- **`limits`** é lido de `/sys/fs/cgroup` (cgroup v2): mostra o limite que o container **recebeu**, não o que foi pedido.

Exemplo encurtado de uma falha na verificação:

```json
{
  "schema_version": 1,
  "status": "failed",
  "exit_code": 6,
  "failure": {"stage": "verify", "reason": "Suíte de testes falhou após a execução do agente (código 1)", "exit_code": 6},
  "tests": {
    "status": "failed", "exit_code": 1,
    "counts": {"failed": 1, "passed": 6, "assertions": 7},
    "agent_claims": {"failed_before_fix": true, "full_suite_passed": true}
  },
  "git": {"base_branch": "main", "work_branch": "firewatch/test-break_tests", "…": "…"},
  "…": "…"
}
```

O que o Laravel faz com o relatório, incluindo o `FailureClassifier`, está em [Resultado e falhas](/investigacao/resultado-e-falhas).

## Regras para quem consome

1. Ler o stdout **linha a linha, sem limite de tamanho**: um `tool_result` pode ter centenas de KB.
2. Uma linha que não é JSON é registrada e ignorada, sem derrubar a leitura.
3. Campos desconhecidos são ignorados: o Claude Code acrescenta campos entre versões.
4. Mascarar `tool_result` e `tool_use_result` antes de gravar ou fazer broadcast.
5. O resultado vem do **código de saída** e do evento `report`.
