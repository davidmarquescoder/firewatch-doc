O runner precisa de rede para **duas** coisas bem diferentes: baixar o repositório e as dependências, e falar com a API do Claude. Os agentes só precisam da segunda. O FireWatch separa as duas fases com um proxy de saída que libera domínios diferentes em cada porta.

```
runner ──(firewatch-runner-net, internal: sem internet)──► firewatch-runner-egress ──► internet
                                                          :3128 setup  → allowlist-setup.txt
                                                          :3129 agent  → allowlist-agent.txt
```

## A rede interna

No `docker-compose.yml`:

```yaml [docker-compose.yml]
networks:
    runner_network:
        name: firewatch-runner-net
        driver: bridge
        internal: true
```

Uma rede `internal` não tem rota nem DNS para fora. Um container ligado só a ela alcança apenas os outros containers da mesma rede. O único deles é o `runner-egress`, que está **também** na `public_network` e por isso consegue sair.

## O proxy: runner-egress

| | |
|---|---|
| Serviço | `runner-egress` (container `firewatch-runner-egress`, imagem `firewatch-runner-egress:latest`) |
| Build | `docker/runner/egress/Dockerfile`: `debian:bookworm-slim` + `squid-openssl` |
| Usuário | `proxy` desde o início. As portas são acima de 1024, então não precisa de root, e o Squid não troca de usuário |
| Processo | `squid -N` em primeiro plano, como PID 1 |
| Allowlists | Montadas de `docker/runner/egress/` como somente leitura |
| Redes | `public_network` e `runner_network` |

O `squid.conf`:

```txt [docker/runner/egress/squid.conf]
http_port 3128 name=setup
http_port 3129 name=agent

acl port_setup myportname setup
acl port_agent myportname agent
acl allow_setup dstdomain "/etc/squid/allowlist-setup.txt"
acl allow_agent dstdomain "/etc/squid/allowlist-agent.txt"

http_access deny !Safe_ports          # só 80 e 443
http_access deny CONNECT !SSL_ports   # túnel só para 443
http_access allow port_agent allow_agent
http_access allow port_setup allow_setup
http_access deny all

cache deny all
forwarded_for delete
via off
httpd_suppress_version_string on
```

| Escolha | Por quê |
|---|---|
| Uma porta por fase, com `myportname` | A mesma instância serve as duas fases com regras diferentes. A porta decide a allowlist |
| `dstdomain` | Filtra pelo nome do destino. No HTTPS, o Squid só vê o `CONNECT host:443` e cria o túnel: **não** abre o TLS |
| Só 80 e 443, `CONNECT` só para 443 | Nada de túnel para SSH, bancos ou portas arbitrárias |
| `cache deny all` | O proxy só filtra. Um cache compartilhado entre execuções poderia vazar dados de um repositório para outro |
| `forwarded_for delete`, `via off`, sem versão | Não expõe o IP interno do runner nem a versão do Squid |

## As allowlists

Um domínio por linha. Começar com ponto (`.github.com`) libera o domínio e todos os subdomínios.

### Setup (porta 3128): clone e instalação

```txt [docker/runner/egress/allowlist-setup.txt]
# Repositórios git
.bitbucket.org
.github.com
.githubusercontent.com

# PHP / Composer (dists vêm de api.github.com / codeload.github.com)
.packagist.org

# Node (npm, yarn, pnpm)
registry.npmjs.org
registry.yarnpkg.com

# Python (pip)
pypi.org
files.pythonhosted.org
```

| Domínio | Por quê |
|---|---|
| `.bitbucket.org`, `.github.com` | Clonar o repositório da aplicação |
| `.github.com`, `.githubusercontent.com` | O Composer baixa os pacotes (dists) de `api.github.com` e `codeload.github.com` |
| `.packagist.org` | Metadados do Composer |
| `registry.npmjs.org`, `registry.yarnpkg.com` | npm, Yarn e pnpm |
| `pypi.org`, `files.pythonhosted.org` | pip: índice e arquivos |

### Agent (porta 3129): Claude Code e testes

```txt [docker/runner/egress/allowlist-agent.txt]
api.anthropic.com
```

**Só a API da Anthropic.** Nessa fase:

- os agentes não baixam pacotes, não instalam ferramentas e não acessam sites, nem os que a fase de setup liberava;
- um dado lido do repositório (um `.env`, um segredo de teste) não tem para onde ir, a não ser a própria API do Claude;
- os testes da aplicação rodam **sem rede externa**. Uma suíte que depende de serviços de fora falha aqui, e é melhor descobrir isso no dry run.

A porta de agent **não herda** a lista de setup. Ela é uma lista separada de propósito.

## Como o runner usa as portas

O entrypoint troca de proxy entre as fases com `use_proxy`, que exporta `HTTPS_PROXY`, `HTTP_PROXY` (e as versões minúsculas) e `NO_PROXY=localhost,127.0.0.1,::1`:

| Momento | Proxy |
|---|---|
| Do `clone` até a etapa `agents` (clone e instalação) | `FIREWATCH_SETUP_PROXY` (`http://firewatch-runner-egress:3128`) |
| Etapa `claude` em diante: Claude Code, fluxo obrigatório e `verify` | `FIREWATCH_AGENT_PROXY` (`http://firewatch-runner-egress:3129`) |

Git, Composer, npm, pip e o Claude Code respeitam essas variáveis. Um programa que as ignora tenta sair direto e falha, porque a rede não tem rota.

## Modos de rede

| `RUNNER_NETWORK` (launch.sh) / `FIREWATCH_RUNNER_NETWORK` (Laravel) | Rede | Proxies |
|---|---|---|
| `restricted` (padrão) | `firewatch-runner-net` | As duas portas |
| `none` | `--network none` | Nenhum. Só serve com repositório e dependências já na imagem |
| `open` | bridge padrão do Docker | Nenhum: internet aberta. **Só para depuração** |

## Editar as allowlists

As listas são montadas, não copiadas para a imagem. Não precisa de rebuild:

```bash
docker compose restart runner-egress
```

Para ver o que foi liberado (`TCP_TUNNEL`) e negado (`TCP_DENIED`), com a porta de cada pedido (formato `firewatch` do `squid.conf`: data, IP do runner, porta, método, destino, status HTTP e resultado):

```bash
docker logs firewatch-runner-egress
```

```txt [exemplo]
2026-11-09T21:26:01 runner=172.30.0.5 porta=3128 CONNECT bitbucket.org:443 200 TCP_TUNNEL
2026-11-09T21:31:12 runner=172.30.0.5 porta=3129 CONNECT repo.packagist.org:443 403 TCP_DENIED
```

Uma instalação que falha com 403 no log é um domínio faltando na lista de setup. Adicionar um domínio na lista de **agent** é uma decisão de segurança: amplia o que um agente consegue alcançar.

## Limitações conhecidas

- **As duas portas estão na mesma rede.** Um agente que redefinir `HTTPS_PROXY` na mão consegue usar a porta de setup. Mesmo assim, ele fica preso à allowlist de setup (git e registries), nunca à internet aberta.
- **Repositórios por SSH (`git@…`) não funcionam** na rede restrita: o proxy é HTTP. Use a URL HTTPS.
- **O filtro é por domínio**, não por caminho: liberar `.github.com` libera qualquer repositório público do GitHub na fase de setup.
- **Sem limite de banda** nem de volume por execução.
