O Firewatch não tem monitoramento externo configurado: nenhum serviço consulta o health check, os logs ficam em arquivo e os workers não avisam quando param. O que existe são as peças abaixo, que se consultam na mão ou se ligam a uma ferramenta de monitoramento.

| Pergunta | Onde olhar |
|---|---|
| A API está de pé? | [Health check](#health-check) |
| Os serviços estão rodando? | `docker compose ps` |
| As filas estão andando? | [Filas](#filas): `queue:monitor`, `queue:failed`, o Horizon |
| Algum incidente está parado? | O painel e o [watchdog](/filas-agendamentos-e-comandos/agendamentos) |
| O que deu errado? | [Logs](#logs): o `laravel.log` e os logs de cada container |
| Quanto já se gastou? | Tela **Custos e limites** ([Budget](/conectores-aplicacoes-budget-e-metricas/budget)) |

## Health check

O back-end tem duas rotas públicas de saúde ([Health check](/referencia-da-api/health-check)):

```bash
curl -s http://localhost:8000/api/health-check
curl -s -H 'Accept: application/json' http://localhost:8000/up
```

| Rota | Resposta | Em manutenção (`artisan down`) |
|---|---|---|
| `/api/health-check` | `{"status":"success","message":"API is running"}` | `503` |
| `/up` | `{"status":"up"}` | `200` |

::warning
As duas só provam que o **PHP responde**. Nenhuma consulta banco, Redis, filas, Reverb ou Docker: com o MySQL fora do ar, ambas continuam respondendo `200`. Um monitor externo apontado para elas não pega a maior parte das falhas que param as investigações.
::

Para cobrir o resto, use as checagens abaixo, ou registre um listener do evento `DiagnosingHealth` que consulte banco e Redis: com ele, o `/up` passa a responder `500` quando algum dos dois cai.

### Checagem rápida

```bash
docker compose ps
docker compose exec app php artisan queue:monitor redis:default,investigations:investigations
docker compose exec app php artisan queue:failed
docker ps --filter label=br.com.firewatch.runner=1
```

| Comando | Saudável |
|---|---|
| `docker compose ps` | `app`, `nginx`, `db`, `redis`, `queue`, `runner-worker`, `reverb`, `scheduler` e `runner-egress` como `Up` |
| `queue:monitor` | Poucos jobs pendentes. Na fila `investigations`, jobs pendentes ou atrasados são normais quando todas as vagas estão ocupadas: quem espera volta a cada 30 s |
| `queue:failed` | Nada novo. Cada linha é um job que esgotou as tentativas |
| `docker ps --filter label=…` | No máximo `FIREWATCH_RUNNER_MAX_CONCURRENT` containers, nenhum com mais de 1 hora |

## Filas

As duas filas e seus workers estão em [Filas e Horizon](/filas-agendamentos-e-comandos). Para monitorar:

- **`queue:monitor`** mostra, por fila, os jobs pendentes, atrasados e reservados, e a idade do mais antigo. Com `--max=N`, dispara o evento `QueueBusy` quando a fila passa de N jobs; o Firewatch ainda não escuta esse evento.
- **`queue:failed`** lista a tabela `failed_jobs`. Um `InvestigateIncident` ali não precisa de ação: o método `failed()` já fechou o incidente e avisou o time. Não use `queue:retry` para ele ([Jobs com falha](/filas-agendamentos-e-comandos#jobs-com-falha)).
- **O Horizon** (`/horizon`) está instalado, mas nenhum serviço roda `php artisan horizon`. Com os `queue:listen` de hoje, ele mostra pouco: métricas e jobs concluídos só aparecem para os jobs que os supervisores dele processam. Os passos para ligá-lo estão em [Antes de usar o Horizon de verdade](/filas-agendamentos-e-comandos#antes-de-usar-o-horizon-de-verdade).

## Logs

O Firewatch tem dois tipos de log: o do **Laravel**, em arquivo, e a **saída de cada container**, no Docker.

### O log do Laravel

| | |
|---|---|
| Arquivo | `storage/logs/laravel.log` |
| Canal | `stack` → `single` (`LOG_CHANNEL`, `LOG_STACK`): um arquivo só, **sem rotação** |
| Nível | `LOG_LEVEL=debug` |
| Quem escreve | Todos os serviços Laravel (`app`, `queue`, `runner-worker`, `reverb`, `scheduler`), que montam o mesmo `storage/` |

```bash
tail -f storage/logs/laravel.log
```

::warning
**O arquivo só cresce.** O canal `single` nunca apaga nada, e no ambiente local o `laravel.log` passou de **460 MB** em dez dias. Para um servidor, use `LOG_STACK=daily` (um arquivo por dia, `LOG_DAILY_DAYS`, padrão 14) ou `LOG_CHANNEL=stderr`, que manda o log para a saída do container e deixa a rotação com o Docker.
::

Duas fontes de ruído encheram o arquivo local, ambas já corrigidas:

- **Os testes escreviam nele.** Até 19/11/2026, o `phpunit.xml` não trocava o canal de log, e `php artisan test` dentro do container gravava as linhas `testing.*` no mesmo arquivo. Hoje os testes usam `LOG_CHANNEL=null`.
- **Redis fora do ar.** Quase todo o volume local (mais de 38 mil linhas) é `php_network_getaddresses: getaddrinfo for redis failed`, cada uma com o stack trace inteiro. Até 19/11/2026, o serviço `redis` era o único do compose sem `restart: unless-stopped`: quando a máquina ligava, o Docker subia os workers e não o Redis. Veja [Troubleshooting](/operacao/troubleshooting#workers-sem-redis).

### O que o Firewatch registra

Além das exceções não tratadas, o código grava estas linhas (todas em inglês, com o contexto em JSON):

| Nível | Mensagem | Quem | Quando |
|---|---|---|---|
| `warning` | `Incoming webhook rejected` | `VerifyIncomingWebhook` | Assinatura ou token recusados. O `reason` diz o motivo; o `ip`, de onde veio |
| `info` | `Incoming webhook ignored` | `WebhookController` | Payload válido, mas que não abre incidente (ex.: issue do Sentry resolvida) |
| `info` | `InvestigateIncident skipped: incident is not queued` | `InvestigateIncident` | O job chegou e o incidente já não estava na fila (reentrega ou reexecução) |
| `error` | `InvestigateIncident failed` | `InvestigateIncident::failed()` | O job caiu com exceção ou estourou o tempo. Vem com a exceção inteira |
| `warning` | `Runner container exceeded the hard timeout; killing it` | `DockerRunner` | O container passou do `hardTimeout()` e foi morto |
| `warning` | `Runner emitted a non-JSON stdout line` | `RunnerStreamMonitor` | Linha do runner que não é JSON: ignorada |
| `error` | `Could not record agent event` | `RunnerStreamMonitor` | Um evento da timeline não pôde ser gravado nem depois de reler a posição. A investigação continua |
| `warning` | `Stale incident marked as failed` | Watchdog | Incidente parado fechado como `stale` |
| `warning` | `DeliverIncidentOutcome skipped: run is not finished` | `DeliverIncidentOutcome` | Entrega chamada para um run ainda aberto |
| `warning` | `Pull request not opened: incident is not in testing` | `DeliverIncidentOutcome` | Run `fixed`, mas o incidente mudou de status antes do PR |
| `error` | `Could not record delivery event` / `Could not record issue tracker event` | Entrega e abertura do card | A integração rodou, mas o evento da timeline não foi gravado |
| `warning` | `Realtime broadcast failed` | `RealtimeBroadcaster` | O Reverb não recebeu um evento. O dado está no banco; só o ao vivo falhou |
| `warning` | `Connector connection test crashed` | Testar conexão | O teste de um conector lançou exceção inesperada |
| `error` | (exceção) | `report($e)` | Falhas capturadas na abertura do PR, nos notifiers, no Jira, no alerta de budget e no fechamento do run |

Nenhuma dessas linhas leva credenciais: os motivos de recusa de webhook nunca incluem a assinatura, e as mensagens dos providers já chegam sem tokens ([Mascaramento](/seguranca/mascaramento)).

### Os logs dos containers

```bash
docker compose logs -f runner-worker
docker compose logs --since 1h queue scheduler
```

| Serviço | O que aparece |
|---|---|
| `runner-worker`, `queue` | Uma linha por job: `RUNNING`, `DONE` ou `FAIL`, com a duração |
| `scheduler` | Cada execução do watchdog e da limpeza da auditoria |
| `reverb` | Conexões e erros do WebSocket |
| `nginx` | Acessos e erros HTTP |
| `runner-egress` | Os acessos do Squid: o que os runners pediram e o que foi negado ([Egress](/runner/egress)) |

### E os logs do runner?

O container `firewatch-run-*` é **apagado** ao fim de cada execução (`docker rm --force`, num `finally`), junto com a pasta de entrada em `storage/app/private/runner/`. O que fica de uma investigação:

| Onde | O quê |
|---|---|
| A timeline do incidente (`agent_events`) | Cada etapa do runner e cada ação dos agentes |
| `agent_runs.report` | O relatório final, com `failure`, `tests.output_tail` e `flow.reproduction.output_tail` |
| `status_reason` do incidente | O motivo da falha, em português |

A saída de erro do runner (git, instalação, testes) é guardada só em memória, as últimas 40 linhas, e usada para o motivo quando o container sai **sem relatório**. Para ver a saída inteira de um caso difícil, rode o mesmo incidente no terminal com o `run-local.sh`, que grava `stderr.log` e `stream.ndjson` em `docker/runner/runs/` ([Testes do runner](/runner/testes)).

## No painel

O próprio painel serve de monitor do que importa para o time:

- **Visão geral**: o que está acontecendo agora, quanto tempo um erro leva até virar PR e com que frequência os agentes acertam ([Métricas](/conectores-aplicacoes-budget-e-metricas/metricas)).
- **Incidentes**: o status e o `status_reason` de cada um. "Aguardando um runner livre…" é espera por vaga; um incidente em **Na fila** há muito tempo indica o `runner-worker` parado.
- **Custos e limites**: o gasto do mês contra o teto. Os alertas de 80% e 100% chegam pelo Slack.
- **Auditoria**: quem mudou o quê, inclusive cada alerta de budget enviado.

## O que falta para monitorar de verdade

| Lacuna | Sugestão |
|---|---|
| Health check não vê banco nem Redis | Listener de `DiagnosingHealth` consultando os dois |
| Ninguém consulta o health check | Um monitor externo (uptime) no `/up` |
| Log sem rotação | `LOG_STACK=daily` ou `LOG_CHANNEL=stderr` |
| Ninguém é avisado se um worker parar | O watchdog fecha os incidentes depois de 3 h, mas só então alguém percebe. Alertar com `queue:monitor --max` ou pelo Horizon (que tem notificações prontas, hoje comentadas no provider) |
| Erros do próprio Firewatch não vão para nenhuma ferramenta | O Firewatch recebe erros do Sentry das aplicações, mas não manda os seus. Um canal de log `slack` (`LOG_SLACK_WEBHOOK_URL`, nível `critical`) já está no `config/logging.php` |
