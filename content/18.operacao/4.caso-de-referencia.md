O **incidente-001** é o caso que validou o runner de ponta a ponta, em **9/11/2026**: um erro real plantado no repositório cobaia, corrigido pelo Claude em cerca de **1 minuto** e **US$ 0,21**, seguindo o fluxo obrigatório. Desde então ele é a regressão do projeto: os testes do runner reaplicam a correção dele, e a demo da tela ao vivo reproduz a gravação dele.

Os arquivos ficam em `firewatch-back/docker/runner/`:

| Arquivo | O que é |
|---|---|
| `examples/incident-001/prompt.md` | O incidente, como os agentes o recebem |
| `examples/incident-001/system-prompt.md` | As regras do plantão: o fluxo obrigatório e o formato do relatório |
| `examples/incident-001/replay.ndjson` | A gravação para a demo, usada pelo `firewatch:replay-run` |
| `test/fixtures/incident-001.patch` | O diff da correção real |
| `test/fixtures/incident-001.agent-report.json` | O relatório que o Claude escreveu na execução real |

## O repositório cobaia

| | |
|---|---|
| Repositório | `firewatch/flowstock-back` no Bitbucket |
| Aplicação | FlowStock, uma API Laravel 13 |
| Branch base | `main` |
| Testes | PHPUnit, banco SQLite em memória |
| Acesso | Repository Access Token (`ATCTT…`), usuário `x-token-auth` |

É um repositório de testes: os bugs são plantados de propósito para o Firewatch encontrar. Use **sempre** ele, nunca um repositório de produção, para qualquer execução real.

## O erro

Usuários recém-criados pelo cadastro de empresa ainda não têm nenhum papel (*role*). Para eles, **todas** as rotas autenticadas de `/api/v1` respondem `500`:

```text
ErrorException: Attempt to read property "name" on null
#0 app/Http/Middleware/EnsureCompanyIsActive.php(28): ...
```

O `prompt.md` traz o que uma ferramenta de monitoramento mandaria: severidade alta, 37 ocorrências em 2 horas, 4 usuários afetados, as rotas, o stack trace, o contexto da requisição com os dados pessoais já mascarados (`***@***.com.br`, `Bearer ***`) e a observação do suporte de que só os usuários sem papel são afetados.

## A causa raiz

O middleware `EnsureCompanyIsActive` decide se o usuário é `developer` lendo o nome do primeiro papel, em duas linhas:

```php [app/Http/Middleware/EnsureCompanyIsActive.php]
if ($user->roles->first()->name !== 'developer' && !$company) {
    // 403: nenhuma empresa vinculada
}

if ($user->roles->first()->name !== 'developer' && !$company->active) {
    // 403: empresa desativada
}
```

Sem papel, `roles->first()` devolve `null`, e ler `->name` de `null` lança a exceção antes de qualquer resposta.

## O que foi entregue

### O teste que reproduz o bug

`tests/Unit/Http/Middleware/EnsureCompanyIsActiveTest.php`, com quatro casos:

| Teste | Antes da correção | Depois |
|---|---|---|
| Usuário sem papel e empresa ativa passa | Falha (`ErrorException`) | Passa |
| Usuário sem papel e sem empresa recebe `403` | Falha | Passa |
| Usuário sem papel e empresa desativada recebe `403` | Falha | Passa |
| Developer sem empresa passa | Passa | Passa |

Os três que falham antes da correção falham **pelo motivo certo**: o mesmo erro de produção, na mesma linha. O quarto protege o comportamento que já funcionava.

### A correção

Dois caracteres em cada uma das duas linhas: o operador nullsafe.

```diff [incident-001.patch]
-        if ($user->roles->first()->name !== 'developer' && !$company) {
+        if ($user->roles->first()?->name !== 'developer' && !$company) {
 ...
-        if ($user->roles->first()->name !== 'developer' && !$company->active) {
+        if ($user->roles->first()?->name !== 'developer' && !$company->active) {
```

Sem papel, a comparação vira `null !== 'developer'`: o usuário é tratado como não-developer e passa pelas mesmas checagens de empresa que os outros. Para quem tem papel, nada muda.

### O relatório

O relatório dos agentes (`incident-001.agent-report.json`) traz o que o Firewatch usa no PR, no Slack e no Jira:

| Campo | Valor |
|---|---|
| `status` | `fixed` |
| `files_changed` | O middleware e o teste novo |
| `test_failed_before_fix` / `full_suite_passed` | `true` / `true` |
| `risk` | `low`: "A mudança são dois caracteres em duas linhas e só afeta o caso em que antes o código quebrava…" |
| `pr_title` | "Corrige erro 500 no EnsureCompanyIsActive para usuários sem papel" |
| `pr_description` | O que quebrou, causa raiz, correção e teste adicionado |

O runner não confia nessas afirmações: depois dos agentes, ele mesmo roda o teste novo **sem** a correção (e confirma que falha) e a suíte completa **com** ela ([Eventos e relatório](/runner/eventos-e-relatorio)).

## Como a execução foi feita

A validação de 9/11 rodou o runner **no terminal**, com o `run-local.sh`, antes de o Laravel orquestrar as investigações:

```bash
docker/runner/run-local.sh docker/runner/examples/incident-001
```

| Etapa | O que aconteceu |
|---|---|
| Configuração | `runner.env` com a credencial do Claude, a URL do cobaia, o token e `BASE_BRANCH=main` |
| Clone e instalação | O runner clonou o `main` e rodou `composer install` |
| Claude Code | Um agente só, seguindo as 7 etapas do `system-prompt.md`. A pasta do exemplo não tem `agents.json`, então o `run-local.sh` roda sem os subagentes do time |
| Resultado | Código de saída `0`, relatório `fixed`, a correção na branch local em `docker/runner/runs/<data>-incident-001/workspace/repo` |

Pelo terminal, **nada sai do container**: o runner não faz push (isso é papel do Laravel), e não há PR, Slack nem Jira. A pasta `runs/` fica fora do git, por isso a gravação bruta dessa execução não está no repositório; o que ficou foi o patch e o relatório em `test/fixtures/`.

## A gravação da demo

O `replay.ndjson` foi **montado** a partir do caso real para ensaiar a demo: as mesmas descobertas, o mesmo teste, a mesma correção e o mesmo relatório, distribuídos entre os agentes do time e com horários espaçados para a tela ao vivo.

| Momento | Quem | O que a timeline mostra |
|---|---|---|
| 0 s | Runner | Configuração, clone do `main`, instalação |
| 12 s | Chefe de Plantão | Recebe o incidente e chama a Sentinela |
| 14 s | Sentinela | Acha o ponto de falha em `EnsureCompanyIsActive.php:28` |
| 26 s | Detetive | `git log`, `git blame` e a relação `roles`: causa raiz provada |
| 43 s | Advogado do Diabo | Escreve o teste e o roda: 3 falhas, 1 passa |
| 58 s | Cirurgião | Aplica o nullsafe nas duas linhas |
| 71 s | Advogado do Diabo | Teste novo e suíte passando |
| 91 s | Escrivão | Redige o PR (risco baixo) |
| 107 s | Runner | Fluxo obrigatório comprovado: o teste falha sem a correção |
| 117 s | Runner | Suíte completa passou; relatório `fixed` |

::warning
A gravação é um **ensaio**, não um registro. Os horários, o modelo (`claude-sonnet-5-5`) e o tamanho da suíte ("214 passed") são ilustrativos: a suíte real do cobaia é bem menor, e a execução real usou um agente só. Para medidas, use os valores da validação (cerca de 1 minuto, US$ 0,21) ou os de uma execução pelo painel.
::

## Repetir o caso

| Para | Rode | Custo |
|---|---|---|
| Ver a tela ao vivo com o caso inteiro | `php artisan firewatch:replay-run` | Zero ([Testar sem gastar créditos](/ambiente-e-setup/testar-sem-creditos)) |
| Testar o runner com a correção real | `docker/runner/test/run-scenarios.sh fix` (com o `fake-claude`, que aplica o `incident-001.patch`) | Zero ([Testes do runner](/runner/testes)) |
| Conferir clone e instalação | `run-local.sh … -e DRY_RUN=1` | Zero |
| Validar uma mudança no runner ou nos prompts com o Claude de verdade | `run-local.sh docker/runner/examples/incident-001` | Cerca de US$ 0,21 |

Antes de uma execução real, confira que o `main` do cobaia **ainda tem o bug**: se alguém fez merge de uma correção, os agentes não têm o que corrigir e a execução falha com **Causa ou correção não encontrada**. Os cenários `fix`, `break_tests`, `no_test` e `test_passes_before` dos testes do runner dependem do mesmo estado, porque aplicam o patch sobre o `main`.

## Pelo painel: o caso de 12/11

O incidente-001 não passa pelo Laravel. A primeira investigação real **de ponta a ponta** pelo painel foi outro bug plantado no mesmo cobaia, em 12/11/2026, e mostra o que o terminal não cobre:

| | |
|---|---|
| Erro | `SQLSTATE[42S22]: Column not found: 1054 Unknown column 'owner_id'` na listagem de empresas |
| Causa | O `select()` de `CompanyController::index()` pedia `owner_id`; na tabela, a coluna é `user_id` |
| Card | `KAN-43` no Jira, criado antes dos agentes |
| Branch | `firewatch/KAN-43-sqlstate-42s22-column-not-found-1054-unk` |
| Time | 6 subagentes chamados, todos concluídos |
| Duração do run | 312 s, do container ao relatório |
| Custo | US$ 1,05 (16 turnos, cerca de 496 mil tokens de entrada) |
| Resultado | PR #2 aberto no cobaia, 5 min e meio depois de o incidente chegar |

Duas lições desse caso:

- **O custo depende do modelo e do time.** Com o time completo, cada subagente lê o código de novo: o caso do painel custou cinco vezes o do terminal, para um bug de tamanho parecido.
- **SQLite esconde erros de banco.** A suíte do cobaia roda em SQLite, que aceita a coluna inexistente sem erro. Os agentes perceberam e escreveram um teste que confere se cada coluna do `select` existe na tabela, e deixaram a ressalva no relatório. Ao escolher um bug para uma demo, prefira um que a suíte da aplicação consiga reproduzir.
