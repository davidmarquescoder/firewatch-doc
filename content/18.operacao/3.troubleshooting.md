Cada problema abaixo segue o mesmo roteiro: o **sintoma** que aparece, **onde olhar** para confirmar e **o que fazer**. Os comandos rodam na pasta `firewatch-back`.

| Sintoma | Seção |
|---|---|
| A ferramenta de monitoramento recebe `401`, `403` ou `404` do Firewatch | [Webhook rejeitado](#webhook-rejeitado) |
| O webhook responde `202`, mas nenhum agente roda | [Webhook aceito sem investigação](#webhook-aceito-sem-investigação) |
| O incidente fica em **Na fila** com "Aguardando um runner livre…" | [Slot ocupado](#slot-ocupado) |
| O incidente falha com **Tempo esgotado** | [Runner com timeout](#runner-com-timeout) |
| A correção ficou pronta, mas o PR não saiu | [Falha ao abrir o PR](#falha-ao-abrir-o-pr) |
| O incidente falha com **Teto de custo atingido**, ou o Claude para no meio | [Budget estourado](#budget-estourado) |
| Os workers enchem o log de erros de conexão com o Redis | [Workers sem Redis](#workers-sem-redis) |

## Webhook rejeitado

**Sintoma.** A ferramenta de monitoramento (Sentry, webhook genérico, Slack) mostra a entrega com erro, e nenhum incidente aparece no painel.

**Onde olhar.** O código HTTP diz em que etapa a requisição parou. O motivo exato fica **só no log**, nunca na resposta, para não ensinar um atacante ([Verificação de assinatura](/entrada/verificacao)):

```bash
grep -a "Incoming webhook rejected" storage/logs/laravel.log | tail -5
```

```text
local.WARNING: Incoming webhook rejected {"connector_id":"01a1…","type":"generic_webhook","reason":"timestamp outside tolerance","ip":"10.0.0.5"}
```

| Resposta | Significa | O que fazer |
|---|---|---|
| `404 Webhook não encontrado.` | O UUID da URL não é de um conector, o conector foi apagado, ou é de um tipo que não recebe webhooks (Bitbucket, GitHub, Jira) | Copie de novo a URL do conector de **entrada** no painel |
| `401 Assinatura do webhook inválida.` | O segredo não confere. Veja o `reason` no log, na tabela abaixo | Conforme o motivo |
| `403 Conector desativado.` | O segredo está certo, mas o conector está `inactive` | Ative o conector no painel |
| `429` | Mais de 120 requisições por minuto do mesmo IP (60 nos comandos do Slack). Assinaturas erradas também contam | Espere um minuto. Se a fonte manda rajadas, agrupe os alertas nela |
| `422` | Passou pela assinatura, mas o corpo não é legível | A mensagem diz o campo ([Payloads ignorados e inválidos](/entrada/payloads-ignorados-e-invalidos)) |

| `reason` no log | Causa provável |
|---|---|
| `connector has no secret`, `…no client_secret`, `…no signing_secret` | O conector foi salvo sem o segredo. O Firewatch **falha fechado**: sem segredo, recusa tudo |
| `missing signature or token`, `missing Sentry-Hook-Signature header`, `missing Slack signature headers` | A fonte não está mandando os cabeçalhos. No Sentry, confira se a URL é a da integração interna que tem o Client Secret copiado |
| `signature mismatch` | Segredo diferente dos dois lados, ou o corpo foi **alterado depois de assinado** (JSON reformatado, quebra de linha final, proxy que reescreve o corpo) |
| `token mismatch` | O token do `Authorization: Bearer` ou do `X-Firewatch-Token` não é o `secret` do conector |
| `timestamp outside tolerance` | O `X-Firewatch-Timestamp` (ou o do Slack) está a mais de **300 s** do relógio do servidor. Sincronize o relógio da fonte e do servidor (NTP), ou o script está reaproveitando um timestamp antigo |
| `missing or invalid X-Firewatch-Timestamp header` | Assinatura sem timestamp, ou timestamp em milissegundos (precisa ser em **segundos**) |

::tip
Para isolar o problema, mande o exemplo da documentação com o `curl` de [Verificação de assinatura](/entrada/verificacao#webhook-genérico). Se ele passar e a ferramenta não, a diferença está em como ela monta o corpo ou o cabeçalho.
::

## Webhook aceito sem investigação

**Sintoma.** O webhook responde `202`, mas nenhum agente roda.

**Onde olhar.** A resposta e o painel:

| O que aparece | Causa | O que fazer |
|---|---|---|
| `202` com `data.ignored: true`, sem incidente | Nenhuma aplicação **ativa** com aquele identificador de monitoramento, ou um evento que não abre incidente (issue do Sentry `resolved`, `assigned`…). O motivo está no log `Incoming webhook ignored` | Confira o **identificador no monitoramento** da aplicação e se ela está ativa |
| Incidente com status **Ignorado** | As regras de acionamento da aplicação descartaram o erro (severidade, ambiente, ocorrências, padrões). O motivo está no `status_reason` | Ajuste as regras ([Motor de regras](/registro-e-trigger/motor-de-regras)) |
| Nenhum incidente novo, e a contagem de ocorrências de um antigo subiu | Deduplicação: o fingerprint é o de um incidente aberto, e o erro foi somado a ele | Nada: é o comportamento esperado ([Registro e trigger](/registro-e-trigger)) |
| Incidente **Na fila** que não sai do lugar | O job foi enfileirado, mas ninguém o pegou | Veja [Slot ocupado](#slot-ocupado) |

## Slot ocupado

**Sintoma.** O incidente fica em **Na fila** com o motivo "Aguardando um runner livre (limite de 2 execuções simultâneas; 2 em andamento).".

Isso é **normal** enquanto houver investigações rodando: no máximo `FIREWATCH_RUNNER_MAX_CONCURRENT` containers ao mesmo tempo, e quem chega depois tenta de novo a cada 30 s ([Slots de concorrência](/investigacao/slots-de-concorrencia)). Vira problema quando a espera não acaba.

**Onde olhar.**

```bash
docker ps --filter label=br.com.firewatch.runner=1
docker compose ps runner-worker
docker compose logs --since 30m runner-worker
```

| O que você vê | Causa | O que fazer |
|---|---|---|
| Containers rodando, um por vaga | As vagas estão ocupadas de verdade | Esperar. Se acontece sempre, aumente `FIREWATCH_RUNNER_MAX_CONCURRENT`, conferindo CPU e memória (`vagas × 2 CPUs`, `vagas × 4 GB`) |
| Nenhum container, e o motivo diz "N em andamento" | A contagem do motivo vem dos runs `running` no banco, não dos containers. Um worker que morreu deixa o run `running` e a **vaga presa** no Redis até o lock expirar (até 67 min) | Esperar o lock expirar, ou, com a lista de containers vazia, liberar as vagas à mão (abaixo). O watchdog fecha o run preso depois de 72 min |
| `runner-worker` parado ou reiniciando | Nenhum worker para pegar o job | `docker compose up -d runner-worker` e veja o log. Um `permission denied` no `docker.sock` é o `DOCKER_GID` errado ([Primeiro acesso](/ambiente-e-setup/primeiro-acesso#problemas-comuns)) |
| Nenhum motivo de espera, incidente em **Na fila** há muito tempo | O job nunca chegou ao worker (Redis perdeu a fila, worker de outra conexão) | Depois de 180 min o watchdog fecha como **Execução sem resposta**. Depois, use **Reexecutar** |

Para liberar as vagas presas (só quando `docker ps --filter label=br.com.firewatch.runner=1` não lista nada, senão duas investigações passam a dividir uma vaga):

```bash
docker compose exec app php artisan tinker --execute='foreach (range(0, config("firewatch.runner.max_concurrent") - 1) as $n) Cache::lock("firewatch:runner-slot:$n")->forceRelease();'
```

::note
A espera por vaga tem prazo: 180 min (`FIREWATCH_RUNNER_STALE_QUEUED_MINUTES`) desde o despacho. Depois disso o incidente falha com o tipo `stale` e o time é avisado. Esperar **não** conta como reexecução.
::

## Runner com timeout

**Sintoma.** O incidente falha com **Tempo esgotado**. O motivo diz a etapa: "Tempo esgotado na etapa de instalação de dependências…", "…na etapa dos agentes…", "O runner excedeu o tempo máximo (3720 s)…".

**Onde olhar.** O `status_reason` do incidente e, na tela do incidente, a última etapa do runner na timeline. O `failure.stage` do relatório diz qual limite estourou ([Timeouts e reexecução](/investigacao/timeouts-e-reexecucao)):

| Etapa | Limite | Causa comum | O que fazer |
|---|---|---|---|
| `install` | 900 s | Dependências pesadas sem cache, ou scripts de instalação lentos (compilação de extensões, *postinstall*) | Confira o comando de instalação da aplicação. Um domínio fora da allowlist não dá timeout: o proxy recusa na hora (`TCP_DENIED`) e a instalação falha com **Falha ao instalar dependências** ([Egress](/runner/egress#editar-as-allowlists)) |
| `claude` | 1800 s | Investigação longa demais, ou a suíte de testes da aplicação lenta, rodada várias vezes pelos agentes | Reexecute. Se repetir, aumente `FIREWATCH_RUNNER_CLAUDE_TIMEOUT` |
| `verify` | 600 s | A suíte completa é lenta | Aumente `FIREWATCH_RUNNER_TEST_TIMEOUT` ou acelere a suíte (banco em memória, paralelismo) |
| `total` | 3600 s | A soma das etapas | Aumente `FIREWATCH_RUNNER_MAX_DURATION` |
| `hardTimeout` | 3720 s | O runner não terminou nem com o próprio limite, e o Firewatch o matou | Raro: indica runner travado. Rode o incidente com o `run-local.sh` para ver onde para |

::warning
Ao aumentar `FIREWATCH_RUNNER_MAX_DURATION` ou `FIREWATCH_RUNNER_KILL_GRACE`, aumente também `FIREWATCH_RUNNER_QUEUE_RETRY_AFTER`, que precisa ficar acima de `MAX_DURATION + KILL_GRACE + 60`. Senão, a fila entrega o mesmo job a um segundo worker no meio da execução.
::

Um timeout **não** é refeito sozinho, porque cada tentativa gasta créditos. Depois de ajustar, use **Reexecutar** no incidente (até 3 vezes, `FIREWATCH_INCIDENT_MAX_RETRIES`).

## Falha ao abrir o PR

**Sintoma.** Os agentes terminaram com a correção verificada, mas o incidente não chegou a **PR aberto**.

**Onde olhar.** O `status_reason` e o último evento do agente `firewatch` na timeline, gravados pelo `DeliverIncidentOutcome` ([DeliverIncidentOutcome](/saida/deliver-incident-outcome)):

| Incidente | Motivo | Causa | O que fazer |
|---|---|---|---|
| Em **Testando**, "Correção pronta, mas a abertura do Pull Request falhou: …" | `Bitbucket: … (HTTP 401)` | Token inválido ou expirado | Gere outro token e atualize o conector de repositório |
| | `… (HTTP 403)` | O token não tem escrita no repositório e em pull requests | Dê as permissões ao token ([Repositórios](/saida/repositorios)) |
| | `… (HTTP 404)` | Slug errado (`workspace/repositorio`) ou repositório fora do alcance do token | Corrija o repositório da aplicação |
| | `… (HTTP 409)` ou `422` no GitHub | Alguém mexeu na branch `firewatch/…` entre a leitura e o envio | Confira a branch no repositório |
| | `A branch "…" já existe com outro conteúdo e tem um Pull Request aberto.` | Uma tentativa anterior do mesmo incidente já abriu um PR que está em revisão | Revise ou feche o PR antigo |
| | `A aplicação "…" não tem um conector Bitbucket.`, `…está inativo.`, `…não tem access token.`, `Slug de repositório inválido…` | Configuração do conector ou da aplicação | Corrija no painel. Um `runner_token` sozinho não basta: abrir o PR exige o `access_token` |
| Em **Testando**, "…a abertura de Pull Request ainda não está disponível para …" | | O tipo de conector não tem provider registrado | Abra o PR à mão |
| **Falhou**, tipo **Correção não enviada** | `Correção não enviada: …` | O relatório não passou nas travas de segurança: suíte que não passou, fluxo obrigatório não comprovado, teste que não falhava sem a correção, diff truncado, branch fora de `firewatch/` | A correção não é confiável: revise pelo painel e trate à mão |

Na falha de API, a correção continua inteira: o incidente fica em **Testando**, e o diff aparece na tela do incidente (e no relatório do run, em `changes.diff`). O Slack e o Jira já foram avisados de que a correção está pronta sem PR.

::warning
**Não há como refazer só a entrega pelo painel.** O **Reexecutar** só aceita incidentes que falharam, e o watchdog não mexe em incidentes em **Testando** com o run `fixed`. As saídas são abrir o PR à mão com o diff, ou, depois de corrigir o token, despachar a entrega de novo pelo `tinker`, sabendo que **o Slack e o Jira serão avisados outra vez**:

```bash
docker compose exec app php artisan tinker --execute='App\Jobs\DeliverIncidentOutcome::dispatch(App\Models\AgentRun\AgentRun::findOrFail("<id do run>"));'
```
::

## Budget estourado

Há dois tetos, e cada um aparece de um jeito ([Budget](/conectores-aplicacoes-budget-e-metricas/budget)):

| Sintoma | Teto | O que aconteceu |
|---|---|---|
| Incidente **Falhou** com **Teto de custo atingido**: "Teto mensal de custo atingido: US$ 50,00 de US$ 50,00 em 2026-11. A investigação não foi iniciada." | **Mensal** | Sobrava menos que US$ 0,05 no mês. Nenhum container subiu e nada foi gasto |
| Incidente **Falhou** com **Erro no Claude**: "O teto de custo desta execução foi atingido…" | **Por execução** | O Claude Code parou ao chegar no teto do run (padrão US$ 2, ou o que sobrava do mês). O que foi gasto até ali conta no mês |
| Incidente **Falhou** com **Erro no Claude**, falando de credencial, saldo ou limite de requisições | Nenhum dos dois | A conta da Anthropic recusou: chave inválida, sem saldo ou limite de taxa |

**Onde olhar.** A tela **Custos e limites** mostra o gasto do mês, o teto e se o mês está bloqueado. Os alertas de 80% e 100% chegam pelo Slack e ficam na Auditoria (`budget_alert`).

**O que fazer.**

- **Mês bloqueado:** aumente o teto mensal (ou desligue **Limitar o gasto mensal**) em Custos e limites e **reexecute** os incidentes que falharam por custo. O run bloqueado conta como uma das 3 reexecuções.
- **Teto por execução:** se as investigações param sempre no meio, aumente o **Teto por execução**. Antes, veja na timeline se os agentes estavam progredindo ou presos num ciclo; nesse caso, o problema é o prompt ou o incidente, não o teto.
- **Conta da Anthropic:** confira a chave (`FIREWATCH_ANTHROPIC_API_KEY` ou `FIREWATCH_CLAUDE_CODE_OAUTH_TOKEN`) e o saldo no console da Anthropic. O teto do Firewatch não sabe o saldo real da conta.

::note
O teto mensal pode ser **ultrapassado** um pouco: runs em paralelo recebem cada um a sobra inteira do mês, porque o custo só entra na conta quando o run termina.
::

## Workers sem Redis

**Sintoma.** Depois de ligar (ou reiniciar) a máquina, o `laravel.log` cresce rápido com `php_network_getaddresses: getaddrinfo for redis failed: Temporary failure in name resolution`, e nenhum job roda.

**Causa.** O Redis não está rodando e os outros serviços estão. Os workers tentam a fila a cada poucos segundos e registram cada falha com o stack trace inteiro: no ambiente local, foram cerca de 2.600 linhas por hora, e mais de 38 mil no total.

Até 19/11/2026, isso acontecia a cada vez que a máquina ligava: o serviço `redis` era o único do `docker-compose.yml` sem `restart: unless-stopped`, e o Docker subia os workers sem ele. Hoje o Redis volta sozinho como os outros; o sintoma só aparece se alguém parar o Redis (`docker compose stop redis`) ou se o container não subir.

**O que fazer.**

```bash
docker compose up -d redis
docker compose logs --tail 50 redis
```

Se o container estava parado, isso basta. Se ele não fica de pé, o log do Redis diz o motivo (memória, disco, porta). Um container antigo, criado antes da mudança, só ganha o `restart` quando é recriado: `docker compose up -d redis` faz isso.

## Outros problemas

| Sintoma | Causa | Onde está a solução |
|---|---|---|
| **Configuração inválida**: "A imagem do runner "…" não existe neste servidor." | O Firewatch não baixa imagens | Construa a imagem ([Imagens do runner](/ambiente-e-setup/imagens-do-runner)) |
| **Configuração inválida**: "…segue o contrato N do runner, e o Firewatch espera o contrato M." | Imagem construída com uma versão antiga do `docker/runner` | Reconstrua a imagem |
| **Configuração inválida**: "Nenhuma credencial do Claude configurada…" | Falta `FIREWATCH_ANTHROPIC_API_KEY` ou `FIREWATCH_CLAUDE_CODE_OAUTH_TOKEN` no `.env` | Preencha e rode `config:clear` (ou `optimize`, se a config estiver em cache) |
| **Falha ao clonar o repositório** | Token sem leitura, slug errado, ou usuário errado na URL (no Bitbucket, o usuário do token é `x-token-auth`) | [Repositórios](/saida/repositorios#clone-no-runner) |
| **Memória esgotada** | A suíte da aplicação passou dos 4 GB | Aumente `FIREWATCH_RUNNER_MEMORY` |
| A timeline não atualiza ao vivo | Reverb: chave, host ou origem | [Primeiro acesso](/ambiente-e-setup/primeiro-acesso#problemas-comuns) |
| Login responde `419` ou `401` | Sanctum: domínio do painel fora de `SANCTUM_STATEFUL_DOMAINS` | [Primeiro acesso](/ambiente-e-setup/primeiro-acesso#problemas-comuns) |
| A mesma falha se repete em toda reexecução | O problema não é momentâneo | O tipo de falha e o próximo passo de cada um estão em [Resultado e falhas](/investigacao/resultado-e-falhas#os-failure-kinds) |
