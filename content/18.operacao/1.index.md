**O Firewatch ainda não tem deploy automatizado nem ambiente de produção.** Não há pipeline de entrega, `docker-compose` de produção ou servidor configurado: o que existe é o `docker-compose.yml` de desenvolvimento ([Pré-requisitos e docker-compose](/ambiente-e-setup)) e o CI, que só testa ([CI e estilo](/testes-e-qualidade/ci-e-estilo)). Esta página descreve o que um deploy precisa, partindo do que o projeto já tem.

::note
O "deploy automático" que o `CLAUDE.md` deixa fora do MVP é outro assunto: o Firewatch nunca publica a correção da aplicação investigada. Esta página trata de implantar o **próprio** Firewatch.
::

## O que vai para o servidor

| Peça | Hoje, no compose | Em produção |
|---|---|---|
| API (PHP-FPM) | `app` + `nginx` na porta 8000 | Igual, atrás de um proxy com HTTPS |
| Fila padrão | `queue`: `queue:listen --timeout=360` | `queue:work --timeout=360`, ou o Horizon |
| Investigações | `runner-worker` com o socket do Docker | Igual: é o motivo de o servidor precisar de Docker |
| WebSocket | `reverb` na porta 8080 | Atrás do proxy com TLS (`wss://`) |
| Agendamentos | `scheduler`: `schedule:work` | Igual |
| Proxy de saída dos runners | `runner-egress` | Igual |
| Banco | `db`: MySQL 8.3, porta 3388 aberta no host | Sem porta no host, ou um MySQL gerenciado |
| Redis | `redis` | Igual, ou gerenciado |
| Imagens do runner | `firewatch-runner:latest` e as de cada stack, construídas no host | Construídas no **mesmo** Docker que o `runner-worker` usa |
| Painel | `pnpm dev` no host, porta 5000 | `pnpm build` e o servidor Node do Nuxt |
| phpMyAdmin | `phpmyadmin` na porta 6060 | **Fora** |

### Por que precisa de um servidor com Docker

Cada investigação sobe um container `firewatch-run-*` pelo Docker do host, a partir do `runner-worker`, que monta `/var/run/docker.sock`. Os runners entram na rede `firewatch-runner-net` (`internal: true`) e só saem pelo `runner-egress` ([Egress](/runner/egress)). Por isso o Firewatch precisa de uma **VM ou servidor com Docker Engine**. Plataformas que não dão acesso ao Docker (serverless, PaaS de containers, Kubernetes sem um daemon Docker) não rodam as investigações sem reescrever o `DockerRunner`.

Dimensione a máquina pelos runners: cada um usa até `FIREWATCH_RUNNER_CPUS` (2) e `FIREWATCH_RUNNER_MEMORY` (4 GB), e o padrão são 2 simultâneos. Some o resto da stack: 8 GB livres só para os runners é o mínimo dos padrões.

## Mudanças no docker-compose

O `docker-compose.yml` foi feito para desenvolver: monta o código com volume, expõe banco e phpMyAdmin e usa `queue:listen`, que relê o código a cada job. Para um servidor, o caminho mais curto é um arquivo de sobreposição (`docker-compose.prod.yml`, ainda não existe) usado com `docker compose -f docker-compose.yml -f docker-compose.prod.yml`:

| Serviço | Mudança | Por quê |
|---|---|---|
| `queue` | `php artisan queue:work --timeout=360 --tries=1` | `queue:listen` sobe um processo PHP por job. Com `queue:work`, rode `queue:restart` a cada versão nova |
| `runner-worker` | Manter `queue:listen`, ou trocar por `queue:work` no mesmo laço | Investigações são longas e raras: o custo do `listen` não pesa. Com `work`, inclua o `queue:restart` |
| `db` | Remover `ports: 3388:3306` | O banco não precisa ficar aberto para fora |
| `phpmyadmin` | Remover | Ferramenta de desenvolvimento |
| `nginx`, `reverb` | Publicar só para o proxy com TLS | O painel precisa de `https://` e `wss://` para os cookies seguros |
| `redis` | Fixar a versão (hoje `redis:latest`) | Uma versão nova não deveria entrar sem querer |

::warning
O `runner-worker` e o `docker/runner/egress/` dependem de caminhos do host (`/var/run/docker.sock`, as allowlists). Ao levar o projeto para outra máquina, confira o `DOCKER_GID` (`stat -c %g /var/run/docker.sock`) antes de subir o serviço.
::

## O .env de produção

As variáveis estão em [Variáveis de ambiente](/ambiente-e-setup/variaveis-de-ambiente). As que mudam em relação ao desenvolvimento:

| Variável | Desenvolvimento | Produção |
|---|---|---|
| `APP_ENV` | `local` | `production` |
| `APP_DEBUG` | `true` | `false`. Com `true`, os erros mostram stack trace e variáveis para quem chama a API |
| `APP_KEY` | gerada no setup | Gerada **uma vez** e guardada. Trocar a chave torna ilegíveis as credenciais dos conectores, cifradas com ela |
| `APP_URL`, `FRONTEND_URL` | `http://localhost:8000`, `:5000` | Os endereços `https://` da API e do painel |
| `SANCTUM_STATEFUL_DOMAINS` | `localhost:5000,…` | O domínio do painel |
| `SESSION_DOMAIN`, `SESSION_SECURE_COOKIE` | `null`, vazio | O domínio comum da API e do painel, e `true` |
| `REVERB_ALLOWED_ORIGINS` | `localhost,127.0.0.1` | O host do painel |
| `LOG_CHANNEL` / `LOG_STACK`, `LOG_LEVEL` | `stack` / `single`, `debug` | `daily` (ou `stderr`) e `info`. Veja [Monitoramento](/operacao/monitoramento#logs) |
| `FIREWATCH_ANTHROPIC_API_KEY` ou `FIREWATCH_CLAUDE_CODE_OAUTH_TOKEN` | a sua | A credencial da conta de produção |
| `FIREWATCH_PANEL_URL` | vazio | O endereço do painel, se não for o `FRONTEND_URL`: é o link que vai no PR, no Slack e no Jira |

E no painel (`firewatch-front/.env`): `NUXT_PUBLIC_SANCTUM_BASE_URL` e `NUXT_SANCTUM_BASE_URL` com a API, `NUXT_PUBLIC_SANCTUM_ORIGIN` e `NUXT_SANCTUM_ORIGIN` com o painel, `NUXT_PUBLIC_ECHO_HOST` com o host público do Reverb e `NUXT_PUBLIC_ECHO_SCHEME=https`.

Dois ajustes no código antes de abrir para a internet:

- **CORS.** O `config/cors.php` aceita qualquer origem (`allowed_origins: ['*']`) com `supports_credentials: true`. Em produção, limite a origem ao painel (`[env('FRONTEND_URL')]`).
- **Horizon.** O gate `viewHorizon` tem a lista de e-mails vazia: fora do ambiente `local`, ninguém abre `/horizon` até ela ser preenchida ([Filas e Horizon](/filas-agendamentos-e-comandos#quem-acessa)).

## Primeira subida

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose exec app composer install --no-dev --optimize-autoloader
docker compose exec app php artisan migrate --force
docker compose exec app php artisan db:seed --force
docker compose exec app php artisan optimize
docker compose --profile runner build runner
```

| Passo | O que faz |
|---|---|
| `composer install --no-dev` | Deixa de fora PHPUnit, Pint e as ferramentas de desenvolvimento |
| `migrate --force` | O `--force` é exigido com `APP_ENV=production` |
| `db:seed --force` | Papéis, permissões e o time padrão de agentes. Pode rodar de novo sem duplicar ([Primeiro acesso](/ambiente-e-setup/primeiro-acesso)) |
| `optimize` | Cache de config, rotas, eventos e views. Depois dele, mudar o `.env` exige `optimize` de novo |
| `build runner` | A imagem base do runner. As imagens de outras stacks seguem [Imagens do runner](/ambiente-e-setup/imagens-do-runner) |

O Firewatch **não baixa imagens**: uma aplicação com uma `runner_image` que não existe no Docker do servidor falha com o tipo `configuration` ("A imagem do runner … não existe neste servidor"). Construa todas as imagens que as aplicações cadastradas usam antes de liberar as investigações.

O primeiro usuário é criado como no desenvolvimento ([Primeiro acesso](/ambiente-e-setup/primeiro-acesso#crie-o-primeiro-usuário)).

### O painel

```bash
cd firewatch-front
pnpm install --frozen-lockfile
pnpm build
node .output/server/index.mjs
```

O `nuxt build` gera um servidor Node em `.output/` (o painel usa SSR). Ele escuta na porta da variável `PORT` (padrão 3000) e precisa das mesmas variáveis `NUXT_*` em tempo de execução. Coloque-o atrás do mesmo proxy com HTTPS e mantenha o processo vivo com um gerenciador (systemd, pm2 ou um container).

## Atualizar para uma versão nova

```bash
docker ps --filter label=br.com.firewatch.runner=1
```

Comece por aí: se houver containers listados, há investigações em andamento. O `docker compose restart` espera 10 s e depois mata os processos do `runner-worker`, com o job no meio. Um container que sobrar segue até o próprio limite, e o incidente só é fechado pelo [watchdog](/filas-agendamentos-e-comandos/agendamentos), como `stale`, até 72 min depois. Espere a lista ficar vazia.

```bash
git pull
docker compose exec app composer install --no-dev --optimize-autoloader
docker compose exec app php artisan migrate --force
docker compose exec app php artisan optimize
docker compose exec app php artisan queue:restart
docker compose restart reverb scheduler runner-worker
```

| Mudou | Também rode |
|---|---|
| `Dockerfile` do back-end | `docker compose up -d --build` |
| `docker/runner/` | `docker compose --profile runner build runner` e as imagens de stack. Se o contrato do runner mudou, o Firewatch recusa imagens antigas ("segue o contrato … e o Firewatch espera o contrato …") |
| `docker/runner/egress/` | `docker compose up -d --build runner-egress` |
| Prompts padrão dos agentes | `firewatch:reset-agent-profiles`, só se quiser descartar as edições feitas no painel ([Comandos Artisan](/filas-agendamentos-e-comandos/comandos-artisan)) |
| Painel | `pnpm install --frozen-lockfile`, `pnpm build` e reiniciar o processo Node |

`queue:restart` avisa os `queue:work` para terminarem o job atual e saírem; o `restart: unless-stopped` do compose os sobe de novo com o código novo. Com `queue:listen` ele não é necessário.

## Checklist

| | |
|---|---|
| Servidor | Docker Engine e Compose, CPU e memória para os runners, `DOCKER_GID` conferido |
| Rede | HTTPS na API, no painel e no Reverb; banco e Redis sem porta pública; phpMyAdmin fora |
| `.env` | `APP_ENV=production`, `APP_DEBUG=false`, `APP_KEY` guardada, domínios e cookies, log com rotação, credencial do Claude |
| Código | CORS limitado ao painel; e-mails no gate do Horizon, se for usá-lo |
| Dados | `migrate --force`, `db:seed --force`, primeiro usuário |
| Runner | Imagens de todas as aplicações construídas; `runner-egress` no ar |
| Depois | [Monitoramento](/operacao/monitoramento): health check, logs e filas |
