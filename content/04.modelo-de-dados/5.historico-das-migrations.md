### Ajustes do domínio · 10/11/2026

Três alterações feitas um dia depois, quando o runner e o painel começaram a ser usados de ponta a ponta.

#### `2026_11_10_120000_add_failure_kind_to_incidents_table`

```php
$table->string('failure_kind')->nullable()->after('status_reason');
$table->index('failure_kind');
```

**Por quê:** até aqui, um incidente `failed` tinha só um texto livre em `status_reason`. Não dava para saber, sem ler a frase, se a falha era do Claude, do repositório, dos testes ou do próprio FireWatch. A coluna guarda a **classificação** (`IncidentFailureKindEnum`) produzida pelo `FailureClassifier` a partir do código de saída do runner. Com ela:

- o painel mostra o rótulo e o **próximo passo** sugerido para o time;
- o Slack e o Jira recebem a mesma classificação;
- o dashboard agrupa as falhas por tipo (por isso o índice).

`transitionTo()` limpa a coluna em qualquer status diferente de `failed`, então uma reexecução não herda o kind anterior.

#### `2026_11_10_130000_add_team_to_agent_runs_table`

```php
$table->json('team')->nullable()->after('report');
```

**Por quê:** os perfis de agentes são editáveis pelo painel. Sem uma cópia, não haveria como saber, depois, **com qual time** uma execução antiga rodou (que prompt, quais ferramentas, qual nível de acesso). O `team` guarda o `toTeamSnapshot()` de cada perfil ativo no início da execução, incluindo o **SHA-256 do prompt**. Serve à auditoria e à timeline, que mostra nome e avatar de cada agente mesmo que o perfil tenha mudado ou sido apagado.

#### `2026_11_10_140000_add_access_to_agent_profiles_table`

```php
$table->string('command_access')->default('none')->after('allowed_tools');
$table->string('write_access')->default('none')->after('command_access');
```

**Por quê:** o campo `allowed_tools` só liga ou desliga uma ferramenta inteira. Ele não diz **quais comandos** o `Bash` pode rodar nem **quais arquivos** o `Edit` pode mudar. Com isso, o Detetive (só leitura) podia, em tese, editar código. As duas colunas alimentam o `policy.json` do runner, que o guarda de ferramentas (`tool-guard.sh`, hook `PreToolUse`) aplica a cada chamada.

A migration também **preenche os perfis existentes** com o acesso padrão do papel, para o time continuar funcionando (com `none`, o orquestrador não conseguiria rodar nada):

| Papel | `command_access` | `write_access` |
|---|---|---|
| `orchestrator` | `full` | `any` |
| `investigator` | `read_only` | `none` |
| `tester` | `tests` | `tests` |
| `fixer` | `tests` | `code` |

Triagem e Pull Request ficaram com o padrão `none`/`none`.

### Custos · 16/11/2026

#### `2026_11_16_120000_create_app_settings_table`

Duas mudanças na mesma migration, ambas do controle de custos (**PL-094**):

```php
Schema::create('app_settings', function (Blueprint $table) {
    $table->uuid('id')->primary();
    $table->string('key')->unique();
    $table->json('value')->nullable();
    $table->timestamps();
});

Schema::table('agent_runs', function (Blueprint $table) {
    $table->decimal('budget_usd', 10, 4)->nullable()->after('cost_usd');
});
```

**Por quê:**

- **`app_settings`**: os limites de custo eram só variáveis de ambiente. Para o time ajustá-los pela tela **Custos e limites**, sem reiniciar nada, eles precisavam ir para o banco. A tabela chave/valor guarda `budget` (os limites) e `budget_alerts` (os alertas já enviados no mês) e serve para futuras configurações globais.
- **`agent_runs.budget_usd`**: registra o **teto** com que cada execução rodou. O teto por execução é reduzido ao que sobra do mês, então ele varia de uma execução para outra. Ao lado de `cost_usd` (o gasto real), mostra quanto da margem cada investigação usou.

## Ao criar uma migration nova

- Use `php artisan make:migration`: o stub já cria **UUID** e soft delete. Remova a linha `foreignUuid('user_id')` se a tabela não pertence a um usuário.
- Para alterar uma tabela existente, crie uma migration nova. Não edite uma migration que já rodou em outro ambiente.
- Escreva o `down()` de verdade (as migrations de ajuste do FireWatch desfazem colunas e índices).
- Quando a coluna nova precisa de valor nos registros existentes, preencha **na própria migration**, como fez a de `command_access`/`write_access`.
- Status e tipos novos entram como `string` + **enum** no modelo, nunca como `ENUM` do MySQL.
- Atualize esta página e a de [Tabelas](/modelo-de-dados/tabelas).
