O status de um incidente só muda por **um caminho**: o método `Incident::transitionTo()`. Ele consulta a tabela de transições do `IncidentStatusEnum` e recusa qualquer mudança que não esteja nela.

## Tabela de transições

Definida em `IncidentStatusEnum::TRANSITIONS`:

```php [app/Enums/Incident/IncidentStatusEnum.php]
private const TRANSITIONS = [
    'received'      => ['ignored', 'queued', 'failed'],
    'queued'        => ['investigating', 'failed'],
    'investigating' => ['fixing', 'failed'],
    'fixing'        => ['testing', 'failed'],
    'testing'       => ['fixing', 'pr_opened', 'failed'],
    'pr_opened'     => [],
    'failed'        => ['queued'],
    'ignored'       => [],
];
```

Três regras resumem a tabela:

- Todo status **não terminal** pode ir para `failed`.
- `pr_opened` e `ignored` são **finais**: nada sai deles.
- `failed` só volta para `queued`, por **reexecução manual**.

## O que dispara cada transição

| De → para | Quem dispara | Condição |
|---|---|---|
| `received` → `queued` | `EvaluateIncidentTriggerAction` | O trigger decidiu **acionar**. Na mesma transação, o job `InvestigateIncident` é disparado (`afterCommit`). |
| `received` → `ignored` | `EvaluateIncidentTriggerAction` | O trigger decidiu **ignorar**. O motivo vai para `status_reason`. |
| `received` → `failed` | (nenhum) | Permitida pela tabela, mas nenhum código usa hoje. |
| `queued` → `investigating` | `RunnerStreamMonitor` | Primeiro evento do runner (`handleRunnerEvent`). |
| `investigating` → `fixing` | `RunnerStreamMonitor` | O orquestrador delegou a um subagente com papel `fixer` (Cirurgião). |
| `fixing` → `testing` | `RunnerStreamMonitor` | O runner começou as etapas `flow` ou `verify`, ou o orquestrador delegou ao `tester` depois da correção. |
| `* → testing` (salto) | `InvestigateIncident::closeIncident()` | Execução `fixed`: o monitor avança pelas etapas que faltaram até `testing`. |
| `testing` → `pr_opened` | `DeliverIncidentOutcome` | PR aberto com sucesso; grava `pr_url`. |
| `testing` → `fixing` | (nenhum) | Permitida, mas o monitor só avança: hoje não há volta automática. |
| qualquer → `failed` | Ver tabela abaixo | Sempre por `markFailed($kind, $reason)`, que grava o `failure_kind`. |
| `failed` → `queued` | `RetryIncidentInvestigationAction` | Botão **Reexecutar** do painel (`POST /api/v1/incident/{id}/retry`). Bloqueado se a aplicação foi removida ou está inativa, ou se o limite de reexecuções acabou. |

### Quem marca `failed`

| Origem | Kind |
|---|---|
| `InvestigateIncident` (budget esgotado antes de começar) | `budget` |
| `InvestigateIncident::closeIncident()` (execução terminou sem correção) | O kind do relatório (`clone`, `tests_failed`, `timeout`…), ou `no_fix` |
| `InvestigateIncident::closeIncident()` (execução `dry_run`) | `dry_run` |
| `InvestigateIncident::failed()` (job estourou tentativas ou lançou exceção) | `stale` (nunca conseguiu slot) ou `internal` |
| `DeliverIncidentOutcome` (relatório barrado antes do PR) | `delivery_blocked` |
| `FailStaleIncidentsAction` (scheduler, a cada 5 min) | `stale` |
| `firewatch:replay-run` (gravação sem correção) | `runner_error` |

## O avanço progressivo

O `RunnerStreamMonitor` nunca pula estados. O método `advanceTo($alvo)` percorre a sequência fixa e faz **uma transição por etapa**:

```php [app/Services/Runner/RunnerStreamMonitor.php]
private const PROGRESSION = [
    IncidentStatusEnum::INVESTIGATING,
    IncidentStatusEnum::FIXING,
    IncidentStatusEnum::TESTING,
];
```

Se o incidente está em `investigating` e o alvo é `testing`, ele passa por `fixing` antes. Assim, cada coluna `<status>_at` é preenchida e o painel mostra todas as etapas, mesmo quando os eventos chegam fora da ordem esperada. Um alvo atrás do status atual não faz nada.

## O que `transitionTo()` grava

```php [app/Models/Incident/Incident.php]
public function transitionTo(IncidentStatusEnum $status, ?string $reason = null): static
{
    if (! $this->status->canTransitionTo($status)) {
        throw InvalidIncidentTransitionException::from($this->status, $status);
    }

    $this->status = $status;
    $this->status_reason = $reason;

    // The kind belongs to the failure: a retry (failed → queued) clears it.
    if ($status !== IncidentStatusEnum::FAILED) {
        $this->failure_kind = null;
    }

    $this->{$status->timestampColumn()} = now();
    $this->save();

    return $this;
}
```

A cada transição válida:

1. `status` muda e `status_reason` é **substituído** (fica nulo se a transição não informar motivo).
2. `failure_kind` é **limpo** em qualquer status que não seja `failed`. Uma reexecução começa sem o kind da falha anterior.
3. A coluna de data do status (`queued_at`, `failed_at`…) recebe o horário atual. Numa reexecução, ela é sobrescrita.
4. O modelo é salvo, o que dispara o broadcast `IncidentStatusChanged` (canais `firewatch` e `incidents.{id}`) e o registro na auditoria (`log_name = incident`).

## Concorrência

Duas ações podem tentar mudar o mesmo incidente ao mesmo tempo (dois eventos do mesmo erro, dois cliques em **Reexecutar**). Os pontos de entrada se protegem com **lock de linha**:

- `EvaluateIncidentTriggerAction` e `RetryIncidentInvestigationAction` releem o incidente com `lockForUpdate()` dentro de uma transação e só agem se o status ainda for o esperado.
- O job `InvestigateIncident` é **único por incidente** (`ShouldBeUnique`) e sai sem fazer nada se o incidente não estiver mais em `queued`.

## `InvalidIncidentTransitionException`

```php [app/Exceptions/InvalidIncidentTransitionException.php]
class InvalidIncidentTransitionException extends DomainException
{
    public static function from(IncidentStatusEnum $current, IncidentStatusEnum $next): self
    {
        return new self("Incident cannot move from [{$current->value}] to [{$next->value}].");
    }
}
```

É lançada por `transitionTo()` (e por `markFailed()`, que a usa) quando a mudança não está na tabela. Exemplos: marcar como `failed` um incidente que já está em `pr_opened`, ou reenfileirar um incidente `ignored`.

Ela **não é capturada** em nenhum lugar de propósito: uma transição proibida é um erro de programação, não uma situação esperada. O efeito depende de onde acontece:

| Onde | Resultado |
|---|---|
| Requisição HTTP | Resposta `500` em JSON; a transação é desfeita |
| Job `InvestigateIncident` | O job falha e o `failed()` encerra o incidente como `internal` (se ele ainda não for terminal) |
| Job `DeliverIncidentOutcome` | O job falha (1 tentativa) e vai para `failed_jobs` |

Os pontos de entrada evitam a exceção conferindo o status antes: `isTerminal()` antes de `markFailed()`, `status === QUEUED` antes de investigar, `status === TESTING` antes de abrir o PR, e o `blocker()` da reexecução, que só aceita `failed`.
