O Firewatch tem três conjuntos de testes, um por parte do sistema:

| Onde | O que testa | Ferramenta | Página |
|---|---|---|---|
| `firewatch-back/tests/` | O Laravel: entrada, regras, investigação, saída, API, tempo real | PHPUnit 12 (`php artisan test`) | Esta parte |
| `firewatch-back/docker/runner/test/` | A imagem do runner: `entrypoint.sh`, `tool-guard.sh`, egress | Scripts shell com um Claude falso | [Testes do runner](/runner/testes) |
| `firewatch-front` | O painel | Só lint e checagem de tipos, **sem testes automatizados** | [CI e estilo](/testes-e-qualidade/ci-e-estilo) |

Esta parte trata dos testes do Laravel, que são a maior parte: **572 testes e 2484 asserções**, rodando em cerca de 16 segundos.

::note
Os testes são classes do **PHPUnit**, com métodos `test_*` e `#[DataProvider]`. O `CLAUDE.md` do projeto fala em Pest, e o `composer.json` libera o plugin do Pest, mas o Pest **não** está instalado e nenhum teste usa a sintaxe dele.
::

## Unit e Feature

O `phpunit.xml` define as duas suítes:

| Suíte | Pasta | Classe base | Sobe o Laravel? | Banco |
|---|---|---|---|---|
| **Unit** | `tests/Unit/` | `PHPUnit\Framework\TestCase` | **não** | nenhum |
| **Feature** | `tests/Feature/` | `Tests\TestCase` (ou `Tests\Feature\Api\ApiTestCase`) | sim | SQLite em memória, recriado por teste (`RefreshDatabase`) |

A regra para escolher:

- **Unit** é para código **puro**: recebe dados e devolve dados, sem banco, config, container ou HTTP. Os adapters de entrada (Sentry, webhook genérico, comando do Slack), o `IncomingEvent`, o `StreamEventMapper` do runner, o mascaramento, o parser de diff e os padrões de ignorar. Como não sobem o framework, são instantâneos, e qualquer dependência do Laravel quebra o teste na hora, o que mantém essas classes puras.
- **Feature** é para tudo o que toca o framework: models e seus hooks, actions, jobs, comandos, controllers pela API, canais do Reverb, as integrações de saída com `Http::fake()`.

Uma mesma área costuma ter os dois: o `SentryAdapterTest` (Unit) prova que o payload vira o `IncomingEvent` certo; o `WebhookEndpointTest` (Feature) prova que o mesmo payload, chegando por HTTP com assinatura, vira um incidente.

### As classes base

`tests/TestCase.php`, a base de toda a suíte Feature, tem uma linha só:

```php [tests/TestCase.php]
protected function setUp(): void
{
    parent::setUp();

    // Tests never start real processes (docker, the runner, Claude Code):
    // every command must be faked with Process::fake().
    Process::preventStrayProcesses();
}
```

Qualquer `Process::run()` que não tenha sido simulado lança exceção. É a primeira trava da regra de nunca chamar o Claude de verdade ([Sem Claude de verdade](/testes-e-qualidade/sem-claude-de-verdade)).

`tests/Feature/Api/ApiTestCase.php` é a base dos 12 testes de API. Usa `RefreshDatabase` e já entra logado com um usuário ativo e sem troca de senha pendente:

```php [tests/Feature/Api/ApiTestCase.php]
$this->actingAs(User::factory()->create([
    'cpf' => fake()->unique()->numerify('###########'),
    'active' => true,
    'must_change_password' => false,
]));
```

Os testes que precisam de outro usuário (desativado, com papel específico) trocam com `actingAs()` dentro do teste.

### O ambiente dos testes

O `phpunit.xml` troca tudo o que é externo ou lento:

| Variável | Valor | Efeito |
|---|---|---|
| `DB_CONNECTION` / `DB_DATABASE` | `sqlite` / `:memory:` | Banco em memória; não precisa do MySQL |
| `QUEUE_CONNECTION`, `FIREWATCH_RUNNER_QUEUE_CONNECTION` | `sync` | Os jobs rodam na hora, dentro do teste |
| `BROADCAST_CONNECTION` | `null` | Nada vai para o Reverb |
| `CACHE_STORE`, `SESSION_DRIVER` | `array` | Sem Redis |
| `MAIL_MAILER` | `array` | Nenhum e-mail sai |
| `LOG_CHANNEL` | `null` | Os testes não escrevem no `storage/logs/laravel.log`, que é o mesmo dos serviços. Os testes que conferem o log usam `Log::spy()` |
| `BCRYPT_ROUNDS` | `4` | Hash de senha rápido |
| `APP_ENV` | `testing` | |

Os valores do `.env` não valem dentro dos testes quando o `phpunit.xml` os define. As chaves do Claude, dos conectores e do runner que um teste precisa são postas com `config([...])` no próprio teste, sempre com valores falsos (`sk-ant-test-…`).

### As factories

`database/factories/` tem uma factory por model principal: `User`, `Connector`, `Application`, `Incident`, `AgentRun`, `AgentEvent`, `AgentProfile`. Os estados mais usados:

| Factory | Estados |
|---|---|
| `ConnectorFactory` | `bitbucket()`, `github()`, `slack()`, `jira()`, `sentry()`, `inactive()` |
| `IncidentFactory` | `status(IncidentStatusEnum)`, `critical()`… |

Os testes criam só o que precisam, com os campos que importam para o caso, e deixam o resto com os padrões da factory.

## Os Fakes

`tests/Fakes/` tem implementações falsas dos três contratos de saída ([Saída](/saida)):

| Fake | Contrato | Guarda | Simula falha com |
|---|---|---|---|
| `FakeRepositoryProvider` | `RepositoryProvider` | `$calls`: cada chamada (`createBranch`, `pushChanges`, `openPullRequest`, `comment`) com os argumentos | `$failOn = 'pushChanges'` → `RuntimeException("pushChanges failed: 403 Forbidden")` |
| `FakeNotifier` | `Notifier` | `$sent` (conector, relatório e o `pr_url` **no momento do envio**) e `$alerts` | `$fail = true` → `channel_not_found` |
| `FakeIssueTracker` | `IssueTracker` | `$opened` e `$synced`; devolve chaves `FW-101`, `FW-102`… | `$failOpen = true` → "Jira indisponível (HTTP 503)" |

O `FakeRepositoryProvider` devolve sempre o commit `c0ffee1` e o PR `42`, com uma URL do Bitbucket.

Eles são ligados pela configuração, do mesmo jeito que as implementações reais:

```php
$this->app->instance(FakeRepositoryProvider::class, $repository = new FakeRepositoryProvider);
config(['firewatch.outgoing.repository' => ['bitbucket' => FakeRepositoryProvider::class]]);
```

Assim o teste do `DeliverIncidentOutcome` confere a **ordem** e o **conteúdo** das chamadas (branch → commit → PR → Slack → Jira) e o que acontece quando um passo falha, sem nenhuma requisição HTTP.

### Fakes ou Http::fake?

São dois níveis diferentes, e os dois são usados:

| Quando | Use |
|---|---|
| O teste é sobre **quem orquestra** (o job de entrega, o job de investigação, os alertas de budget) | Os Fakes: o teste olha as chamadas, não o HTTP |
| O teste é sobre **a integração em si** (`BitbucketRepositoryProvider`, `GitHubRepositoryProvider`, `SlackNotifier`, `JiraIssueTracker`, o teste de conexão) | `Http::fake()` com as respostas da API real, e `Http::preventStrayRequests()` |

Nos testes de integração, `Http::assertSent()` confere o método, a URL e o corpo de cada requisição (por exemplo, que o commit do Bitbucket vai num único `POST /src` multipart com a mensagem, a branch, o commit pai e o conteúdo final de cada arquivo), e `Http::assertNotSent()` prova o que **não** pode acontecer (por exemplo, tentar ler da branch base um arquivo que o diff está criando).

## As Fixtures

`tests/Fixtures/` guarda payloads **reais** de ferramentas externas, salvos como arquivo:

| Arquivo | O que é | Usado em |
|---|---|---|
| `sentry/event_alert.json` | Webhook de alerta de evento do Sentry | `SentryAdapterTest`, `WebhookEndpointTest` |
| `sentry/issue_created.json` | Webhook de issue criada do Sentry | `SentryAdapterTest` |

Uma fixture serve quando o formato vem de fora e é grande demais para escrever no teste. Se o Sentry mudar o formato, troca-se o arquivo, não os testes. Os payloads menores (webhook genérico, comando do Slack, respostas das APIs de saída) são escritos dentro do próprio teste, como array.

O runner tem suas próprias fixtures em `docker/runner/test/fixtures/` e uma gravação completa de uma investigação em `docker/runner/examples/incident-001/` ([Testes do runner](/runner/testes)).

## Como um teste é escrito

Os testes seguem o mesmo formato:

- **Nome em inglês e em frase**, dizendo o comportamento: `test_incident_stuck_in_the_queue_fails_and_the_team_is_notified`, `test_a_timeline_row_that_fails_to_save_does_not_stop_the_run`. A lista de nomes de um arquivo é a especificação daquela área.
- **Um comportamento por teste.** Variações do mesmo comportamento vão num `#[DataProvider]` (os adapters, o mascaramento, o diff, o texto do PR).
- **Sem rede, sem processo, sem relógio real.** `Http::fake()`, `Process::fake()` e `Carbon::setTestNow()` quando o tempo importa (watchdog, budget do mês, métricas por dia).
- **Pelo caminho de verdade.** Um teste de API chama a rota com `postJson()`, com o usuário logado e os middlewares; um teste de job roda o `handle()` com as dependências reais e só o mundo externo simulado.

Os arquivos `tests/Unit/ExampleTest.php` e `tests/Feature/ExampleTest.php` vieram do esqueleto do Laravel. O segundo faz um `GET /` e espera `200`.
