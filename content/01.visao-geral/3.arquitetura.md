O FireWatch tem quatro partes: o **painel** (Nuxt), o **cérebro** (Laravel e seus processos de apoio), o **executor** (runner em Docker, atrás de um proxy de saída) e as **integrações externas**.

## As peças

### Painel · Nuxt

A interface usada pelo time. Configura **conectores**, cadastra **aplicações**, edita os **perfis de agentes**, ajusta **custos e limites**, lista os **incidentes** com a **timeline ao vivo** de cada um, mostra o **dashboard de métricas** e a **auditoria** ([Conectores, aplicações, budget e métricas](/conectores-aplicacoes-budget-e-metricas)). Tem o botão de **simular incidente** para demonstração.

Consome a API REST do Laravel (autenticação por **Sanctum**, sessão com cookie) e escuta os canais privados do **Reverb** com o Laravel Echo (`nuxt-laravel-echo` + `pusher-js`).

### Cérebro · Laravel

Concentra as regras de negócio. Organizado em *Actions*, *Services*, *Jobs*, *Form Requests*, *API Resources* e *Enums*. Responsável por:

- **Receber eventos**: rotas `POST /api/webhooks/{connector}` e `POST /api/slack/commands/{connector}`, protegidas pelo middleware `verify-webhook` e por *rate limit*.
- **Normalizar**: cada origem tem um `IncomingAdapter` (Sentry, webhook genérico, comando do Slack) que converte o payload em um DTO padrão (`IncomingEvent`).
- **Registrar e deduplicar**: lock por *fingerprint* no Redis + transação no MySQL.
- **Decidir**: o `TriggerRulesEngine` avalia as regras da aplicação.
- **Orquestrar**: o job `InvestigateIncident` pega um slot, controla o budget, sobe o runner e consome o stream de eventos.
- **Entregar**: o job `DeliverIncidentOutcome` abre o PR pelo `RepositoryProvider`, notifica pelo `Notifier` e atualiza o card pelo `IssueTracker` ([Saída](/saida)).
- **Transmitir**: cada evento salvo vira um broadcast no Reverb.

O Laravel roda em vários processos, todos da mesma imagem (PHP 8.5-FPM):

| Serviço (compose) | Comando | Papel |
|---|---|---|
| `app` + `nginx` | PHP-FPM atrás do nginx (porta 8000) | API REST e webhooks |
| `runner-worker` | `queue:listen investigations`, um listener por slot | Roda o `InvestigateIncident`. Único serviço com acesso ao socket do Docker. |
| `queue` | `queue:listen --timeout=360` | Fila padrão: entrega (PR, Slack, Jira), alertas de budget |
| `reverb` | `reverb:start` (porta 8080) | Servidor WebSocket |
| `scheduler` | `schedule:work` | A cada 5 min, `firewatch:fail-stale-incidents` encerra incidentes travados como `stale`; diariamente, limpa a auditoria antiga |

### Dados · MySQL e Redis

- **MySQL** guarda o estado durável: conectores (credenciais criptografadas), aplicações, perfis de agentes, incidentes, execuções, eventos, configurações e auditoria.
- **Redis** é a fila (incluindo a conexão dedicada `investigations`), o cache e o lugar dos **locks**: deduplicação por fingerprint, slots de runner e alertas de budget.

### Horizon

O **Laravel Horizon** está instalado como painel de observação das filas no Redis (jobs pendentes, concluídos e com falha, tempos de execução). Em desenvolvimento, os workers sobem com `queue:listen` no `docker-compose.yml`; o runner-worker usa um listener por slot para respeitar o limite de execuções simultâneas.

### Reverb

Servidor WebSocket do próprio Laravel. Publica em dois canais privados:

- `firewatch`: canal global, com as mudanças de status de incidentes e de execuções (listas e dashboard).
- `incidents.{id}`: canal de um incidente, com cada `AgentEvent` e as mudanças de status da execução e do incidente (timeline ao vivo).

Configuração, autorização e payloads em [Tempo real](/tempo-real).

### Executor · runner em Docker

O `runner-worker` usa o Docker do host para criar **um container por execução** (`firewatch-run-<id>`), a partir da imagem configurada na aplicação (`firewatch-runner:latest` por padrão). O container:

1. Recebe o incidente, o prompt do orquestrador, os subagentes e a política de ferramentas em `/runner/input/` (via `docker cp`).
2. Recebe o token do repositório **pelo stdin**, nunca por variável de ambiente.
3. Clona o repositório, instala as dependências e roda o **Claude Code** em modo headless.
4. Confere o fluxo obrigatório, roda a suíte completa e emite o relatório.
5. É removido ao final (`docker rm --force`), com sucesso ou falha.

Isolamento aplicado em toda execução:

| Proteção | Padrão |
|---|---|
| CPU | `--cpus 2` |
| Memória (sem swap) | `--memory 4g` |
| Processos | `--pids-limit 1024` |
| Privilégios | `--cap-drop ALL`, `no-new-privileges`, usuário `runner` |
| Tempo total | 3600 s + 120 s de folga antes do `docker kill` |
| Ferramentas por agente | hook `PreToolUse` (`tool-guard.sh`) lendo `policy.json` |

### Proxy de saída · Squid

Os runners entram só na rede `firewatch-runner-net`, marcada como **`internal`**: sem rota e sem DNS para a internet. A única saída é o container `runner-egress` (Squid), que libera apenas os domínios das allowlists, em duas portas:

| Porta | Fase | Liberado |
|---|---|---|
| `3128` · setup | Clone e instalação de dependências | Bitbucket, GitHub, Packagist, npm, Yarn, PyPI |
| `3129` · agent | Claude Code e testes | **Só `api.anthropic.com`** |

Na fase dos agentes, o Claude Code não consegue baixar pacotes nem acessar outros sites. As allowlists ficam em `docker/runner/egress/allowlist-*.txt` e podem ser editadas sem rebuild (`docker compose restart runner-egress`).

### Integrações externas

| Direção | Integração | Interface no código |
|---|---|---|
| Entrada | Sentry, webhook genérico, comando do Slack | `IncomingAdapter` + `WebhookVerifier` |
| Saída | Bitbucket, GitHub | `RepositoryProvider` (`createBranch`, `pushChanges`, `openPullRequest`, `comment`) |
| Saída | Slack | `Notifier` |
| Saída | Jira | `IssueTracker` |
| Saída | Claude (Anthropic) | Claude Code CLI dentro do runner |

::note
O runner **não faz push**. Ele devolve o diff no relatório, e quem cria a branch, envia as alterações e abre o PR é o Laravel, com o token de escrita que nunca entra no container. Por isso o runner pode usar um `runner_token` somente leitura.
::
