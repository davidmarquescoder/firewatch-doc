O **FireWatch** é uma plataforma interna de resposta automática a incidentes de software. Quando um erro acontece em produção, um time de agentes de IA investiga a causa raiz no código, escreve um teste que reproduz o bug, implementa a correção, valida a suíte de testes e abre um Pull Request. O time é avisado no Slack e o card do Jira acompanha o caso do começo ao fim.

O desenvolvedor só revisa e aprova o PR. **Nada vai para produção sem aprovação humana.**

## O problema

Entre o erro acontecer e a correção estar pronta para revisão, o caminho costuma ser longo e manual:

1. O alerta chega no Sentry (ou em outro monitoramento) e alguém precisa notar.
2. Uma pessoa para o que está fazendo, lê o stack trace e tenta entender o contexto.
3. Ela abre o repositório, procura o trecho, cruza com `git log` e `git blame`.
4. Escreve a correção, às vezes sem um teste que prove o bug.
5. Abre o PR, cria ou atualiza o card e avisa o time.

Esse ciclo leva **horas ou dias**, interrompe quem estava em outra tarefa e depende de quem está de plantão. O FireWatch faz esse ciclo sozinho e entrega o resultado para revisão em **minutos**.

## O que ele faz, do alerta ao PR

::steps{level="3"}

### Recebe o alerta

Um erro chega por **Sentry**, por **webhook genérico** (qualquer ferramenta que envie JSON) ou pelo comando **`/firewatch investigar`** no Slack. A assinatura ou o token da requisição é verificado antes de qualquer coisa.

### Registra o incidente

O evento é normalizado, os dados sensíveis são mascarados e o erro é deduplicado por *fingerprint*. Várias ocorrências do mesmo erro viram **um único incidente**, com contagem de ocorrências e de usuários afetados.

### Decide se aciona os agentes

As regras de acionamento da aplicação (ambiente, severidade mínima, número de ocorrências, usuários afetados, padrões ignorados) decidem entre **acionar**, **aguardar** ou **ignorar**.

### Investiga e corrige em um container isolado

Um job na fila sobe um **runner** (container Docker descartável), que clona o repositório, instala as dependências e roda o **Claude Code** com um time de subagentes. O fluxo é obrigatório: triagem → causa raiz → teste que falha → correção → teste passa → suíte completa passa → relatório.

### Entrega o resultado

Com a correção validada, o FireWatch cria a branch `firewatch/<chave-jira>-<descrição>`, envia o diff e abre o **Pull Request** no Bitbucket (ou GitHub). Depois notifica o **Slack** e atualiza o card do **Jira**.

### Mostra tudo ao vivo

Cada passo dos agentes (arquivos lidos, comandos executados, testes rodados) aparece em tempo real na timeline do incidente no painel, via WebSockets.
::

::tip
Se algo falhar em qualquer etapa, o incidente termina como **Falhou** com o motivo explícito (o *failure kind*) e o próximo passo sugerido. O time é notificado mesmo assim.
::

## O que o FireWatch **não** faz

O FireWatch foi desenhado para propor, não para decidir. Algumas regras não são negociáveis:

::card-group
  :::card{icon="i-lucide-git-merge" title="Nunca faz merge"}
  O agente nunca faz merge nem push na branch base. Só cria branches com o prefixo `firewatch/`.
  :::

  :::card{icon="i-lucide-rocket" title="Nunca faz deploy"}
  O resultado é sempre um Pull Request. Aprovar e publicar continua com o time.
  :::

  :::card{icon="i-lucide-key-round" title="Sem credenciais de produção"}
  O runner recebe só o token do repositório (de preferência somente leitura) e a chave da API do Claude.
  :::

  :::card{icon="i-lucide-eye-off" title="Sem dados sensíveis para o modelo"}
  Tokens, senhas, CPFs, CNPJs, e-mails e telefones são mascarados antes de qualquer envio ao modelo.
  :::
::

## Para quem é

- **Time de desenvolvimento**: recebe um PR com causa raiz, teste e correção, em vez de um alerta cru.
- **Quem está de plantão**: acompanha a investigação pela timeline ao vivo e só entra quando o FireWatch não consegue resolver.
- **Liderança técnica**: vê métricas de incidentes, tempo até o PR, taxa de sucesso e custo por execução no dashboard.
