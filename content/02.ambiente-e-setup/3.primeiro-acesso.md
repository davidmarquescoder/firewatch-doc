Com os [pré-requisitos](/ambiente-e-setup) instalados e os [`.env`](/ambiente-e-setup/variaveis-de-ambiente) preenchidos, siga os passos abaixo uma única vez. Todos os comandos `artisan` rodam dentro do container `app`.

::steps{level="3"}

### Suba os serviços

```bash
cd firewatch-back
cp .env.example .env
docker compose up -d
```

### Instale as dependências e gere a chave

```bash
docker compose exec app composer install
docker compose exec app php artisan key:generate
```

A `APP_KEY` também é a chave que **criptografa as credenciais dos conectores**. Gere uma só vez: trocar a chave depois torna as credenciais salvas ilegíveis.

### Rode as migrations

```bash
docker compose exec app php artisan migrate
```

Cria as tabelas do framework (usuários, cache, jobs, sessões de token, notificações), da auditoria e de permissões, e as do domínio: `connectors`, `applications`, `incidents`, `agent_runs`, `agent_events`, `agent_profiles` e `app_settings`.

### Rode os seeders

```bash
docker compose exec app php artisan db:seed
```

O `DatabaseSeeder` chama, nesta ordem:

| Seeder | O que cria |
|---|---|
| `RoleSeeder` | Papéis `developer` (Desenvolvedor) e `admin` (Administrador) |
| `PermissionSeeder` | Permissões do sistema |
| `PermissionRoleSeeder` | Liga as permissões aos papéis |
| `AgentProfileSeeder` | O time padrão: Chefe de Plantão, Sentinela, Detetive, Advogado do Diabo, Cirurgião e Escrivão, com prompts (de `database/seeders/Agents/prompts`), ferramentas e níveis de acesso |

Os seeders podem rodar de novo sem duplicar nada (`firstOrCreate`). Eles **não sobrescrevem** perfis de agentes que já existem: para voltar um perfil editado ao padrão, use `firewatch:reset-agent-profiles` ([Prompts padrão](/perfis-de-agente/prompts-padrao)).

### Crie o primeiro usuário

```bash
docker compose exec app php artisan add-first
```

O comando `add-first` (`AddFirstDevUser`) pergunta nome, sobrenome, CPF, e-mail e senha (mínimo 8 caracteres, com confirmação), cria o usuário com e-mail já verificado e dá a ele o papel **developer**.

::note
Por segurança, ele só funciona **uma vez**: se já existir um usuário `developer`, o comando recusa. O painel ainda não tem tela de usuários: os próximos são criados pela API (`POST /api/v1/user`) por um `developer` ou `admin`, que pode indicar o papel no campo `role`. Veja [Papéis e permissões](/seguranca/papeis-e-permissoes).
::

### Construa a imagem do runner

```bash
docker compose --profile runner build runner
```

Sem a imagem `firewatch-runner:latest`, toda investigação falha ao subir o container. Detalhes em [Imagens do runner](/ambiente-e-setup/imagens-do-runner).

### Suba o painel e entre

```bash
cd ../firewatch-front
cp .env.example .env
pnpm install
pnpm dev
```

Abra `http://localhost:5000` e entre com o usuário criado no `add-first`.
::

## Depois do primeiro login

Para o FireWatch conseguir investigar um incidente de verdade, cadastre pelo painel:

1. **Conectores**: ao menos um de repositório (Bitbucket ou GitHub) e um de entrada (Sentry ou webhook genérico). Slack e Jira são opcionais. O botão **Testar conexão** confere cada um ([Conectores](/conectores-aplicacoes-budget-e-metricas)).
2. **Aplicação**: identificador no monitoramento, conector e slug do repositório, branch base, imagem do runner e regras de acionamento ([Aplicações](/conectores-aplicacoes-budget-e-metricas/aplicacoes)).
3. **Custos e limites**: confira o teto por execução e defina um teto mensal ([Budget](/conectores-aplicacoes-budget-e-metricas/budget)).

## Comandos úteis de manutenção

| Comando | Para quê |
|---|---|
| `php artisan firewatch:reset-agent-profiles [slugs…] [--force]` | Restaura prompts, ferramentas e permissões padrão dos agentes, desfazendo edições feitas no painel. Sem slugs, restaura todos. |
| `php artisan firewatch:fail-stale-incidents` | Encerra na hora os incidentes travados (o scheduler já roda a cada 5 min). |
| `php artisan firewatch:replay-run` | Ensaia a timeline ao vivo sem IA. Veja [Testar sem gastar créditos](/ambiente-e-setup/testar-sem-creditos). |

## E o `make:auth`?

::warning
**Não rode `make:auth` neste projeto.** Ele já foi aplicado.
::

O `make:auth` (`MakeAuth`) vem do template base do back-end. Ele gera a estrutura de autenticação (Sanctum + sessão) a partir dos stubs em `stubs/auth/`: os controllers em `app/Http/Controllers/Auth`, os Form Requests em `app/Http/Requests/Auth` e o arquivo `routes/auth.php`.

O FireWatch já tem essa estrutura, com ajustes próprios (login com Google, troca de senha obrigatória, bloqueio de usuário inativo). Como o comando **sobrescreve os arquivos sem perguntar**, rodá-lo de novo apagaria essas mudanças. Ele só é útil para começar um projeto novo a partir do mesmo template.

## Problemas comuns

::accordion
  :::accordion-item{icon="i-lucide-circle-help" label="O runner-worker não consegue usar o Docker (permission denied no docker.sock)"}
  O `DOCKER_GID` do `.env` não bate com o grupo do socket no host. Rode `stat -c %g /var/run/docker.sock`, corrija o valor e recrie o serviço: `docker compose up -d --force-recreate runner-worker`.
  :::

  :::accordion-item{icon="i-lucide-circle-help" label="O login funciona, mas a timeline não atualiza ao vivo"}
  Confira se `NUXT_PUBLIC_ECHO_KEY` é igual a `REVERB_APP_KEY`, se `NUXT_PUBLIC_ECHO_HOST` é `localhost` (não `reverb`) e se o host do painel está em `REVERB_ALLOWED_ORIGINS`. O `NUXT_PUBLIC_ECHO_LOG_LEVEL=3` mostra a conexão no console do navegador.
  :::

  :::accordion-item{icon="i-lucide-circle-help" label="O login retorna 419 ou 401"}
  O domínio do painel precisa estar em `SANCTUM_STATEFUL_DOMAINS` (com a porta) e `FRONTEND_URL` precisa apontar para ele. Use sempre o mesmo host (`localhost` ou `127.0.0.1`) no painel e na API.
  :::

  :::accordion-item{icon="i-lucide-circle-help" label="Incidentes ficam em Na fila para sempre"}
  O `runner-worker` não está rodando ou não tem slot. Veja `docker compose logs -f runner-worker`. Depois de 180 min o scheduler encerra esses incidentes como `stale`.
  :::
::
