O back-end segue a estrutura padrão do Laravel 13, com algumas pastas a mais para separar **regras de negócio** (Actions e Services) do **transporte HTTP** (Controllers, Requests e Resources). A regra geral:

::note
**O controller só recebe e responde.** Ele valida pela Form Request, chama uma Action ou um Service, e devolve um API Resource. Regra de negócio não fica no controller.
::

::mermaid
---

## Actions

Uma **Action** é um caso de uso: uma operação que o sistema faz, com um método público (`handle`, na grande maioria) e as dependências injetadas pelo construtor. Ficam agrupadas por domínio:

| Pasta | Exemplos |
|---|---|
| `Actions/Connector/` | `CreateConnectorAction`, `UpdateConnectorAction`, `TestConnectorConnectionAction` |
| `Actions/Application/` | `SaveApplicationAction` (cria e edita) |
| `Actions/AgentProfile/` | `SaveAgentProfileAction` |
| `Actions/Incident/` | `IngestIncomingEventAction`, `RegisterIncomingEventAction`, `EvaluateIncidentTriggerAction`, `RetryIncidentInvestigationAction`, `SimulateIncidentAction`, `FailStaleIncidentsAction`, `OpenIncidentIssueAction` |
| `Actions/Organization/` | `CreateOrganizationAction`, `UpdateOrganizationAction` |
| `Actions/` (raiz) | `CreateAddressAction`, `UpdateAddressAction`, `UploadFileAction` (herdadas do template) |

Uma Action pode chamar outras. O `IngestIncomingEventAction`, por exemplo, só compõe o fluxo de entrada:

```php [app/Actions/Incident/IngestIncomingEventAction.php]
public function handle(IncomingAdapter $adapter, array $payload): IncidentRegistration
{
    $event = $adapter->normalize($payload);

    $application = Application::findByMonitoringIdentifier($event->application)
        ?? throw IgnoredIncomingPayloadException::because("no active application …");

    $registration = $this->register->handle($application, $event);

    return $registration->withDecision($this->evaluate->handle($registration->incident));
}
```

Quando uma Action devolve mais de um valor, ela usa um objeto de resultado na mesma pasta (ex.: `IncidentRegistration`, com o incidente, se foi criado e a decisão do trigger).

## Services

Os **Services** guardam as regras que não são um caso de uso em si: motores, integrações, adaptadores e utilitários de domínio. Cada subpasta é um assunto:

| Pasta | O que tem |
|---|---|
| `Services/Incoming/` | Interface `IncomingAdapter`, os adaptadores (Sentry, webhook genérico, comando do Slack), o DTO `IncomingEvent` e os verificadores de assinatura (`Verification/`) |
| `Services/Trigger/` | `TriggerRulesEngine` e os objetos `TriggerCheck`, `TriggerDecision` e `IgnorePattern` |
| `Services/Runner/` | `DockerRunner`, `RunnerSlots`, `InvestigationPromptBuilder`, `RunnerStreamMonitor`, `StreamEventMapper` e `FailureClassifier` |
| `Services/Outgoing/` | Interfaces em `Contracts/` (`RepositoryProvider`, `Notifier`, `IssueTracker`), as implementações (Bitbucket, GitHub, Slack, Jira), o parser de diff (`Diff/`) e o `InvestigationReport` |
| `Services/Connector/` | Teste de conexão de cada tipo de conector (`Testers/`) |
| `Services/Budget/` | `CostBudget` |
| `Services/Metrics/` | `IncidentMetrics` (dashboard) |
| `Services/Realtime/` | `RealtimeBroadcaster` |
| `Services/Security/` | `SensitiveDataMasker` |
| `Services/Audit/` | `AuditLogger` e o mascaramento da trilha de auditoria |

::tip
**Action ou Service?** Se a classe responde a "o que o sistema faz agora?" (criar um conector, reexecutar um incidente), é uma Action. Se responde a "como uma regra ou integração funciona?" (como decidir o trigger, como falar com o Bitbucket), é um Service. Actions usam Services, e o inverso é raro.
::

Integrações novas entram **pela interface**: um `RepositoryProvider` novo (GitLab, por exemplo) implementa o contrato em `Services/Outgoing/Contracts/` e é registrado no mapa `outgoing` do `config/firewatch.php`. Nenhum código de orquestração muda.

## Enums

Todos os status, tipos e níveis do domínio são **enums com valor `string`**, agrupados por modelo em `Enums/<Domínio>/` e com o sufixo `Enum`:

| Pasta | Enums |
|---|---|
| `Enums/Incident/` | `IncidentStatusEnum`, `IncidentSeverityEnum`, `IncidentFailureKindEnum`, `TriggerOutcomeEnum` |
| `Enums/AgentRun/` | `AgentRunStatusEnum` |
| `Enums/AgentEvent/` | `AgentEventTypeEnum` |
| `Enums/AgentProfile/` | `AgentRoleEnum`, `AgentCommandAccessEnum`, `AgentWriteAccessEnum` |
| `Enums/Connector/` | `ConnectorTypeEnum`, `ConnectorStatusEnum` |
| `Enums/Security/` | `RoleEnum`, `PermissionEnum`, `PermissionRoleEnum` |
| `Enums/Audit/`, `Enums/Auth/`, `Enums/Business/` | Auditoria, provedores de login e enums do template |

Todo enum segue o mesmo formato: os casos em MAIÚSCULAS, a constante `LABELS` com os rótulos em português e os métodos `all()`, `labels()` e `label()`.

```php [app/Enums/AgentRun/AgentRunStatusEnum.php]
enum AgentRunStatusEnum: string
{
    case PENDING = 'pending';
    case RUNNING = 'running';
    case FIXED   = 'fixed';
    case FAILED  = 'failed';
    case DRY_RUN = 'dry_run';

    public const LABELS = [
        self::PENDING->value => 'Aguardando',
        // …
    ];

    public static function all(): array { return array_column(self::cases(), 'value'); }
    public static function labels(): array { return self::LABELS; }
    public function label(): string { return self::LABELS[$this->value] ?? $this->value; }

    public function isFinished(): bool { /* … */ }
}
```

Além disso, o enum é o lugar das **regras que dependem só do valor**: `IncidentStatusEnum::canTransitionTo()` guarda a máquina de estados, `ConnectorTypeEnum::requiredCredentials()` diz quais credenciais cada tipo exige, `IncidentFailureKindEnum::nextStep()` diz ao time o que fazer. As Resources devolvem sempre o par `campo` + `campo_label`, então o painel nunca traduz valores por conta própria.

## Resources

Os **API Resources** (`Http/Resources/<Domínio>/`) definem o JSON de cada modelo. São a fronteira de segurança da resposta: nenhum controller devolve um modelo cru.

O caso mais importante é o `ConnectorResource`, que **nunca devolve credenciais**. No lugar delas, devolve só quais chaves estão preenchidas:

```php [app/Http/Resources/Connector/ConnectorResource.php]
'credentials' => collect($required)->mapWithKeys(
    fn ($key) => [$key => in_array($key, $configured, true)]
),
// { "access_token": true, "runner_token": false }
```

## Traits

| Trait | Onde | Para quê |
|---|---|---|
| `ApiResponse` | `Controller` base | Respostas JSON padronizadas (`success()` e `error()`). Detalhes em [Padrões](/backend/padroes#a-trait-apiresponse). |
| `UploadFile` | `Controller` base | `uploadFile()` e `deleteFile()` para arquivos enviados (logo da organização). |

As duas entram em todos os controllers pela classe base `App\Http\Controllers\Controller`, junto com `AuthorizesRequests`.

## Exceptions

O FireWatch prefere **exceções de domínio perto de quem as lança**. A pasta `app/Exceptions/` só tem o que não pertence a um Service:

| Exceção | Pasta | Quando |
|---|---|---|
| `InvalidIncidentTransitionException` | `Exceptions/` | Transição de status proibida pela máquina de estados (`DomainException`) |
| `InvalidIncomingPayloadException` | `Services/Incoming/` | Payload sem os dados mínimos: a API responde **422** |
| `IgnoredIncomingPayloadException` | `Services/Incoming/` | Evento válido que não abre incidente: a API responde **202** com `ignored: true` |
| `RunnerLaunchException` | `Services/Runner/` | Não deu para subir o runner: vira o kind `configuration` |
| `RepositoryProviderException` | `Services/Outgoing/` | Falha ao falar com Bitbucket ou GitHub |
| `NotificationException` | `Services/Outgoing/` | Falha ao notificar (Slack) |
| `IssueTrackerException` | `Services/Outgoing/` | Falha no Jira |
| `DiffException` | `Services/Outgoing/Diff/` | Diff do relatório que não pode ser aplicado |

As exceções usam **construtores nomeados** (`::because()`, `::from()`) com a mensagem montada dentro da classe. Os erros das integrações de saída são capturados no `DeliverIncidentOutcome` e viram um `AgentEvent` de erro na timeline, sem derrubar as outras entregas.

No `bootstrap/app.php`, toda rota `api/*` (ou requisição que pede JSON) recebe erros em JSON, e a falta de autenticação vira `401` com `{ "message": … }`.

## Outras pastas

| Pasta | Conteúdo |
|---|---|
| `Models/<Domínio>/` | Um modelo por pasta (`Models/Incident/Incident.php`). Todos usam **UUID** (`HasUuids`) e o atributo `#[Fillable]`; a maioria usa `SoftDeletes` (exceto `AgentRun`, `AgentEvent`, `AppSetting` e `User`). |
| `Http/Requests/<Domínio>/` | `Store…Request` e `Update…Request`. Regras comuns entre os dois ficam numa trait `…Rules` na mesma pasta (ex.: `ApplicationRules`). |
| `Http/Middleware/` | `EnsureUserIsActive`, `EnsurePasswordChange` e `VerifyIncomingWebhook`, registrados com alias no `bootstrap/app.php`. |
| `Jobs/` | `InvestigateIncident`, `DeliverIncidentOutcome` e `SendBudgetAlert`. |
| `Events/Realtime/` + `Broadcasting/` | Eventos de tempo real e a definição dos canais `firewatch` e `incidents.{id}`. |
| `Console/Commands/` | `add-first`, `make:auth`, `firewatch:replay-run`, `firewatch:reset-agent-profiles` e `firewatch:fail-stale-incidents`. |
