## A trait `ApiResponse`

Toda resposta da API tem o mesmo envelope: uma **mensagem** legível e os **dados**.

```json
{
  "message": "Conector criado com sucesso.",
  "data": { "id": "9d3c…", "type": "bitbucket", "name": "Bitbucket da empresa" }
}
```

A trait `App\Traits\ApiResponse` monta esse envelope e está em todos os controllers pela classe base `Controller`. Ela tem dois métodos:

| Método | Assinatura | Status padrão |
|---|---|---|
| `success()` | `success(string $message, Model\|Collection\|JsonResource\|LengthAwarePaginator\|array $data = [], int $code = 200)` | `200` |
| `error()` | `error(string $message, array $data = [], int\|string $code = 500)` | `500` |

O `error()` aceita `int|string` no código porque costuma receber `$e->getCode()`, que pode vir como texto (códigos SQL, por exemplo). Qualquer código que não seja um inteiro HTTP válido (menor que 100, zero ou texto) vira **500**.

### Como os controllers usam

```php [app/Http/Controllers/ConnectorController.php]
public function store(StoreConnectorRequest $request, CreateConnectorAction $action): JsonResponse
{
    $connector = $action->handle($request);

    return $this->success(
        message: __('messages.response.connector.store'),
        data: new ConnectorResource($connector->loadCount('applications')),
        code: Response::HTTP_CREATED,
    );
}

public function destroy(Connector $connector): JsonResponse
{
    if ($connector->applications()->exists()) {
        return $this->error(
            message: __('messages.exception.connector.in_use'),
            code: Response::HTTP_CONFLICT,
        );
    }

    $connector->delete();

    return $this->success(message: __('messages.response.connector.destroy'));
}
```

Regras práticas:

- Use **argumentos nomeados** (`message:`, `data:`, `code:`) e as constantes de `Symfony\Component\HttpFoundation\Response` em vez de números soltos.
- A mensagem vem sempre de uma chave de tradução (`__('messages.response.<recurso>.<ação>')`).
- Os dados passam por um **API Resource**, nunca o modelo cru.
- Use `error()` para **regras de negócio** que o cliente precisa entender (ex.: `409` para conector em uso). Erros inesperados ficam com o handler do framework, que já responde em JSON para `api/*`.

::note
**Listagens paginadas** fogem do envelope simples: os controllers montam o JSON à mão para incluir `meta` (paginação) e, em algumas telas, `stats` (contadores para os cards do painel). O formato continua começando por `message` e `data`.
::

```json
{
  "message": "Conectores listados com sucesso.",
  "data": [ … ],
  "meta": { "current_page": 1, "per_page": 10, "total": 4, … },
  "stats": { "total": 4, "active": 3, "error": 1, "inactive": 0 }
}
```

### Duas gerações de controllers

| Estilo | Onde | Como trata erros |
|---|---|---|
| **Template** | `UserController`, `OrganizationController` | `try/catch (\Exception)` em cada método, com `DB::beginTransaction()`/`rollBack()` e `$this->error($e->getMessage())`. É o formato que o stub `controller.api` gera. |
| **FireWatch** | Conectores, aplicações, incidentes, agentes, budget, métricas, webhooks | Sem `try/catch`: valida pela Form Request, delega para uma Action e deixa as exceções inesperadas com o handler. |

Prefira o estilo **FireWatch** em código novo. O `try/catch` genérico devolve a mensagem crua da exceção para o cliente, o que pode expor detalhes internos.

## Stubs customizados

A pasta `stubs/` sobrescreve os modelos que o `php artisan make:*` usa. Quase todos são iguais aos do Laravel (publicados com `stub:publish`); **cinco foram customizados**, e há os stubs próprios do `make:auth`:

### `model.stub`

```php [stubs/model.stub]
#[Fillable([])]
#[Hidden([])]
class {{ class }} extends Model
{
    use HasUuids;
    use SoftDeletes;

    protected function casts(): array
    {
        return [];
    }
}
```

Todo modelo nasce com **UUID** como chave, **soft delete** e os atributos `#[Fillable]`/`#[Hidden]` (em vez das propriedades `$fillable`/`$hidden`). Modelos de histórico que nunca são apagados, como `AgentRun` e `AgentEvent`, removem o `SoftDeletes` depois de gerados.

### `migration.create.stub`

```php [stubs/migration.create.stub]
Schema::create('{{ table }}', function (Blueprint $table) {
    $table->uuid('id')->primary();

    $table->foreignUuid('user_id')->constrained('users');

    $table->timestamps();
    $table->softDeletes();
});
```

Combina com o stub do modelo: chave UUID e `softDeletes()`. A linha `foreignUuid('user_id')` vem do template e **deve ser removida** quando a tabela não pertence a um usuário (é o caso de todas as tabelas do domínio do FireWatch).

### `request.stub`

Igual ao do Laravel, mas `authorize()` devolve **`true`**. A autorização fica nas rotas (middleware `auth:sanctum`, `ensure-user-active`, `ensure-password-change`) e nas permissões, não em cada Form Request.

### `controller.api.stub` e `controller.model.api.stub`

Geram controllers de API com os cinco métodos REST no estilo **template** (`try/catch`, transação, `response()->json` com `message` e `data`). O `controller.model.api` já preenche as chaves de tradução `messages.response.{{ modelVariable }}.<ação>`.

::warning
Esses dois stubs geram `destroy()` com `HTTP_NO_CONTENT` (204) **e** um corpo JSON; a resposta 204 descarta o corpo. Os controllers do FireWatch respondem `200` com a mensagem no `destroy()`. Ajuste o código gerado.
::

## Nomenclatura

### Idioma

| O quê | Idioma | Exemplo |
|---|---|---|
| Código, classes, métodos, variáveis | Inglês | `RegisterIncomingEventAction::handle()` |
| Tabelas, colunas, valores de enum | Inglês | `agent_runs.status = 'pr_opened'` |
| Commits | Inglês | `Add GitHub repository provider` |
| Textos de interface, mensagens da API, rótulos | Português | `'PR aberto'`, `'Conector criado com sucesso.'` |
| Comentários | Inglês, na maioria | |

### Sufixos e lugares

| Tipo | Padrão | Exemplo |
|---|---|---|
| Action | `<Verbo><Objeto>Action` em `Actions/<Domínio>/` | `RetryIncidentInvestigationAction` |
| Enum | `<Modelo><Atributo>Enum` em `Enums/<Domínio>/` | `IncidentFailureKindEnum` |
| Form Request | `Store<Modelo>Request` / `Update<Modelo>Request` | `StoreConnectorRequest` |
| Regras compartilhadas | Trait `<Modelo>Rules` | `ApplicationRules` |
| Resource | `<Modelo>Resource` em `Http/Resources/<Domínio>/` | `IncidentResource` |
| Model | Uma pasta por domínio | `Models/AgentRun/AgentRun.php` |
| Exceção | `…Exception`, com construtor nomeado | `IgnoredIncomingPayloadException::because()` |
| Interface | Nome do papel, sem prefixo `I` | `RepositoryProvider`, `Notifier` |
| Comando | `firewatch:<verbo>-<objeto>` | `firewatch:fail-stale-incidents` |
| Job | Verbo no imperativo | `InvestigateIncident`, `DeliverIncidentOutcome` |

### Outras convenções

- **Rotas da API** em `/api/v1/<recurso-no-singular>` (ex.: `/api/v1/connector`, `/api/v1/incident/{id}/retry`). Webhooks ficam fora do `v1` (`/api/webhooks/{connector}`).
- **Branches dos agentes**: `firewatch/<chave-jira>-<descricao-curta>`.
- **Referências de tarefa** nos comentários: `PL-0xx` (ex.: `// PL-094: cost limits`) aponta para o item do planejamento que motivou o trecho.
- **Formatação**: `.editorconfig` com 4 espaços, LF e newline no fim do arquivo (2 espaços em YAML). O Laravel Pint está instalado (`vendor/bin/pint`), com a configuração padrão.
- **Testes**: PHPUnit 12, em `tests/Feature/<Domínio>` e `tests/Unit/<Domínio>`.

## `CLAUDE.md` e `AGENTS.md`

O back-end tem dois arquivos lidos por assistentes de código. Eles não são usados pelo FireWatch em execução: servem para quem desenvolve **com** IA no repositório.

### `CLAUDE.md`

O **contexto do projeto** para o Claude Code: o que é o FireWatch, contexto de negócio, stack, arquitetura, padrões obrigatórios (`IncomingAdapter`, `RepositoryProvider`, `Notifier`, credenciais criptografadas), modelos de domínio, o time de agentes, as **regras de segurança não negociáveis**, o escopo do MVP, convenções de código e a ordem de desenvolvimento. É carregado automaticamente no início de toda sessão do Claude Code aberta no `firewatch-back`.

Foi escrito no começo do projeto e algumas partes ficaram para trás em relação ao código:

| O `CLAUDE.md` diz | O código hoje |
|---|---|
| Testes com Pest | PHPUnit 12 (o Pest não está instalado; só há `pest.stub` e a permissão de plugin no `composer.json`) |
| GitHub e GitLab fora do MVP | Há um `GitHubRepositoryProvider` implementado |
| "MySQL ou PostgreSQL" | MySQL 8.3 |
| Conectores: sentry, bitbucket, slack, jira, generic_webhook | Também `github` |

::tip
Ao mudar uma regra de arquitetura ou de segurança, atualize o `CLAUDE.md` junto: é o que os assistentes leem antes de mexer no código.
::

### `AGENTS.md`

É o arquivo padrão do esqueleto do Laravel 13 para agentes de IA (Codex, Cursor e outros). Ele **não descreve o FireWatch**: só instrui o agente a conferir PHP e Composer e a instalar o **Laravel Boost** (`composer require laravel/boost --dev` e `php artisan boost:install`), que gera diretrizes específicas do projeto e substitui o próprio arquivo.

O Boost **não está instalado** no projeto. Na prática, o contexto real do FireWatch está no `CLAUDE.md`. Se a equipe usar outros agentes além do Claude Code, vale trocar o conteúdo do `AGENTS.md` pelo do `CLAUDE.md` (ou rodar o `boost:install`).
