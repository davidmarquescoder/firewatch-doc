Uma **aplicação** é um sistema monitorado pelo Firewatch. Ela diz três coisas: como reconhecer os erros dela que chegam pela entrada, onde está o código e como rodar esse código no runner. É cadastrada no painel, em **Aplicações**.

| Peça | Onde |
|---|---|
| Modelo | `app/Models/Application/Application.php` |
| API | `ApplicationController`, `StoreApplicationRequest`, `UpdateApplicationRequest` (regras comuns em `ApplicationRules`), `ApplicationResource` |
| Gravação | `SaveApplicationAction` (criação e edição) |

## Campos

| Campo | Obrigatório | Padrão | Validação | Para quê |
|---|---|---|---|---|
| `name` | Sim | | Único, até 255 | Nome no painel, no Slack e no Jira |
| `monitoring_identifier` | Sim | | Único, até 255 | Como a aplicação aparece no Sentry ou no webhook |
| `repository_connector_id` | Não | | Conector **Bitbucket ou GitHub** existente e não removido | Por onde o código é lido e o PR é aberto |
| `repository_slug` | Com conector | | `dono/repositorio` (`^[\w.-]+/[\w.-]+$`) | Repositório dentro do conector |
| `issue_tracker_connector_id` | Não | | Conector **Jira** existente e não removido | Onde o card do incidente é criado e atualizado. Sem ele, vale qualquer Jira conectado |
| `base_branch` | Não | `main` | Não pode começar com `firewatch/` | De onde o runner parte e para onde o PR aponta |
| `runner_image` | Não | `firewatch-runner:latest` | `^[\w./:@-]+$` | Imagem do container dos agentes |
| `install_command` | Não | `auto` | Até 2000 | Instalação das dependências |
| `test_command` | Não | `auto` | Até 2000 | Suíte de testes |
| `trigger_rules` | Não | `DEFAULT_TRIGGER_RULES` | Ver abaixo | Quais erros acionam os agentes |
| `active` | Não | `true` | Booleano | Aplicação inativa não recebe incidentes |

O `SaveApplicationAction` faz três normalizações antes de gravar:

- `base_branch` ou `runner_image` enviados **vazios** voltam ao padrão;
- comandos vazios ficam `null` no banco e viram `auto` só na hora de montar o runner (`runnerInstallCommand()`, `runnerTestCommand()`);
- remover o conector (`repository_connector_id` vazio) também limpa o `repository_slug`.

### Identificador no monitoramento

É a ponte com a entrada: cada evento traz o nome da aplicação (no Sentry, o slug do projeto; no webhook genérico, o campo `application`), e `Application::findByMonitoringIdentifier()` procura uma aplicação **ativa** com esse valor. Sem aplicação ativa, o evento é ignorado ([Payloads ignorados e inválidos](/entrada/payloads-ignorados-e-invalidos)). Por isso o campo é único.

### Regras de acionamento

`trigger_rules` aceita só as chaves `enabled`, `min_severity`, `min_occurrences` (≥ 1), `min_affected_users` (≥ 0), `environments` e `ignore_patterns` (cada padrão, texto ou `/regex/flags`, é validado pelo `IgnorePattern`). O que é guardado é **mesclado** sobre os padrões por `resolvedTriggerRules()`, então um JSON parcial no banco sempre fica completo na leitura:

```json
{
  "enabled": true,
  "min_severity": "error",
  "min_occurrences": 1,
  "min_affected_users": 0,
  "environments": ["production"],
  "ignore_patterns": []
}
```

A API devolve as duas formas: `trigger_rules` (o que foi gravado) e `resolved_trigger_rules` (o que vale). Como cada regra é avaliada está em [Motor de regras](/registro-e-trigger/motor-de-regras).

## Imagem e comandos do runner

Os três campos de execução viram parte do `docker create` e das variáveis do runner ([DockerRunner](/investigacao/docker-runner)):

| Campo | Vai para | Vazio |
|---|---|---|
| `runner_image` | Último argumento do `docker create` | `firewatch-runner:latest` |
| `install_command` | `INSTALL_COMMAND` | `auto`: o entrypoint detecta Composer, npm/pnpm/yarn ou pip |
| `test_command` | `TEST_COMMAND` | `auto`: idem, para a suíte |

Cada aplicação escolhe a imagem que tem os runtimes do seu projeto: `firewatch-runner:latest` (PHP e Node) ou uma derivada, como `firewatch-runner:python`. Como construir e estender as imagens está em [Imagens do runner](/ambiente-e-setup/imagens-do-runner) e em [Runner](/runner). Uma imagem ou comando errados aparecem como falha `install` na investigação, com a dica "Confira a imagem do runner e o comando de instalação da aplicação."

A imagem recebe o token de clone e a credencial do Claude, por isso o Firewatch só usa imagens que **já estão no host** e têm o label `br.com.firewatch.runner.contract` com o contrato esperado. Ele nunca baixa uma imagem de um registry (`--pull never`). Uma imagem que não passa na conferência faz a investigação falhar antes de subir o container, com kind `configuration` e um motivo que diz o que falta ([A imagem](/investigacao/docker-runner#a-imagem)). Assim, quem edita uma aplicação só escolhe entre as imagens que o administrador do servidor construiu ou baixou.

::note
A validação do formulário confere só o formato do nome. Uma imagem inexistente é aceita no cadastro e só falha na primeira investigação.
::

## Vínculo com os conectores

::mermaid
---
code: |
  flowchart LR
      S[Conector Sentry / webhook] -->|evento com monitoring_identifier| A[Aplicação]
      A -->|repository_connector_id + repository_slug| R[Conector Bitbucket / GitHub]
      A -.->|todos os ativos| N[Conectores Slack]
      A -->|issue_tracker_connector_id, ou qualquer ativo| J[Conector Jira]
---
::

| Conector | Como se liga à aplicação |
|---|---|
| Entrada (Sentry, webhook) | **Sem** chave estrangeira. Qualquer conector de entrada pode trazer eventos de qualquer aplicação; o casamento é pelo `monitoring_identifier` |
| Repositório (Bitbucket, GitHub) | `repository_connector_id` (`belongsTo`). Um conector serve várias aplicações |
| Jira | `issue_tracker_connector_id` (`belongsTo`, opcional). Um único Jira recebe o card de cada incidente (`OutgoingIntegrations::issueTrackerConnectorFor()`): o **vinculado**, e nenhum outro (vinculado mas inativo = sem card); sem vínculo, o **primeiro Jira ativo por nome**; sem nenhum Jira conectado, nada é feito no Jira e o fluxo do PR segue normal, com a branch `firewatch/inc-…` |
| Slack | **Sem** relação. Toda notificação vai para todos os conectores ativos do tipo, para qualquer aplicação |

O conector de repositório é usado em três lugares:

| Onde | O que usa |
|---|---|
| Runner | `REPO_URL` montada com `repository_slug`, usuário por tipo, `runner_token` ou `access_token` ([GitHub e Bitbucket](/saida/repositorios#clone-no-runner)) |
| Entrega | `RepositoryProvider` do tipo do conector, com `access_token` |
| Teste de conexão | O tester lê os `repository_slug` de todas as aplicações ligadas ([Conectores](/conectores-aplicacoes-budget-e-metricas#os-testers)) |

Aplicação **sem** conector de repositório pode ser cadastrada e recebe incidentes, mas a investigação falha ao subir o runner: "A aplicação não tem repositório configurado (conector e repositório)."

A validação não confere se o `repository_slug` existe nem se o conector está ativo. Use o **Testar conexão** do conector depois de ligar a aplicação: ele lê cada repositório ligado.

Integridade:

| Evento | Efeito |
|---|---|
| Remover o conector pela API | Bloqueado (409) enquanto alguma aplicação o usa, como repositório ou como Jira |
| Conector apagado de vez no banco | `repository_connector_id` ou `issue_tracker_connector_id` vira `null` (`ON DELETE SET NULL`) |
| Remover a aplicação | Soft delete. Os incidentes **ficam**, e as métricas mostram o nome da aplicação removida |

## API

| Rota | O que faz |
|---|---|
| `GET /api/v1/application` | Lista paginada (padrão 10, até 100), em ordem de nome, com o conector e `incidents_count`. `search` procura em nome, identificador e repositório; `active` filtra. Devolve `stats`: `total`, `active`, `inactive` |
| `POST /api/v1/application` | Cria |
| `GET /api/v1/application/{id}` | Mostra |
| `PUT/PATCH /api/v1/application/{id}` | Atualização parcial (mesmas regras, com unicidade ignorando a própria aplicação) |
| `DELETE /api/v1/application/{id}` | Soft delete |
| `POST /api/v1/application/{id}/simulate-incident` | Botão **Simular incidente** (até 30 por minuto) ([Simulação](/registro-e-trigger/simulacao)) |

A resposta inclui um resumo do conector, sem credenciais:

```json
{
  "name": "Loja",
  "monitoring_identifier": "loja-back",
  "repository_connector": { "id": "…", "name": "Bitbucket Acme", "type": "bitbucket", "status": "active" },
  "repository_slug": "acme/loja",
  "base_branch": "main",
  "runner_image": "firewatch-runner:latest",
  "install_command": null,
  "test_command": null,
  "trigger_rules": {},
  "resolved_trigger_rules": { "enabled": true, "min_severity": "error", "…": "…" },
  "active": true,
  "incidents_count": 12
}
```

Toda mudança de campo vai para a [auditoria](/seguranca/auditoria) (log `configuration`, só os campos alterados).
