Um **conector** é uma conta de um serviço externo cadastrada no painel, em **Conectores**. Ele guarda as credenciais (criptografadas) e as configurações não secretas que o Firewatch usa para receber erros, mexer no repositório e avisar o time.

| Peça | Onde |
|---|---|
| Modelo | `app/Models/Connector/Connector.php` |
| Tipos e campos | `app/Enums/Connector/ConnectorTypeEnum.php` |
| Status | `app/Enums/Connector/ConnectorStatusEnum.php` |
| API | `ConnectorController`, `StoreConnectorRequest`, `UpdateConnectorRequest`, `ConnectorResource` |
| Gravação | `CreateConnectorAction`, `UpdateConnectorAction` |
| Teste de conexão | `TestConnectorConnectionAction`, `ConnectionTesterFactory`, `app/Services/Connector/Testers/` |
| Formulário do painel | `firewatch-front/app/utils/connectorTypes.ts` (espelha o enum) |

## Os tipos

| Tipo | Rótulo | Categoria no painel | Para quê |
|---|---|---|---|
| `sentry` | Sentry | Entrada de erros | Recebe alertas de uma integração interna do Sentry |
| `generic_webhook` | Webhook genérico | Entrada de erros | Qualquer ferramenta que envie um POST com o erro |
| `bitbucket` | Bitbucket | Repositório | Clone do runner, branch `firewatch/*`, commit e PR |
| `github` | GitHub | Repositório | Idem, no GitHub |
| `slack` | Slack | Notificação e gestão | Mensagem a cada incidente, alertas de custo e o comando `/firewatch` |
| `jira` | Jira | Notificação e gestão | Um card por incidente |

O enum agrupa os tipos com três métodos, usados em todo o backend:

| Método | Tipos | Quem usa |
|---|---|---|
| `isIncoming()` | `sentry`, `generic_webhook` | Entrada de eventos ([Entrada](/entrada)) |
| `receivesWebhooks()` | Os de entrada e `slack` | Middleware `verify-webhook` ([Verificação](/entrada/verificacao)) |
| `isRepository()` / `repositoryTypes()` | `bitbucket`, `github` | Validação da aplicação, runner e providers |

Para Slack e Jira, não há método no enum: as entregas percorrem os tipos registrados em `firewatch.outgoing` ([Contratos e registro](/saida#outgoingintegrations)).

## Os campos de cada tipo

Credenciais são **secretas**: vão para `credentials` (cast `encrypted:array`) e a API nunca as devolve. Settings são **não secretas**: vão para `settings` (JSON) e voltam na API.

| Tipo | Credenciais obrigatórias | Credenciais opcionais | Settings |
|---|---|---|---|
| `sentry` | `client_secret` | | `organization` (opcional) |
| `generic_webhook` | `secret` | | |
| `bitbucket` | `access_token` | `runner_token` | `workspace` (obrigatório) |
| `github` | `access_token` | `runner_token` | `owner` (opcional) |
| `slack` | `bot_token` | `signing_secret` | `channel` (obrigatório) |
| `jira` | `email`, `api_token` | | `base_url` (obrigatório, `https://`), `project_key` (obrigatório, até 20), `issue_type` (opcional) |

O que cada campo faz:

| Campo | Uso |
|---|---|
| `client_secret` (Sentry) | Valida a assinatura `Sentry-Hook-Signature` de cada webhook |
| `secret` (webhook genérico) | HMAC-SHA256 em `X-Firewatch-Signature` ou `Authorization: Bearer`. O painel tem um botão que gera 48 bytes aleatórios |
| `access_token` (repositório) | Escrita, **só no Laravel**: branch, commit e PR ([GitHub e Bitbucket](/saida/repositorios)) |
| `runner_token` (repositório) | Leitura, **o único token que entra no container**, só para o clone. Sem ele, o runner clona com o `access_token` |
| `workspace` (Bitbucket) | Só o teste de conexão usa, quando nenhuma aplicação está ligada ao conector. O repositório de verdade vem do `repository_slug` da aplicação |
| `bot_token` (Slack) | `chat.postMessage` (escopos `chat:write` e `chat:write.public`) |
| `signing_secret` (Slack) | Só para o comando `/firewatch` |
| `channel` (Slack) | Canal ou id que recebe as mensagens |
| `email` + `api_token` (Jira) | Basic auth |
| `base_url`, `project_key`, `issue_type` (Jira) | Onde o card é criado ([Jira](/saida/jira#conector)) |

::note
`organization` (Sentry) e `owner` (GitHub) são aceitos e guardados, mas nenhum código do backend os lê hoje: servem só de anotação no painel.
::

Detalhes de criptografia, auditoria das rotações e o que vai para o runner estão em [Credenciais dos conectores](/seguranca/credenciais-dos-conectores).

## Criar, editar e remover

| Rota | O que faz |
|---|---|
| `GET /api/v1/connector` | Lista paginada (padrão 10, até 100), em ordem de nome, com `applications_count`. Filtros `search` (nome), `type`, `status`. Devolve também `stats`: `total`, `active`, `error`, `inactive` |
| `POST /api/v1/connector` | Cria |
| `GET /api/v1/connector/{id}` | Mostra |
| `PUT/PATCH /api/v1/connector/{id}` | Atualização parcial |
| `POST /api/v1/connector/{id}/test` | Testa a conexão (até 10 por minuto) |
| `DELETE /api/v1/connector/{id}` | Soft delete |

Regras da gravação:

- **Criação.** `type`, `name` (único) e `credentials` são obrigatórios. As regras de cada chave saem do enum: credencial obrigatória `required|string|max:4096`, opcional `nullable`, settings por `settingsRules()`. O `CreateConnectorAction` guarda **só** as chaves que o tipo aceita e descarta valores vazios. `status` aceita `active` ou `inactive`, padrão `active`.
- **Edição.** O tipo **não muda** (`prohibited`), porque é ele que define as credenciais. As credenciais enviadas são **mescladas** com as guardadas: o painel troca um segredo sem conhecer os outros, que a API nunca devolve. Mandar `null` ou `""` numa credencial **opcional** a remove. Settings só são validadas quando enviadas, e substituem as anteriores.
- **Remoção.** Bloqueada com **409** enquanto alguma aplicação usa o conector como repositório. Conectores de Slack e Jira podem ser removidos a qualquer momento.

A resposta (`ConnectorResource`) troca as credenciais por um mapa de booleanos, um por chave aceita:

```json
{
  "type": "bitbucket",
  "status": "active",
  "settings": { "workspace": "acme" },
  "credentials": { "access_token": true, "runner_token": false },
  "last_error": null,
  "last_verified_at": "2026-11-17T12:30:00Z",
  "applications_count": 2
}
```

## Status

| Status | Rótulo | Como chega lá |
|---|---|---|
| `active` | Ativo | Padrão na criação; teste de conexão com sucesso |
| `inactive` | Inativo | Só pelo usuário (criação ou edição) |
| `error` | Com erro | Teste de conexão que falhou num conector ativo |

O `error` só é posto pelo **Testar conexão**: uma falha numa entrega real (Slack fora do ar, token recusado no PR) vai para a timeline do incidente e **não** muda o status do conector.

Quem respeita o status:

| Onde | Comportamento |
|---|---|
| Notifiers e issue trackers | Só conectores `active` recebem resultados e alertas |
| Providers de repositório | Recusam escrever com conector que não está `active` |
| Clone no runner | **Não** confere o status: o runner clona mesmo com o conector `inactive` ou `error`. Só a abertura do PR é recusada depois |

## Testar conexão

`POST /api/v1/connector/{id}/test` chama o `TestConnectorConnectionAction`, que escolhe o tester pelo tipo (`ConnectionTesterFactory`), grava o resultado no conector e registra `connector_tested` na [auditoria](/seguranca/auditoria). Um teste que falha é um resultado válido: a resposta é **HTTP 200** com `result.ok: false`.

```json
{
  "result": {
    "ok": true,
    "message": "Acesso confirmado a 2 repositório(s).",
    "remote": true,
    "details": { "repositories": ["acme/loja", "acme/api"], "runner_token": "read_only" }
  },
  "connector": { "status": "active", "last_error": null, "last_verified_at": "…" }
}
```

O que muda no conector:

| Resultado | `status` | `last_error` | `last_verified_at` |
|---|---|---|---|
| Sucesso | `active` (um `inactive` continua `inactive`) | Limpo | Agora |
| Falha | `error` (um `inactive` continua `inactive`) | A mensagem | Inalterado |

Se o tester lançar uma exceção inesperada, o resultado vira "Erro inesperado ao testar a conexão." e o log guarda só a classe da exceção, porque a mensagem pode repetir dados da requisição.

### Os testers

Todos implementam `ConnectionTester::test(Connector): ConnectionTestResult`. Os que chamam APIs estendem `HttpConnectionTester`, que fixa timeout (`CONNECTOR_TEST_TIMEOUT`, 10 s, com 5 s de conexão) e user agent `Firewatch`, e converte erro de rede em "Não foi possível conectar ao serviço (tempo esgotado ou endereço inacessível)."

| Tester | Tipos | O que confere |
|---|---|---|
| `BitbucketConnectionTester` | `bitbucket` | Sem aplicações ligadas: lista o `workspace`. Com aplicações: lê **cada** `repository_slug`. Com `runner_token`: lê os mesmos repositórios com ele e recusa escopo de escrita |
| `GitHubConnectionTester` | `github` | Sem aplicações: `GET /user`. Com aplicações: lê cada repositório e exige `permissions.push`. Com `runner_token`: lê os repositórios e recusa se ele **pode** fazer push |
| `SlackConnectionTester` | `slack` | `auth.test`. O Slack responde HTTP 200 mesmo em erro, então o tester lê `ok` e `error` do corpo |
| `JiraConnectionTester` | `jira` | `GET myself` (credenciais) e `GET project/<chave>` (projeto) |
| `IncomingWebhookConnectionTester` | `sentry`, `generic_webhook` | **Local**, sem rede: o segredo existe e tem ao menos 16 caracteres. Devolve `remote: false` |

Os conectores de entrada não têm o que chamar: a prova real é o primeiro evento assinado que chega. A mensagem de sucesso diz isso: "Segredo configurado. Conectores de entrada são confirmados quando o primeiro evento assinado chegar."

A conferência do `runner_token` é a parte de segurança do teste: o token que entra no container precisa **ler** os repositórios e **não pode escrever** ([Isolamento](/runner/isolamento)).

| Serviço | Como o tester vê a escrita | Mensagem |
|---|---|---|
| Bitbucket | Cabeçalho `X-OAuth-Scopes` com `repository:write`, `repository:admin` ou `pullrequest:write` | "O token do runner tem permissão de escrita em "acme/loja" (…). Use um token só com Repositories: Read." |
| GitHub | `permissions.push: true` no repositório | "O token do runner tem permissão de escrita em "acme/loja". Use um token só com Contents: Read-only." |

As falhas HTTP seguem um padrão, "Falha ao <ação>: <dica> (HTTP <código>).":

| HTTP | Dica |
|---|---|
| 401 | credenciais inválidas ou expiradas |
| 403 | sem permissão para este recurso |
| 404 | recurso não encontrado |
| 429 | limite de requisições atingido, tente novamente em instantes |
| outro | resposta inesperada do serviço |

Nenhuma mensagem contém valores de credencial: o `ConnectionTestResult` é escrito para o painel, e `details` só leva fatos não secretos (login, workspace, repositórios, projeto).

|---|---|

| `tests/Feature/Api/ConnectorTestConnectionApiTest.php` | Cada tester, `runner_token` só leitura, 401, erro de rede, recuperação de `error` para `active`, `inactive` mantido, limite de 10 por minuto |
