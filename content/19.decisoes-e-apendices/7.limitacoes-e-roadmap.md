Esta página junta, num lugar só, as limitações registradas ao longo da documentação e o que ficou para depois do MVP. Cada item aponta para a página onde ele é explicado.

## O painel não tem "em breve"

O front tem um componente para telas futuras, `LayoutComingSoon` (selo **Em construção**), mas **nenhuma tela o usa**: todas as entradas do menu levam a telas que funcionam ([Layouts e navegação](/frontend/layouts-e-navegacao)). Também não há botões desativados nem itens marcados como "em breve".

O que falta no painel aparece de outro jeito: **recursos que existem na API e não têm tela**.

| Existe na API | No painel |
|---|---|
| Usuários: listar, criar, editar, desativar ([Usuários](/referencia-da-api/usuarios)) | Sem tela. O primeiro usuário vem do comando `add-first` ([Primeiro acesso](/ambiente-e-setup/primeiro-acesso)); os seguintes, pela API |
| Troca de senha obrigatória (`must_change_password`, `403 password_change_required`) | Sem tela de troca de senha ([Middlewares](/seguranca/middlewares)) |
| Organizações ([Organizações](/referencia-da-api/organizacoes)) | Sem tela. Vieram do template e não participam do fluxo de incidentes |

## Fora do MVP

O `CLAUDE.md` do projeto define o que ficou de fora do MVP. Como está hoje:

| Item | Situação |
|---|---|
| **Merge automático** | **Não planejado.** É uma regra de segurança: nenhuma alteração vai para produção sem aprovação humana. O runner não faz push, e os providers só abrem PR em branches `firewatch/` |
| **Deploy automático** da correção | **Não planejado**, pelo mesmo motivo |
| **GitHub** como repositório | **Feito**, antes do previsto: `GitHubRepositoryProvider` e conector `github` |
| **GitLab** | Não feito. Não há tipo de conector nem provider. Pelo [ADR 005](/decisoes-e-apendices/adr-005-contratos-de-saida), é uma classe nova, uma linha no config e o tipo no `ConnectorTypeEnum` |
| **Multi-tenant** | Não feito. Um Firewatch atende uma empresa: conectores, aplicações, budget e trilha de auditoria são globais. As tabelas de organizações do template não separam dados |
| **Pedidos de mudança pelo Slack** (outras equipes pedindo ajustes) | Fase 2. Hoje o comando do Slack só **abre** um incidente (`investigar <aplicação> <descrição>`) ([Adapters](/entrada/adapters)) |

## Limitações conhecidas

### Segurança e acesso

| Limitação | Onde |
|---|---|
| **Papéis e permissões não restringem nada** fora da gestão de usuários. Qualquer usuário logado cria e edita conectores (inclusive credenciais), muda o teto de custo, edita os prompts dos agentes e lê a auditoria inteira | [Papéis e permissões](/seguranca/papeis-e-permissoes) |
| O CORS aceita qualquer origem com `supports_credentials` | [Segurança](/seguranca) |
| A guarda de ferramentas não limita **leitura** por caminho, e a análise de comandos é sintática, não um sandbox | [Guarda de ferramentas](/runner/tool-guard) |
| O egress filtra por domínio, não por caminho; as duas portas do proxy estão na mesma rede; não há limite de banda; repositórios por SSH não funcionam | [Egress](/runner/egress#limitações-conhecidas) |
| O disco do runner não tem limite | [Isolamento](/runner/isolamento) |

### Investigação e entrega

| Limitação | Onde |
|---|---|
| Nada é refeito sozinho: um timeout ou uma falha de API exige **Reexecutar**, até 3 vezes por incidente | [Timeouts e reexecução](/investigacao/timeouts-e-reexecucao) |
| Uma falha ao abrir o PR **não tem botão** para tentar de novo: o incidente fica em **Testando** e o PR sai à mão, ou pelo `tinker` (repetindo os avisos) | [Troubleshooting](/operacao/troubleshooting#falha-ao-abrir-o-pr) |
| `comment()` do `RepositoryProvider` está implementado, mas a entrega não comenta no PR | [DeliverIncidentOutcome](/saida/deliver-incident-outcome) |
| A ordem de quem pega uma vaga livre não é garantida | [Slots de concorrência](/investigacao/slots-de-concorrencia) |
| O watchdog fecha o incidente, mas não mata um container que sobrou | [Timeouts e reexecução](/investigacao/timeouts-e-reexecucao) |
| O teto mensal pode ser ultrapassado por runs em paralelo; o mês é contado em UTC (`APP_TIME_ZONE` não tem efeito) | [Budget](/conectores-aplicacoes-budget-e-metricas/budget) |
| Testes da aplicação que dependem de serviços externos falham na rede restrita | [ADR 003](/decisoes-e-apendices/adr-003-egress-por-allowlist) |
| Só há imagem de runner para PHP/Node e Python | [ADR 004](/decisoes-e-apendices/adr-004-imagem-por-aplicacao) |
| A versão do Claude Code não é fixada na imagem (`latest`) | [ADR 002](/decisoes-e-apendices/adr-002-claude-code-cli) |

### Integrações

| Limitação | Onde |
|---|---|
| Entrada: Sentry, webhook genérico e comando do Slack | [Entrada](/entrada) |
| Repositório: Bitbucket e GitHub. Notificação: só Slack. Card: só Jira | [Saída](/saida) |

### Operação

| Limitação | Onde |
|---|---|
| Sem deploy automatizado nem `docker-compose` de produção | [Deploy](/operacao) |
| O Horizon está instalado, mas nenhum serviço o roda | [Filas e Horizon](/filas-agendamentos-e-comandos) |
| Os health checks não consultam banco, Redis nem filas, e ninguém os monitora | [Monitoramento](/operacao/monitoramento) |
| O log do Laravel é um arquivo só, sem rotação | [Monitoramento](/operacao/monitoramento#logs) |
| O painel não tem testes automatizados; o CI só roda lint e checagem de tipos | [CI e estilo](/testes-e-qualidade/ci-e-estilo) |
| O Dependabot do back não atualiza os pacotes do Composer | [CI e estilo](/testes-e-qualidade/ci-e-estilo) |

## Roadmap

O projeto **não tem um roadmap oficial** depois do MVP. A lista abaixo junta os próximos passos que a documentação e o código sugerem, agrupados pelo que destravam. É uma proposta para discutir, não um compromisso.

### Para usar com mais de um time

1. **Aplicar papéis e permissões nas rotas**: conectores, budget e perfis de agente só para administradores.
2. **Telas de usuários e de troca de senha** no painel, sobre a API que já existe.
3. **Limitar o CORS** à origem do painel.

### Para sair da máquina de desenvolvimento

1. **`docker-compose` de produção** com `queue:work`, sem phpMyAdmin nem portas de banco ([Deploy](/operacao)).
2. **Health check que consulte banco e Redis**, um monitor externo e log com rotação.
3. **Horizon** no lugar dos `queue:listen`, com um supervisor para as investigações.
4. **Fixar a versão do Claude Code** na imagem do runner e testar cada atualização com o incidente-001.

### Para entregar melhor

1. **Tentar de novo só a entrega** (PR, Slack, Jira) pelo painel, sem refazer a investigação.
2. **Comentar no PR** com o resumo da investigação (`comment()`).
3. **GitLab** como repositório e outros notifiers (Teams, Discord, e-mail), seguindo os contratos de saída.
4. **Novas stacks de runner** (Go, Ruby, Java), conforme as aplicações cadastradas pedirem.

### Fase 2

1. **Pedidos de mudança pelo Slack**, que o `CLAUDE.md` deixa para depois do MVP.
2. **Multi-tenant**, se o Firewatch passar a atender mais de uma empresa.
