## Contexto

O MVP entrega em três ferramentas: o PR no **Bitbucket**, o aviso no **Slack** e o card no **Jira**. Mas o `CLAUDE.md` já dizia que o sistema "deve ser agnóstico para permitir GitHub/GitLab depois", e outras empresas usam Teams, Discord, Linear, GitLab. O fluxo que chama essas ferramentas, por outro lado, é sempre o mesmo: depois da investigação, criar a branch, enviar a correção, abrir o PR, avisar o time e atualizar o card, cada passo isolado dos outros.

## Decisão

**Cada tipo de integração é uma interface**, e a implementação é escolhida pelo **tipo do conector**, por um mapa no config:

| Contrato | Métodos | Implementações hoje |
|---|---|---|
| `RepositoryProvider` | `createBranch`, `pushChanges`, `openPullRequest`, `comment` | Bitbucket, GitHub |
| `Notifier` | `notify`, `alert` | Slack |
| `IssueTracker` | `open`, `sync` | Jira |

```php [config/firewatch.php]
'outgoing' => [
    'repository'     => ['bitbucket' => BitbucketRepositoryProvider::class, 'github' => GitHubRepositoryProvider::class],
    'notifiers'      => ['slack' => SlackNotifier::class],
    'issue_trackers' => ['jira' => JiraIssueTracker::class],
],
```

O `DeliverIncidentOutcome`, o `OpenIncidentIssueAction` e o `SendBudgetAlert` só conhecem os contratos e o `InvestigationReport`, uma visão do relatório que todas as integrações leem igual. A entrada segue a mesma ideia com o `IncomingAdapter` ([Adapters](/entrada/adapters)).

Duas decisões vêm junto:

- **A correção vai pela API do provedor, não por `git push`.** O runner nunca faz push; o Laravel aplica o diff do relatório pela API (`pushChanges`). Quem escreve no repositório é sempre o Laravel. Com um `runner_token` (só leitura) no conector, o token de escrita nem entra no container; sem ele, o runner recebe o `access_token` só para o clone, pela entrada padrão, e o apaga antes de chamar os agentes ([Isolamento](/runner/isolamento#o-token-do-repositório)).
- **As regras de segurança ficam fora dos providers.** `BranchPolicy` (só branches `firewatch/`, nunca a base) e as travas do `pullRequestBlocker()` valem para qualquer provider, atual ou futuro.

## Alternativas

| Opção | O que mudaria |
|---|---|
| Chamar Bitbucket, Slack e Jira direto no job | Menos código hoje, mas cada ferramenta nova mexeria no fluxo de entrega, e os testes do fluxo precisariam simular HTTP de cada ferramenta |
| Notificações do Laravel (`Notification` com canais) | Serve bem para o aviso, mas não modela branch, commit e PR nem o ciclo de vida do card |
| Um serviço de integração externo (Zapier, n8n, um webhook genérico de saída) | Configurável sem código, mas as regras de segurança do PR e o texto padronizado sairiam do Firewatch |

## Consequências

**A favor:**

- **Uma integração nova é uma classe e uma linha no config**, sem mexer no fluxo. O GitHub entrou assim, depois do Bitbucket, sem mudar a entrega (`a_notifier_registered_only_in_the_config_is_delivered` prova o mesmo para notifiers).
- O fluxo é testado com **fakes** dos contratos (`tests/Fakes/`), sem nenhuma chamada HTTP ([Estratégia de testes](/testes-e-qualidade)).
- Um passo nunca impede o outro: cada conector roda isolado, e uma falha vira um evento na timeline.
- Os agentes nunca têm como escrever no repositório: o push não existe no runner, e o token sai do ambiente antes deles.

**Contra:**

- **O contrato é o mínimo comum.** Recursos de uma ferramenta que as outras não têm (revisores automáticos, *labels* do PR, threads no Slack) não cabem sem mudar a interface, e mudar a interface obriga a mexer em todas as implementações.
- **Aplicar o diff pela API é mais frágil que `git push`**: o Firewatch reconstrói os arquivos a partir do diff unificado ([Diff](/saida/diff)), e cada provedor tem regras próprias de commit e de proteção contra sobrescrita.
- `comment()` faz parte do contrato e está implementado nos dois providers, mas a entrega ainda não o usa.
- Um tipo de conector sem classe registrada **não é erro**: a entrega registra "ainda não disponível" e segue. Um tipo novo esquecido no config passa despercebido até alguém olhar a timeline.
