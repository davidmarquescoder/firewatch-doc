## Contexto

Dentro do runner há duas coisas valiosas para um atacante: o **código da aplicação** e o que ele carrega (um `.env` de teste, chaves esquecidas no repositório), e a **credencial do Claude**. E há código não confiável rodando: dependências, testes e comandos dos agentes. O payload do incidente também vem de fora e pode tentar instruir os agentes (*prompt injection*).

A rede é o caminho por onde tudo isso sairia. Mas o runner precisa de rede para duas coisas diferentes:

| Fase | Precisa de |
|---|---|
| Setup: clone e instalação | O host do repositório e os registros de pacotes (Packagist, npm, PyPI) |
| Agentes, verificação e testes | Só a API da Anthropic |

## Decisão

**O runner não tem rota para a internet.** Ele entra só na rede `firewatch-runner-net` (`internal: true`), cujo único outro membro é o `runner-egress`, um proxy Squid que também está na rede pública. O proxy tem **duas portas, cada uma com a sua allowlist de domínios**:

| Porta | Allowlist | Libera |
|---|---|---|
| 3128 (setup) | `allowlist-setup.txt` | Bitbucket, GitHub, Packagist, npm, Yarn, PyPI |
| 3129 (agent) | `allowlist-agent.txt` | `api.anthropic.com` |

O entrypoint troca de porta ao fim da instalação: dali em diante, os agentes, o fluxo obrigatório e a suíte de testes só alcançam a API do Claude. Tudo o que não está na lista é negado (`TCP_DENIED` no log do proxy).

## Alternativas

| Opção | O que mudaria |
|---|---|
| Internet aberta | Mais simples, e qualquer dependência ou teste funcionaria. Um agente induzido por *prompt injection*, ou um pacote malicioso, poderia mandar o código e as chaves para qualquer lugar. Continua disponível como `FIREWATCH_RUNNER_NETWORK=open`, **só para depuração** |
| Sem rede nenhuma (`--network none`) | O isolamento máximo, mas exige repositório e dependências já dentro da imagem, e o Claude Code não falaria com a API. Existe como modo `none`, para casos especiais |
| Uma allowlist só para tudo | Os agentes alcançariam os registros de pacotes e o GitHub inteiro: poderiam baixar ferramentas ou publicar dados num repositório público |
| Filtro por IP (firewall) | Os serviços (GitHub, Anthropic) trocam de IP com frequência e ficam atrás de CDNs. O filtro por domínio no proxy acompanha isso sem manutenção |
| Bloquear por lista de proibidos (*denylist*) | Qualquer domínio novo passaria. Para conter código não confiável, só o que é permitido explicitamente é seguro |

## Consequências

**A favor:**

- Um segredo lido do repositório **não tem para onde ir** na fase dos agentes, a não ser a própria API do Claude.
- Os agentes não baixam ferramentas nem pacotes novos: trabalham com o que a instalação deixou.
- As allowlists são arquivos montados no proxy: liberar um domínio é editar uma linha e reiniciar o `runner-egress`, sem reconstruir a imagem do runner.
- O log do proxy mostra tudo o que os runners tentaram acessar.

**Contra:**

- **Testes que dependem de serviços externos falham.** A suíte roda sem rede externa; uma aplicação que chama uma API de verdade nos testes precisa de *mocks*, ou a investigação falha na verificação.
- **Um registro de pacotes novo exige editar a allowlist** (Maven, RubyGems, um registro privado). Até lá, o proxy recusa o pedido (`403 TCP_DENIED`) e a investigação falha com **Falha ao instalar dependências**.
- **Repositórios por SSH (`git@…`) não funcionam**: o proxy é HTTP. Só URLs HTTPS.

**Limitações conhecidas** ([Egress](/runner/egress#limitações-conhecidas)):

- As duas portas estão na mesma rede: um agente que redefina `HTTPS_PROXY` na mão alcança a porta de setup, ainda presa à allowlist de setup.
- O filtro é por domínio, não por caminho: `.github.com` libera qualquer repositório público do GitHub no setup.
- Não há limite de banda nem de volume por execução.
