## Contexto

Para reproduzir um bug e provar a correção, os agentes precisam **rodar a suíte de testes da aplicação**, e isso exige os mesmos runtimes do projeto: a versão certa de PHP e as extensões, Node, Python, o gerenciador de pacotes. Cada aplicação tem os seus, e eles mudam com o tempo.

Ao mesmo tempo, toda imagem de runner recebe o token do repositório e a credencial do Claude, e precisa falar o mesmo protocolo com o Laravel: as mesmas variáveis, os mesmos eventos, o mesmo relatório. Uma imagem qualquer não pode ser executada só porque alguém a cadastrou.

## Decisão

**Cada aplicação escolhe a imagem do runner** no próprio cadastro. Vazio significa `firewatch-runner:latest`. As imagens seguem três regras:

1. **Uma base comum.** `firewatch-runner:latest` traz o entrypoint (`firewatch-run`), o usuário sem privilégios, git, o Claude Code, a guarda de ferramentas e PHP 8.5 com Node 22.
2. **Variações por herança.** Outra versão de PHP ou Node sai da mesma base por *build args* (`firewatch-runner:php8.3-node20`); outra linguagem é uma imagem de stack que faz `FROM firewatch-runner:latest` e só instala o runtime (`firewatch-runner:python`). Nenhuma stack troca o `ENTRYPOINT`.
3. **Um contrato verificado.** Antes de criar o container, o Firewatch confere no Docker do host que a imagem existe, tem o label `br.com.firewatch.runner=1` e segue o contrato que ele espera (`br.com.firewatch.runner.contract`, hoje `1`). O Firewatch **nunca baixa** imagens.

"Por aplicação" é sobre a **escolha**: na prática, várias aplicações da mesma stack apontam para a mesma imagem. Uma imagem dedicada só é necessária quando o projeto precisa de algo que nenhuma outra tem.

## Alternativas

| Opção | O que mudaria |
|---|---|
| Uma imagem única com todos os runtimes | Uma imagem só para manter, mas enorme, e ainda assim sem as versões específicas que cada projeto pede. Conflitos entre versões de um mesmo runtime não têm solução numa imagem só |
| Instalar os runtimes durante a execução (asdf, mise, nvm) | Cada investigação baixaria e compilaria runtimes: lento, e exigiria abrir a rede para os sites deles, contra o [ADR 003](/decisoes-e-apendices/adr-003-egress-por-allowlist) |
| Usar a imagem da própria aplicação (o `Dockerfile` do projeto) | Os runtimes ficariam exatos, mas a imagem não teria o entrypoint, o Claude Code nem as garantias de segurança do runner, e o Firewatch executaria uma imagem que ele não controla com a credencial do Claude dentro |
| Dev containers ou Nix definidos no repositório | Reproduzível, mas cada repositório teria de manter a definição, e o build aconteceria a cada investigação |

## Consequências

**A favor:**

- Cada aplicação roda com os runtimes certos, e a imagem base continua pequena para quem só precisa de PHP e Node.
- Todas as imagens falam o mesmo protocolo: o Laravel não sabe nem precisa saber a linguagem da aplicação.
- Uma imagem errada aparece como erro claro, não como falha estranha nos testes: imagem inexistente ou fora do contrato é **Configuração inválida**, e um projeto Python numa imagem sem Python falha na instalação com "A imagem do runner não tem o runtime exigido pelo projeto".
- O contrato versionado permite mudar o protocolo do runner sem rodar imagens antigas por engano.

**Contra:**

- **Alguém precisa construir as imagens** em todo servidor que roda investigações, antes de cadastrar a aplicação. O Firewatch não baixa nem constrói nada sozinho ([Deploy](/operacao)).
- **Mudar a base exige reconstruir as stacks**, porque elas herdam dela. Com o contrato alterado, as imagens antigas passam a ser recusadas até serem reconstruídas.
- As imagens são grandes (1,7 GB a base, 1,9 GB a Python).
- Hoje só existem a base e a stack Python. Go, Ruby, Java e outras linguagens precisam de uma stack nova, seguindo o modelo de `stacks/python`.
