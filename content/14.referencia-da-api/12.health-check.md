O backend tem duas rotas de saúde, ambas públicas e sem efeito colateral. Nenhuma delas confere banco, fila, Redis, Reverb ou Docker: respondem `200` se o Laravel sobe e atende a requisição.

| Método | Rota | O que faz |
|---|---|---|
| `GET` | `/api/health-check` | Rota do Firewatch: JSON fixo dizendo que a API está rodando |
| `GET` | `/up` | Rota padrão do Laravel: `up` ou `down`, em JSON ou HTML |

## Ver o health check da API

```http
GET /api/health-check
```

| | |
|---|---|
| **Permissão** | Pública: sem login |
| **Sucesso** | `200` |

É uma closure em `routes/api.php`, **fora** do prefixo `/v1` e da pilha do painel (`auth:sanctum`, `ensure-user-active`, `ensure-password-change`). Passa só pelo grupo `api` do Laravel.

### Request

Sem parâmetros.

### Response

Este é o único endpoint que não usa o envelope `message` + `data`: devolve um JSON fixo, sem consultar nada.

| Campo | Valor |
|---|---|
| `status` | Sempre `"success"` |
| `message` | Sempre `"API is running"` (em inglês, fora do `lang/`) |

A chamada não grava nada na [auditoria](/seguranca/auditoria) (`AuditLogApiTest::test_health_check_does_not_write_to_the_trail`).

### Exemplo

```http
GET /api/health-check
```

```json
{
  "status": "success",
  "message": "API is running"
}
```

## Ver o /up do Laravel

```http
GET /up
```

| | |
|---|---|
| **Permissão** | Pública: sem login |
| **Sucesso** | `200` (`500` quando um listener de diagnóstico falha) |

Vem de `health: '/up'` em `bootstrap/app.php`. O Laravel registra a rota sem grupo de middleware (nem `web`, nem `api`) e a tira do modo de manutenção.

### Request

Sem parâmetros. O formato da resposta depende do `Accept`.

### Response

A rota dispara o evento `Illuminate\Foundation\Events\DiagnosingHealth`. Se algum listener lançar exceção, o status vira `500`. O Firewatch **não registra** listener para esse evento, então hoje o `/up` só confirma que a aplicação inicializa.

| `Accept` | Resposta |
|---|---|
| `application/json` | `{"status": "up"}` (ou `"down"` com `500`) |
| Outro (navegador) | Página HTML do Laravel ("Application up") |

Com `APP_DEBUG=true`, a exceção de um listener não vira `down`: ela sobe e aparece como erro comum.

### Exemplo

```http
GET /up
Accept: application/json
```

```json
{ "status": "up" }
```

## Qual usar

| | `/api/health-check` | `/up` |
|---|---|---|
| Definida em | `routes/api.php` | `bootstrap/app.php` (framework) |
| Envelope | `status` + `message` | `status` (JSON) ou HTML |
| Em modo de manutenção (`php artisan down`) | `503`, como o resto da API | Continua respondendo `200` |
| Ponto de extensão | Editar a closure | Listeners de `DiagnosingHealth` |

Nenhum serviço do `docker-compose.yml` nem o painel chamam qualquer das duas hoje.

## Observações

- As duas rotas respondem `200` com o banco fora do ar, porque nenhuma consulta nada. Para um health check que pegue banco ou fila, seria preciso um listener de `DiagnosingHealth` ou uma consulta na closure (`routes/api.php:20`, `bootstrap/app.php:23`).
- A `message` do `/api/health-check` está em inglês e escrita direto no código, fora do `lang/pt_BR/messages.php` usado pelas outras rotas (`routes/api.php:24`).
