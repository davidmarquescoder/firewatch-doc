Uma aplicação é um sistema monitorado: diz como reconhecer os erros dela, onde está o código e como rodá-lo no runner. O significado de cada campo está em [Aplicações](/conectores-aplicacoes-budget-e-metricas/aplicacoes), e a simulação em [Simulação de incidente](/registro-e-trigger/simulacao). Controller: `ApplicationController`.

| Método | Rota | O que faz |
|---|---|---|
| `GET` | `/api/v1/application` | Lista paginada, com `stats` |
| `POST` | `/api/v1/application` | Cria uma aplicação |
| `GET` | `/api/v1/application/{application}` | Mostra uma aplicação |
| `PUT` / `PATCH` | `/api/v1/application/{application}` | Atualização parcial |
| `DELETE` | `/api/v1/application/{application}` | Soft delete (os incidentes ficam) |
| `POST` | `/api/v1/application/{application}/simulate-incident` | Cria um incidente simulado |

## O objeto aplicação

Todas as rotas de CRUD devolvem a aplicação pelo `ApplicationResource`, com o resumo dos conectores de repositório e do Jira (sem credenciais) e `incidents_count`.

| Campo | Tipo | Conteúdo |
|---|---|---|
| `id` | uuid | |
| `name` | string | |
| `monitoring_identifier` | string | Nome da aplicação no Sentry ou no webhook |
| `repository_connector_id` | uuid \| null | |
| `repository_connector` | objeto \| null | `id`, `name`, `type` e `status` do conector |
| `repository_slug` | string \| null | `dono/repositorio` |
| `issue_tracker_connector_id` | uuid \| null | Conector Jira onde o card do incidente é criado |
| `issue_tracker_connector` | objeto \| null | `id`, `name`, `type` e `status` do conector Jira |
| `base_branch` | string | Padrão `main` |
| `runner_image` | string | Padrão `firewatch-runner:latest` |
| `install_command`, `test_command` | string \| null | `null` significa `auto` no runner |
| `trigger_rules` | objeto | O que foi gravado. `{}` quando nada foi gravado |
| `resolved_trigger_rules` | objeto | As regras que valem: o gravado mesclado sobre os padrões |
| `active` | booleano | |
| `incidents_count` | inteiro | Incidentes da aplicação |
| `created_at`, `updated_at` | data | |

## Listar aplicações

```http
GET /api/v1/application
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado |
| **Sucesso** | `200` |

### Request

Parâmetros de query, todos opcionais:

| Campo | Tipo | Obrigatório | Regras |
|---|---|---|---|
| `per_page` | inteiro | Não | 1 a 100. Padrão `10` |
| `search` | string | Não | Até 255. Busca (`like`) em `name`, `monitoring_identifier` e `repository_slug` |
| `active` | booleano | Não | `1`, `0`, `true` ou `false` em JSON. Na query string, use `1` ou `0` |
| `page` | inteiro | Não | Página da paginação |

A ordem é por nome.

### Response

`data` é uma lista de [aplicações](#o-objeto-aplicação), com `meta` da paginação e `stats`:

| Campo | Conteúdo |
|---|---|
| `stats.total` | Todas as aplicações não removidas |
| `stats.active` | Com `active = true` |
| `stats.inactive` | `total − active` |

Os `stats` contam todas as aplicações, sem aplicar `search` nem `active`.

### Exemplo

```http
GET /api/v1/application?per_page=1
```

```json
{
  "message": "Aplicações listadas com sucesso.",
  "data": [
    { "id": "01a1c2d5-…", "name": "Loja API", "monitoring_identifier": "loja-back", "active": true, "incidents_count": 12, "…": "…" }
  ],
  "meta": {
    "current_page": 1,
    "from": 1,
    "last_page": 2,
    "links": ["…"],
    "path": "http://localhost/api/v1/application",
    "per_page": 1,
    "to": 1,
    "total": 2
  },
  "stats": { "total": 2, "active": 2, "inactive": 0 }
}
```

## Criar aplicação

```http
POST /api/v1/application
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado |
| **Sucesso** | `201` |

### Request

Regras do `StoreApplicationRequest` (as comuns ficam em `ApplicationRules`):

| Campo | Tipo | Obrigatório | Regras |
|---|---|---|---|
| `name` | string | Sim | Até 255, único entre as aplicações |
| `monitoring_identifier` | string | Sim | Até 255, único entre as aplicações |
| `repository_connector_id` | uuid | Não | Conector `bitbucket` ou `github` existente e não removido |
| `repository_slug` | string | Com conector | Até 255, `^[\w.-]+/[\w.-]+$` |
| `issue_tracker_connector_id` | uuid | Não | Conector `jira` existente e não removido. Sem ele, o card vai para o primeiro Jira ativo por nome; sem nenhum Jira conectado, não há card |
| `base_branch` | string | Não | Até 255, `^(?!firewatch/)[\w./-]+$`. Vazio vira `main` |
| `runner_image` | string | Não | Até 255, `^[\w./:@-]+$`. Vazio vira `firewatch-runner:latest`. A imagem só é conferida na investigação ([A imagem](/investigacao/docker-runner#a-imagem)) |
| `install_command` | string | Não | Até 2000 |
| `test_command` | string | Não | Até 2000 |
| `active` | booleano | Não | Padrão `true` |
| `trigger_rules` | objeto | Não | Só as chaves abaixo |
| `trigger_rules.enabled` | booleano | Não | |
| `trigger_rules.min_severity` | string | Não | `debug`, `info`, `warning`, `error` ou `critical` |
| `trigger_rules.min_occurrences` | inteiro | Não | ≥ 1 |
| `trigger_rules.min_affected_users` | inteiro | Não | ≥ 0 |
| `trigger_rules.environments` | lista de string | Não | Cada um até 100 |
| `trigger_rules.ignore_patterns` | lista de string | Não | Cada um até 500, texto ou `/regex/flags` válido |

O que cada regra de acionamento faz está em [Regras de acionamento](/conectores-aplicacoes-budget-e-metricas/aplicacoes#regras-de-acionamento).

### Response

A [aplicação](#o-objeto-aplicação) criada, com `incidents_count: 0`.

### Erros

Mensagens próprias de validação (`422`), além das genéricas:

| Campo | Mensagem |
|---|---|
| `repository_connector_id` | "O conector de repositório precisa ser um conector de repositório (Bitbucket ou GitHub) existente." |
| `issue_tracker_connector_id` | "O conector do Jira precisa ser um conector Jira existente." |
| `repository_slug` | "O repositório deve estar no formato workspace/repositorio (Bitbucket) ou dono/repositorio (GitHub)." |
| `base_branch` | "A branch base é inválida (branches firewatch/ são reservadas aos agentes)." |
| `runner_image` | "A imagem do runner é inválida." |
| `trigger_rules.ignore_patterns.*` | "O padrão ignorado é inválido (use um texto ou uma expressão regular no formato /regex/flags)." |

### Exemplo

```http
POST /api/v1/application
```

```json
{
  "name": "Loja API",
  "monitoring_identifier": "loja-back",
  "repository_connector_id": "01a1c5d1-…",
  "repository_slug": "acme/loja-back",
  "trigger_rules": { "min_occurrences": 3, "environments": ["production"] }
}
```

```json
{
  "message": "Aplicação criada com sucesso.",
  "data": {
    "id": "01a1c8a4-…",
    "name": "Loja API",
    "repository_connector": { "id": "01a1c5d1-…", "name": "Bitbucket Acme", "type": "bitbucket", "status": "active" },
    "base_branch": "main",
    "runner_image": "firewatch-runner:latest",
    "trigger_rules": { "min_occurrences": 3, "environments": ["production"] },
    "resolved_trigger_rules": { "enabled": true, "min_severity": "error", "min_occurrences": 3, "…": "…" },
    "active": true,
    "incidents_count": 0,
    "…": "…"
  }
}
```

## Mostrar aplicação

```http
GET /api/v1/application/{application}
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado |
| **Sucesso** | `200` |

### Request

Sem corpo. `{application}` é o `id`. Uma aplicação removida responde `404`.

### Response

A [aplicação](#o-objeto-aplicação).

```json
{
  "message": "Aplicação exibida com sucesso.",
  "data": { "id": "01a1c2d5-…", "name": "Loja API", "…": "…" }
}
```

## Atualizar aplicação

```http
PUT /api/v1/application/{application}
PATCH /api/v1/application/{application}
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado |
| **Sucesso** | `200` |

### Request

Atualização parcial (`UpdateApplicationRequest`). Os campos e regras são os de [Criar aplicação](#criar-aplicação), com duas diferenças:

- `name` e `monitoring_identifier` são opcionais; se enviados, não podem ser vazios, e a unicidade ignora a própria aplicação;
- `trigger_rules` enviado **substitui** o objeto gravado (não é mesclado com o anterior). As chaves ausentes voltam aos padrões em `resolved_trigger_rules`.

Normalizações do `SaveApplicationAction`:

| Enviado | Gravado |
|---|---|
| `base_branch` vazio ou `null` | `main` |
| `runner_image` vazio ou `null` | `firewatch-runner:latest` |
| `repository_connector_id` vazio ou `null` | `repository_slug` também vira `null` |

### Response

A [aplicação](#o-objeto-aplicação) atualizada.

### Exemplo

Desvincular o repositório:

```http
PATCH /api/v1/application/01a1c2d5-…
```

```json
{ "repository_connector_id": null }
```

```json
{
  "message": "Aplicação atualizada com sucesso.",
  "data": {
    "id": "01a1c2d5-…",
    "repository_connector_id": null,
    "repository_connector": null,
    "repository_slug": null,
    "…": "…"
  }
}
```

## Remover aplicação

```http
DELETE /api/v1/application/{application}
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado |
| **Sucesso** | `200` |

### Request

Sem corpo.

### Response

Soft delete. Os incidentes da aplicação **ficam** e continuam nas métricas. `data` vem vazio.

```json
{
  "message": "Aplicação excluída com sucesso.",
  "data": []
}
```

## Simular incidente

```http
POST /api/v1/application/{application}/simulate-incident
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado |
| **Throttle** | `throttle:30,1,simulate-incident` (30 por minuto) |
| **Sucesso** | `201` (incidente criado) ou `200` (somado a um existente) |

::warning
**Pode acionar os agentes de verdade.** Se as regras da aplicação decidirem `trigger`, o incidente entra na fila e uma investigação real começa, consumindo créditos do Claude. Para ensaiar sem custo, veja [Testar sem gastar créditos](/ambiente-e-setup/testar-sem-creditos).
::

### Request

Regras do `SimulateIncidentRequest`. Todos os campos são opcionais: corpo vazio simula o cenário padrão.

| Campo | Tipo | Obrigatório | Regras |
|---|---|---|---|
| `title` | string | Não | Até 512. Padrão "Simulação: erro disparado pelo painel do Firewatch" |
| `stack_trace` | string | Não | Até 20 000 |
| `severity` | string | Não | `debug`, `info`, `warning`, `error` ou `critical`. Padrão `error` |
| `environment` | string | Não | Até 255. Padrão: o primeiro ambiente gravado nas regras da aplicação, ou `production` |
| `occurrences` | inteiro | Não | 1 a 10 000. Padrão `1` |
| `affected_users` | inteiro | Não | 0 a 1 000 000. Padrão `0` |
| `deduplicate` | booleano | Não | Padrão `false`: cada chamada cria um incidente novo. Com `true`, chamadas com o mesmo título somam no mesmo incidente |

Como o payload é montado e passa pelo pipeline está em [Simulação de incidente](/registro-e-trigger/simulacao).

### Response

| Campo | Conteúdo |
|---|---|
| `created` | `true` se um incidente novo foi criado |
| `incident` | O incidente, pelo `IncidentResource` (o mesmo da lista de incidentes) |
| `trigger` | A [decisão das regras](/registro-e-trigger/motor-de-regras#triggerdecision): `outcome`, `outcome_label`, `reason`, `checks`. `null` se o incidente já tinha passado de `received` |

| Status | `message` |
|---|---|
| `201` | "Incidente simulado criado com sucesso." |
| `200` | "Ocorrência simulada registrada no incidente existente." |

Cada chamada grava `incident_simulated` na [auditoria](/seguranca/auditoria).

### Erros

| Status | Quando | Erro |
|---|---|---|
| `422` | Aplicação inativa | Em `application`: "A aplicação está inativa: ative-a para simular incidentes." |
| `422` | O adapter do webhook genérico recusou o payload | Em `payload`, com a mensagem da exceção |
| `429` | Mais de 30 chamadas no minuto | O contador é por usuário e só desta rota |

### Exemplo

```http
POST /api/v1/application/01a1c2d5-…/simulate-incident
```

```json
{ "severity": "critical", "deduplicate": true }
```

```json
{
  "message": "Incidente simulado criado com sucesso.",
  "data": {
    "created": true,
    "incident": {
      "id": "01a1c9b0-…",
      "application_id": "01a1c2d5-…",
      "title": "Simulação: erro disparado pelo painel do Firewatch",
      "environment": "production",
      "severity": "critical",
      "status": "queued",
      "occurrences": 1,
      "…": "…"
    },
    "trigger": {
      "outcome": "trigger",
      "outcome_label": "Acionar agentes",
      "reason": null,
      "checks": ["…"]
    }
  }
}
```

## Observações

- Os `stats` da listagem ignoram `search` e `active` (`ApplicationController.php:33`).
- `?active=false` na query string devolve `422` ("O campo active deve ser verdadeiro ou falso."): a regra `boolean` só aceita `true`, `false`, `0`, `1`, `"0"` e `"1"`, e na query tudo chega como texto (`ApplicationController.php:30`).
- `active` aceita `null` (`nullable|boolean`, `ApplicationRules.php:33`), mas a coluna `active` não é anulável e o `SaveApplicationAction` não troca `null` por um padrão. Pela leitura do código, mandar `"active": null` deve causar erro de banco (`500`), e não `422`. Não foi testado.
- O ambiente padrão da simulação vem das regras **gravadas** (`trigger_rules`), não das resolvidas. Na prática dá no mesmo, porque o padrão das duas é `production` (`SimulateIncidentAction.php:78`).
