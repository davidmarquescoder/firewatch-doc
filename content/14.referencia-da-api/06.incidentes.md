Um incidente é um erro recebido de uma aplicação monitorada. A API só lê incidentes e permite **reexecutar** a investigação de um incidente que falhou. Os status e as transições estão em [Máquina de estados](/modelo-de-dados/maquina-de-estados), e as regras da reexecução em [Timeouts e reexecução](/investigacao/timeouts-e-reexecucao).

| Método | Rota | O que faz |
|---|---|---|
| `GET` | `/api/v1/incident` | Lista paginada, com contagem por status e tempo médio até o PR |
| `GET` | `/api/v1/incident/{incident}` | Mostra um incidente, com o stack trace mascarado |
| `GET` | `/api/v1/incident/{incident}/runs` | Lista as execuções dos agentes do incidente |
| `POST` | `/api/v1/incident/{incident}/retry` | Coloca um incidente com falha de novo na fila |

O payload bruto recebido do monitoramento **nunca** sai pela API. O `IncidentResource` só devolve campos do incidente e, no detalhe, o stack trace já mascarado.

## Listar incidentes

```http
GET /api/v1/incident
```

| | |
|---|---|
| Permissão | Qualquer usuário logado |
| Sucesso | `200` |

**Request** (query string):

| Campo | Tipo | Obrigatório | Regras |
|---|---|---|---|
| `per_page` | inteiro | Não | 1 a 100. Padrão `10` |
| `page` | inteiro | Não | Página do paginador |
| `search` | texto | Não | Até 255. Procura no `title` (`LIKE`) |
| `status` | texto | Não | Um valor de `IncidentStatusEnum`: `received`, `ignored`, `queued`, `investigating`, `fixing`, `testing`, `pr_opened`, `failed` |
| `statuses[]` | lista | Não | Vários status de uma vez, mesmos valores |
| `severity` | texto | Não | `debug`, `info`, `warning`, `error`, `critical` |
| `application_id` | UUID | Não | Só os incidentes dessa aplicação |
| `period` | texto | Não | `24h`, `7d` ou `30d`, contados a partir de `received_at` |

A ordem é sempre `received_at` decrescente (o mais recente primeiro).

**Response**: `data` traz os incidentes no [formato do incidente](#formato-do-incidente), sem `stack_trace`. Além de `meta`, a resposta tem `stats`:

| Campo | O que é |
|---|---|
| `stats.total` | Total de incidentes que passam pelos filtros |
| `stats.by_status` | Contagem por status. Só aparecem os status com pelo menos um incidente |
| `stats.avg_time_to_pr_seconds` | Média de `time_to_pr_seconds` dos incidentes filtrados que chegaram a `pr_opened`, em segundos inteiros. `null` se nenhum chegou |

`stats` segue **todos os filtros menos** `status` e `statuses`. Assim, as abas por status do painel sempre somam o que está na lista sem filtro de status.

**Exemplo**:

```http
GET /api/v1/incident?status=failed&per_page=1
```

```json
{

  "data": [
    {
      "id": "01a1e5f8-…",
      "application_id": "01a1c2d5-…",
      "title": "Division by zero",
      "severity": "error",
      "status": "failed",
      "status_label": "Falhou",
      "failure_kind": "tests_failed",
      "failure_kind_label": "Testes não passaram",
      "…": "…",
      "runs_count": 1,

  "meta": { "current_page": 1, "from": 1, "last_page": 7, "links": ["…"], "path": "http://localhost/api/v1/incident", "per_page": 1, "to": 1, "total": 7 },
```

### Formato do incidente

| Campo | O que é |
|---|---|
| `id`, `application_id` | UUIDs |
| `fingerprint` | Hash que agrupa ocorrências do mesmo erro |
| `title`, `environment` | Texto do erro e ambiente informado pelo monitoramento |
| `severity`, `severity_label` | Valor e rótulo (`Erro`, `Crítico`…) |
| `status`, `status_label` | Valor e rótulo (`Na fila`, `PR aberto`…) |
| `status_reason` | Motivo da última transição, por exemplo a explicação da falha |
| `failure_kind`, `failure_kind_label` | Por que falhou, só em incidentes `failed` ([Os failure kinds](/investigacao/resultado-e-falhas#os-failure-kinds)) |
| `occurrences`, `affected_users` | Contagens vindas do monitoramento |
| `pr_url`, `jira_key` | Links da entrega, quando existem |
| `first_seen_at`, `last_seen_at` | Primeira e última ocorrência |
| `received_at`, `ignored_at`, `queued_at`, `investigating_at`, `fixing_at`, `testing_at`, `pr_opened_at`, `failed_at` | Quando o incidente entrou em cada status |
| `time_to_pr_seconds` | Segundos de `received_at` até `pr_opened_at`. `null` sem PR |
| `application` | `{id, name, monitoring_identifier}`. Inclui aplicação removida (soft delete) |
| `latest_run` | Resumo da execução mais recente: `id`, `status`, `status_label`, `failure_reason`, `started_at`, `finished_at`, `duration_seconds`, `cost_usd`, `team`. `null` se não houve execução |
| `runs_count` | Número de execuções do incidente |
| `retry` | `{allowed, reason, used, max}`: se o botão **Reexecutar** está liberado e, se não, por quê |
| `stack_trace` | Só em [Mostrar incidente](#mostrar-incidente) |
| `created_at`, `updated_at` | Datas do registro |

## Mostrar incidente

```http
GET /api/v1/incident/{incident}
```

| | |
|---|---|
| Permissão | Qualquer usuário logado |
| Sucesso | `200` |

**Request**: sem corpo. `{incident}` é o UUID.

**Response**: `data` é o [incidente](#formato-do-incidente) com o campo extra `stack_trace`:

- vem da cópia mascarada do payload (`sanitized_payload`), nunca do payload bruto;
- uma lista de linhas vira um texto com uma linha por item;
- acima de 20 000 caracteres (`MAX_STACK_TRACE_LENGTH`), é cortado com `\n…` no fim;
- `null` quando o evento não trouxe stack trace.

**Exemplo**:

```http
GET /api/v1/incident/01a1e5f8-…
```

```json
{
  "message": "Incidente exibido com sucesso.",
  "data": {
    "id": "01a1e5f8-…",
    "title": "Division by zero",
    "status": "failed",
    "…": "…",
    "stack_trace": "#0 app/Services/Calculo.php(28)\n#1 app/Http/Controllers/RelatorioController.php(41)",
    "retry": { "allowed": true, "reason": null, "used": 0, "max": 3 }
  }
}
```

## Listar execuções do incidente

```http
GET /api/v1/incident/{incident}/runs
```

| | |
|---|---|
| Permissão | Qualquer usuário logado |
| Sucesso | `200` |

**Request**: sem corpo. Não tem filtros nem paginação.

**Response**: `data` é a lista de **todas** as execuções do incidente, da mais recente para a mais antiga (`created_at`), no [formato da execução](/referencia-da-api/execucoes#formato-da-execução). Aqui o `report` **não** vem: para ver o relatório, use [Mostrar execução](/referencia-da-api/execucoes#mostrar-execução).

**Exemplo**:

```json
{
  "message": "Execuções listadas com sucesso.",
  "data": [
    {
      "id": "01a1d0c9-…",
      "incident_id": "01a1d0c8-…",
      "status": "fixed",
      "status_label": "Corrigido",
      "exit_code": 0,
      "work_branch": "firewatch/LOJA-12-division-by-zero",
      "duration_seconds": 312,
      "cost_usd": "1.0529",
      "…": "…"
    }
  ]
}
```

## Reexecutar investigação

```http
POST /api/v1/incident/{incident}/retry
```

| | |
|---|---|
| Permissão | Qualquer usuário logado |
| Throttle | 10 por minuto (`throttle:10,1,incident-retry`) |
| Sucesso | `202` |

::warning
Cada reexecução sobe o runner e gasta créditos do Claude.
::

**Request**: sem corpo.

O que a rota faz (`RetryIncidentInvestigationAction`), numa transação:

1. trava a linha do incidente (`lockForUpdate`), para dois cliques ao mesmo tempo não enfileirarem duas execuções;
2. confere as travas com a linha já travada;
3. muda o status para `queued` com o motivo "Reexecução solicitada por \<e-mail do usuário\>.";
4. despacha o job `InvestigateIncident` depois do commit.

Também grava o evento `incident_retried` na [auditoria](/seguranca/auditoria), com a descrição "Nova investigação solicitada".

**Response**: `data` é o [incidente](#formato-do-incidente) já em `queued`, sem `stack_trace`. O `retry.allowed` volta `false` (o incidente não está mais `failed`) e o `runs_count` ainda não conta a nova execução, que só é criada quando o job roda.

**Erros**:

| Status | Quando | `errors.incident` |
|---|---|---|
| `422` | O incidente não está `failed` | "Só incidentes com falha podem ser reexecutados (status atual: \<rótulo\>)." |
| `422` | A aplicação foi removida | "A aplicação do incidente foi removida." |
| `422` | A aplicação está inativa | "A aplicação está inativa: ative-a para reexecutar a investigação." |
| `422` | Limite atingido | "Limite de \<max\> reexecuções atingido para este incidente." |
| `429` | Mais de 10 chamadas por minuto | |

As travas são conferidas nessa ordem e só a primeira que falhar aparece. As reexecuções usadas são o número de execuções do incidente menos 1. O máximo vem de `FIREWATCH_INCIDENT_MAX_RETRIES` (padrão `3`). Detalhes em [As travas](/investigacao/timeouts-e-reexecucao#as-travas).

**Exemplo**:

```http
POST /api/v1/incident/01a1e5f8-…/retry
```

```json
{
  "message": "Investigação reenfileirada: os agentes vão rodar novamente.",
  "data": {
    "id": "01a1e5f8-…",
    "status": "queued",
    "status_label": "Na fila",
    "status_reason": "Reexecução solicitada por ana@exemplo.com.",
    "failure_kind": null,
    "…": "…",
    "runs_count": 1,
    "retry": {
      "allowed": false,
      "reason": "Só incidentes com falha podem ser reexecutados (status atual: Na fila).",
      "used": 0,
      "max": 3
    }
  }
}
```

Erro de trava:

```json
{
  "message": "A aplicação está inativa: ative-a para reexecutar a investigação.",
  "errors": {
    "incident": ["A aplicação está inativa: ative-a para reexecutar a investigação."]
  }
}
```

## Observações

- `search` procura só no `title`. `%` e `_` digitados não são escapados e funcionam como curingas do `LIKE` (`IncidentController.php:45`).
- `stats.by_status` omite os status sem incidentes, em vez de devolver `0` (`IncidentController.php:50-56`).
- `latest_run.team` repete o time inteiro (nomes, modelos, ferramentas, hash do prompt) em cada item da lista, o que deixa a resposta grande (`IncidentResource.php:82`).
