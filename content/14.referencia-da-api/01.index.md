A API REST do Firewatch é a que o painel Nuxt usa. Esta parte documenta cada endpoint: método, rota, quem pode chamar, o que mandar, o que volta e um exemplo. Esta página reúne o que vale para **todos** eles.

Os exemplos das páginas seguintes foram conferidos contra a API rodando localmente, com dados fictícios no lugar dos reais.

## Autenticação

Todas as rotas de `/api/v1` (menos as de login) exigem uma sessão do painel. A autenticação é a do **Sanctum em modo SPA**: cookie de sessão, sem token no cabeçalho.

1. `GET /sanctum/csrf-cookie` grava o cookie `XSRF-TOKEN`.
2. `POST /api/v1/auth` com `email` e `password` abre a sessão.
3. Cada chamada seguinte manda o cookie de sessão e o cabeçalho `X-XSRF-TOKEN` com o valor do cookie `XSRF-TOKEN`.

O passo a passo e as rotas de autenticação estão em [Rotas de autenticação](/seguranca#rotas-de-autenticação). O cookie só é aceito para os domínios em `SANCTUM_STATEFUL_DOMAINS` (`localhost:5000` em desenvolvimento).

Todas as rotas protegidas passam pela mesma pilha de middlewares, nesta ordem:

| Middleware | Recusa com |
|---|---|
| `auth:sanctum` | `401` sem sessão |
| `ensure-user-active` | `403` com `code: "user_inactive"` se a conta foi desativada |
| `ensure-password-change` | `403` com `code: "password_change_required"` se a troca de senha está pendente |

Detalhes em [Middlewares](/seguranca/middlewares).

::note
Não existe token de API para integrações de máquina. Quem chama a API é sempre um usuário logado no painel. As únicas rotas sem sessão são as de entrada (`/api/webhooks/{connector}` e `/api/slack/commands/{connector}`), autenticadas pela assinatura do conector ([Entrada](/entrada)), e o [health check](/referencia-da-api/health-check).
::

### Cabeçalhos

| Cabeçalho | Valor | Por quê |
|---|---|---|
| `Accept` | `application/json` | Recomendado. As rotas em `api/*` já respondem erros em JSON mesmo sem ele (`shouldRenderJsonWhen` no `bootstrap/app.php`) |
| `Content-Type` | `application/json` | Corpo das escritas. O upload de logo da organização usa `multipart/form-data` |
| `X-XSRF-TOKEN` | Valor do cookie `XSRF-TOKEN` | Toda escrita (`POST`, `PUT`, `PATCH`, `DELETE`). Sem ele: `419` |
| `Origin` / `Referer` | O endereço do painel | É por eles que o Sanctum reconhece uma chamada do painel e lê o cookie de sessão |

## Formato das respostas

Os controllers respondem pelo trait `App\Traits\ApiResponse`. O corpo de sucesso tem sempre duas chaves:

```json
{
  "message": "Aplicações listadas com sucesso.",
  "data": { }
}
```

| Chave | Conteúdo |
|---|---|
| `message` | Texto em português para mostrar ao usuário, vindo de `lang/pt_BR/messages.php` |
| `data` | O recurso (objeto), a lista (array) ou `[]` quando não há o que devolver (por exemplo, numa remoção) |

O formato de cada recurso vem de uma **API Resource** (`app/Http/Resources`). As Resources nunca devolvem credenciais, senhas nem payloads crus. Valores de enum vêm em par: o valor (`status: "pr_opened"`) e o rótulo em português (`status_label: "PR aberto"`).

| Tipo | Formato |
|---|---|
| Ids | UUID em texto (`"01a1c2d5-5370-73be-…"`) |
| Datas | ISO 8601 em UTC (`"2026-11-17T14:03:12.000000Z"`) |
| Dinheiro | Número em dólares (`cost_usd`). Nas execuções vem como texto com quatro casas, porque a coluna é `decimal` |

Fogem do envelope:

- as rotas de autenticação, que devolvem `{ "user": … }`;
- o health check, que devolve `{ "status", "message" }`;
- as listas paginadas, que acrescentam `meta` (abaixo).

### Códigos de sucesso

| Código | Quando |
|---|---|
| `200` | Leitura, edição, remoção e ações síncronas (testar conector) |
| `201` | Criação (`POST` de um recurso novo) |
| `202` | A ação foi aceita e roda em segundo plano (reexecutar um incidente) |

## Erros

Todo erro também é JSON, com `message`. Em produção (`APP_DEBUG=false`) o corpo é só isso, mais `errors` nos erros de validação. Com `APP_DEBUG=true`, como no ambiente local, o Laravel acrescenta `exception`, `file`, `line` e `trace`: nunca rode produção com debug ligado.

| Código | Quando | Corpo |
|---|---|---|
| `401` | Sem sessão | `{"message": "Unauthenticated."}` |
| `403` | Conta desativada, troca de senha pendente ou ação que o papel não permite | `message` e, nos dois primeiros, `code` |
| `404` | Rota ou registro inexistente (inclusive removido) | `{"message": "No query results for model [App\\Models\\…] <id>"}` |
| `405` | Método errado para a rota | `{"message": "The DELETE method is not supported for route …"}` |
| `409` | Conflito com o estado atual, como remover um conector que aplicações usam | `message` |
| `419` | Escrita sem o `X-XSRF-TOKEN` certo | `{"message": "CSRF token mismatch."}` |
| `422` | Dados inválidos, ou uma regra de negócio recusou a ação | `message` e `errors` (validação) ou `data` (regra) |
| `429` | Passou do limite de requisições | `{"message": "Too Many Attempts."}` |
| `500` | Erro inesperado | `{"message": "Server Error"}` |

As mensagens do framework (`401`, `404`, `405`, `419`, `429`, `500`) ficam em inglês. As do Firewatch e as de validação vêm em português.

### Validação (422)

Os Form Requests validam o corpo e a query. Um erro devolve o primeiro problema em `message` e todos em `errors`, por campo:

```json
{
  "message": "O campo per page deve ser um número inteiro.",
  "errors": {
    "per_page": ["O campo per page deve ser um número inteiro."]
  }
}
```

Quando há mais de um erro, a `message` termina com "(and N more errors)": esse trecho do Laravel não tem tradução no projeto. Os nomes dos campos aparecem como o Form Request os batizou em `attributes()` (por exemplo, "Imagem do runner"), ou com o nome cru quando não há tradução.

Uma regra de negócio que recusa a ação (por exemplo, "Você não pode excluir a própria conta.") usa o mesmo `422`, mas pelo `error()` do `ApiResponse`: vem `message` e `data`, sem `errors`.

### Permissão (403)

Hoje só a gestão de usuários confere o **papel** de quem chama: um usuário sem papel recebe `403` com a mensagem "#10001 - Oops, parece que você não tem autorização para prosseguir com essa ação.". Nas demais rotas, qualquer usuário logado, ativo e sem troca de senha pendente pode ler e escrever ([Papéis e permissões](/seguranca/papeis-e-permissoes)). Cada página diz a permissão de cada endpoint.

## Paginação

As listagens de conectores, aplicações, incidentes, organizações e auditoria são paginadas pelo Laravel. Parâmetros:

| Parâmetro | Padrão | Limite |
|---|---|---|
| `page` | `1` | |
| `per_page` | `10` (`25` na auditoria) | `1` a `100` (organizações não têm máximo) |

A resposta troca `data` por uma página e acrescenta `meta`:

```json
{
  "message": "Conectores listados com sucesso.",
  "data": [ { "id": "…" } ],
  "meta": {
    "current_page": 1,
    "from": 1,
    "last_page": 4,
    "links": [
      { "url": null, "label": "&laquo; Anterior", "page": null, "active": false },
      { "url": "…/api/v1/connector?per_page=1&page=1", "label": "1", "page": 1, "active": true },
      { "url": "…/api/v1/connector?per_page=1&page=2", "label": "Próximo &raquo;", "page": 2, "active": false }
    ],
    "path": "…/api/v1/connector",
    "per_page": 1,
    "to": 1,
    "total": 4
  }
}
```

| Campo | Significado |
|---|---|
| `current_page` / `last_page` | Página atual e última |
| `from` / `to` | Posição do primeiro e do último item da página na lista toda (`null` numa página vazia) |
| `per_page` / `total` | Tamanho da página e total de itens com os filtros aplicados |
| `links` | Botões de paginação prontos, com a query atual preservada |

Algumas listagens acrescentam chaves ao lado de `meta`, como `stats` (contagens para as abas do painel). Cada página de recurso diz quais.

As outras listas vêm inteiras, sem paginação: usuários, perfis de agente, execuções de um incidente e a timeline de uma execução, que tem um cursor próprio ([Execuções](/referencia-da-api/execucoes)).

## Limites de requisições

Não há um limite geral para a API. O `throttle` só existe nas rotas que custam caro ou que alguém de fora pode chamar, todas com janela de **1 minuto**:

| Rota | Limite | Chave do contador |
|---|---|---|
| `POST /api/v1/connector/{connector}/test` | 10 | Usuário, só nesta rota |
| `POST /api/v1/application/{application}/simulate-incident` | 30 | Usuário, só nesta rota |
| `POST /api/v1/incident/{incident}/retry` | 10 | Usuário, só nesta rota |
| `PUT /api/v1/auth/password` | 6 | Usuário, só nesta rota |
| `POST /api/v1/auth` (login) | 5 erros | E-mail + IP. Não é o `throttle`: o `LoginRequest` conta só as tentativas erradas e devolve `429` com "Muitas tentativas de login. Tente novamente em N segundos." |
| `POST /api/webhooks/{connector}` | 120 | IP, só nesta rota ([Rate limits](/entrada#rate-limits)) |
| `POST /api/slack/commands/{connector}` | 60 | IP, só nesta rota |

Ao passar do limite, a resposta é `429` com os cabeçalhos `Retry-After` (segundos até liberar), `X-RateLimit-Limit` e `X-RateLimit-Remaining`. As respostas normais dessas rotas também trazem os dois `X-RateLimit-*`.

::note
Cada rota tem o **próprio** contador. O Laravel monta a chave do `throttle` só com o id de quem chama (ou o IP), então rotas diferentes somariam na mesma contagem. Por isso cada `throttle` leva um prefixo como terceiro argumento (`throttle:10,1,incident-retry`): dez simulações no minuto não impedem o mesmo usuário de reexecutar um incidente. Uma rota nova com `throttle` precisa de um prefixo próprio.
::

Os recursos criados com `apiResource` também aceitam `PATCH` no lugar de `PUT`: as duas fazem a mesma atualização parcial.

## OpenAPI

Esta referência é escrita à mão, a partir do código. Uma alternativa é gerar um arquivo **OpenAPI** direto do Laravel, com o pacote `dedoc/scramble`, que lê as rotas, os Form Requests e as Resources. Ele daria um contrato que o painel e outras ferramentas leem, e não envelheceria com o código. Em troca, ele não explica o porquê das regras, que é o que estas páginas fazem. Os dois podem conviver: o OpenAPI como contrato, estas páginas como guia.
