As contas do painel. É o único grupo da API com restrição por papel: quem não tem papel (`developer` ou `admin`) só consegue ver a própria conta. As regras de cada papel estão em [Papéis e permissões](/seguranca/papeis-e-permissoes#gestão-de-usuários-por-papel).

| Método | Rota | O que faz |
|---|---|---|
| `GET` | `/api/v1/user` | Lista as contas |
| `POST` | `/api/v1/user` | Cria uma conta |
| `GET` | `/api/v1/user/{user}` | Mostra uma conta |
| `PUT`/`PATCH` | `/api/v1/user/{user}` | Edita uma conta |
| `DELETE` | `/api/v1/user/{user}` | Apaga uma conta (soft delete) |

Código: `UserController`, `StoreUserRequest`, `UpdateUserRequest` (regras comuns no trait `UserRules`), `UserResource`. Os gates `manage-users` e `manage-user` ficam no `AppServiceProvider`. Quando um gate nega, a resposta é `403` com a mensagem "#10001 - Oops, parece que você não tem autorização para prosseguir com essa ação."

## O usuário na resposta

Todas as rotas devolvem o `UserResource`. Ele nunca traz a senha, o `remember_token` nem os ids do login social.

| Campo | Tipo | O que é |
|---|---|---|
| `id` | UUID | |
| `name`, `email`, `cpf` | texto | |
| `active` | booleano | Conta inativa não passa pelo middleware `ensure-user-active` |
| `must_change_password` | booleano | Obriga a trocar a senha no próximo acesso |
| `social_login` | booleano | Conta criada por login social |
| `avatar` | texto, nulo | |
| `role` | `developer`, `admin` ou `null` | O primeiro papel da conta |
| `role_label` | texto, nulo | `Desenvolvedor` ou `Administrador` |
| `created_at`, `updated_at` | data ISO 8601 | |

## Listar usuários

```http
GET /api/v1/user
```

| | |
|---|---|
| **Permissão** | Gate `manage-users`: ter papel `developer` ou `admin` |
| **Sucesso** | `200` |

**Request**

| Campo | Tipo | Obrigatório | Regras |
|---|---|---|---|
| `with_inactive` | booleano (query) | Não | `1`/`true` inclui as contas desativadas. Sem ele, só as ativas |

**Response**

`data` é a lista de usuários em ordem de nome, **sem paginação** e sem `meta`. Contas apagadas (soft delete) nunca aparecem.

**Exemplo**

```http
GET /api/v1/user?with_inactive=1
```

```json
{
  "message": "Usuários listados com sucesso.",
  "data": [
    {
      "id": "01a1c1b3-…",
      "name": "Ana Souza",
      "email": "ana@exemplo.com",
      "cpf": "12345678909",
      "active": true,
      "must_change_password": false,
      "social_login": false,
      "avatar": null,
      "role": "developer",
      "role_label": "Desenvolvedor",
      "created_at": "2026-11-09T19:05:57.000000Z",
      "updated_at": "2026-11-09T19:05:57.000000Z"
    },
    "…"
  ]
}
```

## Criar usuário

```http
POST /api/v1/user
```

| | |
|---|---|
| **Permissão** | Gate `manage-users` (checado no `authorize()` do `StoreUserRequest`, antes da validação) |
| **Sucesso** | `201` |

**Request**

| Campo | Tipo | Obrigatório | Regras |
|---|---|---|---|
| `name` | texto | Sim | Até 255 |
| `email` | texto | Sim | E-mail válido, até 255, único em `users` |
| `cpf` | texto | Sim | Exatamente 11 dígitos, só números; único em `users` |
| `password` | texto | Sim | Mínimo 8 caracteres. Gravada com hash |
| `active` | booleano | Não | Padrão do banco: `true` |
| `must_change_password` | booleano | Não | |
| `role` | texto, nulo | Não | Quem é `developer` pode dar `developer` ou `admin`; quem é `admin` só pode dar `admin` |

Nenhum outro campo chega ao modelo: dados de login social, aceite de termos e avatar são ignorados. A conta nasce com `email_verified_at` preenchido. Conta e papel são gravados na mesma transação.

**Response**

`data` é o usuário criado.

**Erros**

| Status | Quando |
|---|---|
| `422` em `role` | Um `admin` tenta criar um `developer` (o valor fica fora da lista permitida) |
| `422` em `cpf` | "O CPF deve conter 11 dígitos, apenas números." |

**Exemplo**

```http
POST /api/v1/user
```

```json
{
  "name": "Bruno Lima",
  "email": "bruno@exemplo.com",
  "cpf": "12345678909",
  "password": "senha-forte-1",
  "must_change_password": true,
  "role": "admin"
}
```

```json
{
  "message": "Usuário criado com sucesso.",
  "data": {
    "id": "01a1c4d2-…",
    "name": "Bruno Lima",
    "email": "bruno@exemplo.com",
    "cpf": "12345678909",
    "active": true,
    "must_change_password": true,
    "social_login": false,
    "avatar": null,
    "role": "admin",
    "role_label": "Administrador",
    "created_at": "2026-11-17T12:00:00.000000Z",
    "updated_at": "2026-11-17T12:00:00.000000Z"
  }
}
```

## Ver usuário

```http
GET /api/v1/user/{user}
```

| | |
|---|---|
| **Permissão** | Qualquer usuário logado para a **própria** conta; para outra conta, gate `manage-users` |
| **Sucesso** | `200` |

**Request**

Sem corpo.

**Response**

`data` é o usuário. A mensagem é "Usuário exibido com sucesso."

## Editar usuário

```http
PUT /api/v1/user/{user}
```

| | |
|---|---|
| **Permissão** | Gate `manage-user` sobre a conta: ter papel, e só um `developer` edita uma conta `developer` |
| **Sucesso** | `200` |

**Request**

Os mesmos campos de [Criar usuário](#criar-usuário), todos opcionais (`sometimes`): só o que vier é alterado. `email` e `cpf` continuam únicos, ignorando a própria conta. Mandar `password` troca a senha de outra pessoa (o evento `password_changed` vai para a [auditoria](/seguranca/auditoria)).

`role` aceita `null` para tirar o papel. Mudar o papel gera o evento `role_changed` na auditoria, com o papel antigo e o novo. Se o papel enviado for igual ao atual, nada é registrado.

**Response**

`data` é o usuário depois da edição.

**Erros**

| Status | Quando |
|---|---|
| `403` | Um `admin` tenta editar um `developer`; ou quem não tem papel tenta editar qualquer conta, mesmo a própria |
| `422` em `active` | A própria conta com `active: false`: "Você não pode desativar a própria conta." |
| `422` em `role` | A própria conta com qualquer `role`: "Você não pode alterar o próprio papel." |
| `422` em `role` | Um `admin` tenta dar o papel `developer` |

**Exemplo**

```http
PUT /api/v1/user/01a1c4d2-…
```

```json
{
  "active": false
}
```

```json
{
  "message": "Usuário atualizado com sucesso.",
  "data": {
    "id": "01a1c4d2-…",
    "name": "Bruno Lima",
    "email": "bruno@exemplo.com",
    "active": false,
    "role": "admin",
    "…": "…"
  }
}
```

## Apagar usuário

```http
DELETE /api/v1/user/{user}
```

| | |
|---|---|
| **Permissão** | Gate `manage-user` sobre a conta |
| **Sucesso** | `200` |

**Request**

Sem corpo.

**Response**

`data` é `[]`. A conta recebe `deleted_at` (soft delete) e some das listagens.

**Erros**

| Status | Quando |
|---|---|
| `403` | Um `admin` tenta apagar um `developer` |
| `422` | A própria conta: `{"message": "Você não pode excluir a própria conta.", "data": []}`, sem `errors` |

**Exemplo**

```json
{
  "message": "Usuário deletado com sucesso.",
  "data": []
}
```

## Observações

- A regra `unique` de `email` e `cpf` (`UserRules`) não ignora contas apagadas: o e-mail ou o CPF de uma conta com soft delete não pode ser reaproveitado numa conta nova.
- Na própria conta, mandar `role` com o **mesmo** papel que ela já tem também dá `422` (`UpdateUserRequest::after()` checa só se o campo veio). Um formulário que reenvia todos os campos precisa omitir `role` quando o usuário edita a si mesmo.
- O `422` de excluir a própria conta não segue o formato de validação: vem só `message`, sem `errors`.
