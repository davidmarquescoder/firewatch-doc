Erros de produção carregam o que não deveriam: cabeçalhos `Authorization`, cookies de sessão, e-mails e CPFs de clientes, a `DB_PASSWORD` num dump de `.env`. O `App\Services\Security\SensitiveDataMasker` remove isso **antes** que o conteúdo chegue ao modelo de IA, ao painel, ao Slack, ao Jira, ao Pull Request ou à auditoria.

O princípio está no próprio docblock da classe: o mascaramento é **best effort e erra para o lado de esconder**. Perder um número que parece telefone num stack trace é melhor do que vazar um telefone real.

## Duas camadas

| Camada | Método | Como funciona |
|---|---|---|
| **Por chave** | `maskArray()` | Se a **chave** de um array parece sensível, o valor inteiro vira `[redacted]`, seja ele qual for |
| **Por texto** | `maskString()` | Padrões (regex) encontram tokens, e-mails, documentos e cartões dentro de **qualquer** string, inclusive nas chaves dos arrays |

O ponto de entrada geral é `mask(mixed $value)`: strings vão para `maskString()`, arrays para `maskArray()` (recursivo) e o resto (números, booleanos, `null`) passa intacto.

### Por chave

Uma chave é sensível quando contém (sem diferenciar maiúsculas) alguma destas palavras:

```text
password  passwd  pwd  secret  token  authorization  api_key  apikey  api-key
cookie  session  private_key  credential  cpf  cnpj  phone  telefone  celular
email  e-mail  senha  dsn  cvv  cvc  card_number  cardnumber  cartao  cartão  iban
```

Exceções, porque ajudam a depurar e não são segredo:

- `token_type`, `auth_type`, `authenticated`, `session_id_present`;
- qualquer chave terminada em `tokens` (`input_tokens`, `total_tokens`…), que são métricas.

Valores `null`, vazios ou booleanos **não** são trocados: `"password": null` continua dizendo que não havia senha, e `"authenticated": true` continua útil.

```php
$masker->maskArray([
    'request' => [
        'url'     => '/api/v1/brand?page=1',
        'headers' => ['Authorization' => 'Bearer abc…', 'Cookie' => 'laravel_session=…', 'accept' => 'application/json'],
    ],
    'user' => ['id' => 42, 'email' => 'ana@empresa.com', 'active' => true],
    'flag' => ['token_type' => 'bearer'],
]);

// [
//   'request' => [
//     'url'     => '/api/v1/brand?page=1',
//     'headers' => ['Authorization' => '[redacted]', 'Cookie' => '[redacted]', 'accept' => 'application/json'],
//   ],
//   'user' => ['id' => 42, 'email' => '[redacted]', 'active' => true],
//   'flag' => ['token_type' => 'bearer'],
// ]
```

**As chaves também são mascaradas** pela camada de texto (`{"joao@x.com": "aberto"}` vira `{"[email]": "aberto"}`). Se duas chaves mascaradas colidirem, a segunda ganha um sufixo (`[email]#2`) em vez de sobrescrever a primeira.

### Por texto

Os padrões são aplicados **nesta ordem** (a ordem importa: chaves privadas e URLs com credenciais saem antes que padrões mais genéricos as quebrem):

| # | O que encontra | Exemplo | Vira |
|---|---|---|---|
| 1 | Número de cartão (15, 16 ou 19 dígitos) que **passa no Luhn** | `4111 1111 1111 1111` | `[cartao]` |
| 2 | Chave privada PEM (inclusive com `\n` escapado em JSON) | `-----BEGIN RSA PRIVATE KEY-----…` | `[private-key]` |
| 3 | Cabeçalho `Cookie` / `Set-Cookie` | `Cookie: laravel_session=…; XSRF-TOKEN=…` | `Cookie: [redacted]` |
| 4 | Usuário e senha em URL | `https://x-token-auth:s3cr3t@bitbucket.org/…` | `https://[redacted]@bitbucket.org/…` |
| 5 | Token como usuário da URL | `https://ghp_abc@github.com/…` | `https://[redacted]@github.com/…` |
| 6 | `Bearer` / `Basic` / `Token` + valor | `Authorization: Bearer abc.DEF-123` | `Authorization: Bearer [redacted]` |
| 7 | JWT | `eyJhbGciOi.eyJzdWIiOiIx.c2ln…` | `[jwt]` |
| 8 | Prefixos conhecidos: Anthropic/OpenAI (`sk-`), Bitbucket/Atlassian (`ATCTT`, `ATATT`), Slack (`xox?-`), GitHub (`ghp_`, `github_pat_`…), GitLab (`glpat-`), AWS (`AKIA`), Stripe (`sk_/pk_/rk_live/test_`), Google (`AIza`), chaves `base64:` do Laravel | `sk-ant-api03-…` | `[token]` |
| 9 | `chave=valor` / `chave: valor` com nome de segredo | `DB_PASSWORD=hunter2`, `senha=Abc@1234` | `DB_PASSWORD=[redacted]` |
| 10 | Nomes no estilo `.env` terminados em `_KEY`, `_DSN`, `_AUTH`, `_PASS`, `_CREDENTIALS` (só maiúsculas) | `STRIPE_KEY=abc` | `STRIPE_KEY=[redacted]` |
| 11 | E-mail (também `%40` codificado em URL) | `joao.silva%40empresa.com.br` | `[email]` |
| 12 | Telefone brasileiro sem formatação | `+5511987654321` | `[telefone]` |
| 13 | CNPJ (formatado ou 14 dígitos) | `12.345.678/0001-90` | `[cnpj]` |
| 14 | CPF (formatado ou 11 dígitos) | `529.982.247-25` | `[cpf]` |
| 15 | Telefone brasileiro formatado | `(11) 98765-4321` | `[telefone]` |

### O que fica de propósito

O teste `SensitiveDataMaskerTest` garante que o mascaramento não destrói o que os agentes precisam para investigar:

| Fica | Por quê |
|---|---|
| `at line 88 of app/Models/Order.php` | Caminhos e números de linha |
| `request id 1234567812345678 failed` | 16 dígitos que **não** passam no Luhn não são cartão |
| `at 1731427200000 job 7 failed` | Timestamps em milissegundos |
| `Duplicate entry for key PRIMARY` | O padrão `.env` só pega nomes em maiúsculas com `_KEY` |
| `used 1200 input tokens` | Contagem de tokens |
| UUIDs, placeholders SQL (`?`) e stack traces inteiros | Indispensáveis para achar a causa |

## Onde é aplicado

| Momento | Onde | O que é mascarado |
|---|---|---|
| **Recebimento** do evento | `RegisterIncomingEventAction` | Gera `incidents.sanitized_payload` com `maskArray()` do evento normalizado. O original vai para `raw_payload`, **criptografado** e oculto (`#[Hidden]`) |
| **Prompt** dos agentes | `InvestigationPromptBuilder` | Título, ambiente, stack trace e contexto |
| **Título no runner** | `DockerRunner` | Título do incidente passado ao container |
| **Saída dos agentes** | `StreamEventMapper` | `content` e `metadata` de cada `agent_events` antes de salvar e transmitir |
| **Falhas** | `FailureClassifier`, `InvestigateIncident` | Explicação da falha e última mensagem do runner |
| **Entregas** | `InvestigationReport`, `JiraIssueTracker` | Título e descrição do PR, mensagens do Slack, card do Jira, motivos e avisos |
| **Painel** | `IncidentResource` | O stack trace exibido vem do `sanitized_payload`, nunca do `raw_payload` |
| **Auditoria** | `MaskedLogActivityAction`, `AuditLogResource` | Tudo o que entra no `activity_log` e o nome do item exibido (veja [Auditoria](/seguranca/auditoria)) |

::note
O `raw_payload` existe para reprocessar ou depurar um evento. Ele **nunca** sai pela API nem vai para o runner. Quem tem acesso ao banco e à `APP_KEY` consegue lê-lo, então trate os dois como segredos de produção.
::

## Estendendo

- **Nova chave sensível**: inclua a palavra em `SENSITIVE_KEYS`. Lembre que a comparação é por "contém": `key` sozinho pegaria `keyboard`, `monkey`…
- **Novo formato de token**: inclua o prefixo na regex do item 8, com tamanho mínimo, para não mascarar palavras comuns.
- **Uma chave útil sendo escondida**: inclua em `SAFE_KEYS`.

Em todos os casos, adicione um caso em `tests/Unit/Security/SensitiveDataMaskerTest.php`: no provider `texts` (deve mascarar) ou `harmless` (deve ficar como está).
