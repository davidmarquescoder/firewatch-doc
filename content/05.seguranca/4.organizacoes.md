::warning
**O FireWatch é single tenant.** As tabelas `organizations` e `organization_memberships` vieram do template base do back-end e existem no banco e na API, mas **nada do domínio do FireWatch pertence a uma organização**: conectores, aplicações, incidentes, execuções e perfis de agentes não têm `organization_id`, e nenhuma consulta filtra por organização. Todo usuário logado vê e altera tudo. Multi-tenancy está explicitamente **fora do escopo do MVP**.
::

## O que existe

| Peça | Arquivo | Situação |
|---|---|---|
| Modelo `Organization` | `app/Models/Organization/Organization.php` | Cadastro de empresa (razão social, CNPJ/CPF, porte, logo, endereço) |
| Modelo `OrganizationMembership` | `app/Models/Organization/OrganizationMembership.php` | Liga um usuário a uma organização |
| `OrganizationController` | `app/Http/Controllers/OrganizationController.php` | CRUD em `/api/v1/organization` + upload de logo |
| Actions | `CreateOrganizationAction`, `UpdateOrganizationAction`, `CreateAddressAction`, `UpdateAddressAction`, `UploadFileAction` | Regras do cadastro |
| Painel | | **Sem tela.** Só a página de auditoria conhece o tipo `organization` |

### organizations

Colunas principais: `legal_name` e `trade_name` (únicos), `business_size` (`BusinessSizeEnum`: MEI, ME, EPP…), `entity_type` (`EntityTypeEnum`: `PJ` ou `PF`), `cnpj`/`cpf`, `email`, `phone`, `logo`, `active`. UUID, timestamps e soft delete. O endereço é polimórfico (`addresses.addressable`, relação `address()`).

Relações no modelo: `address()` (morphOne), `memberships()` (hasMany) e `activityLogs()`.

### organization_memberships

| Coluna | Tipo | Observação |
|---|---|---|
| `id` | UUID | |
| `organization_id` | FK → `organizations` | |
| `user_id` | FK → `users` | |
| `type` | string, nulo | Livre. Não há enum nem regra que leia este campo |
| `active` | boolean, padrão `true` | |
| timestamps + `deleted_at` | | Soft delete |

O modelo tem `organization()` e `user()`, mas **o `User` não tem a relação inversa** (`memberships()` ou `organizations()`), nenhuma rota cria memberships e nada consulta a tabela.

## A API de organizações

Atrás da pilha normal do painel (`auth:sanctum`, `ensure-user-active`, `ensure-password-change`), sem checagem de papel (veja [Papéis e permissões](/seguranca/papeis-e-permissoes)):

| Método e rota | O que faz |
|---|---|
| `GET /api/v1/organization` | Lista paginada (`per_page`, `search` pela razão social) com `stats`: total, ativas, inativas, PJ e PF |
| `POST /api/v1/organization` | Cria a organização e o endereço numa transação |
| `GET /api/v1/organization/{id}` | Detalhe (`ShowOrganizationResource`) |
| `PUT /api/v1/organization/{id}` | Atualiza organização e endereço |
| `DELETE /api/v1/organization/{id}` | Soft delete (`deleted_at`); responde `204` |
| `POST /api/v1/organization/{id}/upload` | Logo: jpeg, png, jpg, gif ou svg até 1 MB, salvo em `organizations/logos/{id}` |

Alterações em `Organization` entram na auditoria (log `configuration`, campos de `#[Fillable]`). O `OrganizationMembership` usa `LogsActivity` sem opções próprias: os registros, se houvesse, iriam para o log `default`, que a tela de auditoria não mostra.

## O isolamento que existe hoje

Sem organizações em uso, a separação de acesso depende só de **quem tem usuário**:

- A API do painel exige sessão de um usuário ativo (veja [Autenticação](/seguranca) e [Middlewares](/seguranca/middlewares)).
- Os canais do Reverb aceitam qualquer usuário ativo: `GlobalChannel` traz o comentário *"single tenant MVP"*.
- Webhooks são por **conector**, não por organização.

## Se um dia virar multi-tenant

Um ponto de partida, para não começar do zero quando a decisão vier:

1. Adicionar `organization_id` em `connectors`, `applications`, `agent_profiles` e `app_settings`. Incidentes, execuções e eventos herdam pela aplicação.
2. Criar a relação `User::organizations()` via `organization_memberships` e guardar a organização ativa na sessão.
3. Um **global scope** nos modelos do domínio filtrando pela organização ativa, e Form Requests validando que IDs recebidos (conector de uma aplicação, por exemplo) são da mesma organização.
4. Canais do Reverb checando se o incidente pertence a uma organização do usuário.
5. Teto de custo (`budget`) por organização, em vez de global.
6. Papéis por organização: o `spatie/laravel-permission` tem suporte a *teams* (`permission:setup-teams`).
