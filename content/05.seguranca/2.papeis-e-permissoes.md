Papéis e permissões usam o **`spatie/laravel-permission`** (^8.3). O modelo `User` tem a trait `HasRoles`, e as tabelas são as do pacote: `roles`, `permissions`, `model_has_roles`, `model_has_permissions` e `role_has_permissions` (veja [Diagrama ER](/modelo-de-dados)).

Os nomes não ficam espalhados pelo código: três enums em `app/Enums/Security` são a fonte da verdade.

## RoleEnum

`App\Enums\Security\RoleEnum` · tabela `roles.name`

| Valor | Rótulo (`label()`) | Quem recebe |
|---|---|---|
| `developer` | Desenvolvedor | O primeiro usuário, criado pelo `add-first` |
| `admin` | Administrador | Quem um `developer` ou `admin` indicar pela API de usuários |

Métodos: `all()` (lista dos valores, usada pelo seeder) e `label()`.

## PermissionEnum

`App\Enums\Security\PermissionEnum` · tabela `permissions.name`

| Valor | Significado |
|---|---|
| `view` | Ver |
| `create` | Criar |
| `edit` | Editar |
| `delete` | Apagar |

São permissões **genéricas**, sem recurso no nome. Métodos: `all()` (todas) e `generic()` (as quatro acima). Hoje as duas listas são iguais; a separação existe para que permissões específicas (por exemplo, `connector.test`) entrem em `all()` sem ir automaticamente para o `admin`.

## A matriz PermissionRoleEnum

`App\Enums\Security\PermissionRoleEnum` liga cada papel às suas permissões pelo método `permissions()`:

```php [app/Enums/Security/PermissionRoleEnum.php]
public function permissions(): array
{
    return match ($this) {
        self::DEVELOPER => PermissionEnum::all(),
        self::ADMIN     => [
            ...PermissionEnum::generic(),
        ],
        default         => [],
    };
}
```

| Permissão | `developer` | `admin` |
|---|:---:|:---:|
| `view` | ✓ | ✓ |
| `create` | ✓ | ✓ |
| `edit` | ✓ | ✓ |
| `delete` | ✓ | ✓ |
| Futuras permissões em `all()` fora de `generic()` | ✓ | |

O `developer` recebe **tudo o que existir**; o `admin` só as genéricas.

## Como os dados chegam ao banco

O `DatabaseSeeder` roda, nesta ordem:

| Seeder | O que faz |
|---|---|
| `Security\RoleSeeder` | `Role::firstOrCreate()` para cada `RoleEnum::all()` |
| `Security\PermissionSeeder` | `Permission::firstOrCreate()` para cada `PermissionEnum::all()` |
| `Security\PermissionRoleSeeder` | `givePermissionTo(PermissionRoleEnum::X->permissions())` em cada papel |

Os três podem rodar de novo sem duplicar nada. Para **adicionar uma permissão**:

1. Crie o `case` em `PermissionEnum` (e inclua em `generic()` se o `admin` também deve ter).
2. Ajuste `PermissionRoleEnum::permissions()` se a regra for diferente.
3. Rode `php artisan db:seed --class="Database\Seeders\Security\PermissionSeeder"` e depois o `PermissionRoleSeeder`.
4. Limpe o cache do pacote: `php artisan permission:cache-reset`.

O papel é atribuído com `$user->assignRole(…)`: pelo comando `add-first` (que usa `User::role('developer')->exists()` para recusar um segundo desenvolvedor) ou pelo campo `role` da API de usuários (abaixo).

## O que é verificado hoje

### Gestão de usuários: por papel

As rotas de `/api/v1/user` passam por dois **gates** definidos no `AppServiceProvider`:

| Gate | Regra |
|---|---|
| `manage-users` | Ter um papel (`developer` ou `admin`). Usuário sem papel recebe `403` |
| `manage-user` (sobre uma conta) | O mesmo, e **só um `developer` mexe em contas `developer`**: um `admin` não consegue desativar, rebaixar ou apagar um desenvolvedor |

| Rota | Quem pode |
|---|---|
| `GET /api/v1/user` | `manage-users`. Lista os ativos; `?with_inactive=1` inclui os desativados |
| `GET /api/v1/user/{id}` | O próprio usuário, ou `manage-users` |
| `POST /api/v1/user` | `manage-users` |
| `PUT /api/v1/user/{id}` | `manage-user` sobre a conta |
| `DELETE /api/v1/user/{id}` | `manage-user` sobre a conta (soft delete) |

Os dados passam pelos Form Requests `StoreUserRequest` e `UpdateUserRequest` (regras no trait `UserRules`). Só estes campos chegam ao modelo:

| Campo | Regras |
|---|---|
| `name`, `email` | Obrigatórios ao criar; e-mail único |
| `cpf` | Obrigatório ao criar; 11 dígitos, único |
| `password` | Obrigatória ao criar; no mínimo 8 caracteres (gravada com hash) |
| `active`, `must_change_password` | Booleanos |
| `role` | `developer` ou `admin` para quem é `developer`; só `admin` para quem é `admin`. `null` remove o papel |

Dados de login social, aceite de termos e avatar não são aceitos. Para ninguém se trancar para fora, um usuário **não pode** desativar a própria conta, mudar o próprio papel nem se apagar (`422`). Trocar o papel de alguém gera o evento `role_changed` na [auditoria](/seguranca/auditoria), com o papel antigo e o novo.

As respostas usam o `UserResource`: nunca devolvem senha, `remember_token` nem ids do login social, e trazem `role` e `role_label`.

### O resto da API: aberto a qualquer usuário logado

::warning
Fora da gestão de usuários, **papéis e permissões ainda não restringem nada**. Nenhuma outra rota usa `role:`/`permission:` e os demais Form Requests devolvem `authorize(): true`. Qualquer usuário autenticado, ativo e sem troca de senha pendente pode criar, editar e apagar conectores, aplicações, perfis de agentes e organizações, e mudar o teto de custo.
::

Isso é coerente com o escopo do MVP (um só time usando o painel). Outros pontos:

- As **permissões** (`view`, `create`, `edit`, `delete`) ainda não são usadas em lugar nenhum; só os papéis são.
- O Horizon (`/horizon`) tem o gate `viewHorizon` com a lista de e-mails vazia: fora do ambiente `local`, ninguém acessa.

### Para começar a usar

O caminho mais curto, sem mudar o modelo de dados:

```php [routes/api.php]
// Só quem tem a permissão "delete" apaga conectores.
Route::delete('connector/{connector}', [ConnectorController::class, 'destroy'])
    ->middleware('permission:delete');
```

```php [app/Http/Requests/Connector/StoreConnectorRequest.php]
public function authorize(): bool
{
    return $this->user()->can(PermissionEnum::CREATE->value);
}
```

O pacote **não registra** os aliases `role`, `permission` e `role_or_permission` sozinho: registre-os em `bootstrap/app.php`, junto dos aliases do FireWatch, apontando para `Spatie\Permission\Middleware\RoleMiddleware`, `PermissionMiddleware` e `RoleOrPermissionMiddleware`. Outra opção são as macros de rota que o pacote já registra: `->role('developer')` e `->permission('delete')`.

Para dar um papel a um usuário que já existe, sem escrever código: `php artisan permission:assign-role admin <id-do-usuário>`.
