O painel usa o **Laravel Sanctum em modo SPA**: não há token no `localStorage`. O login cria uma **sessão** no Laravel (guardada no Redis) e o navegador passa a mandar o cookie de sessão em toda chamada. A proteção contra CSRF vem do par `XSRF-TOKEN` (cookie) / `X-XSRF-TOKEN` (header).

| Peça | Onde | Papel |
|---|---|---|
| `laravel/sanctum` ^4 | back | Guard `auth:sanctum` que aceita a sessão do guard `web` |
| `$middleware->statefulApi()` | `bootstrap/app.php` | Liga sessão, cookies e CSRF nas rotas `api/*` vindas de um domínio "stateful" |
| `nuxt-auth-sanctum` | front | Busca o cookie CSRF, chama login/logout e guarda o usuário |
| `nuxt-laravel-echo` | front | Autentica os canais privados do Reverb com o mesmo cookie |

## Rotas de autenticação

Ficam em `routes/auth.php`, carregado junto com `routes/api.php` (prefixo `/api/v1/auth`).

| Método e rota | Controller | Middleware | O que faz |
|---|---|---|---|
| `GET /sanctum/csrf-cookie` | do Sanctum | | Grava o cookie `XSRF-TOKEN`. Primeira chamada antes do login |
| `POST /api/v1/auth` | `Auth\StoreController` | `guest` | Login com e-mail e senha; regenera a sessão; devolve `{ user }` |
| `GET /api/v1/auth` | `Auth\ShowController` | `auth:sanctum` | Devolve `{ user }` da sessão atual |
| `DELETE /api/v1/auth` | `Auth\DestroyController` | `auth:sanctum` | Logout: encerra o guard `web`, invalida a sessão e troca o token CSRF |
| `PUT /api/v1/auth/password` | `Auth\UpdatePasswordController` | `auth:sanctum`, `ensure-user-active`, `throttle:6,1,password-update` | Troca a própria senha e limpa `must_change_password`. Fica **fora** do `ensure-password-change` de propósito |
| `GET /api/v1/auth/google/redirect` | `Auth\Google\RedirectController` | `guest` | Devolve a URL de consentimento do Google |
| `GET /api/v1/auth/google/callback` | `Auth\Google\CallbackController` | `guest` | Recebe o retorno do Google, cria ou encontra o usuário e faz login |

Todas as demais rotas do painel (`/api/v1/*` em `routes/api.php`) e a autorização dos canais (`POST /api/broadcasting/auth`) passam pela mesma pilha:

```php [routes/api.php]
Route::middleware([
    'auth:sanctum',
    'ensure-user-active',
    'ensure-password-change',
])->group(function () { /* … */ });
```

Os dois middlewares extras estão em [Middlewares](/seguranca/middlewares). As rotas de **webhook** ficam fora dessa pilha: elas não têm sessão e são autenticadas pela assinatura do conector.

## Login com e-mail e senha

A validação e a tentativa ficam no `LoginRequest` (`app/Http/Requests/Auth/LoginRequest.php`):

- Regras: `email` obrigatório e válido, `password` obrigatório. O campo `remember` (booleano) liga o cookie "lembrar de mim".
- `Auth::attempt()` com o guard `web` (senha com hash bcrypt, cast `hashed` no modelo `User`).
- **Limite de tentativas**: 5 erros seguidos para o mesmo par **e-mail + IP** (chave `throttleKey()`) bloqueiam novas tentativas até o `RateLimiter` liberar. O bloqueio dispara o evento `Lockout` e responde com a mensagem `auth.throttle`.
- Sucesso limpa o contador. Em seguida o `LoginRequest` confere `users.active`: conta desativada é deslogada na hora e **não recebe sessão**, mesmo com a senha certa.
- Por fim o controller chama `session()->regenerate()`, o que evita fixação de sessão.

Os erros saem como `ValidationException` e o framework os responde em JSON, com o motivo em `message` e em `errors.email`:

| Situação | Status | Mensagem (`lang/pt_BR/auth.php`) |
|---|---|---|
| E-mail ou senha errados | `422` | `auth.failed` |
| Conta desativada | `403` | `auth.inactive` |
| 5 erros seguidos para o mesmo e-mail e IP | `429` | `auth.throttle` (com os segundos que faltam) |

A resposta de sucesso é o modelo `User` serializado (sem `password` e `remember_token`, que estão em `#[Hidden]`):

```json
{
  "user": {
    "id": "9d3c…",
    "name": "Ana Souza",
    "email": "ana@empresa.com.br",
    "active": true,
    "must_change_password": false,
    "social_login": false,
    "avatar": null
  }
}
```

## Fluxo de login no painel

O `nuxt-auth-sanctum` está configurado em `firewatch-front/nuxt.config.ts`:

```ts [nuxt.config.ts]
sanctum: {
    mode: 'cookie',
    endpoints: {
        csrf: '/sanctum/csrf-cookie',
        login: '/api/v1/auth',
        logout: '/api/v1/auth',
        user: '/api/v1/auth',
    },
    csrf: { cookie: 'XSRF-TOKEN', header: 'X-XSRF-TOKEN' },
    redirect: {
        onLogin: '/dashboard',
        onLogout: '/auth/sign-in',
        onAuthOnly: '/auth/sign-in',
        onGuestOnly: '/dashboard',
    },
    globalMiddleware: { enabled: true },
},
```

Pontos do lado do front:

- **Middleware global.** Com `globalMiddleware.enabled`, toda página exige login, a não ser que declare o contrário. A tela de login (`pages/auth/sign-in.vue`) e a raiz (`pages/index.vue`) usam `definePageMeta({ sanctum: { guestOnly: true } })`: quem já está logado é levado para `/dashboard`.
- **Tela de login.** Valida e-mail e senha no próprio formulário, envia `remember: true` por padrão ("Manter conectado neste dispositivo") e limpa o campo de senha quando dá erro. Mensagens tratadas por `describeError()`:

  | Situação | Mensagem |
  |---|---|
  | Sem resposta do servidor | "Não foi possível conectar ao servidor…" |
  | `419` (CSRF expirado) | "Sua sessão expirou. Recarregue a página…" |
  | `429` (bloqueio do login) | "Muitas tentativas seguidas…" |
  | Outros | O `message` da API, ou "E-mail ou senha incorretos." |

- **Usuário atual.** O composable `useCurrentUser()` lê `user` do `useSanctumAuth()` e calcula `firstName`, `initials` e `avatarUrl` para o cabeçalho.
- **Logout.** O menu do usuário (`components/layout/UserMenu.vue`) chama `logout({ method: 'DELETE' })`. Em caso de falha mostra um toast; em caso de sucesso o módulo redireciona para `/auth/sign-in`.

## Tempo real (Reverb)

Os canais do Reverb são **privados**. Antes de entrar, o Echo chama `POST /api/broadcasting/auth` com o mesmo cookie de sessão (configurado em `withBroadcasting()` no `bootstrap/app.php`, com `auth:sanctum`, `ensure-user-active` e `ensure-password-change`). Cada canal ainda tem sua própria regra:

| Canal | Classe | Quem entra |
|---|---|---|
| `private-firewatch` | `GlobalChannel` | Usuário `active` e sem `must_change_password` |
| `private-incidents.{incident}` | `IncidentChannel` | O mesmo, e o incidente precisa existir (route model binding) |
| `private-App.Models.User.{id}` | closure | Só o próprio usuário (ids comparados como string) |

Detalhes do fluxo de autorização em [Reverb e canais](/tempo-real#a-autorização-em-channelsphp).

## Login com Google

Existe no back, mas **o painel não usa**: não há botão na tela de login. O fluxo é `stateless` (Socialite):

1. `GET /auth/google/redirect` devolve `data.url`, a página de consentimento do Google.
2. O Google volta em `/auth/google/callback`. O `CallbackController` procura o usuário pelo e-mail; se não existir, **cria** um com `social_login = true`, `social_provider = google`, avatar do Google e e-mail já verificado.
3. Faz `Auth::login()` e regenera a sessão.

Como no login por senha, uma conta desativada recebe `403` e não ganha sessão. As configurações padrão (`settings`) só são criadas no primeiro login (`firstOrCreate`).

::note
Antes de ligar esse fluxo no painel, decida quem pode entrar: hoje **qualquer conta Google** cria um usuário novo, sem lista de domínios permitidos e sem papel. Das opções de `LoginProviderEnum`, só o Google está implementado.
::

## Sessão e cookies

| Variável | Valor no `.env.example` | Efeito |
|---|---|---|
| `SESSION_DRIVER` | `redis` | Sessões no Redis |
| `SESSION_LIFETIME` | `120` | Minutos de inatividade até a sessão expirar (com `remember`, o cookie de "lembrar" mantém o login) |
| `SESSION_DOMAIN` | `null` | Cookie só para o host da API |
| `SANCTUM_STATEFUL_DOMAINS` | `localhost:5000,127.0.0.1:5000` | Hosts do painel que recebem sessão. Sem o host certo, o login dá `419`/`401` |
| `FRONTEND_URL` | `http://localhost:5000` | Também entra na lista de domínios stateful |

O cookie de sessão é `http_only` e `same_site=lax` (padrões do Laravel). Em produção, defina `SESSION_SECURE_COOKIE=true` e sirva tudo por HTTPS. O CORS (`config/cors.php`) aceita qualquer origem com `supports_credentials = true`; quem limita o acesso por sessão é a lista de domínios stateful do Sanctum.

Problemas comuns de login em ambiente local estão em [Primeiro acesso](/ambiente-e-setup/primeiro-acesso#problemas-comuns).
