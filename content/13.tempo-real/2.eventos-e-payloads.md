O Firewatch envia três eventos, todos em `app/Events/Realtime/`:

| Evento | Nome no Echo | Canais | Quando |
|---|---|---|---|
| `IncidentStatusChanged` | `.incident.status-changed` | Global e do incidente | Incidente criado ou com status novo |
| `AgentRunStatusChanged` | `.agent-run.status-changed` | Global e do incidente | Execução criada ou com status novo |
| `AgentEventRecorded` | `.agent-event.recorded` | Só o do incidente | Cada linha nova da timeline |

Os três usam `broadcastAs()` com um nome curto. Por isso o Echo ouve com um **ponto** na frente (`.incident.status-changed`): sem o ponto, o Echo procuraria `App\Events\incident.status-changed`. O painel guarda os nomes em `REALTIME_EVENTS` (`app/composables/useRealtime.ts`).

## Como um evento sai

Ninguém chama `broadcast()` diretamente. Os eventos saem dos **hooks dos modelos**, sempre pelo `App\Services\Realtime\RealtimeBroadcaster`:

| Modelo | Hook | Evento |
|---|---|---|
| `Incident` | `created` | `IncidentStatusChanged` com `previous_status: null` |
| `Incident` | `updated`, se o `status` mudou | `IncidentStatusChanged` com o status anterior |
| `AgentRun` | `created` | `AgentRunStatusChanged` com `previous_status: null` |
| `AgentRun` | `updated`, se o `status` mudou | `AgentRunStatusChanged` com o status anterior |
| `AgentEvent` | `created` | `AgentEventRecorded` |

Por isso qualquer caminho que muda um status avisa o painel: o job, a reexecução, o watchdog, a simulação e a entrega. Salvar sem mudar o status (uma ocorrência nova, um `status_reason` novo) **não** envia nada. O anterior vem de `getRawOriginal('status')`, que no hook `updated` ainda guarda o valor antigo.

`RealtimeBroadcaster::send()` recebe uma função que monta o evento e:

::mermaid
---
code: |
  flowchart TD
      S["send(fn)"] --> E{"FIREWATCH_REALTIME_ENABLED?"}
      E -->|não| X[Nada]
      E -->|sim| B["Monta o evento agora<br/>(foto do estado)"]
      B -->|erro| L1["Log: Realtime broadcast failed<br/>stage build"]
      B --> C["DB::afterCommit"]
      C -->|transação desfeita| X2[Descartado]
      C -->|commit, ou sem transação| BR["broadcast()"]
      BR -->|erro| L2["Log: Realtime broadcast failed<br/>stage send"]
---
::

- **O payload é montado na hora.** Ele mostra o estado do momento da mudança, mesmo que o modelo mude de novo antes do envio.
- **O envio espera o commit.** Uma mudança que a transação desfez nunca chega ao painel. Fora de uma transação, sai na hora.
- **Nunca quebra quem chamou.** Um Reverb fora do ar só gera um `warning` no log. A investigação continua e o painel recupera o estado pela API.
- **Sem fila.** Os eventos são `ShouldBroadcastNow`: saem no próprio processo que fez a mudança (o worker do runner, o worker da fila ou a requisição HTTP), sem passar por um job. Assim a timeline não fica atrás de uma fila cheia.

## Os payloads

### incident.status-changed

```json
{
  "previous_status": "investigating",
  "status": "fixing",
  "incident": {
    "id": "9f1c…",
    "title": "ErrorException: Attempt to read property \"name\" on null",
    "status": "fixing",
    "status_label": "Corrigindo",
    "status_reason": null,
    "failure_kind": null,
    "occurrences": 3,
    "pr_url": null,
    "jira_key": "FW-7",
    "fixing_at": "2026-11-17T14:03:12.000000Z",
    "application": { "id": "…", "name": "Loja", "monitoring_identifier": "loja-back" },
    "latest_run": { "id": "…", "status": "running", "cost_usd": null, "team": [ … ] },
    "runs_count": 1,
    "retry": { "allowed": false, "reason": "…", "used": 0, "max": 3 },
    "…": "…"
  }
}
```

O `incident` é o mesmo `IncidentResource` de `GET /api/v1/incident/{id}`, montado numa **cópia** do modelo com a aplicação (inclusive removida), a última execução e a contagem de execuções. Ficam de fora:

- o `stack_trace`, que só vem na leitura detalhada da API (o painel mantém o que já tinha);
- o payload original e o sanitizado, que nunca saem pela API.

`previous_status` é `null` quando o incidente acabou de ser recebido. O valor de `status` é o mesmo que `incident.status`; ele fica em cima para o painel decidir sem abrir o objeto.

### agent-run.status-changed

```json
{
  "incident_id": "9f1c…",
  "previous_status": "running",
  "status": "fixed",
  "run": {
    "id": "…",
    "incident_id": "9f1c…",
    "status": "fixed",
    "status_label": "Corrigido",
    "exit_code": 0,
    "failure_stage": null,
    "failure_reason": null,
    "work_branch": "firewatch/FW-7-errorexception-attempt-to-read",
    "model": "claude-…",
    "started_at": "…",
    "finished_at": "…",
    "duration_seconds": 412,
    "input_tokens": 182340,
    "output_tokens": 9120,
    "cost_usd": "0.8731",
    "num_turns": 41,
    "team": [ … ],
    "created_at": "…",
    "updated_at": "…"
  }
}
```

O `run` é o `AgentRunResource` **sem** o `report`. O relatório (diff, causa raiz, testes) é grande e só vem pela API, quando o painel pede o detalhe da execução. Os status de uma execução são `pending` (criada) → `running` → `fixed`, `failed` ou `dry_run`. Tokens, custo e duração só aparecem preenchidos no evento final.

### agent-event.recorded

```json
{
  "incident_id": "9f1c…",
  "event": {
    "id": "…",
    "agent_run_id": "…",
    "sequence": 57,
    "agent": "cirurgiao",
    "type": "edit_file",
    "type_label": "Editou arquivo",
    "content": "app/Http/Controllers/OrderController.php",
    "content_truncated": false,
    "metadata": { "tool": "Edit", "old_string": "…", "new_string": "…" },
    "tool_use_id": "toolu_…",
    "occurred_at": "…",
    "created_at": "…"
  }
}
```

O `event` é o `AgentEventResource`, o mesmo da API da timeline, com o corte descrito abaixo. Como cada linha do stdout do runner vira um `AgentEvent`, e o que vai em `type`, `content` e `metadata`, está em [Streaming](/investigacao/streaming). O conteúdo já chega mascarado ([Mascaramento](/seguranca/mascaramento)).

`sequence` é a ordem da linha dentro da execução, começando em 1. É ele que deixa o painel perceber que perdeu uma linha.

## O corte do conteúdo

Uma linha da timeline pode ser grande: a saída de uma suíte de testes, um arquivo inteiro escrito pelo Cirurgião. O Reverb recusa publicações acima de `REVERB_MAX_REQUEST_SIZE` (100 000 bytes), e uma publicação recusada é só um `warning` no log: a linha não apareceria ao vivo. Por isso `AgentEventRecorded` corta o conteúdo antes de enviar:

```php
(new AgentEventResource($event))
    ->limitContent(config('firewatch.realtime.max_content_length'))
    ->resolve();
```

| Regra | Detalhe |
|---|---|
| Limite | `FIREWATCH_REALTIME_MAX_CONTENT_LENGTH`, padrão `4000` **caracteres** (não bytes) |
| `content` | Acima do limite, fica com os primeiros 4000 caracteres e um `…` no fim (4001 no total) |
| `metadata` | **Todo** texto dentro dela, em qualquer nível, recebe o mesmo corte (por exemplo, o `old_string` e o `new_string` de um Edit) |
| `content_truncated` | `true` quando o `content` ou qualquer texto da `metadata` foi cortado aqui, **ou** quando o `content` já tinha sido cortado ao salvar. Quer dizer "esta linha veio incompleta" |
| Limite `0` ou vazio | Sem corte |
| Banco | Não muda: o texto completo continua no `AgentEvent` |

São dois cortes diferentes, e o `content_truncated` mistura os dois:

| Corte | Onde | Tamanho | O texto completo |
|---|---|---|---|
| Ao salvar | `AgentEvent::MAX_CONTENT_LENGTH` | 65 535 caracteres | Perdido. `metadata.content_truncated` e `content_original_length` registram o corte |
| No WebSocket | `max_content_length` | 4000 caracteres | Está no banco e vem pela API |

Uma linha com o `content` curto e um `new_string` longo também chega com `content_truncated: true`, então o painel busca a linha inteira pela API em vez de mostrar a `metadata` cortada. Apesar do nome, o campo cobre a linha toda, e não só o `content`. Na prática, o `StreamEventMapper` já limita cada lado de um Edit a 2000 caracteres e a saída de ferramentas a 4000, então o corte da `metadata` raramente acontece.

::note
4000 caracteres não garantem caber em 100 000 bytes em qualquer caso: um caractere pode ocupar até 4 bytes em UTF-8, e a `metadata` pode ter vários textos longos. Com os limites atuais do mapper, uma linha fica bem abaixo disso. Se subir `FIREWATCH_REALTIME_MAX_CONTENT_LENGTH`, suba também o `REVERB_MAX_REQUEST_SIZE`.
::

Os outros dois eventos não têm corte: o `IncidentResource` e o `AgentRunResource` não têm campos de texto livre grandes (o `stack_trace` e o `report` ficam de fora).

## No painel

`app/composables/useRealtime.ts` tem os tipos dos payloads e três funções:

| Função | O que faz |
|---|---|
| `useRealtimeChannel(canal, listeners)` | Assina o canal quando o componente monta e sai quando desmonta. Vários componentes podem ouvir o mesmo canal: o painel conta os inscritos e só chama `leave` quando o último sai. O nome do canal pode ser reativo (o id do incidente da rota) |
| `useGlobalChannel()` / `useIncidentChannel(id)` | Atalhos para os dois canais |
| `useRealtimeConnection()` | Estado da conexão (`connected`, `connecting`, `unavailable`…) para o selo **Ao vivo** / **Tempo real indisponível** |

O que cada tela faz com cada evento:

| Tela | Evento | Reação |
|---|---|---|
| Visão geral (números) | `incident.status-changed` | Relê `GET /api/v1/metrics/overview`, 1,5 s depois do último evento, para juntar mudanças em sequência |
| Incidentes recentes | `incident.status-changed` | Atualiza a linha, ou põe o incidente novo no topo |
| Lista de incidentes | `incident.status-changed` | Atualiza a linha na hora e relê a página 1,2 s depois, sem piscar, para acertar contadores, abas e paginação |
| Lista de incidentes | `agent-run.status-changed` | Atualiza a última execução da linha |
| Incidente | `incident.status-changed` | Junta os campos novos, mantendo o `stack_trace` que já tinha |
| Incidente | `agent-run.status-changed` | Atualiza a execução. Se é uma execução nova (reexecução) e o usuário está olhando a mais recente, passa para ela. Se terminou, relê a timeline e o detalhe com o relatório |
| Incidente | `agent-event.recorded` | Ver abaixo |

Para a timeline, o painel (`useLiveIncident`) só aceita o evento direto do WebSocket quando ele é **da execução que está na tela**, é **o próximo** da sequência e **não** veio cortado. Em qualquer outro caso (uma linha perdida, um `content_truncated`), ele chama `catchUp()`, que busca pela API o que veio depois da última linha conhecida. Assim, o texto completo de uma linha cortada aparece logo em seguida, e uma linha perdida não deixa buraco.

Quando a conexão cai, o painel se recupera de dois jeitos:

- **Ao reconectar**, relê a timeline e o incidente.
- **Enquanto está sem WebSocket** e a execução está ao vivo, consulta a API a cada **5 s**.

Nenhum evento é obrigatório para o painel ficar certo: o WebSocket só deixa a tela mais rápida.

## Para depurar

O serviço `reverb` do compose sobe sem `--debug`, então o log dele não mostra as mensagens. Para ver cada conexão, inscrição e evento, rode um Reverb em modo debug no lugar dele:

```bash
docker compose stop reverb && docker compose run --rm --service-ports reverb php artisan reverb:start --debug
```

```bash
# Falhas de envio do lado do Laravel
docker exec firewatch-app grep "Realtime broadcast failed" storage/logs/laravel.log
```

No painel, `NUXT_PUBLIC_ECHO_LOG_LEVEL=3` mostra no console cada inscrição e cada evento. Uma inscrição recusada aparece como `[realtime] falha ao assinar private-…`. Para ver uma timeline ao vivo sem gastar créditos, reproduza uma execução gravada com `php artisan firewatch:replay-run` ([Testar sem gastar créditos](/ambiente-e-setup/testar-sem-creditos#firewatchreplay-run)).
