O painel mostra os agentes trabalhando sem recarregar a página. Quem faz isso é o **Laravel Reverb**, o servidor WebSocket do próprio Laravel. O caminho tem três peças:

::mermaid
---
code: |
  flowchart LR
      L["Laravel<br/>app, workers"] -->|"HTTP: publica o evento<br/>reverb:8080"| R["Reverb<br/>firewatch-reverb"]
      P["Painel Nuxt<br/>Laravel Echo"] -->|"WebSocket<br/>localhost:8080"| R
      P -->|"POST /api/broadcasting/auth<br/>cookie da sessão"| L
---
::

1. O Laravel **publica** cada evento no Reverb por HTTP, de dentro da rede do compose.
2. O painel abre um **WebSocket** com o Reverb e assina os canais.
3. Como os canais são privados, o Reverb só deixa o painel entrar com uma assinatura que o **Laravel** gera em `POST /api/broadcasting/auth`.

O Reverb não guarda nada: ele só repassa. O que o painel perdeu enquanto estava desconectado é buscado de novo pela API ([Eventos e payloads](/tempo-real/eventos-e-payloads#no-painel)).

## Configuração

### O servidor

O Reverb roda no serviço `reverb` do `docker-compose.yml` (container `firewatch-reverb`, `php artisan reverb:start`), com a porta `8080` publicada no host. O código fica em `config/reverb.php`, que veio do Laravel quase sem mudanças:

| Chave | Variável | Valor no Firewatch | Para quê |
|---|---|---|---|
| `servers.reverb.host` / `port` | `REVERB_SERVER_HOST` / `REVERB_SERVER_PORT` | `0.0.0.0` / `8080` | Onde o servidor escuta dentro do container |
| `servers.reverb.max_request_size` | `REVERB_MAX_REQUEST_SIZE` | `100000` bytes | Tamanho máximo de cada publicação que o Laravel manda. É por isso que o conteúdo da timeline é cortado ([O corte do conteúdo](/tempo-real/eventos-e-payloads#o-corte-do-conteúdo)) |
| `servers.reverb.scaling.enabled` | `REVERB_SCALING_ENABLED` | `false` | Um Reverb só. Com mais de um, ligue e eles se falam pelo Redis |
| `apps.apps.0.key` / `secret` / `app_id` | `REVERB_APP_KEY` / `REVERB_APP_SECRET` / `REVERB_APP_ID` | Valores aleatórios | Identificam o app. A key é pública (vai para o painel); o secret só o Laravel conhece e assina com ele |
| `apps.apps.0.allowed_origins` | `REVERB_ALLOWED_ORIGINS` | `localhost,127.0.0.1` | Hosts do painel que podem abrir o WebSocket. O Firewatch mudou esta linha para ler uma lista separada por vírgula; `*` aceita qualquer origem |
| `apps.apps.0.ping_interval` / `activity_timeout` | `REVERB_APP_PING_INTERVAL` / `REVERB_APP_ACTIVITY_TIMEOUT` | `60` / `30` s | Detectam conexões mortas |
| `apps.apps.0.max_message_size` | `REVERB_APP_MAX_MESSAGE_SIZE` | `10000` bytes | Limite das mensagens que **o navegador** manda. O painel só assina canais, então não chega perto |
| `apps.apps.0.accept_client_events_from` | `REVERB_APP_ACCEPT_CLIENT_EVENTS_FROM` | `members` | Eventos `client-*` entre navegadores. O painel não usa |

### O lado do Laravel

`config/broadcasting.php` usa a conexão `reverb` quando `BROADCAST_CONNECTION=reverb`. Ela aponta para **onde o Laravel encontra o Reverb**, que é diferente de onde o navegador o encontra:

| Variável | Valor | Quem usa |
|---|---|---|
| `BROADCAST_CONNECTION` | `reverb` | Laravel. `null` desliga o envio de verdade (é o padrão dos testes) |
| `REVERB_HOST` / `REVERB_PORT` / `REVERB_SCHEME` | `reverb` / `8080` / `http` | Laravel: o nome do serviço na rede do compose |
| `FIREWATCH_REALTIME_ENABLED` | `true` | `RealtimeBroadcaster`: `false` não monta nem envia nenhum evento |
| `FIREWATCH_REALTIME_MAX_CONTENT_LENGTH` | `4000` | Corte do conteúdo da timeline no WebSocket |

### O lado do painel

O painel usa o módulo `nuxt-laravel-echo` (Laravel Echo + `pusher-js`), configurado na chave `echo` do `nuxt.config.ts`:

| Opção | Variável | Padrão |
|---|---|---|
| `key` | `NUXT_PUBLIC_ECHO_KEY` | Igual a `REVERB_APP_KEY` |
| `host` / `port` / `scheme` | `NUXT_PUBLIC_ECHO_HOST` / `NUXT_PUBLIC_ECHO_PORT` / `NUXT_PUBLIC_ECHO_SCHEME` | `localhost` / `8080` / `http`: o Reverb visto **do navegador** |
| `broadcaster` / `transports` | fixo | `reverb` / `ws` e `wss` |
| `authentication.mode` | fixo | `cookie`: usa a sessão Sanctum do login |
| `authentication.baseUrl` | `NUXT_PUBLIC_SANCTUM_BASE_URL` | `http://localhost:8000` |
| `authentication.authEndpoint` | fixo | `/api/broadcasting/auth` |
| `logLevel` | `NUXT_PUBLIC_ECHO_LOG_LEVEL` | `1` (só erros e avisos; `3` mostra tudo no console) |

::warning
`REVERB_HOST` e `NUXT_PUBLIC_ECHO_HOST` **não** são o mesmo valor. O Laravel fala com `reverb:8080` dentro da rede do compose; o navegador fala com `localhost:8080` no host. Trocar um pelo outro é a causa mais comum de "Tempo real indisponível" no painel, junto com uma `NUXT_PUBLIC_ECHO_KEY` diferente da `REVERB_APP_KEY`.
::

A lista completa das variáveis está em [Variáveis de ambiente](/ambiente-e-setup/variaveis-de-ambiente).

## Os canais

Os nomes dos canais existem em **um** lugar no back-end, `App\Broadcasting\Channels`, e são espelhados no painel em `REALTIME_CHANNELS` (`app/composables/useRealtime.ts`):

| Canal (Laravel) | Nome no Reverb | Classe | O que passa |
|---|---|---|---|
| `Channels::global()` | `private-firewatch` | `GlobalChannel` | Mudanças de status de todos os incidentes e execuções |
| `Channels::incident($id)` | `private-incidents.{id}` | `IncidentChannel` | A timeline do incidente (cada `AgentEvent`) e as mudanças de status dele e das execuções dele |
| (padrão do Laravel) | `private-App.Models.User.{id}` | closure | Nada: o canal está registrado, mas nenhum evento é enviado nele |

| Tela do painel | Canal |
|---|---|
| Visão geral (dashboard e incidentes recentes) | Global |
| Lista de incidentes | Global |
| Página de um incidente | Incidente |

Os dois canais usados são `PrivateChannel`, e não canais de presença: o Firewatch não mostra quem mais está olhando a tela.

## A autorização em channels.php

`routes/channels.php` liga cada padrão de nome à classe que decide:

```php
Broadcast::channel(Channels::GLOBAL, GlobalChannel::class);

Broadcast::channel(Channels::INCIDENT_PATTERN, IncidentChannel::class);

// User ids are UUIDs: compare as strings.
Broadcast::channel('App.Models.User.{id}', function ($user, $id) {
    return (string) $user->id === (string) $id;
});
```

A rota de autorização é registrada em `bootstrap/app.php`, com o prefixo `api` e a mesma pilha de middlewares da API do painel:

```php
->withBroadcasting(
    __DIR__.'/../routes/channels.php',
    [
        'prefix'     => 'api',
        'middleware' => ['api', 'auth:sanctum', 'ensure-user-active', 'ensure-password-change'],
    ],
)
```

::mermaid
---
code: |
  sequenceDiagram
      participant P as Painel (Echo)
      participant R as Reverb
      participant L as Laravel
      P->>R: conecta (key do app)
      R-->>P: socket_id
      P->>L: POST /api/broadcasting/auth<br/>socket_id + channel_name, cookie de sessão
      L->>L: auth:sanctum, ensure-user-active, ensure-password-change
      L->>L: GlobalChannel::join() ou IncidentChannel::join()
      L-->>P: 200 com a assinatura (HMAC com o secret) ou 403
      P->>R: subscribe com a assinatura
      R-->>P: inscrito no canal
---
::

O Reverb confere a assinatura com o mesmo secret. Sem uma assinatura válida, ninguém entra num canal privado, mesmo conhecendo a key e o nome do canal.

### As regras

| Canal | Regra | Recusado quando |
|---|---|---|
| `private-firewatch` | `GlobalChannel::join()`: `$user->active && ! $user->must_change_password` | Usuário desativado ou com troca de senha pendente |
| `private-incidents.{incident}` | `IncidentChannel::join()`: a mesma regra | Também quando o incidente não existe ou foi removido: o `{incident}` é resolvido por route model binding, e o soft delete o esconde |
| `private-App.Models.User.{id}` | O id do canal é o do próprio usuário | Outro usuário |
| Qualquer outro nome | Nenhuma regra registrada | Sempre |

As regras dos canais repetem o que os middlewares já garantem (usuário ativo, senha trocada). A repetição é proposital: o canal continua fechado mesmo se a rota mudar de middlewares.

Visitantes sem sessão recebem `401` do `auth:sanctum`, antes de chegar às classes. Os papéis não entram na conta: qualquer usuário ativo vê a timeline de qualquer incidente, assim como vê pela API ([Papéis e permissões](/seguranca/papeis-e-permissoes)).

::note
A autorização é checada **só na entrada**. Um usuário desativado com o canal aberto continua recebendo eventos até a conexão cair ou o painel tentar entrar de novo. O próximo acesso à API ou ao `broadcasting/auth` já é recusado ([Middlewares](/seguranca/middlewares)).
::

O MVP tem uma organização só, por isso nenhum canal confere a qual organização o incidente pertence ([Organizações](/seguranca/organizacoes)).

## Testes

`tests/Feature/Broadcasting/ChannelAuthorizationTest.php` chama `POST /api/broadcasting/auth` de verdade e cobre:

- os nomes centralizados em `Channels`;
- o usuário ativo entra no canal global e no canal de um incidente existente;
- incidente desconhecido ou removido é recusado;
- visitante não autoriza nenhum canal;
- usuário desativado e usuário com troca de senha pendente são recusados;
- o canal de usuário só aceita o dono;
- canal não registrado é recusado.
